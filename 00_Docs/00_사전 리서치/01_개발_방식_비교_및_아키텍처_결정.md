| 대상 보드 | NU54DK / nRF54L15 CPUAPP |

> 단일 원본이다. 구현·성능·실기 결과는 이 문서에 복제하지 않고 검증 기록으로 연결한다.

## 1. 결정

NU54DK Arduino Core는 **Arduino LLEXT Loader 없이**, 사용자 Sketch, Arduino 호환 계층,
Zephyr kernel과 선택한 NCS 기능을 하나의 build graph에서 구성하여 완전한 firmware image로
정적 빌드한다.

```text
Arduino IDE / Arduino CLI
          ↓
NU54DK Arduino Build Adapter
          ↓
NCS v3.4.0 + west + CMake + Ninja
          ↓
Sketch + Arduino Core + Zephyr/NCS
          ↓
zephyr.elf / zephyr.hex / merged.hex
          ↓
CMSIS-DAP V2 + pyOCD 또는 외장 J-Link
```

이 결정의 핵심 원칙은 다음과 같다.

1. 실제 runtime과 build configuration의 원본은 Zephyr/NCS다.
2. Sketch별 Kconfig, Devicetree, module과 공개 Zephyr/NCS API 사용 자유를 보존한다.
3. Loader, EDK, export symbol과 별도 Sketch ABI를 공식 제품 계약으로 추가하지 않는다.
4. Arduino IDE와 CLI는 frontend이며, Build Adapter는 입력 변환과 결과 연결만 담당한다.
5. 설치 용량과 cold build 비용은 자동 설치, persistent Ninja tree와 compiler cache로 완화한다.
6. 일반 사용자는 검증된 profile과 library feature를 사용하고 전문가는 명시적 override를 쓴다.

### 1.1 `Loader 없음`의 의미

다음을 두지 않는다는 뜻이다.

- 실행 중 별도 Arduino Sketch ELF를 적재하는 LLEXT Loader
- Loader별 EDK, export symbol table과 C/C++ ABI 계약
- Loader firmware와 분리된 전용 Sketch partition
- Loader와 Sketch의 독립 update·호환성 matrix

다음 요소까지 금지한다는 뜻은 아니다.

- nRF54L15 내부 SoC Boot ROM
- 향후 별도 제품선에서 검토할 MCUboot, DFU와 recovery image
- CMSIS-DAP 또는 J-Link probe 내부 firmware
- sysbuild가 필요에 따라 구성하는 보조 firmware domain

Bootloader·firmware update와 runtime extension loading은 서로 다른 문제로 취급한다.

## 2. 배경과 의사결정 조건

결정 당시 다음 기반은 이미 존재했다.

- NU54DK Zephyr board definition, DTS, pinctrl과 defconfig
- NCS v3.4.0에서 NU54DK CPUAPP application build 경로
- 온보드 CMSIS-DAP V2의 SWD 연결과 pyOCD 후보 경로
- 외장 J-Link를 연결할 수 있는 Zephyr runner 구조

nRF54L15 target에는 native USB device peripheral이 없다. NU54DK의 USB connector는 target의
Arduino USB API를 뜻하지 않으며, USB DFU나 UF2에는 interface MCU firmware 또는 별도 전송
경로가 필요하다.

어떤 아키텍처를 택해도 다음 작업은 공통이다.

- ArduinoCore-API 또는 동등한 공통 C++ API
- `setup()`, `loop()`, `init()`과 `yield()` 실행 규칙
- GPIO, 시간, interrupt, Serial, Wire, SPI, ADC와 PWM backend
- NU54DK 논리 pin mapping과 Variant
- Arduino library 호환성, 예제와 회귀 시험
- Boards Manager metadata와 설치·제거 수명주기
- CMSIS-DAP/pyOCD 및 선택 J-Link upload 연결

후보 비교에서는 이 공통 작업을 특정 후보의 추가 비용으로 중복 계산하지 않았다.

### 2.1 우선순위

프로젝트의 우선순위는 다음 순서다.

1. **Zephyr 충실도** — 최종 runtime이 실제 NCS/Zephyr kernel·driver·subsystem인가
2. **구성 자유도** — 프로젝트별 Kconfig, DTS, module과 API 선택이 가능한가
3. **관리 편의성** — 유지관리자와 사용자의 장기 비용을 함께 관리할 수 있는가

다음 조건은 점수로 보상할 수 없는 필수 gate다.

> **G1. 최종 runtime은 실제 NCS/Zephyr kernel, driver와 subsystem을 기반으로 해야 한다.**

Bare-metal이나 다른 RTOS가 빠르고 작더라도 G1을 통과하지 못하면 목표 아키텍처 후보에서
제외한다.

## 3. 평가 방법

G1을 통과한 후보는 다음 가중치로 평가했다.

| 평가 항목 | 가중치 | 의미 |
| --- | ---: | --- |
| Zephyr 충실도 | 45 | 실제 NCS/Zephyr runtime과 build graph 사용 |
| 자유도 | 35 | Sketch별 Kconfig, DTS, module과 API 선택 |
| NUCODE 유지관리 | 12 | ABI, artifact, profile, CI와 release 관리 비용 |
| 최종 사용자 편의 | 8 | 설치, build, upload와 문제 복구 편의 |

관리 편의성 20은 유지관리 12와 사용자 편의 8의 합이며 총점에 다시 더하지 않는다. 점수는
각 항목 0~5점이고 다음 식으로 계산한다.

```text
총점 = Σ(원점수 ÷ 5 × 가중치)
```

| 점수 | 판단 기준 |
| ---: | --- |
| 0 | 요구를 전혀 만족하지 않거나 해당 기반을 사용하지 않음 |
| 1 | 큰 구조 변경 없이는 만족하기 어려움 |
| 2 | 제한된 범위에서만 만족 |
| 3 | 일반 사용은 가능하지만 명확한 제약이 있음 |
| 4 | 대부분 만족하고 제약을 관리할 수 있음 |
| 5 | 구조적으로 요구와 직접 일치 |

점수는 제품의 보편적 우열이 아니라 이 프로젝트의 우선순위에 대한 적합도다. 확인된 사실,
구조에서 도출한 판단과 아직 측정하지 않은 비용 추정을 구분해 해석한다.

## 6. 책임과 경계

| 영역 | 소유 내용 | 소유하지 않는 것 |
| --- | --- | --- |
| `NU54DK_Zephyr_DTS` | 실제 pin, DTS, pinctrl, memory, runner와 board metadata | Arduino API와 논리 pin 순서 |
| NU54DK Arduino Core | Arduino API, Variant, Zephyr backend, Build Adapter와 예제 | 보드 전기 정의의 두 번째 원본 |
| 사용자 Sketch | application code, profile·feature 선택과 전문가 override | Core 내부 파일 직접 수정 |
| NCS/Zephyr | kernel, driver, Bluetooth, radio, filesystem과 build system | Arduino UX와 package policy |

Build Adapter는 west·CMake·Kconfig·Devicetree를 재구현하지 않는다. Arduino frontend가 발견한
Sketch와 library source, profile과 override를 결정적으로 전달하고 최종 artifact와 diagnostic을
Arduino 도구에 연결한다.

물리 pin과 runner는 board package가 소유한다. Core는 board submodule을 고정된 read-only build
입력으로 사용하고 Arduino Variant에는 논리 이름·순서·capability만 둔다.

Full Zephyr 구조가 BLE, IEEE 802.15.4, Thread, filesystem 등을 구성할 수 있다는 사실은 해당
기능의 제품 지원을 뜻하지 않는다. 공개 지원 여부는
[NCS 기능과 예제 지원 매트릭스](../01_아두이노%20코어%20설계/06_NCS_3.4.0_기능과_예제_지원_매트릭스.md)와
버전별 완료 증거를 따른다.

## 7. 결과

### 7.1 수용하는 비용

- NCS source와 Toolchain을 PC에 고정 설치하거나 자동 배포해야 한다.
- 최초 설치와 cold build가 작고 단순한 Arduino Core보다 무겁다.
- Arduino build model과 west를 연결하는 adapter를 유지해야 한다.
- persistent build tree, cache 무효화와 OS별 package 검증이 필요하다.
- 최종 image가 바뀌면 전체 firmware artifact를 다시 link하고 기록한다.

### 7.2 피하는 비용

- Loader와 Sketch 사이의 장기 ABI 유지
- EDK, export symbol과 Loader/Core 조합별 호환표
- Loader용 heap, relocation과 전용 Sketch slot
- 동적 ELF 주소 기반 crash·debug symbolization
- 고정 사전 빌드 profile artifact의 조합 폭증
- 정적/LLEXT 두 공식 경로의 초기 동시 유지
- Zephyr driver와 subsystem을 별도 Arduino runtime에서 재구현

### 7.3 최종 원칙

> **Arduino는 사용자 인터페이스이며, Zephyr가 실제 운영체제이자 build configuration의
> 원본이다.**

## 9. 재검토 조건

### 9.1 LLEXT 또는 사전 빌드 SDK

다음 조건 중 하나 이상이 지속적으로 확인되면 별도 ADR에서 다시 평가한다.

- 측정된 warm build와 flash 시간이 제품 목표를 반복적으로 초과함
- NCS/Toolchain 설치 크기나 설치 시간이 지원 가능한 배포 목표를 초과함
- runtime Sketch 교체가 실제 필수 요구가 됨
- 좁고 안정적인 Arduino C ABI와 export 범위가 확정됨
- 사용 규모가 Loader/EDK 유지비를 상쇄할 만큼 커짐
- 사용자 요구가 소수의 고정 profile로 수렴해 Kconfig/DTS 자유가 더 이상 필수가 아님

재검토 시 LLEXT hot unload보다 Sketch 기록 후 reset-load 구조를 먼저 평가한다.

### 9.2 Bare-metal 또는 다른 RTOS

- Zephyr 우선순위 자체가 변경됨
- Zephyr로 해결할 수 없는 성능·전력·기능 문제가 실측으로 확인됨
- Bluetooth와 저수준 platform stack의 독립 유지 책임을 프로젝트가 수용함

### 9.3 Full Zephyr + LLEXT 이중 지원

- Full Zephyr 공식 경로와 conformance test가 충분히 안정화됨
- 별도 유지 인력, CI 장비와 release 예산이 확보됨
- 두 mode의 API·memory·upload 차이를 명확히 설명할 문서와 지원 정책이 준비됨

### 9.4 Bootloader와 firmware update

MCUboot, signed image, DFU, A/B rollback, field recovery 또는 UF2 요구는 LLEXT와 분리해
평가한다. nRF54L15에는 native USB device가 없으므로 USB MSC/UF2에는 interface MCU firmware
또는 별도 hardware·transport 설계가 필요하다.

---

## 10. 재평가 원칙

- Full Zephyr cold build와 LLEXT warm build를 직접 비교하지 않는다.
- 공통 Arduino API 개발비를 특정 후보에만 포함하지 않는다.
- Kconfig/DTS 자유도를 Zephyr 충실도와 자유도에서 과도하게 이중 계산하지 않는다.
- ABI·CI 비용을 여러 평가 항목에서 중복 감점하지 않는다.
- 유지관리자 비용과 최종 사용자 편의를 별도로 표시한다.
- 동일한 기능 범위에서 install, cold/warm build, config 변경, upload, debug와 update를 비교한다.
- CMSIS-DAP와 J-Link를 runtime Loader로 오인하지 않는다.
