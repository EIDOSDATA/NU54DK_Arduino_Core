## 0. 결정 요약

NU54DK Arduino Core는 **Arduino LLEXT Loader 없이**, 사용자 스케치와 Arduino 호환 계층, Zephyr 커널, NCS 기능을 동일한 빌드 그래프에서 구성하여 완전한 펌웨어로 정적 빌드한다.

~~~text
Arduino IDE / Arduino CLI
          ↓
NU54DK Arduino Build Adapter
          ↓
NCS v3.4.0 + west + CMake + Ninja
          ↓
Sketch + Arduino Core + Zephyr/NCS
          ↓
zephyr.elf / zephyr.hex / merged.hex
          ↓
CMSIS-DAP + pyOCD
또는 J-Link
~~~

이 결정에서 말하는 **Loader 없음**은 다음을 의미한다.

- Arduino 스케치를 동적으로 적재하는 LLEXT Loader를 두지 않는다.
- Loader EDK, export symbol table, Loader ABI 및 전용 user sketch 파티션을 요구하지 않는다.
- 각 스케치를 독립적인 전체 NCS/Zephyr 애플리케이션으로 빌드한다.

다음 요소가 없다는 뜻은 아니다.

- nRF54L15 내부의 SoC Boot ROM
- 향후 필요에 따라 별도로 검토할 MCUboot 또는 DFU update 경로를 제공하는 bootloader
- CMSIS-DAP 및 J-Link 프로브 내부 펌웨어
- sysbuild가 생성할 수 있는 보조 펌웨어 이미지

최종 선택의 핵심 이유는 다음 세 가지 우선순위다.

1. **Zephyr를 포기하지 않는다.**
2. **프로젝트별 Kconfig, Devicetree 및 Zephyr/NCS 기능 구성의 자유를 보존한다.**
3. **Loader ABI나 사전 빌드 프로파일을 이중 관리하지 않고 하나의 표준 빌드 경로를 유지한다.**

설치 용량과 최초 빌드 시간은 선택한 구조의 약점으로 인정한다. 이 문제는 런타임 구조를 제한하는 방법이 아니라 Boards Manager 자동 설치, 영구 Ninja 빌드 트리 및 컴파일러 캐시로 **완화**하고, 실제 효과는 clean-machine PoC와 빌드 시간 측정으로 검증한다.

## 1. 문서 목적

이 문서는 NU54DK에서 Arduino 스케치를 실행할 수 있도록 만드는 여러 방법을 동일한 기준으로 비교하고, 왜 **Loader 없는 Native Full Zephyr 정적 빌드**를 선택했는지 설명한다.

문서가 답해야 하는 질문은 다음과 같다.

- Arduino 스케치가 PC에서 어떻게 빌드되는가?
- 보드에는 어떤 펌웨어가 상주하는가?
- 리셋 후 백그라운드에서는 무엇이 실행되는가?
- 사용자가 Kconfig, DTS overlay 또는 Zephyr 모듈을 바꾸면 무엇을 다시 빌드해야 하는가?
- 개발자, 최종 사용자, CI 서버 및 MCU가 각각 어떤 비용을 부담하는가?
- CMSIS-DAP와 J-Link는 각 구조에서 어떤 역할을 하는가?
- 초기 개발비뿐 아니라 장기 유지비까지 고려했을 때 어떤 방식이 프로젝트 우선순위에 가장 적합한가?

이 문서는 특정 방식이 보편적으로 우수하다고 주장하지 않는다. 공식 Arduino의 LLEXT 구조와 ESP32 및 Adafruit의 구조가 각각의 제품 목표에 왜 적합한지를 확인된 동작과 본 문서의 설계 해석으로 구분해 설명한다.

## 2. 결정 배경

### 2.1 이미 확보된 기반

본 결정은 다음 기반이 이미 존재한다는 전제에서 이루어졌다.

- NU54DK용 Zephyr 보드 정의, DTS, pinctrl 및 defconfig
- NCS v3.4.0에서의 NU54DK 애플리케이션 빌드
- 온보드 CMSIS-DAP를 이용한 SWD 연결
- pyOCD를 이용한 nRF54L15 플래싱 경로
- J-Link를 선택적으로 지원할 수 있는 Zephyr runner 구조

nRF54L15 target MCU에는 native USB peripheral이 없다. NU54DK의 USB 연결은 CMSIS-DAP 인터페이스 MCU 측 연결이며, target MCU에서 Zephyr USB device subsystem이나 Arduino USB API를 직접 제공한다는 뜻이 아니다. USB 기반 DFU 또는 drag-and-drop UF2는 인터페이스 MCU 펌웨어나 별도 하드웨어·전송 경로를 포함해 독립적으로 설계해야 한다.

근거: [nRF54L15 Product Specification — key features](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/keyfeatures_html5.html), [Nordic Developer Academy — DFU over USB 지원 보드 표](https://academy.nordicsemi.com/courses/nrf-connect-sdk-intermediate/lessons/lesson-9-bootloaders-and-dfu-fota/topic/exercise-4-dfu-over-usb/)

따라서 새 Arduino Core가 해결해야 하는 핵심 문제는 디버그 프로브가 아니라 다음 두 영역이다.

1. Arduino API와 실행 규칙을 Zephyr/NCS에 연결하는 것
2. Arduino IDE 또는 CLI의 입력을 재현 가능한 west 빌드로 변환하는 것

### 2.2 NCS v3.4.0을 기준으로 삼는 이유

NCS v3.4.0은 Zephyr 4.4 기반이며 5년 LTS 릴리스다. LTS 기간에는 보안 취약점과 중대한 결함에 대한 패치가 제공되며, 보안상 필요한 경우를 제외하면 breaking change를 포함하지 않는 것이 원칙이다. 이 특성은 장기간 유지할 Arduino Core의 기준선으로 적합하다.

근거: [nRF Connect SDK v3.4.0 릴리스 노트](https://github.com/nrfconnect/sdk-nrf/blob/v3.4.0/doc/nrf/releases_and_maturity/releases/release-notes-3.4.0.rst)

### 2.3 공통으로 필요한 작업

아키텍처를 공정하게 비교하려면 모든 후보에 공통으로 필요한 작업을 먼저 분리해야 한다.

- ArduinoCore-API 또는 이에 대응하는 공통 C++ API
- setup, loop, init 및 yield 실행 규칙
- GPIO, 시간, 인터럽트, Serial, Wire, SPI, ADC 및 PWM 구현
- NU54DK Arduino 논리 핀 매핑
- Arduino 라이브러리 호환성 시험
- 예제, 오류 진단 및 회귀 시험
- Boards Manager 메타데이터
- CMSIS-DAP/pyOCD 및 J-Link 업로드 연결

LLEXT가 Arduino API 구현을 대신하지 않으며, 사전 빌드 라이브러리도 보드 variant와 Arduino API를 대신하지 않는다. 비교표의 아키텍처 고유 비용은 위 공통 작업에 **추가되는 비용**을 뜻한다.

## 3. 용어와 계층 구분

| 용어 | 정의 | 본 결정과의 관계 |
| --- | --- | --- |
| SoC Boot ROM | nRF54L15 내부에 제조 시 들어 있는 초기 부팅 코드 | 제거 대상이 아님 |
| Bootloader | 리셋 직후 이미지 검증, 업데이트, 복구 또는 애플리케이션 실행을 담당하는 펌웨어 | v0.1.0 필수 요소가 아니며 향후 별도 검토 |
| LLEXT Loader | 실행 중인 Zephyr에서 별도 ELF 확장을 읽고 재배치하며 심볼을 연결해 실행하는 펌웨어 | 채택하지 않음 |
| EDK | 특정 Loader 빌드의 generated header와 컴파일 플래그를 확장 개발자에게 제공하는 패키지 | LLEXT를 채택하지 않으므로 불필요 |
| CMSIS-DAP | PC와 대상 MCU의 CoreSight DAP 사이를 SWD/JTAG로 연결하는 표준 및 프로브 펌웨어 | 기본 플래시·디버그 인터페이스 |
| pyOCD | CMSIS-DAP 등을 사용해 MCU를 플래싱하고 디버깅하는 PC 측 도구 | 기본 host tool |
| J-Link | SEGGER의 SWD/JTAG 디버그 프로브 및 host software | 선택 플래시·디버그 인터페이스 |
| west runner | pyOCD, J-Link 같은 host tool을 호출하는 Zephyr 측 Python wrapper | 업로드 방식 선택 계층 |
| 전체 정적 빌드 | 스케치, Core, RTOS 및 선택된 subsystem을 최종 실행 이미지에 함께 링크하는 방식 | 최종 채택 |
| 사전 빌드 SDK | RTOS와 SDK의 고정 구성을 미리 정적 라이브러리로 만들어 배포하는 방식 | 비교 후보 |
| sysbuild | 여러 펌웨어 domain을 하나의 상위 빌드로 구성하는 Zephyr 기능 | Loader와 무관하며 필요 시 허용 |

CMSIS-DAP와 J-Link는 완성된 이미지를 기록하는 도구다. 두 프로브가 존재한다고 Arduino API가 제공되는 것은 아니며, 반대로 두 프로브를 사용하기 위해 LLEXT Loader가 필요한 것도 아니다.

관련 근거:

- [Arm CMSIS-DAP 문서](https://arm-software.github.io/CMSIS_6/latest/DAP/index.html)
- [pyOCD debug probe 문서](https://pyocd.io/docs/debug_probes.html)
- [Zephyr 4.4.0 flash/debug runner 문서](https://docs.zephyrproject.org/4.4.0/develop/west/build-flash-debug.html)

## 4. 우선순위와 평가 방법

### 4.1 사용자 우선순위

본 프로젝트에서 포기할 수 없는 가치의 순서는 다음과 같다.

1. **Zephyr**
2. **자유도**
3. **관리 편의성**

여기서 자유도는 단순히 Arduino API 안에서 임의의 코드를 작성할 수 있다는 의미가 아니다. 다음을 프로젝트 또는 스케치 단위로 선택할 수 있는 능력을 뜻한다.

- prj.conf를 통한 Kconfig 변경
- app.overlay를 통한 Devicetree 변경
- Zephyr/NCS API 직접 사용
- 추가 Zephyr 모듈 연결
- BLE, 802.15.4/Thread, 파일시스템, logging, 전력 관리 및 메모리 설정 변경
- 필요 시 sysbuild 및 보조 이미지 구성

### 4.2 비보상 필수조건

점수 계산 전에 다음 필수조건을 적용한다.

> **G1. 최종 런타임은 실제 NCS/Zephyr 커널, 드라이버 및 subsystem을 기반으로 해야 한다.**

이 조건은 가중치로 상쇄할 수 없다. 빌드 속도나 사용자 편의가 아무리 뛰어나도 Zephyr를 사용하지 않는 후보는 목표 아키텍처에서 제외한다.

### 4.3 가중치

필수조건을 통과한 후보는 다음 가중치로 평가한다.

| 평가 항목 | 가중치 | 평가 의미 |
| --- | ---: | --- |
| Zephyr 충실도 | 45 | 실제 NCS/Zephyr 런타임인가 |
| 자유도 | 35 | 프로젝트별 Kconfig, DTS, module 및 API 선택이 가능한가 |
| 관리 편의성 소계 | 20 | 아래 두 항목의 합이며 총점에 별도로 다시 더하지 않음 |
| └ NUCODE 유지관리 | 12 | ABI, artifact, profile, CI 및 릴리스 조합 관리 |
| └ 최종 사용자 편의 | 8 | 설치, 빌드, 업로드 및 문제 복구 편의 |

총점에 직접 들어가는 열은 `45 + 35 + 12 + 8 = 100`이다. 관리 편의성 20은 12와 8의 소계다.

Zephyr 45점은 포기할 수 없는 1순위를 수치로 보존하지만, G1을 통과한 네 후보는 모두 실제 Zephyr 런타임이므로 동일하게 5점을 받는다. 따라서 이 45점은 통과 후보 사이의 순위를 가르는 변수가 아니라 **게이트를 통과했다는 상수**다. 통과 후보의 순위는 나머지 55점에서 결정된다.

관리 편의성을 유지관리자와 최종 사용자로 분리한 이유는 LLEXT처럼 사용자 비용을 줄이는 대신 공급자 비용을 늘리는 구조를 정확하게 평가하기 위해서다. 이 ADR에서 말하는 관리 편의성은 Quantum/NUCODE가 장기간 릴리스를 유지하는 편의에 조금 더 무게를 두므로 60:40, 즉 12:8로 배분한다. 이는 외부 사실이 아니라 **의사결정 가정**이며, 반대 비율에서 결과가 어떻게 바뀌는지도 민감도 분석에 공개한다.

### 4.4 점수 규칙

각 항목은 0점에서 5점으로 평가한다.

| 점수 | 의미 |
| ---: | --- |
| 0 | 요구를 전혀 만족하지 않거나 해당 기반을 사용하지 않음 |
| 1 | 큰 구조 변경 없이는 요구를 만족하기 어려움 |
| 2 | 제한된 범위에서만 만족 |
| 3 | 일반적인 사용은 가능하지만 명확한 제약 존재 |
| 4 | 대부분 만족하며 관리 가능한 제약만 존재 |
| 5 | 구조적으로 요구와 직접 일치 |

항목별 재현 가능한 기준점은 다음과 같다. 1점, 2점 및 4점은 인접 기준 사이의 정도로 판정한다.

| 항목 | 0점 기준 | 3점 기준 | 5점 기준 |
| --- | --- | --- | --- |
| Zephyr 충실도 | 최종 런타임이 Zephyr가 아님 | 일부 Zephyr 자산만 사용하거나 런타임 소유권이 불명확 | 실제 NCS/Zephyr 런타임이며 G1 통과 |
| 자유도 | 프로젝트별 Zephyr 구성을 사용할 수 없음 | 고정 profile/export 범위에서 가능하고 변경 시 Loader·artifact 재생성 필요 | 프로젝트별 Kconfig, DTS, module 및 API를 전체 build graph에 반영 |
| NUCODE 유지관리 | 복수 ABI·profile·pipeline의 광범위한 수동 관리 | 하나의 추가 artifact 또는 호환 계약을 지속 관리 | 하나의 build graph와 하나의 runtime 계약으로 관리 |
| 최종 사용자 편의 | 수동 설치·빌드·복구 단계가 복잡 | 자동 설치는 가능하나 대용량 설치와 cold build 부담 존재 | 작은 prebuilt artifact 중심의 빠른 빌드·업로드 |

가중 점수 계산식은 다음과 같다.

~~~text
총점 = Σ(원점수 ÷ 5 × 가중치)
~~~

점수는 제품의 절대적인 우열이 아니라 **NUCODE 프로젝트 우선순위에 대한 적합도**다. 비용과 기술 제약은 공식 자료로 확인한 사실과 설계상 추론을 구분한다.

| 표시 | 의미 |
| --- | --- |
| 확인 | 공식 문서, 공식 소스 또는 현재 NU54DK 실기 결과로 확인 |
| 구조상 확인 | 해당 방식의 build/runtime 구조에서 직접 도출되지만 NU54DK Arduino 경로의 PoC는 대기 |

## 5. 후보 A — Bare-metal nRF54 Arduino Core

참고 구현: [lolren/nrf54-arduino-core 기준 커밋](https://github.com/lolren/nrf54-arduino-core/tree/a6bb99879aa14cbff362a5478d5f1189848b4200)

### 5.1 백그라운드 구조

~~~text
Reset
  ↓
C/C++ startup
  ↓
클록·메모리·주변장치 직접 초기화
  ↓
Arduino init
  ↓
setup
  ↓

}
~~~

GPIO, UART, SPI, ADC, PWM, GRTC, 전력 관리 및 무선 기능을 레지스터 또는 전용 HAL 수준에서 직접 구현하거나 별도 HAL·protocol stack으로 통합해야 한다. RTOS를 사용하지 않는다면 백그라운드 처리는 인터럽트, 상태 머신 및 자체 이벤트 큐로 구성한다.

### 5.2 PC 빌드와 플래시

Sketch + Arduino Core + Variant

              ↓

### 5.3 장점

- 전통적인 Arduino 빌드 모델과 가장 가깝다.

### 5.4 단점

- **Zephyr가 아니다.**
- Zephyr 드라이버, Kconfig, DTS, 전력 관리 및 subsystem을 표준 Zephyr build/subsystem 형태로 직접 재사용하기 어렵다.
- Bluetooth, 보안, 동시성, errata 및 저전력 정책의 검증 범위가 프로젝트로 이동한다.
- NCS가 제공하는 BLE, 802.15.4/Thread, 파일시스템, networking 및 다중 이미지 통합을 다시 해결해야 한다.
- 기능이 증가할수록 자체 플랫폼과 SDK를 유지하는 것과 비슷한 비용이 발생한다.

### 5.5 비용 판단

### 5.6 판단

업로드 도구와 Arduino package 구성은 참고할 가치가 있다. 그러나 Zephyr 필수조건 G1을 통과하지 못하므로 기반 아키텍처에서는 탈락한다.

## 6. 후보 B — Adafruit nRF52식 FreeRTOS + nrfx + SoftDevice

참고 구현:

- [Adafruit nRF52 Arduino Core 기준 커밋](https://github.com/adafruit/Adafruit_nRF52_Arduino/tree/343ab5fe7fb3d5657d3176883dfb188d65b79f06)
- [Adafruit nRF52 Bootloader 기준 커밋](https://github.com/adafruit/Adafruit_nRF52_Bootloader/tree/c67f0bcf0fa8e841426335b1bbde91cda6ca1f50)

### 6.1 백그라운드 구조

Adafruit nRF52 Core는 FreeRTOS를 운영체제로 사용하고 nrfx를 주변장치 드라이버로 사용한다. nRF52840 계열에서는 S140 SoftDevice와 별도 bootloader 영역을 사용한다.

~~~text
SoC Boot ROM
    ↓
UF2/DFU Bootloader
    ↓
SoftDevice 영역 + 정적 Arduino 애플리케이션
                    ├─ FreeRTOS scheduler
                    ├─ Arduino loop task
                    ├─ BLE/SoC event 처리
                    └─ USB 및 기타 background task
~~~

Arduino 스케치는 동적으로 적재되지 않는다. Bootloader와 SoftDevice가 존재하지만 LLEXT Runtime Loader는 없다.

### 6.2 PC 빌드와 플래시

~~~text
Sketch + Arduino Core + FreeRTOS + nrfx
                    ↓
              애플리케이션 ELF/HEX
                    ↓
         UF2/DFU 또는 SWD로 애플리케이션 기록
~~~

Boards Manager가 Core와 ARM GCC 및 업로드 도구를 설치하므로 사용자가 Nordic SDK 전체를 직접 설치할 필요는 없다.

### 6.3 장점

- 검증된 Arduino 사용자 경험을 제공한다.
- FreeRTOS를 통해 background task와 동시성을 제공한다.
- 애플리케이션 자체는 정적 링크되어 일반적인 ELF 디버깅이 가능하다.
- 일반 스케치 빌드가 빠르고 사용자 설치가 단순하다.
- Bootloader를 통한 UF2/DFU 복구 및 업데이트 UX가 좋다.

### 6.4 단점

- **Zephyr가 아니다.**
- nRF52용 S140 구조를 nRF54L15에 그대로 이식할 수 없다.
- nRF54용 Bluetooth, startup, 인터럽트 우선순위 및 전력 관리를 새로 설계해야 한다.
- nRF54L15에는 native USB peripheral이 없으므로 nRF52840의 target USB/UF2 경험을 같은 구조로 이식할 수 없다.
- NCS/Zephyr가 이미 통합한 기능을 다시 조합하는 중복 투자가 발생한다.
- SoftDevice 또는 binary controller 경계의 내부 문제는 애플리케이션과 같은 수준으로 디버깅하기 어렵다.

### 6.5 비용 판단

| 비용 주체 | 판단 | 근거 |
| --- | --- | --- |
| 초기 고유 개발비 | 매우 높음 | nRF52 Core 복사가 아니라 nRF54 플랫폼 재설계에 가까움 |
| 반복 유지비 | 높음 | FreeRTOS, nrfx, Bluetooth 및 update transport 조합을 프로젝트가 소유 |
| 사용자 설치비 | 낮음 | Board Package로 필요한 구성만 배포 |
| 사용자 빌드비 | 낮음 | 전체 SDK 재구성 없이 애플리케이션 컴파일 |
| MCU 자원비 | 낮음~중간 | RTOS와 SoftDevice 영역 필요 |
| 디버깅·지원비 | 중간 | 애플리케이션은 단순하나 binary stack 경계 존재 |

### 6.6 판단

Arduino 패키징과 task 구조는 참고할 수 있으나 Zephyr 필수조건 G1을 통과하지 못한다. 또한 nRF54에서 동일 구조를 재현하는 비용이 크므로 탈락한다.

## 7. 후보 C — ESP32식 Zephyr/NCS 사전 빌드 SDK

참고 구조:

- [ESP32 Arduino Lib Builder 기준 커밋](https://github.com/espressif/esp32-arduino-lib-builder/tree/d43f6d51ee93772e7e6e4b2ba21e8899584c865b)
- [ESP32 Arduino package index](https://github.com/espressif/arduino-esp32/blob/1630aecb1fef5719a27267d867f90755b09e65e6/package/package_esp32_index.template.json)

### 7.1 ESP32의 실제 방식

ESP32 Arduino Core는 ESP-IDF와 FreeRTOS의 주요 구성요소를 사전 빌드된 정적 라이브러리로 배포한다. Boards Manager는 해당 라이브러리, Xtensa/RISC-V 컴파일러, esptool 및 OpenOCD 등을 PC에 자동 설치한다.

~~~text
Espressif CI
  ESP-IDF + 고정 sdkconfig
             ↓
  사전 빌드 정적 라이브러리
             ↓
       Boards Manager 배포

사용자 PC
  사전 빌드 ESP-IDF 라이브러리
          + Arduino Core
          + Sketch
             ↓
        최종 정적 펌웨어
~~~

보드에서는 동적 Loader가 아니라 정적으로 링크된 ESP-IDF/FreeRTOS 애플리케이션이 실행된다.

### 7.2 Zephyr에 적용했을 때

~~~text
고정 Board DTS + 고정 Kconfig
              ↓
Zephyr/NCS 사전 빌드 artifact 생성
              ├─ 정적 라이브러리
              ├─ generated headers
              ├─ linker inputs
              └─ post-link 도구 정보
                          ↓
                 Sketch 및 Core 링크
                          ↓
                   최종 정적 이미지
~~~

Zephyr에서는 단순한 라이브러리 파일만 배포해서는 충분하지 않다. Devicetree, Kconfig, generated header, device object, syscall, ISR table, linker script 및 후처리 단계가 서로 연결되어 있기 때문이다.

### 7.3 장점

- 사용자의 설치와 일반 스케치 빌드를 빠르게 만들 수 있다.
- 런타임 Loader와 동적 ABI가 없다.
- 최종 펌웨어는 정적 이미지이므로 실행 구조가 단순하다.
- 전체 NCS source workspace를 사용자에게 노출하지 않을 수 있다.
- 고정된 표준 프로파일에서는 재현성과 사용자 UX가 좋다.

### 7.4 단점

- 사전 빌드 당시의 Kconfig와 DTS에 강하게 묶인다.
- 사용자가 prj.conf 또는 overlay를 바꾸면 관련 artifact를 다시 생성해야 한다.
- BLE, 802.15.4/Thread, logging, filesystem 및 power 조합마다 프로파일이 늘어난다.
- 다음과 같은 artifact 행렬이 생긴다.

~~~text
보드 × NCS 버전 × Toolchain × Kconfig 프로파일
     × DTS 프로파일 × Debug/Release × 선택 subsystem
~~~

- generated header와 binary가 다른 프로파일에서 섞이면 빌드 또는 런타임 오류가 발생할 수 있다.
- CI 시간, 서버 저장공간, checksum, SBOM 및 릴리스 검증 비용이 증가한다.
- 자유도를 보존하려고 프로파일을 늘리면 관리 편의성이 급격히 낮아진다.

### 7.5 비용 판단

| 비용 주체 | 판단 | 근거 |
| --- | --- | --- |
| 초기 고유 개발비 | 높음~매우 높음 | Zephyr artifact 계약과 별도 링크 파이프라인 필요 |
| 반복 유지비 | 매우 높음 | 프로파일 및 버전별 artifact 재생성·검증 |
| 사용자 설치비 | 낮음 | NCS 전체 대신 필요한 artifact만 설치 |
| 사용자 빌드비 | 매우 낮음 | Sketch와 변경된 Core 중심 컴파일 |
| CI·배포비 | 매우 높음 | 프로파일 행렬과 대용량 binary 관리 |
| MCU 자원비 | 전체 정적 빌드와 유사 | 최종 런타임은 정적 Zephyr |
| 디버깅·지원비 | 중간 | 프로파일 내부는 양호하나 artifact mismatch 분석 필요 |

### 7.6 판단

실제 Zephyr 런타임이므로 G1은 통과한다. 그러나 프로젝트별 Kconfig와 DTS 자유도가 두 번째 우선순위와 충돌한다. 자유도를 유지하려면 프로파일이 증가하여 세 번째 우선순위인 관리 편의성도 악화되므로 기본 구조로 채택하지 않는다.

공식 근거:

- [Arduino-ESP32에서 sdkconfig 변경이 사전 빌드 library에 반영되지 않는 이유](https://docs.espressif.com/projects/arduino-esp32/en/latest/faq.html#how-to-modify-an-sdkconfig-option-in-arduino)
- [ESP32 Arduino의 사전 빌드 library 제작 도구](https://github.com/espressif/esp32-arduino-lib-builder/tree/d43f6d51ee93772e7e6e4b2ba21e8899584c865b)

## 8. 후보 D — ArduinoCore-zephyr LLEXT Loader

참고 구현: [arduino/ArduinoCore-zephyr 기준 커밋](https://github.com/arduino/ArduinoCore-zephyr/tree/514a21feaa0fd62c3922243cba1a5a98f9f5fdf1)

### 8.1 백그라운드 구조

Arduino 공식 Zephyr Core는 스케치를 독립 ELF로 만들고, 보드에 미리 플래싱된 Zephyr Loader가 이를 LLEXT로 적재한다.

~~~text
Reset
  ↓
고정 Zephyr Loader
  ├─ Zephyr kernel
  ├─ 고정 Kconfig
  ├─ 고정 DTS
  ├─ 고정 driver/subsystem
  ├─ export symbol table
  └─ LLEXT heap
           ↓
스케치 파티션의 ELF 읽기
           ↓
ELF 구조·section 검사, 재배치 및 심볼 해결
           ↓
Arduino sketch main 실행
~~~

### 8.2 PC 빌드와 플래시

~~~text
플랫폼 CI
  Loader 전체 Zephyr 빌드
           ↓
  Loader firmware + EDK
           ↓
  Board Package로 배포

사용자 PC
  Sketch + Arduino Core
           ↓
  Loader EDK 기준 독립 ELF 생성
           ↓
  스케치 파티션에 기록
           ↓
  Reset 후 Loader가 적재
~~~

EDK는 Loader 빌드의 generated header와 컴파일 플래그를 확장 빌드에 제공한다. Loader, EDK, Core 및 스케치가 서로 호환되는 버전이어야 한다.

LLEXT의 ELF 구조·section 검사는 artifact의 출처나 무결성을 보장하는 암호학적 서명 검증과 다르다. 신뢰할 수 없는 Sketch를 적재하는 제품이라면 signature, key 관리 및 rollback 방지 정책을 별도 보안 계층으로 설계해야 한다.

### 8.3 장점

- 스케치 컴파일과 업로드가 매우 빠르다.
- 사용자가 전체 Zephyr/NCS source workspace를 설치하지 않아도 된다.
- 작은 스케치 ELF만 교체할 수 있다.
- Loader와 스케치를 독립적으로 배포할 수 있다.
- 작은 독립 artifact는 OTA나 애플리케이션 교체 설계에 유리할 수 있다. 다만 storage, transport, signature 및 rollback은 별도 구현이 필요하다.
- 대규모 Arduino 사용자에게 일관된 설치 경험을 제공하기 좋다.
- 이전 NU40 LLEXT Loader의 설계 자산을 일부 재사용할 가능성이 있다.

### 8.4 단점

- Kconfig, DTS, 활성 driver 및 subsystem은 Loader 빌드에 고정된다.
- 필요한 Zephyr 함수가 export되지 않았다면 Loader의 symbol export를 수정해야 한다.
- Loader에 포함되지 않은 subsystem은 스케치만으로 활성화할 수 없다.
- Loader, EDK, compiler flags, generated header 및 Core 사이의 버전 결합이 생긴다.
- C++ 클래스, vtable 및 전역 객체를 경계에 직접 노출하면 C++ ABI 변경에 취약하다.
- Loader와 스케치 영역, symbol table 및 LLEXT heap에 Flash/RAM이 필요하다.
- 동적 적재 주소를 고려한 디버깅과 crash symbolization이 정적 ELF보다 복잡하다.
- 실행 중 unload를 지원하면 callback, thread, timer, work item 및 BLE 등록을 모두 안전하게 정리해야 한다.
- Loader와 스케치를 함께 시험하고 자동 동기화하는 릴리스 도구가 필요하다.

### 8.5 관리 편의성의 정확한 해석

LLEXT는 관리 편의성이 일률적으로 낮거나 높은 방식이 아니다.

| 관리 대상 | LLEXT의 효과 |
| --- | --- |
| 최종 사용자의 스케치 빌드·업로드 | 매우 편리 |
| 장치에서의 애플리케이션 교체 | 매우 편리 |
| 플랫폼 공급자의 Loader/EDK 릴리스 | 관리 대상 증가 |
| Core ABI와 export symbol 유지 | 관리 대상 증가 |
| 프로젝트별 Kconfig/DTS 변경 | Loader 재빌드가 필요하여 불편 |
| 동적 확장 디버깅 | 정적 이미지보다 복잡 |

따라서 정확한 표현은 다음과 같다.

> LLEXT는 사용자 운영 비용을 낮추는 대신, 플랫폼 공급자와 CI가 Loader, EDK, export 및 호환성 비용을 중앙에서 부담하는 구조다.

### 8.6 공식 Arduino LLEXT 구조에서 확인되는 효과와 설계 해석

공식 구현에서 확인되는 사실은 Arduino가 Loader와 EDK를 미리 배포하여 사용자가 전체 Zephyr 환경 없이 작은 스케치를 빌드할 수 있게 했다는 점이다. 현재 공식 Core의 업로드 도구는 포트가 노출한 Loader의 `configuration` 버전과 설치된 Core 버전을 비교하고, 불일치하면 Loader를 조건부로 다시 플래싱한다.

이 자동 갱신은 LLEXT가 제공하는 기능이 아니라 **Arduino platform과 업로드 도구가 구현한 배포 정책**이다. NU54DK의 CMSIS-DAP/pyOCD 경로에 저절로 생기는 기능이 아니다. NU54DK에서 LLEXT를 채택한다면 Loader 버전의 저장·조회 방법, 조건부 재플래시, 실패 복구 정책을 별도로 구현해야 한다.

이 구조가 대규모 최종 사용자의 설치 부담과 반복 빌드 시간을 줄이려는 제품 목표에 적합하다는 설명은 위 동작을 바탕으로 한 **본 문서의 설계 해석**이며, 공식적으로 선언된 채택 사유를 인용한 것이 아니다. 공식 문서가 직접 명시하는 제한은 다음과 같다.

- export되지 않은 Zephyr 함수는 Loader export 목록에 추가하고 Loader를 다시 빌드해야 한다.
- Loader에 없는 subsystem은 보드 conf에 추가하고 Loader를 다시 빌드해야 한다.

## 9. 후보 E — Loader 없는 Native Full Zephyr 정적 빌드

### 9.1 백그라운드 구조

Arduino는 Zephyr를 대체하는 운영체제가 아니라 Zephyr 애플리케이션 내부의 호환 API 계층으로 동작한다.

~~~text
Reset
  ↓
SoC 및 Zephyr architecture 초기화
  ↓
Kernel 및 device init level 실행
  ↓
Zephyr scheduler
  ├─ system workqueue
  ├─ 활성 구성에 따른 Bluetooth/logging 등 subsystem thread
  ├─ interrupt·workqueue 기반 driver 처리
  ├─ kernel idle 및 power management 정책
  └─ Arduino application context
          ↓
        setup 1회
          ↓
        loop 반복
          ↓
        event 처리 및 idle 정책
~~~

loop가 반환할 때 단순히 k_yield만 호출하면 idle을 보장하지 않으므로, 실제 구현에서는 이벤트 대기, 짧은 sleep 또는 구성 가능한 idle 정책을 별도로 정의해야 한다. 이 문제는 전체 정적 빌드 여부와 독립적인 Arduino runtime 구현 과제다.

### 9.2 PC 빌드

~~~text
NU54DK board DTS/defconfig
          +
Arduino Core Zephyr module
          +
Sketch 및 Arduino libraries
          +
M13 resolved profile / feature 구성
또는 고급 사용자 prj.conf / app.overlay / module
          ↓
west + CMake 구성
          ↓
DTS/Kconfig/generated headers 생성
          ↓
Ninja 증분 컴파일
          ↓
최종 zephyr.elf / zephyr.hex / merged.hex
~~~

모든 구성요소가 같은 CMake, Kconfig, Devicetree 및 linker 문맥에서 빌드된다.

`prj.conf`/`app.overlay`를 반영할 수 있다는 것은 Full Zephyr의 고급 확장 경계를
의미하지, 일반 Arduino 사용자가 매 예제마다 두 파일을 직접 편집해야 한다는 뜻이
아니다. `v0.1.0`의 기본 Arduino build/upload는 패키지 기본값만으로 동작한다.
`v0.2.0` M13은 일반적인 기능 선택을 profile·feature resolver와 Tools 메뉴로 소유하고,
직접 sidecar는 고급 사용자의 escape hatch로 유지한다.

### 9.3 플래시

~~~text
최종 전체 이미지
   ├─ west flash -r pyocd
   │      ↓
   │   온보드 CMSIS-DAP
   │
   └─ west flash -r jlink
          ↓
       J-Link
~~~

일반 업로드에서는 mass erase를 기본으로 사용하지 않는다. 복구 또는 보안 상태 해제를 위한 destructive 작업은 별도 메뉴와 명령으로 분리한다.

### 9.4 장점

- 모든 스케치가 실제 NCS/Zephyr 애플리케이션이다.
- 고급 프로젝트는 prj.conf와 overlay를 자유롭게 변경할 수 있고, 일반 사용자는 M13 profile UX를 사용한다.
- Zephyr/NCS API와 module을 직접 사용할 수 있다.
- BLE, 802.15.4/Thread, 파일시스템, logging 및 power management를 빌드별로 선택할 수 있다.
- 사용하지 않는 기능은 Kconfig와 section 단위 linker garbage collection에 의해 제거될 수 있다. 실제 결과는 참조 관계와 build 설정에 따라 달라진다.
- Loader, EDK, export symbol table 및 동적 ABI 경계가 없다.
- 최종 ELF의 주소와 실제 실행 코드가 일치하므로 동적 LLEXT보다 디버깅과 symbolization이 단순하다.
- 보드 DTS와 Arduino Core가 하나의 build graph에서 함께 검증된다.
- NCS 변경에 따른 API와 구성 문제를 소스 빌드 단계에서 발견할 수 있다.
- pyOCD와 J-Link를 동일한 west runner 계층에서 제공할 수 있다.
- Loader 전용 Flash/RAM 영역이 필요하지 않다.

### 9.5 단점

- PC에는 NCS/Zephyr source와 Toolchain이 기술적으로 필요하다.
- self-contained Boards Manager 패키지의 다운로드 및 설치 용량이 커질 수 있다.
- 최초 cold build가 다른 방식보다 느리다.
- Arduino의 단순 compile recipe와 west/CMake를 연결하는 build adapter가 필요하다.
- NCS, Toolchain, Python, west, CMake 및 Ninja 버전을 고정·검증해야 한다.
- Windows, Linux 및 macOS용 패키징과 clean-machine 시험이 필요하다.
- 전체 이미지를 기록하므로 작은 LLEXT 파일만 기록하는 방식보다 전송량이 크다.

### 9.6 전체 빌드와 전체 재빌드는 다르다

전체 정적 빌드는 매번 모든 소스를 처음부터 컴파일한다는 뜻이 아니다. 동일한 Zephyr build directory를 유지하면 west와 Ninja는 변경된 파일만 증분 컴파일한다.

정상 빌드 정책은 다음과 같다.

- 스케치·보드·설정 조합별 영구 build directory
- 일반 경로에서 pristine always 사용 금지
- 필요한 경우에만 pristine auto 또는 명시적 clean
- Ninja dependency graph 유지
- ccache 또는 sccache 적용
- Sketch source root, Build Adapter schema, NCS, Toolchain, Core, Board, Kconfig 및 overlay 기반 build-tree cache key
- Sketch 한 줄 변경 시 해당 translation unit과 영향받은 library 및 최종 링크만 실행

Zephyr 공식 문서도 기존 build directory가 있으면 증분 빌드하고, pristine always는 build directory를 새로 만드는 동작이라고 설명한다.

근거: [Zephyr 4.4.0 west build와 증분 빌드](https://docs.zephyrproject.org/4.4.0/develop/west/build-flash-debug.html)

### 9.7 사용자가 NCS를 직접 설치해야 하는가

전체 source build에는 NCS와 Toolchain이 PC 어딘가에 있어야 한다. 그러나 사용자가 nRF Connect for Desktop이나 west workspace를 수동으로 설치해야 한다는 뜻은 아니다.

~~~text
Boards Manager
     ↓
NU54DK Core와 고정 Toolchain/NCS 자동 설치 또는 bootstrap
     ↓
Arduino IDE의 Verify/Upload 버튼
     ↓
내부적으로 west build + west flash
~~~

ESP32와 Adafruit도 compiler, Core, SDK library 및 업로드 도구를 Arduino data directory에 설치한다. NU54DK도 동일한 UX를 제공하되 내부 빌드 소유권을 Zephyr에 유지한다.

### 9.8 비용 판단

| 비용 주체 | 판단 | 근거 |
| --- | --- | --- |
| 초기 고유 개발비 | 중간 | 공통 Core 외에 build adapter와 cache 필요 |
| 반복 유지비 | 낮음~중간 | 단일 build graph와 NCS 버전 pin |
| 사용자 최초 설치비 | 높음 | NCS source와 Toolchain 다운로드 |
| 사용자 cold build비 | 높음 | 전체 Zephyr 구성 및 최초 컴파일 |
| 사용자 warm build비 | 낮음~중간 | 영구 Ninja tree와 compiler cache 적용 |
| CI·배포비 | 중간 | 대용량 도구 패키지와 OS별 검증 필요 |
| MCU 자원비 | 중간 | Zephyr 비용은 있으나 LLEXT 추가 영역은 없음 |
| 디버깅·지원비 | 낮음~중간 | 정적 ELF symbolization은 단순하나 전체 지원비는 PoC 후 확인 |

### 9.9 판단

Zephyr 필수조건을 만족하면서 Kconfig, DTS 및 module 자유도를 가장 잘 보존한다. 관리 비용도 Loader/EDK 또는 프로파일 행렬 대신 하나의 표준 build graph에 집중된다. 현재 우선순위에 가장 적합하다.

## 10. 후보 F — Full Zephyr와 LLEXT 동시 지원

### 10.1 구조

~~~text
사용자가 빌드 방식 선택
  ├─ Native Full Zephyr
  └─ LLEXT Sketch
~~~

### 10.2 장점

- 고급 사용자는 Kconfig/DTS 자유도를 얻는다.
- 일반 사용자는 빠른 LLEXT 빌드와 작은 업로드를 얻는다.
- 다양한 사용자층에 대응할 수 있다.
- 기존 NU40 LLEXT 경험과 Native Zephyr 개발을 모두 활용할 수 있다.

### 10.3 단점

다음 항목을 이중으로 관리해야 한다.

- build pipeline
- upload pipeline
- linker와 memory layout
- Core API의 정적 경로와 export ABI 경로
- 예제와 사용자 문서
- 오류 진단과 디버깅 방법
- Loader/Core/EDK 버전
- CI 및 보드 실기 시험
- 릴리스 artifact

두 모드의 동작이 조금씩 달라지면 Arduino library 호환성 문제도 두 번 분석해야 한다.

### 10.4 비용 판단

| 비용 주체 | 판단 |
| --- | --- |
| 초기 고유 개발비 | 가장 높음 |
| 반복 유지비 | 가장 높음 |
| 사용자 편의 | 높음 |
| CI·배포비 | 가장 높음 |
| 디버깅·지원비 | 가장 높음 |
| v0.1.0 적합성 | 낮음 |

### 10.5 판단

기능 선택권은 가장 넓지만 세 번째 우선순위인 관리 편의성을 크게 훼손한다. v1에서 두 방식을 동시에 공식 지원하지 않는다.

다만 런타임은 하나로 유지하면서 Board Manager 자동 설치, Ninja cache 및 compiler cache를 추가하는 **배포·캐시 하이브리드**는 채택한다.

## 12. 상대 비용 구조 분석

### 12.1 비용 등급

아래 평가는 공식 일정, 금액 또는 인월 견적이 아니다. 아직 구현량, 지원 OS, 사용자 수, 릴리스 횟수 및 재사용률을 실측하지 않았으므로 상대적인 구조만 표시한다. 모든 후보가 동일한 목표 기능 범위와 품질 수준을 달성한다는 가정이며, GPIO-only bare-metal MVP처럼 기능 범위가 작은 제품의 비용을 뜻하지 않는다.

| 등급 | 의미 |
| --- | --- |
| 낮음 | 공통 작업 외 추가 계층이 거의 없음 |
| 중간 | 하나의 명확한 도구 또는 패키징 계층 추가 |
| 높음 | 별도 artifact, ABI 또는 프로파일 관리 필요 |
| 매우 높음 | 플랫폼 기능 재구현 또는 복수 파이프라인 운영 |

표의 `가장 낮음`, `가장 높음` 및 범위 표시는 위 네 등급 안에서 후보 간 상대 위치를 강조한 표현이다.

### 12.2 비용 주체별 비교

| 방식 | 아키텍처 고유 초기비 | 반복 유지비 | 사용자 설치비 | 사용자 반복 빌드비 | CI·배포비 | MCU 자원비 | 지원·디버깅비 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Bare-metal | 매우 높음 | 매우 높음 | 낮음 | 낮음 | 낮음~중간 | 가장 낮음 | 중간~높음 |
| Adafruit식 | 매우 높음 | 높음 | 낮음 | 낮음 | 중간 | 낮음~중간 | 중간 |
| ESP32식 사전 빌드 | 높음~매우 높음 | 매우 높음 | 낮음 | 매우 낮음 | 매우 높음 | 중간 | 중간 |
| LLEXT | 높음 | 중간~높음 | 낮음 | 가장 낮음 | 높음 | 높음 | 높음 |
| Full Zephyr | 중간 | 낮음~중간 | 높음 | 낮음~중간 | 중간 | 중간 | 낮음~중간 |
| 정적+LLEXT | 가장 높음 | 가장 높음 | 중간 | 모드별 상이 | 가장 높음 | 모드별 상이 | 가장 높음 |

### 12.3 Full Zephyr의 비용이 집중되는 곳

- NCS와 Toolchain의 자동 설치·업데이트·제거
- Windows/Linux/macOS별 tool package
- Arduino builder와 west를 잇는 adapter
- 영구 build directory와 cache 무효화
- clean-machine CI
- 대용량 다운로드의 checksum, SBOM 및 license manifest

### 12.4 LLEXT의 비용이 집중되는 곳

- Loader firmware
- EDK 생성과 배포
- export symbol 및 C/C++ ABI
- Loader/Core/EDK 버전 호환표
- user sketch 파티션과 uploader
- Loader 버전 감지, 조건부 update 및 실패 복구 정책
- LLEXT heap과 memory layout
- 동적 ELF debug 및 crash symbolization

### 12.5 비용 결론

초기 기능 완성만 놓고 보면 Full Zephyr가 가장 적은 아키텍처 고유 계층을 가진다. LLEXT를 선택해도 Arduino API와 Zephyr backend는 동일하게 필요하며 그 위에 Loader 관련 작업이 추가된다.

반대로 사용자가 매우 많고 스케치 빌드 횟수가 많아지면 LLEXT는 중앙의 유지비를 감수하고 전체 사용자 시간을 크게 줄일 수 있다. 공식 Arduino 구현에서 확인되는 빠른 스케치 빌드와 prebuilt 배포 효과를 바탕으로, 본 문서는 이 구조가 규모의 경제와 제품 UX에 잘 맞는다고 해석한다.

### 13.2 점수 근거

#### Full Zephyr — 94.4

- Zephyr 5: 실제 NCS/Zephyr build graph가 최종 펌웨어를 소유한다. **확인**
- 자유도 5: prj.conf, DTS overlay 및 module을 프로젝트별로 반영할 수 있고, NU54DK Arduino Build Adapter 경로도 `v0.1.0`에서 실증됐다. **확인**
- 유지관리 4: NCS/toolchain 패키징 부담은 있으나 runtime/ABI가 하나다. **추정**
- 사용자 편의 3: 최초 설치와 cold build는 무겁지만 자동 설치와 cache로 개선 가능하다. **추정**

#### LLEXT — 80.0

- Zephyr 5: Loader 자체는 실제 Zephyr 애플리케이션이다. **확인**
- 자유도 3: Loader에 이미 포함된 subsystem과 export 범위에서는 자유롭지만 build-time 구성은 Loader 재빌드가 필요하다. **확인**
- 유지관리 2.5: Loader, EDK, export 및 Core 호환성 관리가 추가된다. **확인 + 추정**
- 사용자 편의 5: 전체 Zephyr 환경 없이 작은 스케치를 빠르게 빌드·업로드할 수 있다. **확인**

#### 사전 빌드 Zephyr — 72.2

- Zephyr 5: 최종 런타임은 정적 Zephyr다. **구조상 확인**
- 자유도 2: 사전 빌드 Kconfig/DTS 프로파일에 묶인다. **구조상 확인**
- 유지관리 2.5: profile matrix와 binary/generated artifact 동기화가 필요하다. **추정**
- 사용자 편의 4.5: 설치와 반복 빌드는 빠르지만 지원 프로파일 밖에서는 별도 SDK가 필요하다. **확인 + 추정**

#### 이중 지원 — 91.6

- Zephyr 5: 두 모드 모두 실제 Zephyr runtime을 제공한다. **구조상 확인**
- 자유도 5: Full 모드가 프로젝트별 전체 구성을 제공한다. LLEXT 모드 자체의 자유도는 더 낮다. **구조상 확인**
- 유지관리 1.5: 두 build/runtime 계약, 업로드 경로, 메모리 구조 및 문서를 동시에 유지해야 한다. **추정**
- 사용자 편의 5: 사용자가 빠른 LLEXT와 자유로운 Full 모드를 선택할 수 있다고 가정한다. 실제 전환 UX는 PoC 전이다. **추정**

### 13.3 민감도 분석

G1 통과 후보의 Zephyr 45점은 모두 같으므로 Zephyr 가중치를 바꾸는 실험은 순위 정보를 주지 않는다. 다음 표는 통과 후보의 차이를 만드는 자유도, NUCODE 유지관리 및 최종 사용자 편의의 비율을 바꿔 본 결과다.

| 가중치 프로파일: Zephyr / 자유도 / 유지관리 / 사용자 | 사전 빌드 Zephyr | LLEXT | Full Zephyr | 이중 지원† |
| --- | ---: | ---: | ---: | ---: |
| 기준: 45 / 35 / 12 / 8 | 72.2 | 80.0 | **94.4** | 91.6 |
| 자유도 강조: 45 / 40 / 9 / 6 | 70.9 | 79.5 | **95.8** | 93.7 |
| 관리 소계 강조: 45 / 30 / 15 / 10 | 73.5 | 80.5 | **93.0** | 89.5 |
| 사용자 비중 역전: 45 / 35 / 8 / 12 | 73.8 | 82.0 | 93.6 | **94.4** |

현재의 60:40 관리 가정과 사용자 우선순위에서는 Full Zephyr가 1위다. 반대로 관리 소계 안에서 최종 사용자 편의를 60%로 두면 이중 지원 전략이 1위로 역전된다. 이는 결론이 가정과 무관한 절대값이 아님을 보여 준다.

그럼에도 v0.1.0은 하나의 구현 경로를 먼저 안정화해야 하며, 이중 지원은 Full 경로 자체를 포함한 뒤 LLEXT를 추가하는 roadmap 전략이다. 따라서 v0.1.0 기반 결정은 Full Zephyr로 유지하고, 이중 지원은 §19.4의 재검토 조건으로 분리한다. 향후 최종 사용자 설치·빌드 속도가 자유도와 NUCODE 유지관리보다 높은 우선순위가 되면 LLEXT 또는 사전 빌드 방식도 다시 평가한다.

## 14. 최종 결정이 도출된 과정

~~~text
1. 실제 Zephyr 사용이 필수
   ├─ Bare-metal 탈락
   └─ Adafruit식 FreeRTOS/SoftDevice 탈락

2. 프로젝트별 Kconfig/DTS 자유가 중요
   ├─ 고정 사전 빌드 프로파일 불리
   └─ 고정 LLEXT Loader 구성 불리

3. 장기적으로 하나의 구성 원본과 build graph가 필요
   ├─ Loader/EDK/ABI 이중 관리 회피
   ├─ profile artifact 행렬 회피
   └─ 정적+LLEXT 동시 공식 지원 회피

4. 남은 약점은 설치 용량과 최초 빌드 시간
   └─ 자동 설치, Ninja 증분 빌드 및 compiler cache로 완화하고 PoC로 검증

5. 최종 선택
   └─ Loader 없는 Native Full Zephyr 정적 빌드
~~~

결정문은 다음과 같다.

> **NU54DK Arduino Core는 Arduino의 빠른 스케치 교체를 위해 Zephyr의 빌드 구성 자유를 제한하지 않는다. 각 스케치를 완전한 NCS/Zephyr 애플리케이션으로 정적 빌드하고, 설치 용량과 빌드 속도 문제는 Board Manager 자동 설치, 영구 Ninja build tree 및 compiler cache로 완화한다. 완화 효과와 배포 가능성은 clean-machine PoC 및 실측으로 검증한다.**

위 문구는 2026-08-26 결정 당시의 수락 조건을 보존한다. 이후 `v0.1.0`에서 Arduino CLI/IDE
compile·upload, cache, Boards Manager 설치와 clean Windows 경로를 완료했으며, 다음 설계 단계는
`v0.2.0` M12~M18이다.

### 15.1 저장소별 소유권

| 저장소/영역 | 소유 내용 | 중복 금지 |
| --- | --- | --- |
| NU54DK_Zephyr_DTS | 실제 핀, DTS, pinctrl, 메모리, runner 및 board metadata | Arduino variant에 하드웨어 정보를 다시 복제하지 않음 |
| NU54DK_Arduino_Core | Arduino API, Zephyr backend, 논리 핀 순서, build adapter 및 examples | 보드 전기적 정의를 독립 원본으로 만들지 않음 |
| 사용자 Sketch | 애플리케이션 코드와 profile/feature 선택; prj.conf, overlay, module은 고급 선택 | Core 내부 파일 직접 수정에 의존하지 않음 |
| NCS/Zephyr | kernel, driver, Bluetooth, 802.15.4/Thread, filesystem 및 build system | 프로젝트가 동일 subsystem을 자체 재구현하지 않음 |

### 15.2 빌드 소유권

- west, CMake, Kconfig 및 Devicetree가 실제 펌웨어 빌드를 소유한다.
- Arduino IDE와 CLI는 스케치 전처리, library 탐색, 옵션 전달 및 결과 표시를 담당하는 frontend다.
- Build Adapter는 Zephyr build system을 재구현하지 않고 입력을 변환하는 얇은 계층이어야 한다.
- 최종 ELF, map, .config 및 generated Devicetree 파일을 문제 분석에 보존한다.

### 15.3 플래시 소유권

- 기본 runner는 NU54DK 온보드 CMSIS-DAP에 맞춘 pyOCD다.
- 외장 J-Link를 사용하는 환경을 위해 J-Link runner를 별도 제공한다. NU54DK의 온보드 프로브는 CMSIS-DAP다.
- pyOCD의 nRF54L target 지원과 NU54DK CMSIS-DAP 구현의 조합은 지원 버전을 고정한 뒤 실기 검증한다.
- 프로브 UID 또는 serial number 선택 기능을 제공한다.
- 일반 Flash와 destructive Recovery를 분리한다.
- J-Link software의 재배포는 가정하지 않고 SEGGER 배포 조건에 맞는 설치 정책을 별도로 확정한다.

## 16. 빌드·캐시·패키징 정책

### 16.1 영구 빌드 디렉터리

Build Adapter는 다음 값을 포함하는 cache key를 생성해야 한다.

- Sketch의 canonical project ID와 application source root
- Build Adapter schema와 version
- NCS tag와 manifest revision
- Toolchain revision
- Arduino Core version, source revision 및 개발 tree의 dirty state
- NU54DK board target, board package revision 및 개발 tree의 dirty state
- sysbuild 사용 여부
- prj.conf 및 추가 conf 내용
- DTS overlay 내용
- 선택된 Arduino/Zephyr library와 module의 resolved canonical path, package version 또는 revision
- 빌드 전에 복사·생성되는 interface/artifact가 있다면 해당 artifact fingerprint
- Debug/Release 옵션

같은 key에서는 build directory를 재사용하고, key가 달라지면 별도 directory를 사용한다.

Sketch와 library의 일반 소스 변경은 같은 build tree 안에서 Ninja 의존성으로 추적하여 증분 빌드한다. source 내용 자체를 매 편집마다 새 build-tree key로 만들어 cold build를 유발하지 않는다.

### 16.2 pristine 정책

- 정상적인 Sketch 수정에서는 pristine always를 사용하지 않는다.
- CMake가 자동으로 의존성을 추적하도록 한다.
- 명백한 board/application 불일치에는 pristine auto를 사용할 수 있다.
- 자동 복구가 실패하면 사용자가 선택할 수 있는 Clean Build 기능을 제공한다.
- clean이 발생한 이유를 로그에 표시한다.

### 16.3 컴파일러 캐시

- ccache 또는 sccache를 지원한다.
- 다른 Sketch라도 동일한 NCS/Core object를 재사용할 수 있는지 검증한다.
- 캐시 적중률과 무효화 원인을 진단 로그로 남긴다.

### 16.4 캐시 수명과 정리

- build directory와 compiler cache에 크기 quota를 둔다.
- 마지막 사용 시각을 기록하고 LRU 정책으로 오래된 항목을 정리한다.
- 현재 Sketch의 `Clean Build`와 전체 `Clear Build Cache`를 분리한다.
- 자동 정리가 수행되면 제거한 대상과 회수한 용량을 로그에 표시한다.

### 16.5 개발 단계와 배포 단계

#### 개발 단계

- 이미 설치된 NCS v3.4.0 Toolchain을 사용한다.
- west 직접 빌드로 Core 기능을 먼저 검증한다.
- Arduino CLI 연결은 west 기반 smoke test 이후 진행한다.

#### 공개 배포 단계

- Boards Manager가 필요한 Core와 tool dependency를 자동 설치하도록 한다.
- NCS source와 Toolchain은 고정 버전, checksum 및 license manifest를 가진다.
- 사용자가 nRF Connect for Desktop을 수동 설치하지 않아도 되는 UX를 목표로 한다.
- 동일한 tool package를 여러 Sketch가 공유하도록 한다.
- Windows clean-machine 검증 후 Linux/macOS 지원 범위를 확정한다.

## 18. 구현 전 검증 항목 — 역사적 수락 기준

아래 체크박스는 ADR 수락 당시의 구현 전 PoC 기준을 그대로 보존한 역사 기록이다.
현재 완료 판정은 `v0.1.0` 릴리스 기록과 M0~M11 검증 문서가 소유하며, 이 목록을
현재 미완료 상태표로 해석하지 않는다. 일반 사용자의 구성 UX는 M13 profile이 소유하고,
아래의 직접 `prj.conf`/overlay 항목은 고급 확장 경계를 검증한 기록이다.

### 18.1 빌드 Adapter

- [ ] Arduino CLI가 Blink Sketch를 입력으로 받아 west 빌드를 실행한다.
- [ ] .ino 전처리 및 library 탐색 결과가 Zephyr source target에 정확히 전달된다.
- [ ] 컴파일 오류가 원래 Sketch 파일과 줄 번호로 표시된다.
- [ ] 경로에 공백과 한글이 있어도 동작한다.
- [ ] 동시에 두 Sketch를 빌드해도 build directory가 충돌하지 않는다.

### 18.2 구성 자유도

- [ ] Sketch별 prj.conf 변경이 최종 .config에 반영된다.
- [ ] Sketch별 app.overlay 변경이 generated Devicetree에 반영된다.
- [ ] Sketch에서 Zephyr 공개 API를 직접 include하고 사용할 수 있다.
- [ ] 외부 Zephyr module을 프로젝트에 추가할 수 있다.
- [ ] 구성 변경 후 cache가 올바르게 재구성된다.

### 18.3 빌드 속도

- [ ] cold build 시간을 기록한다.
- [ ] 변경 없는 재빌드 시간을 기록한다.
- [ ] Sketch 한 줄 변경 후 warm build 시간을 기록한다.
- [ ] Arduino library 한 파일 변경 후 시간을 기록한다.
- [ ] prj.conf 변경 후 재구성 시간을 기록한다.
- [ ] overlay 변경 후 재구성 시간을 기록한다.
- [ ] cache hit/miss와 clean 발생 이유를 로그로 확인할 수 있다.

초기 문서에서는 근거 없는 목표 초 수치를 고정하지 않는다. 기준 구현의 실측값을 확보한 뒤 릴리스 완료 기준을 정한다.

### 18.4 플래시와 디버그

- [ ] pyOCD와 온보드 CMSIS-DAP로 반복 플래시한다.
- [ ] J-Link runner로 동일 이미지를 플래시한다.
- [ ] 여러 프로브 연결 시 명시적으로 대상을 선택한다.
- [ ] 일반 업로드가 mass erase를 수행하지 않는다.
- [ ] zephyr.elf를 이용해 source-level debug를 수행한다.
- [ ] sysbuild가 활성화되면 필요한 모든 domain을 올바르게 기록한다.

### 18.5 재현성과 배포

- [ ] NCS, Toolchain, Core 및 board revision이 빌드 로그에 기록된다.
- [ ] clean PC에서 문서화된 설치 절차로 빌드와 업로드가 된다.
- [ ] package checksum, license 및 SBOM 생성 절차가 있다.
- [ ] Core 업데이트 후 cache 호환 또는 무효화가 결정적으로 동작한다.

## 19. 선택하지 않은 방식의 재검토 조건

### 19.1 LLEXT 재검토

다음 조건 중 하나 이상이 실제 요구사항이 되면 별도 연구 브랜치에서 재검토한다.

- 측정된 warm build + flash 시간이 제품 목표를 지속적으로 초과
- 전체 NCS/Toolchain 설치 크기가 배포 목표를 초과
- OTA 또는 런타임 Sketch 교체가 필수
- Arduino Core의 좁고 안정적인 C ABI가 확정
- 사용자 규모가 Loader/EDK 유지비를 상쇄할 만큼 증가
- NU40 Loader 자산의 재사용률과 nRF54 메모리 비용이 실측으로 유리함

재검토 시에는 실행 중 hot unload보다 **Sketch 기록 후 reset-load** 방식을 우선 평가한다.

### 19.2 사전 빌드 Zephyr 재검토

- 사용자 요구가 1개에서 3개의 고정 프로파일로 수렴
- Sketch별 Kconfig와 DTS 자유가 더 이상 필수가 아님
- 프로파일 artifact를 자동 생성·시험할 CI와 저장 인프라 확보

### 19.3 Bare-metal 또는 Adafruit식 재검토

- Zephyr 우선순위 자체가 변경
- Zephyr로 해결할 수 없는 성능·전력·기능 문제가 실측으로 확인
- Bluetooth 및 저수준 platform 유지 책임을 프로젝트가 수용

### 19.4 정적+LLEXT 이중 지원 재검토

- Native Full Zephyr 경로가 안정화
- 공통 Arduino conformance test가 구축
- 별도 유지 인력과 CI 예산이 확보
- 두 모드의 차이를 사용자에게 명확히 설명할 문서 체계가 준비

### 19.5 Bootloader 및 update 경로 재검토

MCUboot 기반 bootloader, DFU update 경로 및 UF2 UX는 LLEXT와 별개의 문제다. DFU는 하나의 특정 bootloader 이름이 아니라 firmware update 방식 또는 전송 경로를 뜻한다. 다음 요구가 생기면 독립적으로 검토한다.

- OTA/DFU
- signed image와 secure boot
- A/B rollback
- 현장 복구
- drag-and-drop UF2

nRF54L15에는 native USB peripheral이 없다. 따라서 drag-and-drop UF2에는 USB MSC/UF2를 제공하는 인터페이스 MCU 펌웨어 또는 별도 USB 하드웨어·전송 경로가 필요하다. 온보드 CMSIS-DAP가 있다는 사실만으로 target MCU의 UF2 update 경로가 자동으로 제공되지는 않는다.

## 20. 결정의 결과

### 20.1 수용하는 결과

- NCS와 Toolchain을 PC에 설치하거나 자동 배포해야 한다.
- 최초 빌드는 상대적으로 느리다.
- Arduino build adapter와 cache manager를 개발해야 한다.

- export symbol 누락에 따른 Loader 재빌드
- Loader EDK와 Core의 버전 결합
- LLEXT heap과 전용 sketch slot
- 동적 ELF 주소 기반 디버깅
- 고정 사전 빌드 Kconfig/DTS 프로파일
- 정적/LLEXT 두 경로의 동시 유지

> **Arduino는 사용자 인터페이스이며, Zephyr가 실제 운영체제이자 빌드 구성의 원본이다.**

## 21. 편향 방지 메모

향후 이 결정을 재평가할 때 다음 오류를 피한다.

- 이미 정한 결론에 맞도록 기준을 숨기는 outcome bias
- Kconfig/DTS 자유를 Zephyr 충실도와 자유도에서 과도하게 이중 계산
- ABI/CI 비용을 관리 점수와 TCO에서 중복 감점
- Full Zephyr cold build와 LLEXT warm build를 직접 비교
- 유지관리자 비용과 최종 사용자 편의를 분리 표시하지 않은 채 하나의 관리 점수로 혼합
- CMSIS-DAP 또는 J-Link를 Runtime Loader로 오인
- ESP32와 Adafruit의 제품 규모와 NU54DK의 조건을 동일하다고 가정
- 공통 Arduino API 개발비를 특정 후보에만 산입
- 정적 링크를 Kconfig/DTS 고정으로 오해

모든 후보는 clean install, cold build, warm build, config change, upload, debug 및 release update라는 동일한 시점과 깊이로 비교해야 한다.
