# NCS 3.4.1 변경과 NU54DK 개발 영향

검토일: **2026-10-01** · 기준 source: `da6bc81227c21fe3709b02ef2080d11936cd7ce4`

상태 갱신: **2026-10-03**. 아래 SDK 영향 분석은 검토 당시 source·설정을 기준으로 보존한다.
이후 NCS 3.4.0에서 M32 W01~W12를 완료했으며, W08의 실패와 후속 성공은 §5에서 구분한다.

## 결론과 적용 정책

**NCS 3.4.0으로 현재 개발을 이어갈 수 있지만, 관련 SDK 결함이 없다는 뜻은 아니다.**
연결 latency/Subrating, CIS·BIS·CS, Mesh LPN 종료와 MCUboot watchdog은 현재 또는 후속 사용
조건과 연결된다. 기존 기능 PASS는 해당 시험 조건의 결과이지 SDK 결함 전체의 부재 증명이 아니다.
당시 W08 BLOB의 UART 결과 누락을 이 수정 목록으로 설명할 근거는 확인하지 못했다.

2026-10-01 사용자 결정에 따라 **v0.6.0은 NCS 3.4.0을 유지하고, v0.7.0은 NCS 3.4.1 전체 SDK
전환만 수행**한다. 신기능 없이 기존 기능을 유지·재검증하며 상세 계획은
[v0.7.0 TODO](../TODO_v0.7.0.md)의 SDK-W01~SDK-W06에서 관리한다. 현재 **0/6, 모두 미착수**다.
2026-10-01 검토에서는 설정·공식 이력 대조와 계획 문서만 갱신했으며 SDK 설치·checkout·lock·toolchain·board
gitlink와 firmware를 변경하지 않았다. 버전 배정은 실제 전환·실기 재개나 공개 승인이 아니다.
현재 사용 경로의 중대 보안 노출·assert·데이터 손상이 재현되면 버전 계획과 별도로 보고하고
회피·수정·전환 선택지를 결정한다. SDK pin 변경이나 임의 backport를 자동 수행하지 않는다.

| 구분 | 현재 판단 |
| --- | --- |

## 4. 보안 수정 — 사용 여부와 입력 도달성을 함께 확인

붙여준 5개 Mbed TLS CVE와 TF-PSA 주요 수정은 공식 공개 내역에서 확인했다. 다만 이는
**주요 항목이지 전체 보안 수정 목록은 아니다.**
[Mbed TLS 4.1.1](https://github.com/Mbed-TLS/mbedtls/releases/tag/mbedtls-4.1.1),
[TF-PSA-Crypto 1.1.1](https://github.com/Mbed-TLS/TF-PSA-Crypto/releases/tag/tf-psa-crypto-1.1.1).

| 공개 항목 | 확인할 실제 사용 조건 |
| --- | --- |
| CVE-2026-50580: ECDHE-PSK TLS 1.2 client overflow | 큰 PSK identity·출력 buffer 조건까지 확인. ‘CBC OFF’ 하나만으로 노출을 판정하지 않음 |
| CVE-2026-50586: TLS 1.2 ticket callback 오류 시 4-byte 노출 | 서버·ticket callback 사용 및 오류 경로 |
| CVE-2026-50588: EC-JPAKE ServerKeyExchange OOB read | TLS 1.2 EC-JPAKE 사용·외부 메시지 입력 |
| CVE-2026-49300: 잘못된 basicConstraints CA 해석 | 비신뢰 사용자 인증서를 직접 수용하고 별도 구현의 trusted-root 등록 판정과 기기 해석이 달라지는 경로. 공식 권고상 신뢰 CA 발급 인증서만 수용하는 경우는 비영향 |
| CVE-2026-50585: session reset 뒤 DTLS 상태 잔존 | DTLS·세션 재사용·SRTP 설정 |
| TF-PSA CVE-2026-50587 / 50584 / 50583 | 각각 RSA PKCS#1 v1.5 복호화 timing, raw ChaCha20 counter 경계, 잘못된 ECC 공개키 parse |

세부 조건은 [ECDHE-PSK 권고](https://mbed-tls.readthedocs.io/en/latest/security-advisories/mbedtls-security-advisory-2026-07-tls12-ecdhe-psk-client-buffer-overflow/),
[X.509 권고](https://mbed-tls.readthedocs.io/en/latest/security-advisories/mbedtls-security-advisory-2026-07-x509-ca-bit-forgery-invalid-basicconstraints/),
[ECC parser 권고](https://mbed-tls.readthedocs.io/en/latest/security-advisories/mbedtls-security-advisory-2026-07-zero-length-ecc-public-key-oob-read/)를 따른다.

2026-10-01에 읽은 W08 생성 `.config`에서는 TLS/DTLS 사용 경로를 찾지 못했고, app watchdog·raw
ChaCha20·RSA PKCS#1 v1.5 복호화는 비활성이었다. **그러나 X.509/CRT/PK parse 옵션은 활성**이다.
Core/library의 `mbedtls_pk_parse*`, X.509 parser 직접 호출은 검색에서 발견하지 못했지만,
정적 검색만으로 모든 SDK 내부 경로와 사용자 Sketch의 도달성을 부정할 수 없다.
따라서 ‘BLE만 쓰므로 보안 영향 없음’, ‘crypto 전체 OFF’ 또는 ‘모든 CVE 비적용’으로 쓰지 않는다.
ECDSA P-256 이미지 서명 검증을 곧바로 TLS/X.509 실행으로 간주해서도 안 된다.

고급 `prj.conf`에서 TLS·인증서·외부 공개키·알고리즘/driver를 바꾸는 사용자는 설정만 아니라
최종 `.config`·link map·실제 입력 경로를 함께 점검해야 한다. 현재 설정 검토를 커스텀 구성의
보안 보증으로 재사용하지 않는다. 공개 전에는 당시 최신 보안 권고와 실제 배포 image로 재평가한다.

### 설정 대조의 재현 경계

2026-10-01에 `C:\t\blob-latest-dev`의 세 role app/MCUboot/sysbuild `.config`와
`C:\t\mdfu-target-b-pinned`를 읽었다. 이는 로컬 build 설정 관찰이며 새 exact HIL·재현 빌드가 아니다.
선별한 안전한 설정 값과 source 연결만 이 문서에 남긴다. 로컬 절대 경로·과거 config를 다음
PC의 입력으로 강제하지 않으며 signing key·원시 probe UID·전체 비공개 환경은 저장하지 않는다.
관찰한 12개 config의 역할·domain별 byte SHA-256은 [감사 원장](../document-review.json)의
`configuration_observations`에 남긴다. 기존 build를 새로 재현하거나 각 config를 clean source
commit에 다시 결합한 것은 아니므로, SDK 전환·실기 재개 시에는 새 build identity를 확보한다.

## 5. W08의 과거 실패와 후속 완료

[283번 기록](<../04_검증 기록/283_M32_W08_BLOB_Mesh_DFU_software와_HIL_blocker.md>)의
`8dcb033e…` 실행은 **FAIL 유지**다. Client·target A의 최종 UART 결과와 target B debugger
완료 상태는 전송 완료를 지지하지만 target B `RESULT/END` 및 session STOP 증거가 없다.
CFSR/HFSR 0과 idle PC 관찰은 그 순간 CPU fault가 보이지 않았다는 범위만 말한다.

VCOM 재개방 경합은 원인 후보다. 정확한 유실 위치, SDK 연관, 다른 잠재 오류 부재는 확정하지
않았다. 당시 결과 재출력·동일 중복 허용 보강의 Host/build PASS는 실기 완료와 구분한다.

후속 clean source `40e4c46b…`의 BLOB 시험은 10/10회·두 target의 digest와 세 역할 STOP/cleanup을
PASS했다. Signed MDFU는 clean `e0a1b7fd…`에서 5회·두 target 10/10 배포와 negative·confirm/rollback을
PASS했다. 당시 FAIL 원본, timeout 진단과 완료 근거는
[294번 기록](<../04_검증 기록/294_M32_W08_BLOB_PASS와_MDFU_timeout_진단.md>)을 따른다.
이 완료는 NCS 3.4.0의 별도 exact 시험 결과이며, 3.4.1 수정 목록을 실패 원인이나 해결 증거로
사용한 것이 아니다. M32 전체 완료·후속 인계는 [M32 TODO](../TODO_M32.md)가 소유한다.

## 6. v0.7.0 SDK 전환 전용 계획

3.4.1에 새 칩 지원·DULT v2·MCUboot 복수 검증 키 등이 있어도 v0.7.0 신기능으로 추가하지
않는다. M34~M37 Security·Storage·Update 확장은 v0.8.0, M38~M41 Radio·Network는 v0.9.0,
M42~M45 Matter는 v0.10.0으로 배정한다. 기존 M 번호·기능 소유권은 유지한다.

실행·완료 조건의 단일 원본은 [v0.7.0 TODO](../TODO_v0.7.0.md)다.

| SDK-W01 | 3.4.0 baseline 보존, 3.4.1 전체 manifest·module SHA·대응 toolchain·board 호환성과 적용 결함 조건 |

SDK-W04에서는 기존 3.4.0 기반 image의 업데이트·invalid key/image·counter/rollback·활성
watchdog의 erase/swap/hash를 적용 조건대로 확인한다. 새 실제 power-cut·다중 layout/transport
확장은 v0.8.0 M36의 별도 정책·fixture·사용자 요청을 따른다. 3.4.1이 patch라는 이유나 새 SDK
build PASS만으로 무회귀·전환 완료를 가정하지 않는다. HOST-W04~W08의 사용자 보류는 유지하며,
완료한 M32 실기를 SDK 전환 착수 지시로 다시 예약하지 않는다.

읽기 전용 이력 비교에는 각 저장소의 실제 tag가 있는지 먼저 확인한 뒤
`git log v3.4.0..v3.4.1`(nrf), `git log ncs-v3.4.0..ncs-v3.4.1`(zephyr),
`git diff v3.4.0 v3.4.1 -- softdevice_controller/CHANGELOG.rst mpsl/CHANGELOG.rst`(nrfxlib)를
사용할 수 있다. 이 문서는 모든 하위 저장소 commit을 열거한 전체 diff나 새 SDK 실기 보고서가 아니다.
