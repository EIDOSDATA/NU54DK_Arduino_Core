## 2. 제품 원칙

1. Arduino Core는 Zephyr를 대체하지 않고 Zephyr application 안의 호환 계층으로 구현한다.
2. 보드 GPIO, pinctrl, peripheral과 runner는 고정 board submodule이 소유한다.
3. 첫 제품선은 NCS v3.4.0과 Zephyr 4.4.0에 고정한다.
4. 일반 사용자는 `.ino`, library와 검증된 Tools profile을 사용한다.
5. 전문가는 명시적 `prj.conf`·overlay와 Zephyr/NCS 공개 API를 사용할 수 있다.
6. Arduino 사용자 예제는 `libraries/*/examples`를 단일 원본으로 사용한다.
7. 정상 build에서 무조건 `pristine always`를 사용하지 않는다.
8. CMSIS-DAP V2/pyOCD를 기본 upload 경로, 외장 J-Link를 선택 경로로 둔다.
9. Build PASS를 runtime, HIL 또는 제품 지원 PASS로 확대하지 않는다.
10. RC와 stable artifact는 exact source와 package metadata에 고정하고 같은 version을 덮어쓰지 않는다.
11. Loaderless 기본 layout은 영구 저장소를 제외한 RRAM 전체를 단일 application에 제공한다.
    MCUboot/DFU dual-slot은 실제 update·rollback 기능과 함께 검증한 고급 선택으로만 제공한다.
12. 객체 이름, register wrapper 또는 build 성공을 독립 instance 지원이나 DMA 검증으로 확대하지 않는다.
13. 모든 공개 peripheral은 실제 hardware identity, 자원 충돌과 동시 실행 가능 범위를 진단할 수 있어야 한다.
14. Bluetooth LE 완료 범위는 nRF54L15와 고정 NCS가 제공할 수 있는 기능군과 승인 profile catalog로
    한정하고 BR/EDR·모든 adopted profile·qualification을 자동 포함하지 않는다.
15. 고정 NCS의 nRF54L15 지원 Bluetooth 예제마다 Arduino 제공 경로를 배정한다. 일반 기능은 wrapper,
    고급 기능은 direct API·validated profile·application template로 제공하고 예제 단위로 검증한다.
16. 2026-09-16 사용자 결정에 따라 무선 기능의 기본 수락 범위는 보드 3개로 수행하는 프로토콜·데이터·
    수명주기·오류 복구다. 정밀 RF 보정·음질·절대 거리/각도 정확도는 필수 gate 밖이다. 외부 장치 전용
    경로의 미실행 결과는 해당 제공 형태와 함께 공개하며 기능 HIL 성공으로 바꾸지 않는다.
17. Apple/Google·외부 vendor 기능과 mic/speaker·외장 장치 경로도 작동 가능한 구현·예제·설정/연결
    안내·자동 가능한 검사를 제공한다. 실제 장치 운용·상호운용은 사용자가 추후 검증하며 해당 실기의
    `NOT RUN`은 v0.5.0 개발·공개를 차단하지 않는다. 검증되지 않은 장치 지원·호환성을 선언하지 않는다.
18. Ubuntu/macOS의 실제 설치·USB upload·serial·debug는 사용자가 최종 릴리스 단계에서 검증한다.
    중간 개발은 기다리지 않으며 세 Host 정식 지원을 위한 최종 실물 증거 gate는 M33에 유지한다.

## 3. 단계 상태

| 상태 | 의미 |
| --- | --- |
| 완료 | 완료 기준과 필수 검증을 통과했고 증거를 보관함 |
| 진행 중 | 구현 또는 검증을 시작했으나 완료 기준을 모두 통과하지 않음 |
| 계획 | 제품 범위와 순서를 정했지만 아직 구현을 시작하지 않음 |
| 대기 | 선행 단계 또는 결정 gate를 기다림 |
| 차단 | 기술·법적·hardware 문제 때문에 진행할 수 없음 |
| 재검토 | 전제가 바뀌어 범위나 구조를 다시 결정해야 함 |

단계 번호는 구현 순서이며 일정 날짜가 아니다. `계획`과 `대기`는 지원 상태가 아니며, code나
header가 존재해도 완료 증거 전에는 API matrix를 상향하지 않는다.
M28은 W01~W08·9개 test ID, M29와 M30은 W01~W08·10개 test ID를 완료했다.
M30 실제 전원 차단은 네 지점 × 3회, 12/12 PASS이며 M31~M45는 계획이다. M28~M30 완료는
v0.5.0 공개, cross-vendor 상호운용 또는 Bluetooth qualification 완료가 아니다.

`AC-01`~`AC-03`은 전역 마일스톤 번호가 아니라 `v0.3.0`의 Arduino Compatibility 하위 작업
package다. M0~M22와 AC-01~AC-03은 공개 제품 이력으로 번호와 의미를 고정한다. 아직 착수하지
않았던 기존 M23~M34 계획은 2026-09-03 경쟁 범위 재검토에서 M23~M45로 재배치했다. 이전 번호와
새 번호의 대응은 14절에 보존한다.

검증으로 구분하며, RX candidate를 검증된 지원으로 올리거나 기본 controller를 자동 교체하지 않는다.
정적 source 근거와 미확정 결정은 [착수 계획 §2](../TODO_v0.5.0.md#2-현재-확인된-지원성-결정-항목)에 있다.

M31-A/B/C와 M32-A/B/C는 각 마일스톤 내부 기능군이다. 작업 분모는 M31 8개, M32 12개,
M33 8개이며 test family·하위 case·upstream sample 개수와 별도로 집계한다. 기능별 연결/stream 수,
손실·반복·timeout·복구 기준은 [착수 계획 §5](../TODO_v0.5.0.md#5-장비와-정량-판정-기준)와 단계 TODO에서
고정한다. 보드 3개 제공은 사용자 확인이며 실제 probe SHA-256·serial·role·image는 실행 직전 다시 대조한다.
OS별 BLE peer 상호운용과 Arduino 개발 Host 지원은 서로 다른 matrix다. Host 작업의 범위·순서·
완료 조건은 [다중 Host 지원 착수 계약](<../02_빌드 설계/10_v0.5.0_다중_Host_지원_착수_계약.md>)을 따른다.

M31의 기능 HIL은 ISO 실제 송수신, 합성 PCM/LC3 경로, 지원되는 CTE 송신과 적용 가능한 raw IQ
수신, connected ACL 기반 CS/RAS procedure·결과·복구를 검증한다. CS는 DF와 별도 경로이며
A1_B1의 두 보드 역할을 기본 자동 검증 대상으로 삼는다. Raw IQ의 미실행 사유는 controller/build/
runtime 조사 결과로 기록하며 안테나 배열 부재로 자동 제외하지 않는다.
외부 audio·Apple/Google·타 vendor 경로는 구현·예제·설정/연결 안내·자동 검사까지 M31~M33에서
완성한다. 실제 장치 운용·상호운용은 사용자 추후 검증 `NOT RUN`으로 인계하고 v0.5.0 개발·공개를
차단하지 않는다. 정밀 거리/각도 보정·음질 계측은 필수 gate 밖이며, 실제 검증된 호환성과
qualification의 주장 범위는 M33에서 각각 증거에 맞춘다.

모든 항목의 upstream 경로·Arduino 제공 방식·예제·negative·장비는
[전체 기능 실행 계약](19_NCS_Bluetooth_전체_기능과_예제_실행_계약.md)에 명시한다.

### 9.2 문서 검토 후 적용할 실행 보완

- M30-W08은 A 도구·provenance 안정화 → B 산출물·preflight 재생성 → 사람 준비 확인 →
  C 실제 4지점 × 3회 전원 차단 → D 회귀·마감을 완료했다. 세부 근거는 161번 기록에 보존한다.
- M31-A/B/C와 HOST-W04~HOST-W06은 독립 가능한 부분을 병행한다. Host는 별도 8개 작업이며
  현재 3/8 완료이고 M31/M32 기능 완료의 분모에 합치지 않는다. 세 Host 정식 지원의 최종 gate는 M33이다.
- M32는 다른 radio의 단독 TX/RX 근거 뒤 공존을 검증하며 HOST-W07의 실행기·절차·자동 검사를
  병행 준비한다. Ubuntu/macOS 실제 설치·USB/serial/debug는 사용자가 최종 릴리스에 검증하고
  중간 개발의 대기 조건으로 삼지 않는다.
- M33의 사용자 경로 정리에 ARF-04A 기존 API 목적별 예제를 추가한다. 새 public API·자원 정책은
  별도 ARF 작업으로 분리하고 M30 완료 조건에 추가하지 않는다.
- ARF-01은 M32-W04로 통합하고 ARF-05/06A → 03 → 02, 조건부 04B/06B의 후속 순서는
  [개정 실행 계획](18_문서_전면검토와_개선_마일스톤.md)을 따른다.
  M33 이후 ARF의 배포 버전은 착수 시 API·자원·HIL 비용과 기존 제품선 영향을 확인해 결정한다.
  `v0.5.1`이나 `v0.6.0`에 임의 배정하지 않으며 M34~M45의 번호·주제를 유지한다.

## 10. `v0.6.0` 제품선 — M34~M37 Security/Update

이 제품선은 storage, PSA Crypto/Cracen, secure boundary와 production update/recovery를 다룬다.
M30의 BLE DFU용 최소 secure-update 기반을 모든 transport와 layout으로 확장하고 hardening한다.
M30은 고정 boot/layout·서명·초기 설치·BLE update·실패 복구와 제공 형태를 먼저 마련한다.
현재 native build/upload 경로를 MCUboot 지원으로 간주하거나 그 기반 전부를 M36까지 미루지 않는다.

| 단계 | 계획 범위 | 완료 전 필수 경계 |
| --- | --- | --- |
| M34 | Storage 범위, PSA Crypto/Cracen·KMU API와 direct 경로 | Key·entropy·lifetime·secure storage·보안 오용 경계 |
| M35 | TF-M `/ns`, secure/non-secure ownership과 recovery | Secure service, fault 격리와 복구 가능성 HIL |
| M36 | Memory layout preset, MCUboot, BLE/serial/외부 update transport, sysbuild와 partition | Loaderless 기본값 불변, signed update, rollback·power-loss·migration |
| M37 | `v0.6.0` package와 공개 | 실패 복구, key/layout migration, security 운영 문서와 재현 gate |

Runtime wrapper가 적절하지 않은 기능은 validated profile 또는 application template로 제공한다.
Update 성공 경로만 확인하고 recovery를 검증하지 않은 상태에서는 제품 지원을 선언하지 않는다.
Arduino Tools에는 임의 byte 입력 대신 검증한 layout preset을 제공한다. Boot reservation과 dual slot은
실제 MCUboot/DFU profile에서만 선택할 수 있다.

M34→M35→M36은 key 식별자·소유자·저장 형식·삭제/복구·migration 정책을 인계한다.
M32 Mesh DFU/BLOB·배포자의 내부 RRAM 예산과 M33 credential template 요구도 이때 인계한다.
M36은 고급 layout·외부 storage·다중 transport를 확장하며 M32의 최소 Mesh update 경로를 소급 완료하지 않는다.
M30의 최소 구현과 회귀 근거를 재사용하되, TF-M `/ns` 또는 controller/profile 변경은 해당
서비스·무선 조합의 지원성부터 다시 판정한다. 기존 단일 profile PASS를 새 보안 경계로 복사하지 않는다.

## 11. `v0.7.0` 제품선 — M38~M41 Radio/Network

| 단계 | 계획 범위 | 완료 전 필수 경계 |
| --- | --- | --- |
| M38 | M32-C 기반 재사용, RADIO/MPSL resource·clock·timeslot·diagnostic profile와 NCS radio 예제 inventory | profile ownership·동시 조합·cache identity, public/direct 제공 경로와 적용 build |
| M39 | IEEE 802.15.4 raw MAC 및 ESB PTX/PRX, ACK/retry/payload/channel과 공개 짝 예제 | 각 방향 payload·address filtering·timeout·stop/restart·허용 BLE 공존 HIL |
| M40 | OpenThread 역할/commissioning·dataset·join/leave·IPv6/UDP·저전력·영속성과 NCS network 예제 | 지원 FTD/MTD/router/child 역할 판정, network traffic·peer loss·reset recovery |
| M41 | `v0.7.0` package와 공개 | Profile migration, coexistence 제약과 network HIL |

M17의 OpenThread NU54DK Build PASS는 join이나 network runtime 지원이 아니다. BLE와 다른 radio
protocol을 함께 쓰는 구성은 M32의 MPSL coexistence gate를 통과한 조합만 허용한다.
M32에서 검증용 backend/profile과 각 radio의 단독 TX/RX를 먼저 확보하고, M38/M39에서 공개
API·예제·지원 조건을 확장한다. 조합·부하·profile이 달라지면 영향받는 공존 검증도 추가한다.
이 최소 기반과 제품화의 구분을 통해 기존 M 번호와 제품 순서를 유지한다.

## 12. `v0.8.0` 제품선 — M42~M45 Matter

M42 시작 조건에는 Matter transport, Thread 선택 시 M40의 network 근거, 적용할 M32 공존
조합과 최소 secure-update 경로를 연결한다. NU54DK 외장 flash 미탑재를 고려한 RAM/RRAM·
partition 예산과 개발용/생산용 factory data·credential 정책을 먼저 정한다.

| 단계 | 계획 범위 | 완료 전 필수 경계 |
| --- | --- | --- |
| M42 | transport·Partition·factory data·개발/생산 credential·provisioning | NU54DK storage와 Thread/공존/secure update 선행 근거 |
| M43 | nRF54L15 적용 Matter sample별 template, cluster/event/attribute와 Arduino UX | 예제별 build/resource·생성 코드·Core/application 소유권 |
| M44 | BLE commissioning·Thread 운용, fabric 추가/제거·access control·subscription·reset persistence | 실제 commissioner·network·credential·update/recovery HIL; 외부 controller 없으면 NOT RUN |

## 13. 공통 완료 규칙

마일스톤을 `완료`로 바꾸려면 해당 범위에 필요한 다음 증거를 연결한다.

1. 고정 source, board, NCS, Zephyr와 Toolchain identity
2. Public API signature와 compile/link contract
3. 정상·경계·오류·negative semantic test
4. Profile, Kconfig, DTS와 resource conflict 검증
5. 필요한 NU54DK HIL과 fixture 경계
6. Arduino CLI/IDE example과 package 사용자 경로
7. 알려진 제약, 범위 제외와 복구 절차
8. Version별 release artifact와 공개 승인

후속 실기는 test ID별 source/profile·장비·입력·수치 합격 기준·최대 시간/반복·오류 중단 및
유한 재검증 조건을 실행 전에 고정한다. 미확정 값·장비 미확보·실험적 SDK 기능은 판정 항목으로
남기며, 계획 정비만으로 필수 시험을 지우거나 물리 PASS로 바꾸지 않는다.

Hardware 의존 기능은 build 성공만으로 완료하지 않는다. 프로젝트 소유자가 명시적으로 승인한
비지원·NOT RUN 범위는 지원표에 정확히 표시하고 해당 milestone의 비차단 제외가 될 수 있다.
v0.5.0의 Apple/Google·외부 vendor 및 mic/speaker·외장 장치 실물 운용은 이 비차단 범위로 확정했다.
작동 가능한 구현·예제·설정/연결 안내와 자동 가능한 검사 완료는 필수이며, 실물 운용·호환성은
사용자 추후 검증 `NOT RUN`으로 표시한다. 적용 가능한 보드 기반 기능 HIL과 M33의 최종 세 Host
실물 증거는 계속 필수다. 상세 scope는 [전체 기능 계약](19_NCS_Bluetooth_전체_기능과_예제_실행_계약.md)을 따른다.
다만 AC-01~AC-03에서 구현 목표로 확정한 항목은 자동으로 비차단 제외하지 않는다. 안전한 구현,
하드웨어 비적용 판정 또는 별도 scope 개정 승인 전까지 해당 AC package와 M22를 완료하지 않는다.

## 14. 변경 관리

- 단계 상태를 바꿀 때 완료 기준과 증거 링크를 함께 갱신한다.
- 상세 수치와 실행 log는 검증 기록에만 추가하고 master roadmap에 복제하지 않는다.
- API 지원 범위가 바뀌면 API matrix와 필요한 예제·시험을 같은 변경에서 갱신한다.
- AC package 상태를 바꿀 때 해당 API별 난이도·의미 차이·HIL 범위와 M22 선행조건을 함께 갱신한다.
- Board 변경은 별도 board 저장소에서 검증한 뒤 Core의 gitlink만 의도적으로 갱신한다.
- NCS upgrade는 기존 v3.4.0 기준선을 덮어쓰지 않고 별도 호환성 평가와 migration으로 결정한다.
- RC나 stable version 이름으로 다른 byte의 artifact를 다시 만들지 않는다.
- M23~M33 상세 범위와 경쟁 기준은
  [전 인스턴스·DMA·BLE 경쟁 마일스톤](08_전_인스턴스_DMA_BLE_경쟁_마일스톤.md)에 고정한다.
- AC-01~AC-03은 `v0.3.0` 전용 하위 작업 ID이며 이후 전역 M 번호를 대체하거나 재번호화하지 않는다.

2026-09-16 개정 10.1은 외부 장치 구현/자동 검사와 사용자 추후 실물 검증을 구분하고 후자의
NOT RUN을 v0.5.0 비차단으로 확정했다. Ubuntu/macOS 실기는 최종 릴리스 사용자 검증으로 배치하며
세 Host 최종 증거 gate를 유지한다. DF raw IQ의 배열 비필수·controller 후보 검증과 CS 두 보드 경로를 명시했다.
2026-09-16 개정 10.0은 사용자 요청에 따라 Bluetooth 전체 기능·NCS 예제를 M31~M33에 재배치했다.
M31 8개·M32 12개·M33 8개 실행 TODO와 전체 기능 계약을 연결하고 ARF-01을 M32-W04로 통합했다.
보드 3개 기능시험을 기본으로 하며 정밀 RF/audio/거리/각도 계측은 필수 gate 밖으로 개정했다.
M34~M45 번호·제품 주제는 유지하면서 Mesh update·radio·Thread·Matter 예제 인계를 명시했다.
2026-09-15 개정 9.8은 M30 W08 실제 전원 차단 12/12 완료와 M31 착수 지점을 반영했다.
개정 9.7은 전체 문서 검토에 따라 M30 재개 복구 단계를 명시하고, M33 예제 보강과
후속 ARF를 분리했다. 완료 기록·시험 분모·M34~M45 제품 배정은 변경하지 않았다.
근거는 [160번 기록](<../04_검증 기록/160_전체_문서_검토와_마일스톤_개정.md>)이다.
