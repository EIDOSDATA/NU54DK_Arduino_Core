## 2. 제품 원칙

1. Arduino Core는 Zephyr를 대체하지 않고 Zephyr application 안의 호환 계층으로 구현한다.
2. 보드 GPIO, pinctrl, peripheral과 runner는 고정 board submodule이 소유한다.
3. 첫 제품선은 NCS v3.4.0과 Zephyr 4.4.0에 고정한다.
4. 일반 사용자는 `.ino`, library와 검증된 Tools profile을 사용한다.
5. 전문가는 명시적 `prj.conf`·overlay와 Zephyr/NCS 공개 API를 사용할 수 있다.
6. Arduino 사용자 예제는 `libraries/*/examples`를 단일 원본으로 사용한다.
7. 정상 build에서 무조건 `pristine always`를 사용하지 않는다.
8. CMSIS-DAP V2/pyOCD를 기본 upload 경로, 외장 J-Link를 선택 경로로 둔다.
9. Build PASS를 runtime, HIL 또는 제품 지원 PASS로 확대하지 않는다.
10. RC와 stable artifact는 exact source와 package metadata에 고정하고 같은 version을 덮어쓰지 않는다.
11. Loaderless 기본 layout은 영구 저장소를 제외한 RRAM 전체를 단일 application에 제공한다.
    MCUboot/DFU dual-slot은 실제 update·rollback 기능과 함께 검증한 고급 선택으로만 제공한다.
12. 객체 이름, register wrapper 또는 build 성공을 독립 instance 지원이나 DMA 검증으로 확대하지 않는다.
13. 모든 공개 peripheral은 실제 hardware identity, 자원 충돌과 동시 실행 가능 범위를 진단할 수 있어야 한다.
14. Bluetooth LE 완료 범위는 nRF54L15와 고정 NCS가 제공할 수 있는 기능군과 승인 profile catalog로
    한정하고 BR/EDR·모든 adopted profile·qualification을 자동 포함하지 않는다.

## 3. 단계 상태

| 상태 | 의미 |
| --- | --- |
| 완료 | 완료 기준과 필수 검증을 통과했고 증거를 보관함 |
| 진행 중 | 구현 또는 검증을 시작했으나 완료 기준을 모두 통과하지 않음 |
| 계획 | 제품 범위와 순서를 정했지만 아직 구현을 시작하지 않음 |
| 대기 | 선행 단계 또는 결정 gate를 기다림 |
| 차단 | 기술·법적·hardware 문제 때문에 진행할 수 없음 |
| 재검토 | 전제가 바뀌어 범위나 구조를 다시 결정해야 함 |

단계 번호는 구현 순서이며 일정 날짜가 아니다. `계획`과 `대기`는 지원 상태가 아니며, code나
header가 존재해도 완료 증거 전에는 API matrix를 상향하지 않는다.

`AC-01`~`AC-03`은 전역 마일스톤 번호가 아니라 `v0.3.0`의 Arduino Compatibility 하위 작업
package다. M0~M22와 AC-01~AC-03은 공개 제품 이력으로 번호와 의미를 고정한다. 아직 착수하지
않았던 기존 M23~M34 계획은 2026-09-03 경쟁 범위 재검토에서 M23~M45로 재배치했다. 이전 번호와
새 번호의 대응은 14절에 보존한다.

## 7. `v0.3.0` 완료 상태 — M19~M22와 AC-01~AC-03

상세 API, 완료 조건과 제외 범위는
[v0.3.0 구현 마일스톤](07_v0.3.0_구현_마일스톤.md)을 단일 원본으로 사용한다.

```text
BLE:           M19 BLE Core/GAP
                 → M20 범용 GATT server/client
                 → M21 pairing·bonding·표준 profile ─┐
                                                     ├→ M22 v0.3.0 RC/stable
Compatibility: AC-01 Core·GPIO·시간
                 → AC-02A 핀·주변장치 소유권 기반
                 → AC-02B runtime handover·tone·Servo
                 → AC-03 Storage·library 호환성 ─────┘
```

BLE 트랙과 Compatibility 트랙은 M18 완료 기준선에서 병렬로 진행했고 M22에서 합류했다.

`v0.3.0`은 public library 8개와 예제 29개를 제공한다. `Standard peripherals` 22개와 BLE 7개를
M22 stable 설치본 exact 목록으로 compile했다. `v0.2.0`의 library 4개·예제 14개 기록은 역사
자료로 소급 변경하지 않는다.

### M19 — BLE Core와 GAP

- 난이도: **상** — 추가 instance와 PWM/timer/console 자원 소유권을 profile·DTS와 함께 조정해야 함
- 핵심 구현 범위: `Serial1`, Wire/SPI runtime lifecycle과 제한된 `setPins()`, ADC 8-channel
  metadata·resolution, PWM resolution·frequency, `tone()`/`noTone()`와 Servo

- 핵심 gate: instance conflict·unsupported pin negative, bus·ADC·PWM·tone·Servo build/semantic 및
  필요한 NU54DK HIL

AC-02A는 heap 없는 고정 슬롯 manager와 owner/resource key, 원자적 reserve/commit/rollback/release,
generation/epoch 기반 stale lease 방지, ISR 변경 거부를 구현했다. AC-02B는 이 기반 위에 실제

미지원 instance와 mode는 fail-closed로 유지한다. Cross-board Wire 진단에서 확인한 P1.2/P1.3
continuity 불연속은 controller 실패와 분리했다. 최종 3-wire fixture는 공통 GND, peer
P2.5↔DUT P1.12 공유선과 DUT P2.2↔P2.4 local SPI loopback이다. Wire는 DUT 온보드 BQ25186
`0x6A` register `0x0C == 0x41`의 read-only 100/400 kHz repeated-start와 end/rebegin으로 검증했다.
공유선은 peer가 ADC LOW/HIGH를 구동한 뒤 DUT가 같은 A0/P1.12를 PWM20으로 넘기고 peer가 bounded
polling으로 25%·75% duty를 포착했다. Serial1, Wire, SPI, ADC raw 0/3757과 PWM 25%/75%가 모두 PASS했다.
상세 증거는 [AC-02A 소유권 기준선](<../04_검증 기록/26_AC-02A_핀과_주변장치_소유권_기준선.md>)과
[AC-02B runtime 기준선](<../04_검증 기록/27_AC-02B_Peripheral_Analog_runtime_기준선.md>)을 따른다.

### AC-03 — Storage facade와 library 생태계 Compatibility

- 상태: **완료** — exact commit `0b7f89283cd82a68a7f3f0910f4fc59b8dd01bfb` 두 보드 HIL PASS
- 난이도: **상** — persistence·migration·용량 경계와 제3자 library의 compile/runtime 차이를 관리해야 함
- 핵심 범위: Settings/ZMS 위 1024-byte Arduino EEPROM mirror, 전용 32 KiB LittleFS,
  8개 library·29개 예제의 compile/runtime 호환성과 문서
- 핵심 gate: reset persistence·용량·손상·migration negative, 대표 library Arduino CLI compile과
  hardware 의존 항목의 선택 HIL

RC3는 AC-03의 LittleFS `0x16c000..0x174000`과 Settings/ZMS
`0x174000..0x17d000` 주소를 유지하면서, 사용하지 않던 boot reservation과 두 번째 image slot을

696 KiB dual-slot 표기는 당시 artifact의 역사 기록으로 보존한다.

각 보드는 reset 3회 동안 EEPROM/LittleFS 영속성, 손상 자동 수용 거부, 명시적 복구와 최종
시험 데이터 정리를 통과했다. AC-03의 facade는 `v0.3.0` 내부 storage 호환 계층에 한정한다. 외부 flash, secure storage,
PSA Crypto/Cracen과 고급 update/recovery용 partition은 M34~M37의 `v0.6.0` 범위로 재배치했다. Native USB,
DAC, Wi-Fi와 AVR Harvard memory처럼 NU54DK hardware에서 같은 의미를 제공할 수 없는 기능은 AC
완료 조건에 포함하지 않고 명시적 하드웨어 비지원으로 유지한다.

## 13. 공통 완료 규칙

마일스톤을 `완료`로 바꾸려면 해당 범위에 필요한 다음 증거를 연결한다.

1. 고정 source, board, NCS, Zephyr와 Toolchain identity
2. Public API signature와 compile/link contract
3. 정상·경계·오류·negative semantic test
4. Profile, Kconfig, DTS와 resource conflict 검증
5. 필요한 NU54DK HIL과 fixture 경계
6. Arduino CLI/IDE example과 package 사용자 경로
7. 알려진 제약, 범위 제외와 복구 절차
8. Version별 release artifact와 공개 승인

Hardware 의존 기능은 build 성공만으로 완료하지 않는다. 프로젝트 소유자가 명시적으로 승인한
비지원·NOT RUN 범위는 지원표에 정확히 표시하고 해당 milestone의 비차단 제외가 될 수 있다.
다만 AC-01~AC-03에서 구현 목표로 확정한 항목은 자동으로 비차단 제외하지 않는다. 안전한 구현,
하드웨어 비적용 판정 또는 별도 scope 개정 승인 전까지 해당 AC package와 M22를 완료하지 않는다.

## 14. 변경 관리

- 단계 상태를 바꿀 때 완료 기준과 증거 링크를 함께 갱신한다.
- 상세 수치와 실행 log는 검증 기록에만 추가하고 master roadmap에 복제하지 않는다.
- API 지원 범위가 바뀌면 API matrix와 필요한 예제·시험을 같은 변경에서 갱신한다.
- AC package 상태를 바꿀 때 해당 API별 난이도·의미 차이·HIL 범위와 M22 선행조건을 함께 갱신한다.
- Board 변경은 별도 board 저장소에서 검증한 뒤 Core의 gitlink만 의도적으로 갱신한다.
- NCS upgrade는 기존 v3.4.0 기준선을 덮어쓰지 않고 별도 호환성 평가와 migration으로 결정한다.
- RC나 stable version 이름으로 다른 byte의 artifact를 다시 만들지 않는다.
- M23~M33 상세 범위와 경쟁 기준은
  [전 인스턴스·DMA·BLE 경쟁 마일스톤](08_전_인스턴스_DMA_BLE_경쟁_마일스톤.md)에 고정한다.
- AC-01~AC-03은 `v0.3.0` 전용 하위 작업 ID이며 이후 전역 M 번호를 대체하거나 재번호화하지 않는다.
