## 1. 문서 목적

이 문서는 NU54DK Arduino Core를 실제로 구현할 순서와 각 단계의 종료 조건을 정의한다. 일정이나 구현 완료를 과장하지 않기 위해, 코드가 존재한다는 사실과 실기에서 검증되었다는 사실을 구분한다. 단계가 완료되려면 소스뿐 아니라 재현 가능한 명령, 시험 결과 및 결정 기록이 있어야 한다.

로드맵은 다음 원칙을 따른다.

1. Arduino Core는 Zephyr를 대체하지 않고 Zephyr 애플리케이션 내부의 호환 계층으로 구현한다.
2. 보드의 실제 GPIO, pinctrl, 주변장치 및 runner 정의는 `NU54DK_Zephyr_DTS`가 소유한다.
   Core 개발에서는 고정된 서브모듈을 읽기 전용 빌드 입력으로 사용한다.
3. 첫 번째 공개 경로는 NCS v3.4.0과 Zephyr 4.4.0으로 고정한다.
4. west-native 수직 경로를 먼저 통과하고, API를 대량 구현하기 전에 Arduino CLI Build Adapter 위험을 검증한다.
5. 정상 빌드에서 `pristine always`를 사용하지 않는다.
6. pyOCD/CMSIS-DAP를 기본 플래시 경로로 삼고 외장 J-Link는 선택 경로로 검증한다.
7. LLEXT Loader, bootloader 및 OTA는 v0.1의 일부가 아니다.

## 2. 상태와 결정 게이트

### 2.1 단계 상태

| 상태 | 의미 |
| --- | --- |
| 완료 | 완료 기준과 필수 검증을 통과했고 증거를 보관함 |
| 진행 중 | 구현 또는 검증이 시작되었으나 완료 기준을 전부 통과하지 않음 |
| 대기 | 선행 단계 또는 결정 게이트를 기다림 |
| 차단 | 기술적·법적·하드웨어 문제로 다음 단계로 진행할 수 없음 |
| 재검토 | 전제가 바뀌어 범위나 구조를 다시 결정해야 함 |

### 2.2 결정 게이트 결과

| 결과 | 의미 |
| --- | --- |
| GO | 다음 단계로 진행 가능 |
| CONDITIONAL GO | 명시한 제한과 후속 조치를 조건으로 진행 가능 |
| HOLD | 자료나 검증이 부족하여 현재 단계에 머묾 |
| STOP/REDESIGN | 현재 접근으로 핵심 조건을 만족하지 못해 설계를 변경함 |

단계 번호는 구현 순서이며 달력 일정이 아니다. 서로 독립적인 host test 준비와 문서 작업은 병렬로 진행할 수 있지만, 결정 게이트를 건너뛰어 API 범위를 확대하지 않는다.

## 4. 공통 검증 명령 규칙

아래 명령은 NCS v3.4.0 Toolchain 환경이 활성화된 PowerShell에서 실행하는 것을 전제로 한다. 아직 생성되지 않은 sample 또는 도구에 대한 명령은 해당 단계에서 구현할 목표 인터페이스다. 실제 명령이 달라지면 문서와 CI를 함께 수정한다.

~~~powershell
$NcsRoot = "C:/ncs/v3.4.0"
$CoreRoot = (Resolve-Path ".").Path
$BoardRoot = Join-Path $CoreRoot "board_package/NU54DK_Zephyr_DTS"
$Board = "nrf54l15dk/nrf54l15/cpuapp/nu54dk"
~~~

기본 west-native 빌드 형태는 다음과 같다.

~~~powershell
west -z "$NcsRoot/zephyr" build `
  -b $Board `
  "$CoreRoot/samples/zephyr/blink" `
  -d "$CoreRoot/build/west-blink" `
  -- `
  -DBOARD_ROOT="$BoardRoot" `
  -DEXTRA_ZEPHYR_MODULES="$CoreRoot"
~~~

`<PROBE_UID>`, `<JLINK_SERIAL>` 및 `<NU54DK_FQBN>`은 실제 환경이나 패키지 설계에서 확정할 자리표시자다. 이를 문서 예시의 실제 검증값으로 간주하지 않는다.

## 6. M1 — 도구 환경과 보드 실기 기준선

### 상태

**완료 (2026-08-26).** 상세 환경, 명령과 실기 결과는
[M1 도구 환경과 보드 실기 기준선](<../04_검증 기록/01_M1_도구와_보드_기준선.md>)에
보관한다. Core `a8d62ea75fef57cdf166738eb45ad4f61e0eaa9c`와 읽기 전용 보드
`fe65f2f0880bd05b32e562d9bf1ee59142b4f4d3` 조합에서 pristine 재빌드를 확인했다.
CMSIS-DAP V2/pyOCD 실기는 기존 VS Code 검증을 사용하며 이번 갱신에서는 플래시하지 않았다.

### 선행조건

- M0 완료
- NU54DK 실물과 데이터 통신 가능한 USB 케이블
- NCS v3.4.0 Toolchain 환경
- 지원 후보 pyOCD 버전

### 작업

- NCS, Zephyr, compiler, CMake, Ninja, Python, west 및 pyOCD 버전을 기록한다.
- 서브모듈의 보드 정의를 `BOARD_ROOT`로 전달하여 최소 C/C++ 애플리케이션을 빌드한다.
- `runners.yaml`에서 선택된 기본 runner와 pyOCD target 인자를 확인한다.
- 온보드 CMSIS-DAP의 UID를 식별한다.
- 일반 플래시가 mass erase 없이 동작하는지 확인한다.
- uart20/DAP UART에서 boot 또는 sample 로그를 시도한다. GPIO 실행 증거로 M1을 진행한
  경우 VCOM 미확인 항목은 Serial 단계로 명시적으로 넘긴다.
- clean build, 변경 없는 rebuild 및 반복 flash의 기준 로그를 보존한다.

### 산출물

- 환경 manifest
- baseline build log와 `zephyr.elf`, `zephyr.hex`, `.config`, `zephyr.dts`
- pyOCD probe 식별 및 flash log
- 실기 연결 메모

### 완료기준

- C++ source를 포함한 clean build가 성공한다.
- 같은 image를 온보드 CMSIS-DAP/pyOCD로 3회 연속 기록하고 reset 후 실행한다.
- UART 또는 관측 가능한 GPIO로 매번 실행을 확인한다.
- 일반 flash에서 `--erase`, recover 또는 mass erase를 사용하지 않는다.
- 실패 시 build 문제와 probe 문제를 구분할 수 있는 로그가 남는다.

### 검증명령

~~~powershell
west --version
cmake --version
ninja --version
python --version
pyocd --version
pyocd list

west build -b $Board "<BASELINE_SAMPLE>" -d build/m1-baseline -- -DBOARD_ROOT="$BoardRoot"
west flash -d build/m1-baseline -r pyocd --dev-id <PROBE_UID>
~~~

### 범위제외

- Arduino API
- `.ino` 빌드
- J-Link 정식 지원
- 성능 최적화와 compiler cache

### 주요위험

- pyOCD 버전과 `nrf54l` target 지원이 맞지 않을 수 있다.
- CMSIS-DAP는 인식되지만 target voltage, SWD 또는 reset 경로 문제로 flash가 실패할 수 있다.
- 보드 DTS의 console UART와 실물 solder bridge 상태가 다를 수 있다.

### 결정 게이트

**완료 — 2026-08-26.** NCS v3.4.0/Zephyr 4.4.0에서 C++와 Blinky pristine build를
완료했다. 생성된 `runners.yaml`의 pyOCD 인자는 `--dt-flash=y`와
`--target=nrf54l`뿐이며 flash/debug 기본 runner는 `pyocd`다. clean Blinky HEX는
기존 실기 검증 image와 같은 SHA-256을 유지한다. CMSIS-DAP V2/pyOCD 플래시와 LED 실행은
기존 VS Code 검증으로 충족하며 이번 갱신에서는 재실행하지 않았다.

상위 gitlink와 실제 서브모듈 HEAD는 모두 `fe65f2f0880bd05b32e562d9bf1ee59142b4f4d3`이며
서브모듈 작업 트리는 clean이다. 보드 package는 읽기 전용 입력이고 runner 변경, 별도
보드 commit 또는 gitlink 갱신은 M1 후속 조건이 아니다. UART/VCOM은 Serial 단계에서
계속 추적한다.

## 7. M2 — Zephyr module과 Core 골격

### 상태

**완료 (2026-08-26).** 상세 명령, build 산출물과 실기 결과는
[M2 Zephyr module과 runtime 기준선](<../04_검증 기록/02_M2_Zephyr_Module과_Runtime_기준선.md>)에
보관한다. clean Core·보드 revision으로 runtime, Core 비활성 회귀와 C++ 정책을 pristine
재빌드했다.

### 선행조건

- M1 완료
- Core와 board package의 소유권 규칙 확정

### 작업

- `zephyr/module.yml`, Zephyr CMake와 Kconfig 연결을 구현한다.
- `cores/arduino/`를 별도 Zephyr library target으로 연결한다.
- C++ 표준, exception, RTTI, static initialization 및 heap 정책의 초기값을 정한다.
- `setup()`과 `loop()`를 호출하는 runtime entry를 구현한다.
- 초기 PoC에서는 Zephyr main thread가 `setup()`과 `loop()`를 실행하게 하고, 전용 thread는 fairness HIL 이후에만 재검토한다.
- weak symbol과 사용자 Sketch symbol의 소유권을 정한다.
- Core 내부 API와 공개 `Arduino.h` 경계를 분리한다.
- west-native sample이 Arduino CLI 없이 Core를 링크하도록 한다.

### 산출물

- Zephyr module metadata와 Kconfig
- Core library target
- 최소 `Arduino.h`와 runtime entry
- `samples/zephyr/runtime_smoke` 검증 sample
- C++ runtime 정책 기록

### 완료기준

- west가 Core 저장소를 Zephyr module로 인식한다.
- 사용자 source의 `setup()`이 정확히 한 번 실행되고 `loop()`가 반복된다.
- 전역 C++ 객체 constructor가 `setup()` 이전에 실행됨을 시험한다.
- Core를 사용하지 않는 일반 Zephyr sample에 불필요한 symbol이 들어가지 않는다.
- 빌드 결과에 NCS, Toolchain, Core 및 board revision이 기록된다.

### 검증명령

~~~powershell
west -z "$NcsRoot/zephyr" build --pristine always --no-sysbuild `
  -b $Board `
  -s "$CoreRoot/samples/zephyr/runtime_smoke" `
  -d "$CoreRoot/build/m2-runtime" `
  -- `
  "-DBOARD_ROOT=$BoardRoot" `
  "-DEXTRA_ZEPHYR_MODULES=$CoreRoot"

west -z "$NcsRoot/zephyr" flash `
  -d "$CoreRoot/build/m2-runtime" `
  --dev-id <PROBE_UID>

west -z "$NcsRoot/zephyr" build -d "$CoreRoot/build/m2-runtime"
~~~

### 범위제외

- 전체 ArduinoCore-API
- Arduino library discovery
- Serial, Wire, SPI, ADC 및 PWM
- Boards Manager metadata

### 주요위험

- Zephyr C++ 설정과 Arduino library가 기대하는 exception/RTTI 정책이 다를 수 있다.
- `main()` 소유권이나 static constructor 순서를 잘못 다루면 전역 Arduino 객체가 초기화되지 않을 수 있다.
- Core가 내부 NCS API에 직접 결합되면 NCS upgrade 비용이 커진다.

### 결정 게이트

**완료 — 2026-08-26.** Core를 독립 Zephyr module과 library로 링크했고 C++ 전역 생성자,
`setup()` 단일 호출과 반복 `loop()` 구조를 확인했다. Core 비활성 `hello_world`에는
Core archive, live record와 runtime symbol이 생성되지 않았다. C++20 minimal build는
30,568 B / 6,856 B, `CONFIG_COMMON_LIBC_MALLOC=y`를 포함한 full
libstdc++·exception·RTTI build는 53,172 B / 7,032 B로 통과했다.

이번 갱신은 pristine build·link 회귀이며 플래시는 수행하지 않았다. 기존 runtime HIL을
실행 증거로 유지한다. Core와 board provenance에는 각각 `a8d62ea75fef`,
`fe65f2f0880b`가 dirty suffix 없이 기록되며 서브모듈 수정이나 gitlink 갱신은 필요하지
않다.

### 작업

- `Common`, `Print`, `Stream`, `String`과 `HardwareSerial`을 생산 image에 통합했다.

- `attachInterrupt()`, `attachInterruptParam()`과 `detachInterrupt()`를 raw electrical edge
  기준으로 구현하고 직접 ISR callback 문맥을 명시했다.
- 잘못된 pin·mode·문맥, callback 소유권 충돌과 `pinMode()` auto-detach를 시험했다.
- Serial Echo와 Interrupt Button 예제 및 자동 HIL runner를 추가했다.
- 각 `loop()` 뒤 `serialEventRun()`이 존재하면 호출하고 그 뒤 post-loop 정책을 적용한다.

## 12. M7 — 버스·아날로그·PWM API

### 상태

**조건부 완료.**

### 선행조건

- M6 조건부 완료와 잔여 P1.13 수동 확인 항목 문서화
- 읽기 전용 보드 package의 I2C22, SPI00, SAADC channel 5와 pwm20 역할 확인
- M7의 공개 API, chosen, Kconfig와 builder 기본 profile 확정

### 작업

- `TwoWire &Wire`를 I2C22(P1.2 SDA, P1.3 SCL)에 연결하고 100/400 kHz와 blocking
  controller 전송을 구현한다.
- `endTransmission(false)`의 write를 보류해 같은 주소의
  `requestFrom(..., true)`에서 repeated-start로 결합한다. `requestFrom(..., false)`는
  지원하지 않고 명시적으로 진단한다.
- HIL image와 host protocol은 `0x6A`에 완전히 접근하지 않고 오직 `0x6B`의
  `WHO_AM_I(0x0F)` 1-byte read만 허용한다. 기대 반환 값은 `0x6A`다.
- `SPIClass &SPI`를 SPI00(P2.1 SCK, P2.2 MOSI, P2.4 MISO)에 연결한다. Core overlay가
  controller를 활성화하고 `uart00`과의 충돌을 빌드 구성에서 드러낸다.
- SPI chip-select는 Core가 추정하지 않고 Sketch가 별도 GPIO로 직접 제어한다.
- `analogRead(A0)`를 P1.12/SAADC channel 5의 고정 12-bit raw 0..4095 입력으로 구현한다.
  Core overlay는 nRF54L15에서 지원하지 않는 보드 gain 1/6을 1/4로 override한다.
- `analogWrite(PIN_PWM0, value)`를 P1.10/pwm20의 고정 20 ms·8-bit 출력으로 구현한다.
  `LED_BUILTIN` P2.9는 PWM 역할로 사용하지 않는다.
- `analogReadResolution()`과 `analogWriteResolution()`은 구현하지 않는다.
- emulator와 승인된 실제 보드 경로를 이용한 자동 시험을 만들고 실행 증거를 기록한다.

### 산출물

- Wire, SPI, ADC 및 PWM backend
- 기본 Arduino peripheral overlay/profile
- `Wire.h`와 `SPI.h` Arduino library discovery 진입점
- 핀/instance 충돌 진단 규칙
- 고정 `0x6B/0x0F` I2C HIL host protocol
- [M7 Wire·SPI·ADC·PWM 기준선](<../04_검증 기록/07_M7_Wire_SPI_ADC_PWM_기준선.md>)

### 완료기준

- Wire의 buffer·clock·generic driver 오류 변환과 deferred repeated-start를 emulator에서 검증한다.
- 실제 I2C HIL은 address나 register를 입력받지 않는 고정 protocol로 `0x6B/0x0F`만 읽고,
  반환 값 `0x6A`와 repeated-start 증거를 확인한다. 어떠한 `0x6A` probe·read·write도 하지 않는다.
- SPI mode 0~3, bit order, 주파수 설정과 8/16/buffer full-duplex 의미를 emulator에서 검증한다.
  shipped sample/HIL은 실제 SPI00에서 유효한 4 MHz/div32를 쓰고, Core가 임의의 가까운
  주파수를 별도로 탐색하지 않는다. nrfx runtime prescaler predicate가 허용하지 않는 값은
  `beginTransaction()`에서 거부한다. 실제 SPI
  fixture가 없으면 물리 SPI만 미검증으로 명시할 수 있다.
- ADC는 A0의 12-bit raw 범위와 오류 `-1`을 검증한다. 외부 정밀 전압 계측은 필수가 아니다.
- PWM은 P1.10 역할의 0·중간값·255 driver 적용을 검증한다. 외부 주파수 계측은 필수가 아니다.
- 사용할 수 없는 pin이나 충돌 profile은 조용히 오동작하지 않고 configure/build 단계에서 실패한다.
- API의 제약과 미검증 항목을 지원 범위표와 검증 기준선에 정확히 반영한다.

### 검증명령

~~~powershell
west twister -T tests/zephyr/m7_core_api -p $Board --board-root $BoardRoot --extra-args "EXTRA_ZEPHYR_MODULES=$CoreRoot" --outdir build/twister-m7
python -m unittest tests.hil.test_m7_i2c_imu
~~~

실제 NU54DK HIL의 명령·flash sequence·UART 결과와 미검증 fixture는 M7 기준선에 기록한다.
연결되지 않은 fixture의 동작은 통과로 추정하지 않는다.

### 범위제외

- 임의의 모든 GPIO에서 동일한 PWM 기능 보장
- AVR register compatibility
- Servo, audio 및 advanced DMA library
- Arduino IDE/CLI Upload·Flash recipe와 pyOCD/J-Link 선택; 이는 미구현 M8 범위

### 주요위험

- Zephyr Devicetree에서 비활성인 controller는 runtime API로 켤 수 없다.
- SPI00과 uart00은 같은 하드웨어 instance를 공유하므로 동시에 활성화할 수 없다.
- SPI00의 128 MHz clock/even prescaler 범위 밖 주파수는 driver가 거부한다.
- 회로의 solder bridge 상태가 문서와 실제 보드마다 다를 수 있다.
- Qwiic 장치의 실제 address strap이 `0x6B`가 아니면 안전 규칙상 `0x6A` fallback을 할 수 없다.
- ADC 분압기와 PWM에 연결된 LED 회로가 raw 결과와 관찰 상태에 영향을 줄 수 있다.

### 단계 판정

- **완료:** 대표 bus와 analog 기능이 승인된 자동/HIL 범위에서 검증됨.
- **조건부 완료:** 외부 fixture 부재 또는 하드웨어 제약으로 일부가 부분 지원이며,
  자동 검증 결과와 미검증 범위를 지원표·예제·diagnostic에 명확히 기록함.

NU54DK Twister target 11/11, Arduino CLI M7 4/4, 전체 Builder 회귀 8/8, host protocol unittest 10/10,
config negative 3/3과 ADC/PWM/SPI driver 실기 경로를 통과했다. I2C HIL은 `0x6A`
접근·scan·fallback 없이 종료했지만 고정 `0x6B`
IMU의 `WHO_AM_I`는 RX 오류로 확인하지 못했다. 물리 SPI data 경로도 fixture가 없어 검증하지
못했으므로 M7을 **조건부 완료**로 판정한다.

- blocker와 high-severity 결함이 열려 있지 않다.
- release archive checksum과 내부 revision manifest가 일치한다.

### 검증명령

~~~powershell
ctest --test-dir build/host --output-on-failure
west twister -T tests/zephyr -p $Board --board-root $BoardRoot --extra-args "EXTRA_ZEPHYR_MODULES=$CoreRoot" --outdir build/twister-release
arduino-cli compile --fqbn <NU54DK_FQBN> examples/01.Basics/Blink --verbose
arduino-cli upload --fqbn <NU54DK_FQBN> -p <PROBE_UID> examples/01.Basics/Blink --verbose
Get-FileHash <RELEASE_ARCHIVE> -Algorithm SHA256
~~~

### 범위제외

- 문서화되지 않은 API의 암묵적 지원
- v0.1 이후 API, multi-board, OTA 및 Loader
- 검증하지 않은 OS 또는 probe 조합

### 주요위험

- 시험한 source tree와 실제 release archive 내용이 다를 수 있다.
- API 명칭만 존재하고 edge case나 hardware 의미가 검증되지 않을 수 있다.
- 성능 수치가 다른 PC 또는 cache 상태와 함께 해석되지 않을 수 있다.

### 결정 게이트

- **GO:** v0.1 공개 배포.
- **CONDITIONAL GO:** 명확한 experimental/pre-release 표기와 제한된 사용자 평가.
- **HOLD:** 증거, license 또는 clean-machine 재현 중 하나라도 부족함.

## 17. v0.1 전체 범위 제외

다음은 특정 단계의 실험 코드가 존재하더라도 v0.1 지원 기능으로 선언하지 않는다.

- LLEXT Loader와 EDK
- runtime loadable Sketch
- bootloader, MCUboot, UF2, drag-and-drop 및 OTA
- target native USB CDC/HID
- Bluetooth, 802.15.4, Thread 및 Matter Arduino library
- network client/server compatibility layer
- filesystem, EEPROM emulation 및 external flash library
- multi-board와 nRF54L의 다른 qualifier
- Linux/macOS 공식 지원
- 임의 NCS 또는 Zephyr version 선택

이 기능들은 Full Zephyr 앱 안에서 사용자가 Zephyr/NCS API로 직접 실험할 수 있다는 사실과 Arduino Core가 정식 API로 지원한다는 사실을 구분한다.

## 18. 변경 관리

- 단계 상태 변경은 완료기준과 증거 링크를 함께 수정한다.
- `완료`로 바꿀 때 실제 검증 환경, command, revision 및 결과를 기록한다.
- 지원 범위가 바뀌면 `04_Arduino_API_지원_범위.md`와 시험 계획을 같은 변경에서 갱신한다.
- Core 저장소의 보드 서브모듈은 읽기 전용으로 유지한다. runner, pin 또는 peripheral route 변경은 별도 보드 저장소에서 검증한 뒤 상위 Core의 gitlink만 의도적으로 갱신한다.
- NCS upgrade는 기존 v3.4.0 지원 branch를 조용히 덮어쓰지 않고 별도 호환성 평가 후 결정한다.
