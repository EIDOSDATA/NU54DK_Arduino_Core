## 1. 문서 목적

로드맵은 다음 원칙을 따른다.

1. Arduino Core는 Zephyr를 대체하지 않고 Zephyr 애플리케이션 내부의 호환 계층으로 구현한다.
2. 보드의 실제 GPIO, pinctrl, 주변장치 및 runner 정의는 `NU54DK_Zephyr_DTS`가 소유한다.
   Core 개발에서는 고정된 서브모듈을 읽기 전용 빌드 입력으로 사용한다.
3. 첫 번째 공개 경로는 NCS v3.4.0과 Zephyr 4.4.0으로 고정한다.
4. west-native 수직 경로를 먼저 통과하고, API를 대량 구현하기 전에 Arduino CLI Build Adapter 위험을 검증한다.
5. 정상 빌드에서 `pristine always`를 사용하지 않는다.
6. pyOCD/CMSIS-DAP를 기본 플래시 경로로 삼고 외장 J-Link는 선택 경로로 검증한다.
7. LLEXT Loader, bootloader 및 OTA는 v0.1의 일부가 아니다.
8. 일반 사용자는 `prj.conf`와 overlay를 직접 편집하지 않으며, 검증된 profile과 library
   feature 선언으로 필요한 Zephyr 구성을 선택한다.
9. 고급 사용자의 Zephyr/NCS 공개 API와 전문가용 project override는 유지한다.
10. Arduino 사용자 예제는 `libraries/*/examples`를 단일 원본으로 사용한다.

## 2. 단계 상태

| 상태 | 의미 |
| --- | --- |
| 완료 | 완료 기준과 필수 검증을 통과했고 증거를 보관함 |
| 진행 중 | 구현 또는 검증이 시작되었으나 완료 기준을 전부 통과하지 않음 |
| 대기 | 선행 단계 또는 결정 게이트를 기다림 |

## 4. 공통 검증 명령 규칙

아래 명령은 NCS v3.4.0 Toolchain 환경이 활성화된 PowerShell에서 실행하는 것을 전제로 한다. 아직 생성되지 않은 sample 또는 도구에 대한 명령은 해당 단계에서 구현할 목표 인터페이스다. 실제 명령이 달라지면 문서와 CI를 함께 수정한다.

~~~powershell
$NcsRoot = "C:/ncs/v3.4.0"
$CoreRoot = (Resolve-Path ".").Path
$BoardRoot = Join-Path $CoreRoot "board_package/NU54DK_Zephyr_DTS"
$Board = "nrf54l15dk/nrf54l15/cpuapp/nu54dk"
~~~

기본 west-native 빌드 형태는 다음과 같다.

~~~powershell
west -z "$NcsRoot/zephyr" build `
  -b $Board `
  "$CoreRoot/samples/zephyr/blink" `
  -d "$CoreRoot/build/west-blink" `
  -- `
  -DBOARD_ROOT="$BoardRoot" `
  -DEXTRA_ZEPHYR_MODULES="$CoreRoot"
~~~

`<PROBE_UID>`, `<JLINK_SERIAL>` 및 `<NU54DK_FQBN>`은 실제 환경이나 패키지 설계에서 확정할 자리표시자다. 이를 문서 예시의 실제 검증값으로 간주하지 않는다.

## 5. M0 — 저장소와 보드 패키지 기준선

### 상태

**완료** — 보드 서브모듈 연결 범위에 한함.

### 선행조건

- `NU54DK_Zephyr_DTS` 저장소가 공개 또는 접근 가능한 Git 원격에 존재한다.
- Arduino Core와 보드 정의의 소유권 분리 원칙이 승인되었다.

### 작업

- `board_package/NU54DK_Zephyr_DTS` 경로에 보드 저장소를 Git 서브모듈로 연결한다.
- `.gitmodules`와 상위 저장소 gitlink가 동일 경로를 가리키게 한다.
- Core 저장소가 참조할 보드 commit을 고정한다.
- 빈 구현 디렉터리와 문서 디렉터리의 책임을 정의한다.
- 소스 clone과 공개 release archive에서 서브모듈을 취급하는 방법을 분리한다.

### 산출물

- `.gitmodules`
- `board_package/NU54DK_Zephyr_DTS` gitlink
- `00_Docs/01_아두이노 코어 설계/01_저장소_폴더_구조.md`

### 완료기준

- 상위 저장소에서 서브모듈 commit이 고정되어 있다.
- `git submodule update --init --recursive` 후 보드 파일을 읽을 수 있다.
- `BOARD_ROOT`가 저장소 내부 서브모듈 경로로 문서화되어 있다.
- 상위 저장소와 서브모듈의 변경 상태를 독립적으로 식별할 수 있다.

### 검증명령

~~~powershell
git submodule status
git -C board_package/NU54DK_Zephyr_DTS rev-parse HEAD
Test-Path board_package/NU54DK_Zephyr_DTS/boards/nucode/nu54dk/board.yml
~~~

### 범위제외

- 보드가 실제로 빌드되는지에 대한 검증
- pyOCD 및 J-Link 플래시 검증
- release archive에 서브모듈 내용을 포함하는 staging 도구

### 주요위험

- 사용자가 `--recurse-submodules` 없이 clone하여 보드가 비어 있을 수 있다.

## 12. M7 — 버스·아날로그·PWM API

### 상태

**완료.**

### 선행조건

- M7의 공개 API, chosen, Kconfig와 builder 기본 profile 확정

### 작업

- `TwoWire &Wire`를 I2C22(P1.2 SDA, P1.3 SCL)에 연결하고 100/400 kHz와 blocking
  controller 전송을 구현한다.
- `endTransmission(false)`의 write를 보류해 같은 주소의
  `requestFrom(..., true)`에서 repeated-start로 결합한다. `requestFrom(..., false)`는
  지원하지 않고 명시적으로 진단한다.
- HIL image와 host protocol은 온보드 BQ25186의 고정 주소 `0x6A`에서 읽기 전용
  `MASK_ID(0x0C)` 1-byte repeated-start만 허용한다. 하위 Device ID nibble의 기대값은 `0x1`이다.
- P1.2/P1.3을 TWIM으로 사용하기 위해 Core overlay에서 `uicr`의
  `nfct-pins-as-gpios`를 설정한다. 보드 package는 읽기 전용으로 유지한다.
- `SPIClass &SPI`를 SPI00(P2.1 SCK, P2.2 MOSI, P2.4 MISO)에 연결한다. Core overlay가
  controller를 활성화하고 `uart00`과의 충돌을 빌드 구성에서 드러낸다.
- SPI chip-select는 Core가 추정하지 않고 Sketch가 별도 GPIO로 직접 제어한다.
- `analogRead(A0)`를 P1.12/SAADC channel 5의 고정 12-bit raw 0..4095 입력으로 구현한다.
  Core overlay는 nRF54L15에서 지원하지 않는 보드 gain 1/6을 1/4로 override한다.
- `analogWrite(PIN_PWM0, value)`를 P1.10/pwm20의 고정 20 ms·8-bit 출력으로 구현한다.
  `LED_BUILTIN` P2.9는 PWM 역할로 사용하지 않는다.
- `analogReadResolution()`과 `analogWriteResolution()`은 구현하지 않는다.
- emulator와 승인된 실제 보드 경로를 이용한 자동 시험을 만들고 실행 증거를 기록한다.

### 산출물

- Wire, SPI, ADC 및 PWM backend
- 기본 Arduino peripheral overlay/profile
- `Wire.h`와 `SPI.h` Arduino library discovery 진입점
- 핀/instance 충돌 진단 규칙
- 고정 `0x6A/0x0C` BQ25186 I2C HIL host protocol
- [M7 Wire·SPI·ADC·PWM 기준선](<../04_검증 기록/07_M7_Wire_SPI_ADC_PWM_기준선.md>)

### 완료기준

- Wire의 buffer·clock·generic driver 오류 변환과 deferred repeated-start를 emulator에서 검증한다.
- 실제 I2C HIL은 address나 register를 입력받지 않는 고정 protocol로 `0x6A/0x0C`만 읽고,
  `MASK_ID & 0x0F == 0x1`과 repeated-start 증거를 확인한다. register data write, scan과
  fallback은 하지 않는다.
- SPI mode 0~3, bit order, 주파수 설정과 8/16/buffer full-duplex 의미를 emulator에서 검증한다.
  shipped sample/HIL은 실제 SPI00에서 유효한 4 MHz/div32를 쓰고, Core가 임의의 가까운
  주파수를 별도로 탐색하지 않는다. nrfx runtime prescaler predicate가 허용하지 않는 값은
  `beginTransaction()`에서 거부한다. 실제 SPI00은 P2.2 MOSI와 P2.4 MISO를 직접 연결하고
  4 MHz에서 40-byte 고정 패턴이 모두 일치하는지 검증한다.
- ADC는 A0의 12-bit raw 범위와 오류 `-1`을 검증한다. 외부 정밀 전압 계측은 필수가 아니다.
- PWM은 P1.10 역할의 0·중간값·255 driver 적용을 검증한다. 외부 주파수 계측은 필수가 아니다.
- 사용할 수 없는 pin이나 충돌 profile은 조용히 오동작하지 않고 configure/build 단계에서 실패한다.
- API의 제약과 미검증 항목을 지원 범위표와 검증 기준선에 정확히 반영한다.

## 17. v0.2.0 개발 단계

v0.2.0은 M12~M18로 진행한다. 이 문서에서는 전체 제품 순서만 관리하고 각 단계의 작업,
완료 기준과 범위 제외는 [v0.2.0 구현 마일스톤](05_v0.2.0_구현_마일스톤.md)을 단일 원본으로
사용한다.

```text
M12 CI/CD
  → M13 profile·Arduino 예제 UX
  → M14 Core API·Variant 정리
  → M15 board/system library
  → M16 basic BLE
  → M17 NCS coverage 첫 묶음
  → M18 RC 패키지·Draft
  → RC1 공개 검증과 결함 교정
  → RC2 Public Prerelease·Boards Manager 검증
  → 프로젝트 소유자 승인·v0.2.0 stable 공개
```

M12~M18과 `v0.2.0` 정식 공개를 완료했다. M14는 Core API·DTS 기반 Variant의 로컬·원격
software/runtime 검증과 `PIN_LED2..3`·`PIN_BUTTON1..3` NU54DK 물리 HIL을 모두
통과했다. M15 비-System-OFF 자동 HIL은 두 보드에서 2/2 통과했다.

M15 완료 기준 Core는 `c47239d954c45fd173d8d1393e3ea5c9c86e111a`다.
[Software Gates run 33295587578](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/33295587578)은
성공했고,
[Reproducible Builds run 33295588535](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/33295588535)의
Zephyr job도 성공했다. SWD를 격리한 System OFF 결합 HIL은 timed GRTC wake를
`2062 ms`/cause `2048`로, 사용자 SW0/P1.13 wake를 `20406 ms`/cause `128`로 통과했다.

M15의 PMIC API는 DTS의 BQ25186 node를 disabled로 유지하고, 매 boot RAM write 승인 뒤에만
검토된 field를 변경한다. 배터리 전기 HIL은 `NOT RUN`인 프로젝트 소유자 승인
범위 제외이며, 사용자가 자신의 배터리·전원 조건에서 직접 검증한다. 실제 배터리 NTC
온도 보호는 미지원이다. 이 범위 제외는 M15 완료를 차단하지 않는다.

M16은 NUS Peripheral/Central Stream과 두 보드 BLE HIL을 완료했다. M17은 exact NCS·Zephyr·
board revision을 고정한 9개 machine-readable record를 만들고 대표 sensor·crypto와 세 무선
기능의 build feasibility를 분류했다. OpenThread는 공식 보드와 NU54DK에서 build됐지만,
802.15.4와 Matter의 NU54DK 적용 build는 각각 NVMC symbol과 `factory_data_partition` 제약으로
실패했다. 세 무선 항목 모두 v0.2.0에서 `deferred`이며 정식 지원이 아니다.

M18 RC2는 commit `1c5dcecfc0dba2ef25e06963dcba61c63f454db9`의 Public Prerelease로
공개됐다. 격리 Boards Manager `post_install`, 설치본 예제 14/14 compile, Blink 명시 UID
upload, 대응 UART READY와 설치본 NUS Peripheral↔Central 원문 연속 수신은 PASS다. 이번
공개 예제 transparent bridge HIL은 M16/RC1의 frame boundary·disconnect/reconnect 전문 HIL과
구분한다. RC1·RC2 tag와 자산은 후보 검증의 불변 기록으로 유지한다. 프로젝트 소유자가
정식 공개를 승인했고 M18은 `v0.2.0` stable 공개로 완료됐다. stable tag·package index·asset의
exact identity는 v0.2.0 릴리스 문서와 정식 공개 기록을 단일 원본으로 사용한다.

표준 Arduino 사용자는 M13 이후 `.ino`, library와 Tools 메뉴만 사용한다. `prj.conf`와
`app.overlay`는 전문가용 escape hatch로 유지하며, 사용 시 build manifest에 명시한다.

NCS v3.4.0 기능은 모두 같은 Arduino wrapper로 재작성하지 않는다. 기능마다 Arduino wrapper,
NCS direct example, validated profile, application template 또는 제외 중 적합한 경로를 선택한다.
지원 상태는 [NCS 기능과 예제 지원 매트릭스](06_NCS_3.4.0_기능과_예제_지원_매트릭스.md)에
기록한다.

M19는 device lifecycle, local name, advertising data·interval, scan filter와 connection
설정을 다룬다. M20은 16/128-bit UUID, service/characteristic, read, write,
write-without-response, notify, indicate와 CCC를 제공한다. GATT schema는 Bluetooth 시작 전에
등록하는 수명주기를 기본으로 하며 실행 중 임의 schema 변경은 지원 계약에 포함하지 않는다.
M21은 pairing, bonding, SMP, passkey, bond 저장·삭제와 BAS/DIS/BLE HID를 다룬다. BLE callback
문맥에서 사용자 code를 직접 실행하지 않고 기존 M16과 같은 Arduino main-thread event 전달
원칙을 유지한다.

M22는 public example 전체 compile, 두 보드 BLE 회귀, clean Windows Boards Manager
설치·업그레이드·downgrade·제거와 RC/stable 공개를 검증한다. Windows 또는 스마트폰의 pairing
UI와 HID 입력처럼 외부 사용자 동작이 필요한 항목은 자동 HIL과 수동 호환성 확인을 구분한다.
BLE Mesh, Channel Sounding, ISO와 BLE/802.15.4 multiprotocol은 `v0.3.0` 범위가 아니다.

M23~M34는 순서와 제품선만 정한 **계획** 상태다. 각 제품선 착수 전에 API와 hardware fixture,
보안·복구 정책, 완료 기준을 별도 상세 문서에서 승인하며 현재 지원 기능으로 표시하지 않는다.

| 제품선 | 마일스톤 | 계획 범위 | 명시적 경계 |
| --- | --- | --- | --- |
| `v0.4.x` | M23~M26 | storage·PSA/Cracen, MCUboot/DFU, TF-M와 recovery | update 실패 복구와 보안 경계를 검증하기 전 정식 지원 금지 |
| `v0.5.x` | M27~M30 | radio profile, IEEE 802.15.4, ESB, OpenThread와 network 계층 | OpenThread build PASS를 runtime 지원으로 확대하지 않음; multiprotocol 별도 gate |
| `v0.6.x` | M31~M34 | Matter partition/factory data, application template와 commissioning | Matter 인증 획득과 Arduino Core 지원을 동일시하지 않음 |

Sensor, audio, Wi-Fi/nRF70과 기타 외장 hardware 기능은 위 제품선의 자동 필수 범위가 아니다.
NCS coverage ledger에서 hardware와 사용 가치가 확인될 때 direct example, profile, 외부 library
또는 별도 add-on 제품선으로 분류한다.

## 19. v0.1 전체 범위 제외

다음은 특정 단계의 실험 코드가 존재하더라도 v0.1 지원 기능으로 선언하지 않는다.

- LLEXT Loader와 EDK
- runtime loadable Sketch
- bootloader, MCUboot, UF2, drag-and-drop 및 OTA
- target native USB CDC/HID
- Bluetooth, 802.15.4, Thread 및 Matter Arduino library
- network client/server compatibility layer
- filesystem, EEPROM emulation 및 external flash library
- multi-board와 nRF54L의 다른 qualifier
- Linux/macOS 공식 지원
- 임의 NCS 또는 Zephyr version 선택

이 기능들은 Full Zephyr 앱 안에서 사용자가 Zephyr/NCS API로 직접 실험할 수 있다는 사실과 Arduino Core가 정식 API로 지원한다는 사실을 구분한다.

## 20. 변경 관리

- 단계 상태 변경은 완료기준과 증거 링크를 함께 수정한다.
- `완료`로 바꿀 때 실제 검증 환경, command, revision 및 결과를 기록한다.
- 지원 범위가 바뀌면 `04_Arduino_API_지원_범위.md`와 시험 계획을 같은 변경에서 갱신한다.
- Core 저장소의 보드 서브모듈은 읽기 전용으로 유지한다. runner, pin 또는 peripheral route 변경은 별도 보드 저장소에서 검증한 뒤 상위 Core의 gitlink만 의도적으로 갱신한다.
- NCS upgrade는 기존 v3.4.0 지원 branch를 조용히 덮어쓰지 않고 별도 호환성 평가 후 결정한다.
