## 2. Upstream sample 분류

기존 master parity 생성기의 M33 owner 규칙을 다음처럼 세분화했다.

| Owner | Sample / variant | 범위 |
| --- | ---: | --- |
| M33-W01 | 40 / 160 | 일반 application·기존 기능 연결·근거 있는 제외와 추가 catalog 판정 |
| M33-W02 | 47 / 92 | 표준 GATT service/client, generic GATT/NUS, beacon·observer |
| M33-W03 | 7 / 9 | Fast Pair, ANCS/AMS, MDS·EnOcean·AuraConfig ecosystem template |
| M33-W04 | 14 / 57 | DTM, HCI transport, power profiling과 진단 template |

모든 190개 sample 행은 owner, 전달 route, test ID, variant 목록, nRF54L15 allow/exclude/integration,
`build_only` metadata와 source hash를 가진다. M33 신규 범위는 역할·최소 보드·외장 부품·peer 정책을
직접 기록하고, 완료된 M31/M32 범위는 해당 exact readiness 계약에 위임한다. 제외와 W01 catalog 판정도
별도 실행 요구 상태를 가진다. Arduino 전달 route·owner·원본과 native/NU54DK/Arduino build,
runtime, negative, interoperability 결과 stage를 모든 sample에서 추적한다. `build_only`, allowlist 또는 source 존재만으로 NU54DK
runtime이나 공개 지원을 주장하지 않는다. 제외 행은 upstream 경로와 이유를 보존한다.

다음 명령은 고정 SDK metadata와 생성 원장의 byte drift를 검사한다.

```powershell
.\.venv\Scripts\python.exe tools\bluetooth\m31_inventory.py `
    --sdk-root C:\ncs\v3.4.0 --check
.\.venv\Scripts\python.exe tools\bluetooth\m33_contract.py `
    --sdk-root C:\ncs\v3.4.0 --check
```

## 3. 기존 예제와 M33 계획의 경계

`libraries/*/examples`의 `.ino` 187개를 실제 파일 hash와 함께 전수 등록했다. 이 중 BLE·radio는
164개, core·peripheral은 23개다. M31은 `example_roles`의 exact build/runtime 결과를, M32는 capability별
`planned_examples`와 실제 Sketch를 연결한다. M28~M30 예제는 완료 기준선과 library/기능 owner를
보존하고, 다른 v0.5.0 core·peripheral 예제도 별도 domain으로 보존한다. `ModernLeCapabilities`는
시험 image이므로 설치 Sketch 분모에 넣지 않는다.

각 Sketch 행은 같은 폴더의 설정·overlay·README·보조 source를 `companion_files`로 추적한다. 상태는
`source_candidate`, `native_build`, `arduino_build`, `functional_hil`, `external_peer_interop`로 분리한다.
파일 존재는 `PRESENT`일 뿐 compile·실기·외부 제품 상호운용 PASS가 아니며, 외부 peer 미실행은
`NOT_RUN`으로 유지한다.

현재 187개 예제는 기존 완료 범위이며 M33 신규 예제 완료 수가 아니다. M33-W02~W04가 새 예제를
추가하면 이 원장의 파일 목록·hash·owner drift가 먼저 바뀌고, W05에서 package 발견·compile·역할별
runtime 분모를 별도로 확정한다. `.ino`의 존재를 build 또는 HIL PASS로 승격하지 않는다.

### 3.1 중복 제거 결과

중복은 목적에 따라 다음 세 분모를 구분한다.

| 기준 | 제거 전 | 제거 후 | 해석 |
| --- | ---: | ---: | --- |
| 전체 SDK test variant → sample | 474 | 190 | 같은 sample의 설정·보드 variant를 한 sample로 묶음 |
| M33 test variant → sample | 318 | 108 | M33 owner 범위에서 같은 기준 적용 |
| 설치 `.ino` byte 내용 | 187 | 187 | SHA-256 완전 중복 group 0 |
| 설치 Sketch 이름 | 187 | 187 | 같은 Sketch 이름 group 0 |

전체 187개 중 BLE·radio가 164개이고 core·peripheral이 23개다. 따라서 기존 설치 예제를 단순
삭제해 줄일 수 있는 수는 0개다. 반면 신규 M33 제공 범위를 사용자
기능으로 묶으면 W02 12개(표준 GATT 9 + beacon 3), W03 4개, W04 6개(DTM 1 + HCI transport
5), 합계 22개 기능군이다. 이는 최종 `.ino` 파일 수가 아니다. Central/Peripheral,
advertiser/observer처럼 역할·상태 전이·negative 조건이 다른 Sketch는 중복으로 합치지 않고, 공통
구현만 library backend로 공유한다.

### 3.2 사용자가 예제를 찾는 3층 구조

164개를 README 첫 화면에 나열하지 않는다. 코드 자산은 모두 보존하되 탐색 순서를 다음처럼 고정한다.

1. `Start Here`: 전역 사용 의도 12개만 먼저 보여 주고, 각 항목에서 필요한 역할 Sketch 1~3개를 안내한다.
2. `Functional Recipe`: 현재 전체를 28개 primary 기능군으로 묶고, M33 신규 22개 기능군을 그 하위
   확장분으로 관리한다. 설정, 보드 수, 역할, 예상 출력과 오류 해결에서 해당 Sketch로 연결한다.
3. `Reference`: 설치 Sketch 187개 전체를 library, 기능, 역할, 난이도, 필요한 보드·외장 장치와
   검증 상태로 검색할 수 있게 유지한다.

`Start Here`의 12개 의도는 보드 첫 실행, 통신·pin, 저장, Peripheral Fabric, 첫 BLE 연결, BLE UART,
보안 센서/입력, 두 link/L2CAP, Mesh 제어, LE Audio stream, Channel Sounding 거리 측정, 서명 update다. 대표 목록은
Sketch를 숨기거나 지원에서 제외하는 필터가 아니다. Root README에는 이 짧은 입구만 두고 전체 목록은
생성 원장과 기능별 안내에서 제공한다. W05는 각 대표 항목에 `무엇을 하는가 → 준비물 → 실행 순서 →
성공 출력 → 흔한 오류 → 다음 예제` 형식의 짧은 안내를 적용한다. 이 안내 계약은 대표 24개에만
적용하지 않는다. 설치 예제 187개 모두에 목적, 준비물, 설정, 실행 순서, 성공 출력, 흔한 오류,
다음 예제의 7개 필드를 제공하되, `Start Here` 항목은 초보자가 먼저 보는 요약을 추가한다.

## 4. SIG service와 profile 차이

고정 Zephyr `include/zephyr/bluetooth/uuid.h`의 `0x18xx` service UUID 69개를 전수 수집한다.
현재 분류는 다음과 같다.

| 분류 | 수 | 의미 |
| --- | ---: | --- |
| M28~M30 기존 기준선 | 7 | GAP/GATT와 BAS·DIS·HID·HRS·ESS |
| M31 Audio 기존 완료 | 19 | Audio control·BAP/CAP·Media/Call·TMAP/HAP service |
| M32 Mesh 기존 완료 | 3 | Mesh Provisioning·Proxy·Proxy Solicitation |
| M33-W02 계획 | 9 | OTS, ANS, CTS, HTS, CSC, RSCS, CGMS, BMS, ETS |
| M33-W01 추가 catalog 판정 | 31 | 고정 header에는 있으나 전용 sample/API·Arduino 제공 판단이 별도인 service |

이 표는 UUID 존재를 기능 지원으로 바꾸지 않는다. 전용 source가 없는 service도 행을 삭제하지 않고
`catalog_only_no_fixed_sample`로 유지해 W02 채택 여부·제공 route·근거를 결정한다. Profile 전달
원장은 SIG, Apple, Google, 비-SIG beacon, 진단 transport를 구분한다. iBeacon·Eddystone·BTHome,
ANCS·AMS와 Fast Pair를 SIG adopted profile로 잘못 표시하지 않는다.

## 5. Test family와 정량 계약

M33 작업 분모 8개와 시험 family 12개를 구분한다. Readiness에는 16개 하위 case가 있고 각 case는
역할, 최소 보드 수, timeout, 반복, 관측 분모, 허용 실패, negative class, 30초 복구 상한과 진단
재시험 최대 1회를 가진다.

| Test family | 소유 작업 | 현재 목적 |
| --- | --- | --- |
| `M33-INV-01` | W01 | upstream 664행, service 69행, 설치 예제 187개와 정책 negative |
| `M33-PROFILE-01` / `M33-BEACON-01` | W02 | GATT profile 9군과 beacon 3형식 |
| `M33-ECOSYSTEM-01` | W03 | Fast Pair·ANCS·AMS·OS UX 자동 가능 경로 |
| `M33-DIAG-01` | W04 | DTM 수신 packet과 HCI transport class |
| `M33-EXAMPLE-01` | W05 | package 발견·설정·build·runtime 분모 |
| `M33-REG-01` / `M33-RESOURCE-01` / `M33-INTEROP-01` | W06 | 기존 기능 회귀·자원·peer별 자동/실물 상태 |
| `M33-PACKAGE-01` / `M33-INSTALL-01` | W07 | 이중 package와 세 Host 지원 gate |
| `M33-RELEASE-01` | W08 | 별도 승인·게시·공개 설치 |

W02 이후의 수치는 첫 실제 시험 전에 기능별 payload·허용 loss·상태 전이 조건으로 더 세분화한다.
현재 숫자는 유한 실행 계약이며 제품 성능 보증이 아니다.

## 6. 책임·릴리스 승격 규칙

- 구현·예제·자동 검사는 `developer/development/true/true`다. 사용자 후속으로 숨길 수 없다.
- Apple/Google 제품, 외장 audio/sensor, 정밀 RF 계측과 qualification 실물은
  `user/user_follow_up/false/false`다. `NOT_RUN`은 PASS가 아니며 릴리스 blocker도 아니다.
- Ubuntu/macOS 실제 설치·USB upload·serial·debug·lifecycle는
  `user/final_release/false/true`다. 해당 OS 지원을 선언하기 전에 실제 evidence가 필요하다.
- Source candidate, build-only 또는 문서 등록만으로 지원 catalog에 승격하지 않는다.
- 공개 상태는 `not_published`를 유지한다. M33-W08의 exact source·package plan·자산 hash에 대한
  별도 소유자 승인 전에는 tag·Release·stable index를 게시하지 않는다.

## 7. SDK 위험의 시험 연결

NCS 3.4.1 기록 중 현재 기능과 조건부로 연결되는 항목만 회귀 입력으로 등록했다.

- `DRGN-29228`: 매우 잡음 많은 DTM RX assert 조건을 `M33-DIAG-01`에 연결한다.
- `DRGN-29270`: Subrating latency/timeout ACK 경계를 `M33-REG-01`에 연결한다.
- `DRGN-29446`, `DRGN-29320`: CIS 종료 부하와 BIS 잡음 손실 조건을 회귀한다.
- `DRGN-29669`: CS 중 ACL 해제·radio scheduling 충돌의 새 assert를 기존 counter gap 정책과 구분한다.
- Mesh LPN Friend Clear와 실제 활성 watchdog의 MCUboot update 경로를 조건이 맞을 때 회귀한다.

수정 목록과 조건이 비슷하다는 이유만으로 재현 실패의 원인을 확정하지 않는다. DTM은 M33-W04가
실제 구현·시험할 때 적용하고, 그 전에는 `not_reproduced_not_assumed` 상태를 유지한다.

## 8. W01 완료 gate

W01은 exact source `a3585ffbd168d69726a42f785c5e6888f172899f`와
[296번 검증 기록](<../04_검증 기록/296_M33_W01_전체_예제_원장과_릴리스_계약.md>)으로 다음 gate를
모두 만족해 완료했다.

- 고정 SDK 재수집과 parity byte drift 검사 PASS.
- M33 release readiness 정상 검사와 negative unit test PASS.
- upstream sample 190/190, variant 474/474, M33 sample 108/108, variant 318/318의 owner/test 연결.
- 설치 Arduino Sketch 187/187(BLE·radio 164, core·peripheral 23)과 SIG service UUID 69/69의
  누락·중복·미배정 0.
- 이유 없는 제외, source/build-only 지원 승격, 사용자 후속 실물 PASS 승격, 필수 구현 은닉,
  Ubuntu/macOS 최종 gate 제거가 모두 거부됨.
- TODO·인계·검증 기록에 exact source, 실행 명령, 결과와 남은 W02~W08 범위를 연결함.

W01 완료는 W02 기능 구현·Arduino build·보드 HIL 또는 v0.6.0 공개 완료가 아니다.
