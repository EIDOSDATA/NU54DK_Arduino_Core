## 1. 설계 원칙

1. NU54DK의 물리 GPIO, pinctrl, 주변장치와 runner는 보드 저장소가 단독으로 소유한다.
2. Core는 `board_package/NU54DK_Zephyr_DTS` 서브모듈을 읽기 전용 build 입력으로 사용한다.
3. Arduino Variant는 논리 pin과 capability를 제공하고 물리 DTS의 두 번째 원본이 되지 않는다.
4. Arduino Core, 기능 library, build adapter와 package tool의 책임을 분리한다.
5. Native Zephyr reference는 `samples/zephyr`, Arduino 사용자 예제는 `libraries/*/examples`에 둔다.
6. 한 예제의 복사본을 여러 경로에 두지 않는다.
7. 보드별 HIL은 `tests/hil/<board>` 아래에 둔다.
8. 생성물과 cache는 Git source tree에 포함하지 않는다.
9. 공개 stable archive는 exact source/tooling commit에 고정한다.
10. 구현되지 않은 미래 디렉터리를 빈 placeholder로 미리 만들지 않는다.

| 경로 | 책임 | 포함하지 않는 것 |
| --- | --- | --- |
| `00_Docs/` | 결정, 설계, 검증과 릴리스 기록 | 생성 build artifact |
| `board_package/NU54DK_Zephyr_DTS/` | 보드 DTS, pinctrl, runner, 회로 문서 | Core 전용 local patch |
| `coverage/ncs-v3.4.0/` | exact upstream pin, 기능별 제공 경로·상태와 검증 결과 | NCS 전체 지원이라는 포괄 선언 |

## 4. Arduino 예제 단일 원본

Arduino IDE는 platform bundled library의 `examples`를 열거한다. 따라서 사용자 예제는 다음
경로만 사용한다.

```text
libraries/<소유-library>/examples/<Sketch>/<Sketch>.ino
```

루트 `examples/`는 사용하지 않는다. package allowlist와 host/CLI test도 이 규칙을 강제한다.

정식 `v0.2.0` archive의 역사적 기준은 library 4개와 예제 14개다. RC2와 RC3 source는
`NUCODE_BLE_Security`, `Servo`, `EEPROM`, `LittleFS`를 포함한 library 8개와 예제 29개다.
`Standard peripherals` 22개와 BLE 7개를 M22 고정 목록으로 compile한다. RC3는 이 목록을
유지하면서 loaderless memory contract를 교정한다. 이 RC 수치를 공개 `v0.2.0` 기록에 소급하지
않는다.

기능별 예제 소유 원칙은 다음과 같다.

- 보드 GPIO, pin 역할, console과 M15 board/system API: `NUCODE_NU54DK`
- 버스 API: `Wire`, `SPI`
- BLE Core/GAP·GATT·NUS: `NUCODE_BLE`
- BLE security·표준 profile·HID: `NUCODE_BLE_Security`
- Servo pulse: `Servo`
- byte-addressed persistent mirror: `EEPROM`
- internal filesystem facade: `LittleFS`
- Zephyr driver 자체 검증: `samples/zephyr` 또는 `tests/zephyr`

## 5. 보드 정의와 회로 문서

Core가 사용하는 보드 루트는 다음 하나뿐이다.

```text
-DBOARD_ROOT=<Core>/board_package/NU54DK_Zephyr_DTS
```

보드 변경은 다음 순서를 따른다.

1. `NU54DK_Zephyr_DTS` 저장소에서 수정·검증·commit한다.
2. Core에서는 새 보드 commit을 검토한다.
3. 상위 gitlink만 의도적으로 갱신한다.
4. Core/Variant/API 회귀를 실행한다.

회로도 PDF도 보드 저장소를 단일 원본으로 사용한다. Core `00_Docs`에 동일 PDF 복사본을 두지
않는다.

## 6. Source, generated와 release artifact

| 종류 | 위치 | Git |
| --- | --- | --- |
| 직접 관리 source | 위 트리의 코드·문서 | 포함 |
| 보드 source | submodule gitlink와 별도 저장소 | gitlink만 포함 |
| build tree/cache | `build/`, 외부 cache root | 제외 |
| Python cache | `__pycache__`, `*.pyc` | 제외 |
| Boards Manager archive | release asset/검증 임시 출력 | source Git에서 제외 |
| package index | 저장소 루트 stable/preview JSON | 의도한 채널만 포함 |
| 대용량 HIL evidence | CI/release artifact | Git에는 요약·hash만 포함 |

공개 `v0.1.0`은 commit `5dbc5e37270e477d21f578dd877f4b5226b44a0d`와 그 시점의
패키징 도구에 고정한다. 후속 main에서 같은 버전 archive를 다시 만들지 않는다.

```text
tests/host/test_m13_profiles.py      # profile schema, 병합과 conflict 회귀
coverage/ncs-v3.4.0/                # M17 machine-readable coverage ledger
tools/coverage/                     # ledger 검증·요약 생성
tests/zephyr/m17_sensor_direct/      # sensor direct build-only contract
tests/arduino-cli/m17_adafruit_lsm6ds_compile/ # 외부 LSM6DS3TR-C compile fixture
```

profile과 feature library 구조는
[구성 프로필과 Arduino 예제 배포](../02_빌드%20설계/07_구성_프로필과_Arduino_예제_배포.md)를
따른다.

`v0.3.0`은 `AC-01 → AC-02 → AC-03` Arduino Compatibility 작업선과
`M19 → M20 → M21` BLE 작업선을 병렬로 진행한 뒤 M22 통합 릴리스에서 합류한다. 현재
AC-01~AC-03과 M19·M20·M21 구현·검증은 완료됐다. M21은 두 보드 RF HIL과 Windows 11 실제
HID pairing·입력·bond 복원을 통과했다. AC-02B는 exact commit `0b7f89283cd82a68a7f3f0910f4fc59b8dd01bfb`의
3-wire fixture에서 runtime pinctrl/PM, Serial1, DUT 온보드 BQ25186 Wire, local SPI와 공유
P2.5↔P1.12 선의 ADC→PWM handover를 통과했다. AC-03도 같은 exact commit의 두 보드에서
  EEPROM/LittleFS 영속성·손상 거부·명시적 복구·최종 정리를 통과했다. M22 RC2는 package,
  public prerelease, 29개 설치 예제, 실제 Upload와 public clean-room lifecycle·cleanup을 통과했다.
`NUCODE_BLE`는 NUS/Core/GAP/GATT를, 별도 `NUCODE_BLE_Security`는 보안·표준 profile·HID를
소유한다. 아래 경로의 존재나 compile 성공만으로 미완료 작업선을 정식 지원으로 간주하지 않는다.

```text
cores/arduino/, variants/nu54dk/     # AC-01 Core·GPIO·시간과 AC-02 dynamic peripheral/analog backend
dts/nucode/                          # Arduino pin metadata와 runtime device profile include
libraries/                           # AC-02 peripheral/Servo, AC-03 Storage/library와 BLE 공개 진입점
libraries/NUCODE_BLE/examples/       # NUS, GAP와 custom GATT 예제
libraries/NUCODE_BLE_Security/       # M21 보안·BAS/DIS·HID API와 SecureKeyboard 예제
tests/host/                          # Compatibility·BLE API, 수명주기와 negative 계약
tests/zephyr/                        # profile, target build·semantic test
tests/hil/nu54dk/ac02b_peripheral.py # nonce/exact image/UID/COM fail-closed AC-02B HIL
tests/hil/nu54dk/                    # 핀·주변장치·storage와 두 보드 BLE 회귀
00_Docs/01_아두이노 코어 설계/
└─ 07_v0.3.0_구현_마일스톤.md       # AC-01~AC-03, M19~M22 단일 원본
```

GATT service와 characteristic은 Bluetooth stack 시작 전에 선언·등록하는 수명주기를 기본으로
한다. 실행 중 임의 schema 변경, Bluetooth callback 문맥에서의 사용자 code 직접 실행과
무제한 동적 할당은 계획 범위에 포함하지 않는다.

Compatibility 작업선은 보드 DTS가 소유한 물리 pin·peripheral을 Core에 다시
하드코딩하지 않는다. `Wire1`·`SPI1`은 승인된 board route가 없어 가짜 객체로 만들지 않는다.
AIN0~7 이름은 모두 제공하되 UART20/PMIC system owner와 SW0/LED 부하를 우회하지 않는다.

## 8. 릴리스 문서 구조

기존 `00_Docs/05_릴리스/00_*`~`12_*`는 v0.1 역사 링크를 보존한다. 다음 버전부터 전역 번호를
계속 늘리지 않고 버전 디렉터리를 사용한다.

```text
00_Docs/05_릴리스/v0.2.0/
├─ README.md
├─ RELEASE_NOTES.md
├─ KNOWN_ISSUES.md
├─ MIGRATION.md
└─ TROUBLESHOOTING.md
```

`v0.3.0-rc.2`, `v0.3.0-rc.3`와 stable `v0.3.0`은 위 다섯 파일에 `TESTING.md`를 더해 서로
다른 디렉터리에 둔다. RC는 공개된 역사 기록으로 동결하며 stable 문서는 현재 설치·지원
경계를 소유한다. Stable 승격 뒤에도 RC 문서를 덮어쓰지 않는다.

## 9. 이름과 버전 규칙

- 제품 릴리스: 문장과 Git tag에서 `v0.2.0`, `v0.3.0`; package metadata에서 앞의 `v`를 생략
- 마일스톤: `M12`처럼 제품 버전과 독립된 연속 번호
- Compatibility 작업선: `AC-01`처럼 `v0.3.0` 내 Arduino 호환성 단계를 식별
- 문서 개정: `1.0`, `2.0`처럼 제품 SemVer와 분리
- 내부 schema/cache 경로: `schema v1`, `cache schema v1`처럼 대상을 함께 표기
- bare `v1`을 제품 버전 의미로 사용하지 않음
- 검증 기록 파일은 완료 뒤 역사적 이름과 결과를 유지
