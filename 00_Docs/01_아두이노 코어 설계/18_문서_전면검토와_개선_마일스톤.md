첨부 제안서의 작업 지시는 검토 입력이지 실행 허가가 아니다. M30 전원 HIL은 후속 사용자 지시로 완료했다.

## 1. 이번 개정의 결정

1. 완료한 M0~M29·T01~T25·R00~R14를 재개하거나 재번호화하지 않는다.
2. M30은 W01~W08 완료다. W08 실제 전원 차단은 W07 secure multi-link와 별도 증거로 보존한다.
3. 과거 W08 준비/preflight와 최종 12/12 실행 증거를 분리해 보존한다.
4. M31~M33은 [전체 Bluetooth 기능·예제 계약](19_NCS_Bluetooth_전체_기능과_예제_실행_계약.md)을 따른다.
   2026-09-16 사용자 결정에 따라 보드 3개 기반 프로토콜·데이터·복구를 기본 gate로 삼고 정밀 RF 보정·
   음질·절대 거리/각도 계측은 필수 밖으로 개정한다. Apple/Google·외부 vendor·mic/speaker·외장 장치는
   작동 가능한 구현·예제·설정/연결 안내·자동 검사가 필수이며 실제 운용/interop는 사용자 추후 검증
   NOT RUN으로 남긴다. 해당 외부 실기는 v0.5.0 개발·공개 비차단이며 미검증 호환성은 선언하지 않는다.
   Ubuntu/macOS 실제 설치·USB/serial/debug는 사용자 최종 릴리스 검증으로 배치하며 세 Host 최종 gate를 유지한다.
5. Adafruit의 사용성 개선은 채택하되 Zephyr 기반·Fabric 자원 소유권·고정 buffer·기존 API를 보존한다.
   Driver 이식, SDK/board 교체 또는 전면 재작성은 이 계획에 포함하지 않는다.
6. 새 공개 API를 포함한 개선을 `v0.5.1`로 미리 확정하지 않는다. 기존 `v0.6.0` M34~M37
   Security/Update 계획도 PWM/NUS 개선으로 대체하지 않는다.

### M30-W08 내부 실행 단계

아래 A~D는 새 전역 마일스톤이나 test ID가 아니다. M30 분모 8개 작업·10개 test ID는 유지한다.
W08-A~D는 exact `ae5186f7…` 실제 전원 차단 12/12와 161번 완료 기록으로 종료했다.

| 순서 | 수행 내용 | 완료 판정 |
| --- | --- | --- |
| W08-A 재개 도구 안정화 | 실패 원본 보존, Python/toolchain 실행 환경과 source fingerprint·manifest 재사용 검증 진단 및 수정 | 정상 입력은 통과하고 source/build/runner/키/계획 불일치는 거부하는 Host 회귀. 원인을 증명하기 전 CMake 단독 문제로 확정하지 않음 |
| W08-B 준비 재생성 | 확정 source에서 DUT 두 image와 central image·build record·manifest 생성, 실제 장비 mapping 확인 뒤 preflight | 모든 파일 존재·hash·role·revision 일치, DFU 재시도와 보안 수준 확인. 완료 후 사람에게 준비 결과를 알리고 기다림 |
| W08-C 실제 차단·복구 | 사람이 준비됐다고 확인한 뒤 arm. 기존 네 주입 지점마다 3회 실제 DUT 전원 차단 | 12회 각각 주입 지점·실제 전원 조건·복구 log 확보, invalid boot·복구 실패 0. reset·케이블 감지만으로 대체 금지 |
| W08-D 회귀·마감 | 변경 영향 회귀, 10개 test ID와 예제·문서·기계 원장 대조, 승인된 commit/push의 CI 확인 | 모든 필수 증거 연결 후에만 W08·M30 완료. 실행 중 CI나 준비 성공을 완료로 세지 않음 |

W08-A의 구체적 보강 조건은 다음과 같다.

- Git revision과 실제 compiler 입력의 byte digest를 모두 보존한다. 줄바꿈·필터·dirty/untracked
  입력의 차이를 진단하고, 단순 Git blob hash 치환이나 검증 우회로 기존 image를 통과시키지 않는다.
- Producer/consumer의 입력 정규화 계약을 먼저 고정한다. 비컴파일 문서만 바뀐 경우와 실제
  firmware 입력 변경을 구분하는 회귀를 추가하고, `.config`·DTS·role 옵션·toolchain을 함께 결합한다.
  문서 변경으로 firmware를 무조건 다시 만들거나 반대로 모든 변경을 무시하지 않는다.
- 재사용 검증에는 기록된 build record, runner와 공통 helper 의존성, image/bootloader, 신뢰 공개키,
  injection plan·criteria와 유효한 preflight 근거를 결합한다. 구조 변경 시 schema와 재생성 규칙을 명시한다.
- 현재 runner의 `validate_manifest()`는 저장한 `build_records` 등 일부 항목을 비교하지 않는다.
  [공통 build 검증](../../tests/hil/nu54dk/ble_pair_hil_common.py)과
  [전원 runner](../../tests/hil/nu54dk/m30_power_loss.py)의 실제 데이터 흐름을 함께 고친 뒤 negative 시험한다.
- stale manifest, 삭제·변조된 image/record, 다른 source/role/키, helper 변경, 미완료 preflight를
  모두 거부한다. 과거 준비 파일을 새 source의 PASS로 수정하지 않고 새 실행 디렉터리에 기록한다.
- 좁은 주입 window를 사람의 준비 확인 전에 열지 않는다. 놓친 window는 미실행/실패로 기록하며
  복구 상태를 확인하지 않은 자동 재시작·무한 재시도는 금지한다.
- DUT에 배터리·별도 전원·역급전이 없는지 확인해 실제 전원 상실이 성립하도록 한다.
  USB/COM disappearance와 CPU reset만으로 power loss를 추정하지 않는다.

현재 파일 존재 확인과 과거 준비의 차이는 [160번 기록](<../04_검증 기록/160_전체_문서_검토와_마일스톤_개정.md>)에
남긴다. 과거 장비 UID/COM mapping은 참고용이며 현재 연결을 임의 추정하지 않는다.

M31~M33의 구현·예제·자동 검사는 외부 peer·장치 또는 Ubuntu/macOS PC의 확보를 기다리지 않는다.
Ubuntu/macOS 실제 설치·USB/serial/debug는 사용자가 최종 릴리스 단계에서 검증하며 현 PC의 mock/CI로
대신하지 않는다. M30 최소 DFU는 M36에서 새로 시작할 일이 아니며,
M36은 M30 증거를 이어받아 **확대된** layout·transport·보안 경계에서 다시 검증한다.

M33은 M30에서 인계한 OS별 pairing·bond/HID UX 및 security/profile 상호운용을 기능별 matrix
행으로 추적한다. Apple/Google·외부 vendor 경로의 작동 가능한 구현·예제·설정/연결 안내·자동 검사를
완료하고 실제 장치 운용은 사용자 추후 검증 NOT RUN으로 인계한다. 이 외부 실기는 v0.5.0 개발·공개를
차단하지 않으며 기본 GATT 또는 NU54DK scripted pairing PASS로 외부 호환성을 주장하지 않는다.

DF raw IQ는 안테나 배열을 일괄 필수로 요구하지 않는다. 고정 SDC TX-only와 Zephyr LL RX source
candidate를 구분하고 W01에서 nRF54L15 적용성 조사/build, W04에서 가능한 2보드 raw IQ 수신을 검증한다.
현재 RX build/runtime은 미확인이다. 실제 안테나 전환·각도·정밀 교정은 사용자 외장 후속 검증이며,
CS/RAS는 DF와 별도 A1_B1 두 보드 자동 검증 경로로 진행한다.

### 우선순위와 릴리스 배치

1. **지금:** M30 완료 근거를 보존하고 M31-W01 전체 기능·예제 원장과 capability, HOST-W04를 우선한다.
   ARF-01은 M32-W04로 이관하며 다른 ARF를 M31 완료 조건에 끼워 넣지 않는다.
2. **M33 사용자 경로 정리:** ARF-04A를 기존 API 예제 보강 하위 작업으로 배치한다. 새 wrapper는
   넣지 않으며, 배선이 필요한 예제는 배선 확인 전 HIL 자동 완료로 계산하지 않는다.
3. **M33 이후 낮은 위험의 API 개선:** ARF-05 → ARF-06A를 우선 검토·구현한다.
4. **비동기·자원 관리 개선:** ARF-03 → ARF-02 순으로 별도 변경을 검증한다.
   서로 기술적 필수 선행은 아니지만 회귀 원인과 증거를 분리하기 위한 통합 순서다.
5. **조건부 후속:** ARF-04B는 04A에서 필요성이 입증될 때만, ARF-06B는 HAL/errata 적용성 판정 후 진행한다.

M32-W04로 통합한 ARF-01 외 M33 이후 ARF의 **배포 버전은 아직 확정하지 않는다**. 첫 API 개선 착수 gate에서 변경 API,
RAM/RRAM·시험 비용과 기존 Security/Update 일정 영향을 제시하고, 다음 minor 제품선에 포함할지
별도 minor 제품선을 둘지 범위를 확정한다. 그 결정 전 `v0.5.1` 공개를 약속하거나 M34~M45 번호를
바꾸지 않는다. 이 배포 gate는 작업을 누락한 것이 아니라 기존 제품 계획의 무단 변경을 막는 선행 결정이다.

## 6. 완료 보고 규칙

- 문서 검토 완료와 firmware 완료를 분리한다. 새 계획은 기존 PASS를 늘리지 않는다.
- 작업마다 source·profile·입력·상한·실제 결과와 실패 원본을 연결한다. 구조가 바뀌면 영향 회귀를 재실행한다.
- README/HANDOFF는 현황 요약과 링크, 계약/JSON은 API·수치, 검증 기록은 당시 결과를 소유한다.
- SDK·third-party·board submodule·과거 release와 raw evidence는 이 문서 정비로 수정하지 않는다.
- 일정은 구현량과 독립 장비/Host 대기를 나눠 산정한다. 정밀 계측은 현재 필수 일정에 예약하지 않는다.
