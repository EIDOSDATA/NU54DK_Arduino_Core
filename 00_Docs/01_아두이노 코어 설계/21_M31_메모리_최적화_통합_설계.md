# M31 메모리 최적화 통합 설계 — 기능 선택·정적 자원·검증

## 1. 적용 범위와 결론

2026-09-21 사용자가 제시한 두 최적화 설명과 후속 정정을 하나의 구현 지침으로 통합한다.
소스 대조 기준은 `main`의 `4683d825eb43638ffa9445992b4dfe9a97f93f11`이다.
초기 통합 설계 개정은 문서화만이었으나, 2026-09-21 `M31-MEM-OPT`에서 P0 구현을 시작했다.
현재는 stable capability registry, 공개 `nucode-build.json` 선언 schema, library `feature.yml`
capability 요구, transitive resolver와 compiler-assisted probe engine을 현행 builder link/cache에
연결했다. 실험적 `adaptive` profile에서 resolution 단일 원본으로 최종 Kconfig·분할 overlay·기존
CMake source gate를 합성하며, Serial-only·SPI include-only·Serial+SPI clean build와 동일 입력 cache
재사용을 확인했다. 10개 초기 BLE role preset과 ISO 11개 역할 전체에 Audio BAP 7개, HAP 2개,
Audio Control 2개, Media Control 2개, Call Control 2개, CAP 5개, CSIP 2개, PBP 2개, TMAP 4개,
GMAP 4개 역할을 더한 총 52개 preset의 capacity·역할별 bundled source 선택과 clean build도 확인했다.
BAP 공개 예제 9개, HAP 공개 예제 2개, Audio Control 공개 예제 2개, Media Control 공개 예제 2개, Call Control 공개 예제 2개, CAP 공개 예제 5개, CSIP 공개 예제 2개, PBP 공개 예제 2개, TMAP 공개 예제 4개와 GMAP 공개 예제 4개는 검증된 role sidecar를 제공한다. HAP는 공통 Audio facade와 Hearing Access
backend, pairing·bond·ZMS settings 보안 source만 선택하고 BAS·DIS·HID·HRS는 제외한다. 기존 `standard`는
기본 full 호환 profile로 유지한다. ELF/map·Devicetree 금지 항목과 RAM 기준선은
후속 P0/P1 범위이며 물리 HIL은 수행하지 않았다.
M31 기능 상태는 **W01~W03 완료 3/8**을 유지한다.

**빌드 시 필요한 기능과 간접 의존성을 결정하고, 그 기능의 설정·소스·드라이버·정적 저장소만
포함한다. 포함되는 기능의 저장 공간도 역할별 검증된 상한에 맞춘다.**

사용자가 추가로 확정한 목표는 **동일 기능·동일 설정의 nRF native 예제에 우리 공개 API의 필수
비용만 더해진 구조**다. 단지 현재 큰 이미지에서 일부 RAM을 회수하는 것이 아니라, 사용자가 선언한
API/라이브러리·역할과 필수 의존성만 선택되는 경로를 차기 개발의 목표 기본 경로로 만든다.
사용하지 않는 범용 Core·최대 pool을 편의를 위해 추가하지 않는다. API가 요구하는 최소 실행 기반도
별도 비용으로 설명하며, “Arduino라서 필요”라는 이유만으로 기존 공통 비용을 전부 인정하지 않는다.
native와 byte 단위 동일하거나 특정 차이 이내라고 미리 보증하지 않고 §6의 동일 조건 비교로 확인한다.

`prj.conf` 수동 축소와 linker garbage collection(GC) 중 하나를 고르는 문제가 아니다.
기능 선언 → 의존성 해석 → Kconfig/Devicetree → source/init 선택 → 링크 → ELF/map 검증을
함께 적용한다. 사용자가 복잡한 Zephyr 설정을 매번 조립하지 않도록 builder가 구성을 합성한다.
링커는 최종적으로 도달하지 않는 section을 제거하는 수단이지 역할·버퍼 요구를 추론하는 도구가 아니다.

측정 원본·고점유 image 목록·P0~P2의 상위 회귀 조건은
[219번 감사 계약](<../04_검증 기록/219_M31_W06_메모리_점유_감사와_최적화_계약.md>)에 보존한다.
이 문서는 이전 설명의 정정, 현재 구현과의 차이, 수정 단위와 완료 조건을 소유한다.
전체 순서는 **메모리 최적화 → W04·W05 잔여·영향 재검증 → W06 → W07 → W08**이다.
후속 구현 브랜치 이름은 `M31-MEM-OPT`이며 현재 checkout/원격 상태는 착수 때 다시 확인한다.

두 제안은 별도 최적화 두 건이 아니다. **2번은 1번의 Core 분리·역할별 정적 상한을 포함하고,
사용자 선언 해석·설정 합성·자동 회귀 gate까지 구체화한 확장안**이다. 아래 P0~P2를 한 번
구현한다. 1번을 먼저 끝내고 같은 구조를 2번에서 다시 만드는 순서로 계산하지 않는다.

## 4. 사용자 코드와 기능 선택의 계약

### 4.1 빌드 시 포함과 실행 중 시작·종료를 구분한다

아래는 **선언 기반 기본 경로의 목표**이며 현재 `standard`가 이미 자동으로 이렇게 동작한다는 뜻이 아니다.
최적화를 위해 매 예제마다 불필요한 기능의 OFF 목록을 작성하는 방식은 최종 사용자 경로로 삼지 않는다.

| 사용 요구 | 포함할 것 | 다른 의존성이 없을 때 제외할 것 |
| --- | --- | --- |
| Serial 출력만 | 선택한 console/Serial 경로, 실행 기반·클록·필수 stack/libc | SPI·Wire·PWM·BLE 및 그 전용 저장소 |
| Serial + SPI | 위 기반 + SPI driver/route/전송 상태·필요한 핀 소유권 | Wire·PWM·BLE |
| Serial + BLE | 위 기반 + 선택 BLE 역할·Host/controller·필수 buffer/보안 | SPI·Wire 및 미선택 BLE 기능 |
| BLE + SPI 센서 | BLE 역할과 센서 library가 요구하는 SPI의 합집합 | 그 외 미선택 기능 |

`Serial.print()` 호출이 SPI를 해제하지 않는다. 새 기능을 추가하면 그 기능이 포함되도록 다시
빌드·업로드한다. `begin()`은 포함된 기능을 시작하며, `end()`/STOP은 계약된 실행 자원과 핀을
반환한다. 정적 `.bss` 전체를 범용 heap으로 돌려주는 동작이나 실행 중 기능 로딩과는 다르다.

### 4.2 사용자 선언을 결정하는 방법

P0의 구현 방법을 다음으로 고정한다. C/C++ source 문자열에서 함수 이름을 찾는 정규식은 사용하지 않는다.

1. Arduino가 선택한 sketch와 library source를 현행 source record로 확정한다.
2. 동일 compiler와 section GC 조건의 **capability probe compile/link**를 수행한다. `setup()`/`loop()`,
   전역 생성자와 선택 library에서 실제로 도달 가능한 공개 API 참조만 남기고, compiler가 만든 symbol
   reference와 전용 requirement section을 읽는다.
3. 안정된 public API symbol/requirement ID를 manifest에 매핑한다. 예를 들어 `SPI` object와
   `SPI.begin()` 경로는 `arduino.spi`, `Wire`는 `arduino.wire`, `Serial1`은
   `arduino.serial1`, `analogWrite()`는 `arduino.pwm`을 요구한다. C++ mangled name 자체를
   영구 공개 ID로 쓰지 않고 고정 SDK/toolchain에서 생성·검사하는 mapping을 둔다.
4. 선택 library의 `feature.yml`이 선언한 간접 의존성을 합친다. 센서 library가 내부에서 SPI를
   사용하면 sketch가 `SPI`를 직접 호출하지 않아도 SPI를 포함한다.
5. BLE 역할·최대 연결/stream/ASE처럼 호출만으로 안전하게 결정할 수 없는 값은 library가 제공하는
   검증된 role preset 또는 sketch의 공개 build declaration으로 지정한다. 이는 저수준 Kconfig 목록이
   아니라 `cs-initiator`, `audio-tmap-gateway`, connection 1 같은 제품 의미의 선언이다.
6. resolver가 요구사항의 transitive closure와 충돌·지원성·capacity를 계산해
   `resolved-capabilities.json`을 만든다. 이것을 단일 원본으로 `prj.conf`, overlay, source/init
   선택과 cache key를 생성한 뒤 최종 firmware를 pristine configure/build한다.

따라서 최종 구조에서 사용자가 Arduino sketch에서 `SPI.begin()`을 실제 도달 경로로 사용하면
`arduino.spi`가 검출되고, builder가 SPI Kconfig·Devicetree instance·Core/backend source·route와
필요한 ownership만 준비한다. 사용자는 SPI용 `prj.conf`를 작성하지 않는다. 컴파일 조건으로 제거된
호출은 요구가 아니며, 런타임 조건 안에 남아 실행될 수 있는 호출은 요구로 포함한다.

단순히 `<SPI.h>`를 include했지만 SPI object/API를 사용하지 않은 경우에는 library의 명시적
dependency가 없는 한 SPI backend를 넣지 않는 것을 목표로 한다. 반대로 외부 library가 function
pointer·가상 호출·inline wrapper 등으로 기능을 간접 사용하면 해당 library manifest가 requirement를
선언해야 한다. probe와 manifest가 모순되거나 요구를 판정할 수 없으면 기능명과 보완 방법을 표시해
빌드를 실패시킨다. 조용히 기능을 빼거나 full profile로 되돌리지 않는다.

`<NUCODE_BLE.h>` 하나로 원하는 역할·연결 수·MTU·ASE 수를 추론하지 않는다. umbrella header는
API 발견용이고, 실제로 도달한 API requirement와 role preset/declaration의 합집합만 활성화한다.
기존 `standard`/`ble` full 동작과 API·기본 capacity는 명시적 legacy/compatibility 선택지로
보존한다. **차기 기본 경로는 선언 기반 최적화**이며 일부 BLE 예제만 줄이는 것으로 완료하지 않는다.
profile 명칭·공개 declaration·기존 sketch migration은 구현과 회귀 뒤 문서화한다. 공개 v0.4.1
패키지는 소급 변경하지 않는다.

공개 `.ino`에는 읽고 수정 가능한 C++/NUCODE payload·오류·종료 흐름을 유지한다. Zephyr 호출은
backend가 소유하며, 마일스톤명·시험 ID·HIL protocol·sketch-local 개발용 macro로 역할을 고르지 않는다.

### 4.3 메뉴 정책과 전문가 override의 공존

최종 사용자 경로는 하나만 강제하지 않고 역할을 분리한다.

- `자동(adaptive)`은 실제 API 도달성, library manifest와 role/capacity 선언으로 세부 capability를
  결정하는 기본 최적화 경로다.
- Arduino Tools 메뉴의 상위 정책 preset은 향후 radio disabled/BLE/802.15.4/dual radio,
  controller, 안테나처럼 사용자가 의도적으로 고를 전역 정책만 선택한다. BLE preset 하나로 모든
  GAP 역할·GATT·SMP·Audio를 켜지 않으며 세부 설정·source gate는 adaptive resolver가 계속 소유한다.
- 고급 사용자는 Sketch root에 `prj.conf`와 `app.overlay`를 두어 생성 결과의 마지막 override로
  사용할 수 있다. 이 두 파일은 cache/provenance 입력이며 임의 CMake·module·source 주입은 아니다.

병합 순서는 `template → profile/상위 정책 → resolver capability·library fragment → Sketch override`로
결정적이어야 한다. 마지막 override도 resolver가 요구한 필수 Kconfig, 검증된 capacity, board 장치와
partition 경계를 약화할 권한은 없다. Zephyr가 dependency 때문에 값을 되돌리거나 사용자가 필수 값을
끄면 최종 `.config`·Devicetree gate가 원래 요구와 함께 오류를 출력한다. 반대로 검증된 capacity 상향이나
application 고유 옵션은 허용하고 최종 값과 출처를 `resolved-capabilities.json` 및 artifact manifest에
기록한다.

상위 정책 preset은 향후 UX 확장이고, Sketch `prj.conf`/`app.overlay` 병합은 현재 builder에 이미
구현돼 있다. P0는 일반 사용자가 수동 OFF 목록을 작성하지 않아도 최소 image가 생성되는 것을 완료
조건으로 삼으며, 전문가 override의 존재를 자동 경로의 불완전함을 가리는 수단으로 사용하지 않는다.

[250번 native RAS/DF 재진단](<../04_검증 기록/250_M31_P2_native_CS_비교와_DF_재진단.md>)에서

### P0 — 기능 선택·설정·소스 제외

1. 변경 전 대표 full/lean 후보의 exact source·board·SDK lock·toolchain·controller·역할을 고정하고,
   최종 `.config`·Devicetree·source list·ELF/map·상위 RAM symbol을 보존한다.
2. capability probe의 API requirement mapping과 공개 role/capacity declaration schema를 구현한다.
   `SPI.begin()`·Wire·Serial1·ADC/PWM·GPIO/interrupt와 bundled/외부 library의 직접·간접 요구,
   compile-time dead code·runtime branch·전역 생성자 경계를 Host test로 고정한다.
3. 명시적 full 호환 구성과 선언 기반 최소 구성을 분리하고, BLE core/NUS/GATT server/client/CoC/security/periodic/PAwR와
   ISO·Audio·DF·CS 역할을 조합 가능한 capability로 선언한다. 선언된 역할 안에서 런타임 전환해야 하는
   기능은 모두 포함한다. 예제의 초기 경로만 보고 나중에 쓰는 기능을 제거하지 않는다.
4. `configuration.py`의 resolver를 확장해 간접 의존성·순환·누락·controller/역할 비호환·자원 충돌을
   검사한다. 각 설정의 출처와 선택 이유를 출력한다. capacity는 동시 사용의 합인지 공유 pool의 상한인지
   명시하고, 무조건 합산·최댓값·마지막 값 우선으로 결정하지 않는다.
5. 사용자 `prj.conf` override는 전문가 호환 경로로 보존하되 필수 의존성을 깨거나 검증된 capacity를
   벗어나면 진단한다. 일반 사용자의 최소 구성에 sidecar 수동 작성이 필요하면 P0 완료가 아니다.
   Kconfig의 `select/default`까지 적용한 **최종 `.config`**를 의도한 capability와 대조한다.
6. CMake/source gate·전용 정적 상태·공통 registry/init와 Devicetree 장치 활성화를 함께 정리한다.
   Arduino SPI 소스가 빠졌어도 다른 SPI consumer나 장치 초기화가 남아 있을 수 있으므로 각각 확인한다.
7. 현재 최종 feature 재구성/cache 흐름을 재사용한다. probe/compiler identity, resolver schema,
   확정 capability·역할 capacity와
   구성/source 선택 입력을 cache identity에 반영한다. 필요한 library 선택을 발견하기도 전에 gate가
   경로를 막는 순환이 없는지 확인하고, 구성 실패/중단의 이전 cache를 성공 이미지로 재사용하지 않는다.
8. Serial/Print만 사용하는데 String·malloc arena 등 다른 API의 지원 때문에 큰 예약이 붙는 경로도
   감사한다. 사용하는 API의 의존성은 유지하되 공통 API 묶음이라는 이유만으로 미사용 구현·힙을 강제하지 않는다.

`--whole-archive`를 일괄 제거하지 않는다. 장치·init·callback·iterable section의 유지를 확인한 뒤
일반 미참조 section을 GC한다. source 분리, Kconfig OFF, symbol 부재는 각각 다른 검사다.

### P1 — 포함되는 정적 상태의 크기와 수명을 줄인다

**핀·route 소유권**

- mode/owner/generation 등 정상 유지 정보와 전환 중 이전 상태·rollback 정보를 분리한다.
- GPIO 한 핀, peripheral block, 실제 route pin 수에 맞는 bounded lease/transaction을 설계한다.
  기존 compact token은 rollback 전제가 다른 경로에 무조건 대입하지 않는다.
- pin alias·sparse 번호·canonical mapping을 보존한다. 실제 핀 수만 센 배열로 바꾸면서 공개 인덱스를
  깨뜨리지 않는다. interrupt 복구 상태는 필요한 구성에만 두되 ISR/atomic 계약을 보존한다.
- generation·stale lease·부분 성공·rollback·faulted 차단·STOP 반환을 회귀한다. Peripheral Fabric의
  128-slot 계약을 공통 축소하지 않는다. 큰 전역 구조를 스택으로 옮기기만 한 결과는 절감으로 세지 않는다.

**GATT·GAP·L2CAP**

- 범용 GATT facade의 local server storage와 client/discovery/cache storage를 역할별로 나눈다.
  CS RAS·Audio 서비스가 요구하는 upstream GATT/ATT를 범용 facade와 혼동해 전부 끄지 않는다.
- generic GATT Peripheral은 `ble-gatt-server-peripheral`, Central은 `ble-gatt-client-central`로
  선언해 반대 방향 source·Kconfig·정적 상태를 제외한다. 한 image에서 server/client와
  NUS를 모두 쓰는 기존 사용자는 `ble-gatt-nus-dual-role`을 그대로 사용한다.
- CoC-only 역할은 Zephyr ATT/GATT 기반을 유지하되 NUCODE 범용 GATT facade와 dynamic DB를
  선택하지 않는다. `NUCODE_BLE_GATT.cpp`·`internal/gatt` object 부재를 final source graph에서
  검사하고, include search path 존재만으로 facade가 링크됐다고 판정하지 않는다.
- service·characteristic·descriptor·value·connection·event depth가 실제 내부 배열에 반영되게 한다.
  공개 최대 지원 범위와 lean image의 예약 용량을 구분하고 초과 시 명시적으로 거부한다.
- adaptive build declaration의 `ble.gatt-services`와
  `ble.gatt-characteristics-per-service`는 검증된 1~8 범위에서 내부 배열 Kconfig를 생성한다.
  실제 등록이 선언값을 넘으면 기존 schema 등록 경로가 fail-closed로 거부하며, 선언이 없는
  full/호환 경로는 4-service/8-characteristic 기본값을 유지한다.
- characteristic별 notify/indicate snapshot은 선언한 수만큼의 bounded shared TX pool에
  보존한다. notification 완료 또는 indication destroy 이전에 재사용하지 않으며, stale completion과
  cross-link 이벤트를 억제한다. pool 고갈/backpressure와 해제 후 재시도를 Host에서 시험한다.
- 미사용 PAwR/periodic/CoC 전용 queue와 pool은 제외하고, 사용하는 scan/event queue는 필요한 depth로
  제한한다. 메모리 절약을 이유로 이벤트 유실을 성공으로 숨기지 않는다.
- 고정 배열을 일괄 heap 전환하지 않는다. 동적 할당이 필요한 기존 public API는 수명·실패 처리를 유지한다.

### P2 — 실제 부하를 측정한 뒤 역할별 용량을 조정한다

1. ACL/ATT/L2CAP MTU·count·size, 연결·bond·CCC 수, ISO stream·Audio ASE/codec 방향을 역할에 맞춘다.
   security 필수 RNG/ECDH/AES/CMAC이나 필요한 settings/DFU 보호를 사용하지 않는 기능으로 오인하지 않는다.
2. SDC pool은 검증된 controller 역할·count 설정과 고정 SDK의 요구 크기/정렬에 따라 산정한다.
   임의 byte 수로 잘라 줄이거나 SDK source를 수정해 맞추지 않는다.
3. DF는 connectionless/connected, TX/response/RX를 구분한다. CS는 최대 procedure·step·fragmented RAS와
   initiator/reflector 수신/재조립 경로를 각각 산정한다. Audio-over-ISO의 실제 결합은 유지한다.
4. main/workqueue/BT thread stack·malloc arena·Zephyr heap의 계측 방법과 분모를 기록한다. 정상 전송뿐
   아니라 연결·암호화·탐색·최대 payload·이벤트 집중·오류·복구 조건에서 high-water를 관찰한다.
5. 219번의 20~30% 여유는 역할별 예산 목표이지 충분한 안전성을 보장하는 수치가 아니다. 계측되지 않는
   경로, 계측 기능의 메모리/타이밍 비용과 최종 image 차이, heap fragmentation·할당 실패도 검토한다.
   측정이 부족하면 기존 크기를 유지하고 해당 축소 판정을 HOLD/NOT RUN으로 남긴다.

## 6. 절감량·비교·자동 검사

219번의 25,344-byte route, 26,112-byte pin state, 45,248-byte GATT slot은 당시 이미지의
**점유 후보**다. 전부 불필요한 것은 아니고 이미지·역할별로 보존할 부분이 다르다. 이를 단순 합산하거나
CS 50~80KB/50~100KB 절감을 확정 목표·보증으로 쓰지 않는다. Audio 96% 이미지의 개선 폭도 실측 전에는 미정이다.

| 지표 | 기록할 의미 |
| --- | --- |
| 정적 예약 | `.data`, `.bss`, 기타 RAM section과 정렬, linker RAM region 전체 사용량 및 분모 |
| 동적 사용 | stack별 예약/관찰 high-water/잔여, heap별 예약·peak·실패·fragmentation 관측 범위 |
| 변경량 | 동일 역할·기능·조건의 변경 전후 절대 byte, 어떤 symbol/pool이 왜 줄었는지 |
| native 비교 | 동일 SDK/board/controller·연결·MTU·보안·로그·서비스·codec/stream 조건의 일치/차이 |
| image identity | source/board/lock/toolchain·설정·ELF/map/HEX hash와 pristine 여부 |

정적 예약률과 실행 중 실제 사용률을 혼용하지 않고, 예약된 stack/heap에 관찰 사용량을 다시 더해
중복 계산하지 않는다. nRF native와의 차이 전체를 Arduino 낭비로 간주하지 않는다. 공통 기반과
공개 API와 그 안전 계약에 필요한 **최소 추가 비용**만 남겨 동등 기능 native에 가깝게 만드는 것이
목표다. 남는 차이는 object/pool별로 설명하고, 근거가 없는 추가 예약은 잔여 최적화 대상으로 추적한다.

비교는 고정 SDK의 원래 native 예제, 기능·부하 조건을 맞춘 native 기준, 같은 조건의 Arduino API
이미지를 구분한다. 조건을 맞춘 이유와 각 차이를 기록하며 Arduino의 과대 설정을 native에도 켜서
차이를 숨기지 않는다. compiler 최적화·로그·계측 조건도 맞춘다. 필요한 data path에 기존 native
buffer를 사용할 수 있으면 재사용하고, API wrapper라는 이유만으로 동일 크기의 별도 queue/payload
사본을 추가하지 않는다. 별도 복사가 꼭 필요하면 비동기 수명·소유권 근거와 최대량을 명시한다.

자동 gate는 다음을 검사하도록 구현한다.

- 선택 capability와 최종 `.config`·Devicetree·source list의 정합, pool 크기에 설정이 실제 반영되는지.
- `SPI.begin()` 직접 사용, library 내부 SPI 사용, include-only, compile-time dead call, runtime branch를
  구분하고 동일 source의 pristine/cache build가 같은 requirement를 만드는지.
- 역할별 금지 symbol/section의 부재와 필요한 init/callback의 유지. symbol 이름 하나가 사라진 것만으로
  storage 제거를 증명하지 않고 ELF/map과 실제 region 사용량을 함께 확인한다.
- 역할별 FLASH/RAM 상한·headroom·이전 기준선 대비 증가량·상위 RAM symbol·pool/stack 설정.
- Serial-only → SPI 추가 → 제거 → BLE 역할 추가/교체/제거, 간접 library 의존성과 깨끗한/재사용 cache의 일치.
- full/lean의 공개 예제 compile, 누락/충돌/용량 초과 오류, 기존 API·기본 capacity 호환.

219번의 초기 예산 정책은 75% 경고, 85% 이상 실패 또는 명시적 승인이다. 적용 지표·분모와
역할별 최종 상한은 pristine 최적화 기준선에서 고정한다. 과거 설명의 “CS 200KB”는 예시이지
확정 gate가 아니며, 상한 이하라는 사실만으로 기능·안전성 PASS를 부여하지 않는다.

## 7. 구현 완료 체크리스트와 W04~W06 인계

아래 체크리스트는 현재 구현과 실기 판정을 구분한다. `adaptive` 구현 완료와
기본 메뉴값 전환·사용자 migration 완료는 다른 조건이다.

- [x] P0 기준선·compiler-assisted capability probe·공개 role/capacity schema·full 호환 계약·의존성/충돌/override/cache 시험
- [ ] 선언 기반 기본 경로와 명시적 full 호환 경로·migration 확정; 사용자 수동 OFF 목록 없이 선택 API/역할만 구성
- [x] P0 최종 설정·장치·source/init 선택과 ELF/map의 미사용 자원 제외 확인
- [x] P1 GPIO/route의 pin mapping·generation·rollback·부분 실패·고갈·반환 회귀
- [x] P1 CoC-only 역할의 범용 GATT facade/dynamic DB/event queue·state 제외와 실제 공개 예제 compile
- [x] P1 GATT service/characteristic capacity와 실제 server slot 배열 연결·초과 거부·공개 예제 compile
- [x] P1 GATT client context를 실제 `CONFIG_BT_MAX_CONN`과 공개 2-link 상한에 맞춤
- [x] P1 GATT event payload capacity와 queue record 연결·초과 입력 fail-closed
- [x] P1 GATT server TX payload capacity와 notification/indication snapshot 연결·무절단 fail-closed
- [x] P1 GATT inline cached value capacity와 public object 배열 연결·caller-owned 512 B 우회 보존
- [x] P1 GATT server/client 방향 분리·공유 TX 수명·고갈·disconnect·stale callback 및 GAP 영향 회귀
- [ ] P2 역할별 controller/transport 용량·stack/heap 계측과 안전 여유·한계 기록
- [ ] 동등 기능 native 대비 FLASH/RAM 차이를 항목별 비교하고 필수 API 비용 외의 미사용 예약·중복 pool 제거
- [ ] 대표 full/lean 및 채택 공개 예제 pristine build, 변경 이미지의 필요한 국소 HIL
- [ ] 최적화 image에서 W04·W05 잔여 기능과 변경 영향 재검증
- [ ] W06 독립 image별 자원 manifest·수명주기·M19~M30 영향 회귀

국소 메모리/기능 회귀와 W04/W05 마감, W06 전체 영향 회귀는 서로 다른 판정이다. 중간 변경도
검증하고 안정된 구현 단위로 커밋한다. 최적화 전 고점유 이미지를 먼저 최종 마감한 뒤 같은 마감
묶음을 반복하지 않되, 변경된 source/image에 필요한 재검증은 생략하지 않는다.

W04는 controller별 source·target build·HCI 수락·실제 IQ report를 구분하고 connectionless와
connected RX를 따로 판정한다. CTE TX·일부 IQ 수신을 raw IQ 안정성·각도 PASS로 확대하지 않는다.
W05는 flash 직후 중단 원인, 같은 ACL RAS read, wrong-key negative, 양 역할 stop/restart와
disconnect/reconnect를 보존된 계약대로 검증한다. 100 procedure·20회 복구는 소유 시험의 기준이지
모든 stack/controller 경로의 검증을 대체하지 않는다. 비보정 RTT를 정밀 거리 PASS로 기록하지 않는다.

W06은 ISO·Audio·DF·CS **독립 role image**의 예산·수명주기·회귀이며 네 기능 전체를 단일 MCU에서
동시 실행하는 요구가 아니다. M19~M30 회귀는 변경 영향으로 정하고 과거 모든 실기를 무조건 재예약하지 않는다.

물리 시험 전 현재 probe identity·image hash·역할·COM을 재확인하고 배타 lock·watchdog·lease·STOP을
지킨다. 기존 미완료 cleanup을 성공으로 가정하지 않는다. 자동 mass erase/unlock/recover와 임의 전원·배선·
USB 변경은 금지한다. SDK/board pin, 기존 실패 원본과 공개 자산은 보존한다. HOST-W04~W08은 계속 보류한다.

각 결과는 PASS·FAIL·HOLD·NOT RUN·UNSUPPORTED를 구분한다. Host/mock/build는 물리 HIL PASS가 아니다.
외장 PDM/I2S·상용 peer 실물은 사용자 후속 NOT RUN 경계를 유지한다. CI/CD 요청·조회·대기는 생략한다.
M31 기능 8/8과 Windows 패키지·설치·RC·별도 공개 승인은 별개이며 문서화는 릴리스 허가가 아니다.
