## 1. 이 문서의 역할과 근거 구분

이 문서는 기존 통합안의 R00~R14를 없애거나 다시 번호 매기는 문서가 아니다. T11 완료 뒤 **언제 착수하고, 어느 변경을 `v0.4.0` 검증 이미지에 넣으며, 무엇을 재검증할지**를 정한다.

| 근거 구분 | 적용 방법 |
| --- | --- |
| 사용자 전달 사실 | D 드라이브 DUT·E 드라이브 peer로 Fixture 301을 재연결했고 exact 전체 campaign이 PASS했다. 원시 증거와 해시는 50번 기록을 따른다. |
| 첨부 문서 | 01번의 F01~F08과 02번의 R00~R14, 완료 기준, 보존 계약을 유지한다. 원본은 수정하지 않는다. |
| 저장소 재확인 | 기능 기준 `e2f045c`, 활성 TODO, 보드 gitlink, SPIM/TWIM의 동기 transfer 구간을 다시 확인했다. |
| 이번 문서의 확정 범위 | R00~R13의 공개 전 병합 순서, 최종 통합 실기 전환점, 변경 영향 분류와 작업 양식을 확정한다. 아직 구현된 결과로 표시하지 않는다. |
| 이번 계획 개정과 구분할 사항 | Fixture 301 실기와 DUT/peer target build는 별도 검증 기록이 소유한다. 리팩토링 R00 이후 source 구현은 아직 시작하지 않았다. |

현재 작업 상태의 원본은 저장소의 `00_Docs/TODO_v0.4.0.md`다. 실제 기능 판정은 기존 검증 기록·원시 증거·readiness가 소유한다. 이 문서의 체크박스나 R 작업 완료만으로 T11, T15 또는 release readiness를 PASS로 바꾸지 않는다. [S1][S2]

### 2.2 Fixture 301 완료 조건과 과거 실패를 보존한다

Revision 1에서 요구하던 외부 pull-up이 실제로 없는 첫 시도는 유효한 코어 PASS/FAIL로 집계하지
않는다. Revision 2의 **target TWIS 내부 pull-up** 조건에서 드러난 지연 buffer 결함은 exact
`e2f045c`에서 교정하고 새 전체 campaign으로 PASS했다. 무효·실패 원본은 삭제하지 않는다. [S1][S3]

이 리팩토링 문서는 결선표나 과거 판정을 다시 정의하지 않는다. 과거 외부 저항 조건, 내부 pull-up
실패와 수정 후 PASS를 한 시험 결과로 합산하지 않는다. 현재 점퍼는 R00~R13 software 작업 중
유지해도 되며, 외부 결선 PASS 캠페인은 R13과 전체 software gate가 끝난 뒤 시작한다. 그때 두 보드의
전원을 끄고 current-source T11 회귀의 첫 fixture부터 새 confirmation을 사용한다.

## 3. 확정 착수 순서

### 3.1 한 가지 기본 경로

```text
현재: T11 완료 / Fixture 301 exact evidence 보존
          ↓
R00 기준선·characterization 계약
          ↓
T14: R01~R05 정확성 수정
          ↓
R06 builder → R07 Event → R08 자원/route → R09 SPI → R10 Serial
          ↓
R11 Analog/Stream → R12 BLE/Storage → R13 package/Kconfig/CMake/문서
          ↓
전체 Host·target·예제·package gate와 최종 image 고정
          ↓
current-source T11 회귀 → T12 단독 기능 → T13 복구·동시성·soak
          ↓
T14 결함 재진입 → T15 지원 범위 확정
          ↓
T16~T18 사용자용 통합 → R14 RC 재고정 → T19~T25 검증·승인·공개·마무리
```

T 단계의 의미는 기존 TODO를 따르고, 위 배치는 외부 결선 캠페인을 최종 구조에서 한 번 수행하기 위한 확정 순서다. T14는 어느 단계에서도 다시 진입할 수 있다. [S1][S2]

### 3.2 작업 종류별 시점

| 작업 | 확정 착수 순서 | 현재 `v0.4.0` 경로에 반영하는 조건 |
| --- | --- | --- |
| 문서·기준선·실패 시나리오 정리(R00) | 다음 작업 | T11 exact evidence와 다음 source 기준을 분리하고 변경 금지 계약 고정 |

| Analog/Stream 동기화 수정(R03) | R02 뒤 | 해당 source 경로·실패 조건을 확인하고 파일 이동 없이 정확성만 수정 |

| 최종 후보 재고정(R14) | current-source T11~T15와 T16~T18 뒤 | 기존 T19~T24를 그대로 적용. 별도의 간소화된 공개 경로를 만들지 않음 |

**완료일을 날짜로 고정하지 않는다.** 결함 재현 결과·영향 HIL·하드웨어 가용성에 따라 달라지므로 위의 검증 종료 조건으로 작업을 전환한다.

### 3.3 통합 실기 전에 구조 분할을 수행하는 조건

R06~R13은 `v0.4.0`의 최종 외부 HIL 전에 수행한다. 이는 모든 작업을 한 변경으로 합친다는 뜻이 아니다. 작은 함수 추출이나 파일 이동도 독립적인 기준선·검증·되돌리기 단위를 유지한다. [S2]

각 구조 분할은 다음을 모두 충족한다.

1. 현재 캠페인이 끝났거나 안전하게 중단되어 기존 결과가 고정됐다.
2. 변경할 기능의 기준 동작, 파일·상태 소유권 대응표와 회귀 범위가 준비됐다.
3. 결함 수정과 파일 이동이 리뷰·되돌리기 가능한 별도 변경으로 분리됐다.
4. 수정 후 target/HIL/설치 검증 비용을 감수하기로 범위를 결정했다.
5. T19 최종 RC 고정 전에 병합하고, 변경 영향이 있는 T11~T15 판정까지 다시 연결한다.

T19 이후 새 source를 넣어야 한다면 RC를 다시 고정하고 필요한 gate를 다시 수행한다. “단순 리팩토링”이라는 이름으로 freeze 예외를 자동 허용하지 않는다.

## 4. T11 체크포인트 뒤 할 일

### 4.1 R00 기준선

현재 source를 수정하기 전에 다음 정보를 모은다. **Fixture 301 기능 image와 문서 정비 뒤 착수 HEAD를 분리해서 기록한다.**

| 기록 항목 | 필요한 내용 |
| --- | --- |
| 소스 | 실제 로컬 Core HEAD, dirty 여부, 미커밋 변경의 소유자·범위, 보드 gitlink와 실제 checkout |
| 도구 | NCS·Zephyr revision, toolchain, Python, Arduino CLI, 빌더와 runner identity |
| 시험 입력 | Fixture 301 catalog revision, role별 시험 profile·`.config`·overlay·vector 집합 |
| 실행 이미지 | DUT/peer 각각의 ELF·HEX 또는 실제 flash 파일 경로와 SHA-256 |
| 장치·세션 | 공개 문서에는 DUT/peer UID hash, 역할, 실행 세션 식별자, confirmation과 실행 시각 |
| 증거 | 원시 log/journal/result 경로·hash, 시작/종료/중단 상태와 최초 실패 ID |
| 변경 경계 | 현재 캠페인 종료 전 바꾸지 않을 source·runner·image·catalog·공유 출력 경로 |

확인할 수 없는 값은 `미확인` 또는 `NOT RUN`으로 남긴다. 표의 빈칸을 과거 대화의 경로나 hash로
채우지 않는다. 작업용 표는 04번 문서에 있고, 단계 진행은 05번 체크리스트에 기록한다.

### 4.2 R00~R13에서 하지 않을 것

기준선 확정 전에 SDK·board·public API·package identity를 바꾸거나 build directory를 삭제하지 않는다.
기능 수정과 전체 format·대형 파일 이동을 한 변경에 섞지 않고, 동일 artifact 이름으로 서로 다른
source의 출력을 덮어쓰지 않는다. 과거 실패를 제거하거나 새 source의 PASS로 옮기지 않는다.

보드·probe·COM은 R00~R13의 target smoke나 결함 진단에 필요할 때만 점유한다. 새 외부 결선 PASS
캠페인은 R13 뒤로 모은다. 진단 목적의 flash도 관련 범위와 confirmation을 확인한 별도 단계에서만
수행하며 recover·mass erase를 자동 실행하지 않는다. [S1][S2]

### 4.3 보존한 Fixture 301 결과의 사용 원칙

| 현재 근거 | 사용할 수 있는 범위 | 사용할 수 없는 범위 |
| --- | --- | --- |
| exact `e2f045c` Fixture 301 PASS | 해당 source·catalog·route의 TWI 단독 기능 | 이후 runtime 변경, T13 동시성·soak 또는 공개 승인 |
| 이전 무효·실패 실행 | 결선 계약과 TWIS 지연 buffer 결함의 원인 추적 | PASS 수치 합산 또는 새 campaign 완료 |
| 문서·metadata만 바뀐 commit | runtime payload 동등성을 별도로 증명한 경우의 추적 | 문자열·API 이름만으로 바이너리 동등성 선언 |

R01~R13이 runtime이나 link 결과를 바꾸면 영향받는 T11 시험을 R13 뒤 최종 exact image로
재수행한다. 중간 실기는 원인 분리용 진단으로만 기록하며 최종 PASS를 대신하지 않는다. T13의
동시성·장시간 검증은 여전히 별도 필수 gate다. [S1]

| F07: 공유 mutex 아래 긴 stop | R03 관련 범위, R10 구조 반영 | T12·T13·T14 | 지연·다른 block 진행을 확인. 근거 없이 교착 또는 성능 개선이라고 단정하지 않음 |
| F08: 제품 버전 표시 | R05 | T16~T19 | 표시 의미·생성 입력 정리. 별도 작업으로 진행 |

이번 문서 작성에서는 격리 재현 시험을 다시 실행하지 않았다. 01번에 기재된 이전 실험 결과는 그 문서의 과거 근거이며, 현 보드 검증 완료가 아니다. 301의 모든 vector가 문제의 동기 `transfer()`를 호출하는지까지 이번에 추적한 것은 아니므로, **R00에서 현재 시험의 호출 경로와 독립적인 데이터 판정 수단을 먼저 확인한다.**

실기 PASS와 소스 결함 발견은 모순되지 않는다. 해당 실행에서 관측되지 않은 stale event·동시 호출·timeout 경계가 남아 있을 수 있으므로, 필요한 회귀를 추가한다. 반대로 source 지적만으로 기존 모든 물리 PASS를 무효화하지도 않는다. [S5]

## 6. R 작업을 실제 구현으로 옮길 때의 필수 보완

### 6.1 R01: 빌드 소속만 최소 수정한다

SPIM/SPIS/TWIM/TWIS source도 `NUCODE_ARDUINO_CORE_SOURCES`에 모으고 Core target 생성 후 등록한다. 실제 `CONFIG_NUCODE_ARDUINO_SERIAL_FABRIC_*` 이름과 기존 파일 경로를 유지한다. Kconfig 구조 분할이나 SDK 변경은 별도 작업이다. [S2]

검증은 configure 성공만으로 끝내지 않는다. 허용 profile마다 요청한 설정과 resolved `.config`, 선택 source의 정확히 한 번 등록, 실제 소속 target, 참조 smoke의 target build와 최종 link를 확인한다. 정상적인 미참조 symbol 제거를 실패로 취급하지 않는다.

### 6.2 R02: 작업 식별·이벤트 소비·버퍼 반환을 함께 정의한다

**operation generation은 제출 시 확정한 작업과 연결한다.** 늦은 callback에 단순히 “지금의 generation”을 붙이는 방식은 이전 callback을 새 작업으로 잘못 표시할 수 있으므로 허용하지 않는다. driver가 요청 ID를 제공하지 않으면 정지 확인·IRQ 정리·다음 제출 허용 조건까지 명시한다.

동기 함수의 내부 완료 기록과 사용자가 읽는 event queue의 역할을 분리한다. 같은 queue를 둘이 경쟁해 소비하지 않도록 한다. queue 비우기 또는 buffer 주소 비교만으로 F01을 해결했다고 판정하지 않는다. [S2]

| 결과 | 구현 전에 확정할 계약 |
| --- | --- |
| 성공 | 자신이 제출한 작업의 완료 및 해당 DMA 접근 종료를 무엇으로 증명하는가 |
| timeout | 대기 중단인지, 취소 요청인지, 취소·정지 완료까지인지 구분 |
| timeout 이후 미정지 | buffer 재사용 금지 상태와 사용자가 반환 완료를 확인할 경로 |
| 취소 이후 늦은 완료 | 이전 작업에 귀속시키거나 명시적으로 폐기. 새 작업의 성공으로 처리 금지 |
| stop 확인 실패 | fault와 필요한 lease를 유지하고 충돌하는 재사용 거부 |
| 같은 handle의 교차 호출 | 원자적인 operation 예약과 busy 거부 또는 명시적 직렬화 |

**lease 유지와 사용자 buffer 내용 보호는 같은 것이 아니다.** API 문서에 timeout 이후 buffer의 유효 수명·재사용 조건을 적는다. 기존 공개 signature를 바꾸기보다 기존 상태·이벤트를 활용할 수 있는지 우선 검토하고, 불가피한 API 변경은 별도 호환성 결정으로 처리한다.

시간 처리는 고정 종료 시점 또는 overflow 없는 잔여 시간 기반으로 한다. timeout 0·최댓값·wrap·완료 누락의 의미를 기존 API와 대조한다. 변경 때문에 오류 enum이나 기존 반환 코드를 무심코 바꾸지 않는다.

### 6.3 R03: 공유 데이터의 소유권부터 적는다

각 필드에 writer, reader, IRQ 활성 구간, 보호 수단, 초기화/종료 시점을 기록한다. 일반 필드라는 이유만으로 모두 atomic으로 바꾸지 않는다. 진단 결과와 native error는 같은 사건의 snapshot으로 읽혀야 한다. [S2]

기존 고정 큐의 순서·용량·overflow 의미와 DMA buffer 공급 시점을 보존한다. overflow 보고를 가득 찬 동일 queue에만 의존하지 않는다. stop notification은 현재 상태·generation과 함께 확인하며, mutex를 풀고 기다리는 동안의 start/deactivate 진입을 규정한다.

파일 이동과 동기화 수정을 한 PR로 묶지 않는다. PDM/I2S/SAADC의 서로 다른 buffer lease 의미를 먼저 통일시켜 버리지 않는다.

### 6.4 R04: 공유 slot과 개별 File 객체를 구분한다

서로 다른 File 객체가 같은 slot을 참조하는 경우의 retain/release, generation 확인, 마지막 close를 일관된 동기화 정책으로 묶는다. 동일 File 객체의 동시 변경 지원 범위는 별도로 명시한다. no-op mutex stub만으로 경쟁 검증을 통과했다고 표시하지 않는다. [S2]

파일 format·partition·기존 복사 API는 유지한다. 참조 수 수정 PR에 Storage 전체 파일 분할을 함께 넣지 않는다.

### 6.5 R08: Route 상태와 자원 보유 기록을 둘 다 유지한다

lifecycle enum은 PM reference·pinctrl 설치 여부·pin별 handover phase·block lease 기록을 대체하지 않는다. 복구가 실패한 자원은 무조건 반환하지 않으며 안전이 증명되지 않은 경우 fault/소유권을 유지한다. [S2]

이번 운영계획은 다음 순서 보존 조건을 추가한다.

> **현재 어댑터의 suspend 확인 → pinctrl 설정 교체 → runtime resume 순서를 보존한다. 순서 변경이 필요하면 해당 driver의 실제 동작과 실패 복구를 별도 변경으로 검증한다.**

실제 착수 HEAD의 `RuntimePeripheralRoute::activate()`를 다시 읽어 순서와 실패 경로를 대응표에 넣는다. 함수 이름을 `acquirePower()` 또는 `applyPins()`로 정리한다는 이유로 실행 순서를 바꾸지 않는다.

### 6.6 작은 파일 분할의 의존성을 불필요하게 늘리지 않는다

Event는 첫 Fabric 분할 파일럿으로 유지한다. 이후 Analog/Stream의 **동작을 바꾸지 않는 이동**은 관련 기준선과 R03의 회귀가 갖춰지면 검토할 수 있다. 모든 ResourceManager·Arduino facade 재설계가 끝나야 파일 이동을 시작할 수 있다는 추가 의존성을 만들지 않는다. 반면 공통 lease/stop 정책을 실제로 교체할 때는 그 공통 의미가 검증돼야 한다. [S2]

첫 분할 PR은 source·context·include·CMake 연결에 국한한다. init 순서·IRQ symbol·linker section·정적 객체·RAM/flash 영향을 확인하고, 여러 파일에 mutable `extern`을 늘리는 방식은 피한다.

### 7.1 기존 PASS를 다루는 원칙

기존 commit/image의 PASS를 보존한다. 새 source에 동일 PASS를 복사하지 않는다. 변경이 없는 경로는 기존 증거를 **참조**할 수 있지만, 새 이미지에서 실행한 결과처럼 표시하지 않는다.

문서·metadata만 바뀌었고 runtime payload의 동등성이 실제로 증명된 경우에는 기존 release 절차가 허용하는 방식으로 그 근거를 연결한다. 문자열 하나가 같거나 public API가 같다는 이유만으로 바이너리·시간 동작의 동등성을 선언하지 않는다. [S1][S2]

재시험 범위는 “항상 모든 시험을 처음부터” 또는 “리팩토링이니 아무 시험도 불필요”의 두 극단으로 정하지 않는다. **diff → 사용 경로 → 관측 위험 → 필요한 gate**를 기록한다. 기존 release 절차가 전체 검증을 요구하는 구간은 그대로 적용한다.

| 빌드·배포 | target source·feature·package 포함 목록과 설치 entrypoint가 일치 |
| 검증 | 실행한 gate와 NOT RUN, 실기/인프라 실패의 차이를 정확히 기록 |
| 증거 | 로그·journal·artifact·hash·fixture 조건이 연결되고 과거 원본이 보존됨 |
| 되돌리기 | 되돌릴 작은 변경과 재시험 조건을 식별. 다른 작업의 변경을 파괴하지 않음 |

리그 또는 DMA 정지가 불확실하면 먼저 기존 안전 절차로 장치 상태를 확정한다. 코드 revert가 실행 중 하드웨어의 안전 정지를 대신하지 않는다. 원인 불명의 상태에서 자동 mass erase/recover를 실행하지 않는다.

현 브랜치 전체를 과거 상태로 강제 reset하는 대신, 문제가 된 작은 변경을 식별해 승인된 수정/revert로 처리한다. 이 문서에는 자동 삭제·강제 push·flash 명령을 넣지 않는다.
