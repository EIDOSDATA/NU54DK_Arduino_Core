# NU54DK Arduino Core — 진단 비교와 최종 판단

작성일: 2026-09-06
분석 기준 Core: `4af93daa542b4b84e39381317d4747b3df3ff5c8`
보드 서브모듈: `fe65f2f0880bd05b32e562d9bf1ee59142b4f4d3`

> 이 문서는 `4af93da` 기준의 진단 근거를 보존한다. 현재 실행 순서와 상태는
> [통합 실행계획](./02_리팩토링_통합_실행계획.md)과
> [진행 체크리스트](./05_리팩토링_진행_체크리스트.md)를 따른다.

> 현재 일정 결정은 R00~R13을 `v0.4.0` 공개 전에 완료하고 최종 source의 외부 HIL을 한 번 수행하는
> 것이다. 이 문서의 `후속` 표현은 기술 작업군의 관계를 뜻하며 공개 이후 일정으로 해석하지 않는다.

**두 진단은 함께 사용하는 것이 좋다. 다른 컴퓨터의 문서는 파일 분할과 작업 순서를 구체화하는 데 강점이 있고, 기존 분석은 전송·자원 수명주기의 문제와 현재 검증 수준을 더 구체적으로 다룬다. 최종 권고는 ‘동작 결함 안정화 → 작은 범위의 구조 분리 → 검증 후 확대’다.**

다른 문서에서 새롭게 채택할 핵심은 **ISR–스레드 동기화, CMake source 등록 순서, 스케치 전처리 회귀 시험, EventFabric 분할 파일럿**이다. 기존 분석의 **이전 전송 완료 이벤트 오인, timeout overflow, File 참조 수 동기화, 기존 Arduino 경로와 Fabric의 소유권 관계**도 실행계획에서 빠지면 안 된다.

실행 순서와 작업별 완료 기준은 [02_리팩토링_통합_실행계획.md](./02_리팩토링_통합_실행계획.md)에 정리했다. 이 문서는 비교·설계 제안이며, 저장소 수정이나 하드웨어 시험을 수행한 기록은 아니다.

## 3. 다른 진단 덕분에 추가로 확인한 사항

### 3.1 CMake 지적은 유효하다. 다만 최종 링크 실패와는 구분해야 한다

현재 SPIM/SPIS/TWIM/TWIS는 `zephyr_library_sources()`로 등록한 뒤, 나중에 `zephyr_library_named(nucode_arduino_core)`를 호출한다. UARTE 등 나머지 source는 목록에 모았다가 Core target 생성 후 등록한다. [현재 등록 순서](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/zephyr/CMakeLists.txt#L128)

설치된 NCS v3.4.0의 Zephyr 구현에서 `zephyr_library_sources()`는 `target_sources(${ZEPHYR_CURRENT_LIBRARY} ...)`를 호출한다. `zephyr_library_named()`가 이 변수를 설정한다. Zephyr 상위 CMake도 `zephyr` target을 만든 뒤 외부 module을 추가하는 구조다.

이번에는 원본의 source 등록 구간과 설치 SDK의 두 CMake 함수를 가져온 **configure 전용 격리 시험**을 실행했다. 상속 target을 `zephyr`로 설정했을 때 네 adapter source는 `zephyr`에 등록되고 `nucode_arduino_core`에는 등록되지 않았다. CMake configure/generate는 성공했다. 부수적인 두 metadata helper는 stub 처리했으며 실제 펌웨어 컴파일·링크는 하지 않았다.

따라서 ‘이전 target context에 의존한다’는 판단은 근거가 있다. 반면 두 target이 최종 ELF에 함께 링크될 수 있으므로, 이를 ‘현재 firmware가 반드시 깨진다’고 표현하면 과장이다. **소스를 목록에 모아 명시적인 Core target에 등록**하고, 유효한 personality 조합마다 실제 소속 target·중복 등록·최종 참조 심볼을 확인하는 것이 적절하다. ELF에 심볼이 있다는 확인만으로 source 소속 문제까지 해결됐다고 판단하지 않는다.

참고 문서 §5.1의 코드는 개념 예시로만 사용해야 한다. 현재 파일명·심볼은 `cores/arduino/SpimFabric.cpp`, `CONFIG_NUCODE_ARDUINO_SERIAL_FABRIC_SPIM` 등이며, 예시의 `cores/arduino/Arduino.cpp`와 `internal/SpimFabric.cpp`는 현 트리와 맞지 않는다.

### 3.2 ISR 동기화는 기존 분석에 추가해야 할 중요한 문제다

Analog/Stream의 event queue는 spinlock으로 보호하지만, queue overflow 이후 ISR callback이 쓰는 `last_result`·`last_driver_error`는 그 보호 범위 밖에 있다. 일반 스레드의 getter는 별도의 mutex만 잡는다. ISR은 이 mutex에 참여하지 않으므로 조회 측 잠금만으로 양쪽 접근을 동기화할 수 없다. [Analog queue와 callback](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/AnalogFabric.cpp#L104), [Analog 진단 쓰기](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/AnalogFabric.cpp#L501), [I2S callback](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/StreamFabric.cpp#L529), [I2S getter](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/StreamFabric.cpp#L976)

I2S의 `volatile bool stopped_seen`도 일반적인 동기화 수단으로 보기 어렵다. 현재 stop은 공유 mutex를 잡고 이 값을 busy wait한다. [I2S stop](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/StreamFabric.cpp#L1291)

이것은 소스에서 확인한 동기화 공백이다. 실제 보드에서 데이터 손상·교착을 재현하거나 latency를 측정한 결과는 아니다. 다음 조건을 붙여 참고 문서의 방향을 채택한다.

- ISR에서만 사용하는 필드까지 모두 atomic으로 바꿀 필요는 없다. 필드별 writer/reader, IRQ 활성 구간, 소유권 이전 시점을 먼저 기록한다.
- 진단 결과와 native error가 한 사건을 나타내면 두 값을 일관된 snapshot으로 전달한다. 서로 다른 atomic 두 개로 바꾸는 것만으로 사건의 일관성이 보장되지는 않는다.
- queue overflow를 같은 가득 찬 queue에만 기록하면 누락된다. 별도의 관측 수단을 둔다.
- semaphore는 깨어나는 수단이다. 이전 stop의 신호로 다음 세대의 stop을 완료 처리하지 않도록 generation/상태를 검증한다.
- mutex를 풀고 기다릴 때 다른 start/deactivate가 끼어들 수 있다. 먼저 stopping 상태와 해당 세대의 소유권을 확정하고 대기 후 재검증한다.
- DMA buffer 공급처럼 driver가 요구하는 ISR 시점의 작업은 유지한다. 모든 callback 일을 무조건 일반 스레드로 옮기지 않는다.

### 3.3 빌더 분할 예시에는 실제 실행 환경을 반영해야 한다

현재 `.cmd`는 최종적으로 Python의 `-I` 옵션으로 단일 Python 파일을 실행한다. 참고 문서처럼 옆에 `nu54_builder/` package를 만들고 `from nu54_builder.cli import main`만 추가하면, 격리 모드에서 그 디렉터리가 import 경로에 자동으로 포함되지 않는다. [실제 launcher](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/tools/nu54-builder/nu54-builder.cmd)

같은 형태의 최소 package/wrapper를 만들고 현재 고정 toolchain Python으로 실행한 결과, 일반 실행은 성공했고 `-I` 실행은 `ModuleNotFoundError`로 실패했다. **이는 제안된 분할 방법의 부족함을 재현한 것이며, 현재 단일 파일 빌더가 실패한다는 의미는 아니다.**

`-I`를 제거하는 대신, launcher 자신의 신뢰된 설치 경로에서 내부 package를 명시적으로 로드하도록 설계하는 편이 좋다. checkout 밖의 작업 디렉터리, 공백·한국어 경로, 압축 해제한 실제 설치본, package 허용 목록까지 검증해야 한다.

### 3.4 전처리 회귀 시험은 채택하되 기존 자산 위에 추가한다

현재 Arduino CLI smoke에는 prototype 생성·다중 INO 탭·Zephyr 혼합 스케치 검사가 있다. 동시에 직접 Zephyr/Bluetooth include를 정규식으로 찾아 prototype 단계에서 보류하는 로직이 있다. 이를 ‘전처리 검증이 없다’고 진단하면 부정확하다. [전처리 구현](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/tools/nu54-builder/src/nu54_builder.py#L1652), [기존 smoke](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/tests/arduino-cli/run_smoke.py#L519)

추가할 시험은 조건부 include, 주석·raw string 안의 유사 텍스트, 여러 줄 macro, CRLF, 한국어 경로, 원본 오류 위치다. 정상 출력 비교뿐 아니라 **변환 후 스케치의 실제 compile 결과와 오류 위치**까지 확인한다. prototype 단계의 경고 억제와 최종 사용자 source의 warning 옵션 전달도 구분한다.

## 4. 그대로 적용하지 않을 제안

### 4.1 모든 항목을 P0로 묶지 않는다

다른 진단의 P0는 ‘분할 전에 처리할 항목’에 가깝다. 서비스 전체 장애와 같은 통상적인 최상위 심각도로 받아들이지 않는다. 전송 완료·동기화 문제는 사용 중인 기능의 정확성 문제이고, 버전 원본 정리와 golden test는 성격이 다르다. 실행계획은 **수정 필요성, 근거 수준, 검증 의존성**으로 순서를 정한다.

### 4.2 버전·feature manifest 정리는 기존 구현 위에서 진행한다

builder에는 이미 `PROFILE_SCHEMA_VERSION`, `FEATURE_SCHEMA_VERSION`, `CACHE_SCHEMA_VERSION`, `SESSION_CONTEXT_SCHEMA_VERSION`, `ARTIFACT_MANIFEST_SCHEMA_VERSION`, `SOURCE_RECORD_SCHEMA_VERSION`이 있다. 각각의 수명주기를 유지해야 한다. `BoardSystem::coreVersion()`의 `0.2.0-dev` 표시처럼 실제 불일치부터 고친다. [버전 상수](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/tools/nu54-builder/src/nu54_builder.py#L25), [제품 진단 문자열](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/libraries/NUCODE_NU54DK/src/NUCODE_NU54DK.cpp#L335)

cache key가 입력 변경 때문에 달라질 때마다 schema를 올리는 규칙도 적절하지 않다. 저장 형식·해석·호환성 계약이 바뀌면 schema 변경이나 명시적인 무효화가 필요하지만, 정상적인 source hash 변화는 key의 본래 목적이다.

bundled library feature는 이미 schema와 allowlist를 통해 읽는다. 원문 §13.4의 제안은 하드코딩된 allowlist를 신뢰된 package manifest로 옮길 수 있다는 것이다. 이를 ‘manifest가 없으니 새로 만들어야 한다는 제안’으로 요약한 것은 부정확했다. 기존 loader와 schema를 바탕으로 allowlist의 원본과 package 신뢰 경계를 정리하는 방향을 검토한다. 버전 제안 역시 기존 상수의 존재와 별개로 identity 원본을 연결할 가치가 있다. [현재 feature loader](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/tools/nu54-builder/src/nu54_builder.py#L425)

### 4.3 상태 enum은 부분적으로 남은 자원을 대신할 수 없다

RuntimePeripheralRoute에는 block lease, handover된 pin, pinctrl 설치 여부, PM reference 등의 정보가 있다. 실패 후 일부만 복구된 경우를 기록하기 위한 값이다. lifecycle의 phase는 enum으로 정리할 수 있지만, **자원 획득·반납 기록을 함께 유지**해야 안전한 역순 복구와 재시도가 가능하다. [현재 상태 구성](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/cores/arduino/internal/RuntimePeripheralRoute.h#L137)

### 4.4 디렉터리·public API 개편은 작은 범위에서 검증한다

공개 header 경로·singleton·Arduino 의미를 보존한다. 원문 §12는 고급 API가 아직 안정화되지 않았다면 experimental namespace를 사용하라는 조건부 제안이며 모든 기존 타입의 즉시 이동을 요구한 것은 아니다. 이 조건을 실제 공개·후보 상태와 대조하고, 현재 API의 namespace 변경은 별도 호환성 검토 후 결정한다. public header의 Zephyr/nrfx 결합을 줄이는 목표는 채택하되 기존 노출을 일괄 제거하지 않는다. 원문 §25.3도 두 번째 실제 보드/MCU 요구 전 범용 HAL 도입을 경계하므로, 이 부분은 두 진단의 공통 원칙이다.

정책 로직은 hardware backend와 board capability를 입력으로 받게 한다. ‘SoC 계층이 보드 계층에 의존하는’ 일렬 구조를 강제하지 않는다. 공통화는 실제 두 번째 사용처와 같은 의미가 확인된 뒤 한다.

### 4.5 활성 TODO·기존 증거·과거 공개 자산은 유지한다

현재 TODO는 T01~T10 완료, T11 진행 상태를 기록하며, 미완료 작업이 있는 동안 유지하도록 저장소 진입점에서 요구한다. 다른 진단의 Issues/Projects 이전 제안 때문에 이를 지금 지우거나 대체하면 안 된다. [현재 TODO](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/00_Docs/TODO_v0.4.0.md), [저장소 작업 규칙](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/blob/4af93daa542b4b84e39381317d4747b3df3ff5c8/AGENTS.md)

HIL 재시도도 실패 종류만으로 허용하면 부족하다. 장치 변경 전 실패이거나 알려진 상태 복구를 확인한 경우에 한해 횟수를 제한하고 모든 시도를 보존한다. 시험 문서를 만드는 일은 보드 flash·결선 변경·릴리스 공개를 수행하라는 지시와 별개다.

## 6. 검증 결과를 해석하는 기준

기존 분석에서 같은 commit에 실행한 결과는 Host 596건 중 595 통과·1 조건부 skip, CI contract 45/45, package 20/20, 문서 149개, 정렬 227개 통과였다. inventory와 readiness 계약도 통과했지만 **release blocker 8개는 남아 있었다**. 별도 예제 발견 검사는 전체 펌웨어 compile과 다르다.

기존에 확인한 동일 commit의 [Software Gates](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/33971830913)와 [Reproducible Builds](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/33971830874)는 success였다. 해당 결과는 원격 CI 기록이며, 이번 작업의 로컬 전체 firmware build 결과로 표시하지 않는다.

이번 비교에서는 제품 소스를 바꾸지 않았으므로 전체 gate를 반복하지 않았다. 추가로 CMake source 소속 configure 시험과 Python 격리 import 시험을 실행했고, ISR 등은 정적 대조했다. **이번 비교에서 로컬 전체 펌웨어 빌드와 실제 HIL은 수행하지 않았다.**

기존 검사가 통과한 상태에서도 위 문제가 발견된 것은 검증이 무가치하다는 뜻이 아니다. 기존 검사가 보호하는 공개 계약·패키지·기본 동작 위에, stale event·overflow·부분 복구·동시 호출이라는 실행 경계를 더해야 한다는 의미다.

## 7. 참고 문서 반영 범위를 다시 대조한 결과

사용자의 누락 확인 요청에 따라 원문과 작성 문서를 다시 대조했다. 초기 통합 계획은 큰 작업 범위를 다루었지만 원문의 세부 실행 항목을 모두 명시적으로 연결한 계획은 아니었다. 아래 세 종류를 구분한다.

| 구분 | 해당 항목 | 판단 |
| --- | --- | --- |
| 의도적으로 방식 수정 | LOC 임계값의 강제성, 단일 enum으로 route 상태 통합, cache key 변경마다 schema bump, public header 노출 일괄 제거 | 책임·부분 복구·호환성 기준을 적용해 대체 |
| 조건 확인 또는 순서 조정 | experimental namespace, 테스트/문서 디렉터리 이동, legacy 스크립트 이동, active TODO의 Issues/Projects 이전, scheduled HIL | 방향을 폐기한 것이 아니며 기존 경로·진행 상태·fixture 조건을 먼저 확인 |
| 초기 계획에서 누락 또는 구체화 부족 | Kconfig/CMake 모듈 분할, 정적 분석 도구, ABI/deprecation, ADR, pairwise CI, 빌더 세부 계약, 패키저 SBOM/license/provenance 책임, 전체 public header/외부 라이브러리 호환성 시험, 기존→신규 파일 대응표 | 기술적 반대가 아니며 실행계획 §10에 보완 |

원문은 ‘파일 크기만 줄이기’, ‘모든 코드를 무조건 experimental로 이동’, ‘feature manifest가 전혀 없음’, ‘너무 이른 범용 HAL’을 주장하지 않는다. 초기 설명에서 이런 대립으로 읽힐 수 있었던 표현을 위 비교표와 §4에서 바로잡았다.

각 기능의 상세 파일명·디렉터리 예시는 그대로 복사하지 않았다. 책임 경계는 채택하되 실제 source·잠금·초기화·설치 경로를 확인해 확정하려는 판단이었다. 다만 이를 보류라고만 말하고 작업 전에 작성할 대응표의 완료 기준을 적지 않은 것은 계획의 부족함이었다. [실행계획 보완](./02_리팩토링_통합_실행계획.md#10-참고-문서에서-누락되거나-구체화가-부족했던-항목의-보완)에 이를 명시했다.
