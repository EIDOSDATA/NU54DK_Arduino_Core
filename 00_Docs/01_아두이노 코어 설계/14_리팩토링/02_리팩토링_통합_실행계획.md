## 1. 목표와 유지할 계약

목표는 파일 개수 증가가 아니라 **실패·재시작·동시 사용에서도 예측 가능한 주변장치 동작, 독립적으로 시험할 수 있는 내부 구조, 설치본까지 동일하게 동작하는 개발 도구**다.

| 유지할 항목 | 이유 |
| --- | --- |
| Arduino 공개 함수·header 경로·Serial/Serial1/Wire/SPI 이름·핀 번호·FQBN | 기존 스케치와 라이브러리 호환성 |
| 전체 Zephyr firmware build와 고정 SDK/toolchain/보드 참조 | 현재 플랫폼의 빌드·배포 재현성 |
| IoResourceManager의 물리 자원 identity·lease·generation/epoch | 별칭 충돌 방지와 오래된 소유권의 재사용 방지 |
| 고정 context·제한된 큐·명시적인 DMA 수명주기 | 임베디드 메모리 상한과 비동기 buffer 안전성 |
| 정지·복구 확인 실패 시 fault 상태 및 필요한 lease 유지 | 미정지 하드웨어에 자원을 중복 배정하지 않기 위함 |
| EEPROM/파일 저장 형식·flash partition·기존 공개 release 자산 | 기존 장치 데이터와 설치 호환성 |
| CLI subcommand·exit code·diagnostic code·manifest 계약 | Arduino IDE/CLI와 자동화 호환성 |
| 한국어 Doxygen, BSD/Allman, 4칸, 제어문 중괄호 필수 | 사용자 및 저장소 코드 규칙 |

API나 데이터 형식을 바꿔야 한다면 내부 이동 PR과 분리해 migration을 설계한다. 분할을 위해 `shared_ptr`, 동적 컨테이너, 예외, 다층 가상 HAL을 기본 도입하지 않는다.

## 2. 현재 v0.4 작업과 연결하는 방법

현재 TODO는 T01~T11을 완료했고 다음 신규 기능 물리 작업은 T12 Fixture 401이다. 그러나 R06~R13을
공개 뒤 수행하면 UART·SPI·TWI와 analog/stream 결선을 다시 반복해야 한다. 따라서 R00~R13을
T11과 최종 physical campaign 사이의 하나의 리팩토링 구간으로 둔다. 다른 고정 이미지의 과거 PASS는
역사적 증거로 보존하되 수정된 코드의 PASS로 옮겨 적지 않는다. R13 뒤 최종 exact source로 영향받는
T11 회귀를 수행한 다음 T12로 전환한다. 실제 착수 시 HEAD·TODO·관련 계약을 다시 확인한다.
[활성 TODO](../../TODO_v0.4.0.md)

확정한 기본 운영은 다음과 같다.

1. **정확성 수정을 구조 이동보다 먼저 한다.** 현재 v0.4 후보에 영향을 주는 문제는 T14의 결함 수정·재시험으로 연결한다. 어떤 문제를 정식 공개 차단 사유로 삼을지는 실제 지원 경로와 재현 결과로 판단한다.
2. **R06~R13도 v0.4 공개 선행조건으로 포함하되 작은 단위로 진행한다.** 한 번에 전체 디렉터리를 바꾸지 않고 작업별 Host·target·package gate와 되돌리기 경계를 유지한다.
3. 중간 물리 실행은 결함 진단에 필요한 경우로 제한한다. 최종 구조가 고정된 뒤 영향받는 T11과 T12~T15를 새 commit 기준으로 수행하고 R14에서 RC를 다시 고정한다.
4. 변경 범위·해당 T 항목·검증 결과·다음 checkpoint를 기존 TODO에 연결한다. 이 외부 실행계획은 현재 TODO를 대체하지 않는다.

이 계획 개정 자체는 리팩토링 source 구현이나 새 HIL을 뜻하지 않는다. 아래 R00부터 별도 구현·검증 단위로 실행한다.

## 4. 처음 착수할 작업

### R00 — 기준선과 실패 시나리오를 고정한다

**목적:** 무엇을 보존하고 무엇을 수정할지 리뷰 가능한 형태로 만든다. 새 대규모 테스트 체계를 만드는 작업으로 확대하지 않는다.

- 실제 착수 HEAD·보드 gitlink·NCS/toolchain·Arduino CLI·package identity를 기록한다. 고정 SDK 변경은 포함하지 않는다.
- 현재 Host/contract/package 결과와 CI build·HIL 증거를 구분해 연결한다. 과거 기준 결과는 재사용 가능한 증거로 보존하되 새 commit 통과로 표시하지 않는다.
- 공개 API/include/singleton/FQBN, 대표 예제, 저장 형식, partition, CLI/JSON schema의 변경 금지 목록을 작성한다.
- F01~F08을 추적 항목으로 연결한다. 각 항목에 재현 조건, 근거 수준, 영향 기능, 필요한 시험을 적는다.
- CMake source membership, stale completion, timeout 경계의 최소 재현을 제품 테스트로 편입할 위치를 정한다. 격리 스크립트를 그대로 복사해 검증이 끝났다고 보지 않는다.
- Blink·BLE 등 대표 profile의 빌드 시간과 flash/RAM을 측정할 절차를 고정한다. 아직 측정하지 않은 숫자는 빈 값 또는 NOT RUN으로 남긴다.
- Fixture 301 exact `e2f045c`의 PASS와 이후 metadata·runner 변경을 구분한다. Runtime byte가 달라지지
  않은 문서 정비를 새 HIL로 오인하지 않으며, 다음 source 변경 전 현재 ELF·map·symbol 기준을 저장한다.

**완료 기준:** 다음 수정 PR을 작성하는 사람이 기준점·관련 계약·재현 절차를 찾을 수 있다. 실제로 실패해야 하는 새 시험은 해당 수정 PR에서 수정 전 실패·후 통과를 함께 보여준다. main에 의도적으로 실패하는 gate를 먼저 병합할 필요는 없다.

### R01 — CMake source를 명시적인 Core target에 등록한다

**범위:** `zephyr/CMakeLists.txt`의 SPIM/SPIS/TWIM/TWIS source 등록. 실제 파일 경로와 기존 `CONFIG_NUCODE_ARDUINO_SERIAL_FABRIC_*` 이름을 유지한다.

**변경:** 네 source도 `NUCODE_ARDUINO_CORE_SOURCES`에 모으고, Core target 생성 후 등록한다. 큰 CMake 파일 분할·Kconfig 개편·SDK 갱신은 이 PR에 넣지 않는다.

**필수 확인:**

- SPIM/SPIS/TWIM/TWIS 단독, UARTE 단독, 허용되는 복수 personality 조합, 모든 personality 비활성의 유효한 profile을 구성한다.
- 요청한 Kconfig 값과 실제 `.config` 결과가 같은지 검사한다. 의존성이 false라서 기능이 꺼진 build를 해당 기능 PASS로 세지 않는다.
- 선택 source가 `nucode_arduino_core`에 정확히 한 번 등록됐는지 확인한다. CMake target 정보와 생성된 build 정보를 함께 확인한다.
- 실제 참조하는 smoke sketch의 target build와 최종 심볼을 확인한다. 비참조 symbol은 linker의 정상적인 제거 대상일 수 있으므로 무조건 잔존을 요구하지 않는다.
- 기존 재현 빌드와 package source 포함 규칙에 회귀가 없는지 확인한다.

**완료 기준:** source 소속 target과 feature별 실제 빌드가 명시적으로 검증된다. 이번 비교의 configure-only 재현만으로 완료 처리하지 않는다.

### R02 — SPI/TWI 전송 완료와 timeout을 바로잡는다

**범위:** `SpimFabric.cpp`, `TwimFabric.cpp`, 필요한 최소 내부 상태·시험. F01/F04를 다루며 같은 handle 호출 규칙도 함께 명시한다.

**먼저 확정할 계약:**

1. 동기 호출은 자신이 제출한 작업의 terminal 상태만 기다린다.
2. 완료·오류·취소 이벤트의 소비자는 누구인지 정의한다. 같은 queue를 사용자와 동기 함수가 경쟁해서 소비하게 두지 않는다.
3. timeout 반환과 DMA buffer 재사용 가능 시점을 구분한다. 정지가 확인되지 않으면 자원을 성공 해제한 것처럼 보고하지 않는다.
4. 같은 handle에서 여러 스레드가 동시에 요청할 때 직렬화 또는 명시적인 busy 거부 동작을 정의한다. 최소 권고는 진행 중 operation을 원자적으로 예약하고 충돌 연산을 거부하는 방식이다.

**구현 방향:** 내부 operation generation과 terminal 기록을 연결한다. 필요한 경우 공개 event 구조의 호환성 영향을 별도로 검토하며, 편의를 위해 public API를 즉시 바꾸지 않는다. 단순 queue 비우기나 buffer 주소 비교만으로 해결하지 않는다. 시간은 overflow 없는 monotonic deadline 또는 잔여 시간 기반 bounded wait로 관리한다.

**필수 시험:** 이전 완료 뒤 새 전송, 같은 buffer 주소 재사용, cancel 후 늦은 완료, 오류 뒤 재시작, 완료 queue overflow, 완료 이벤트 소비 경합, timeout 0·최댓값·시간 경계, 완료 누락, transfer/deactivate 교차 호출.

**완료 기준:** 수정 전 실패·수정 후 통과하는 동작 시험이 있고 실제 전송 완료 전 성공 반환이 차단된다. target build와 영향을 받는 SPI/TWI 기능·오류·cancel/stop 실기 시험을 별도 기록한다. 공개 지원 판정에는 필요한 HIL 결과가 있어야 한다.

### R03 — ISR 진단 전달과 stop 동기화를 수정한다

**범위:** 먼저 Analog/Stream의 확인된 접근 경로. 큐·신호·필드의 실제 ownership을 표로 만든 뒤 작은 수정으로 진행한다.

R03a에서는 진단 snapshot과 overflow 관측을, R03b에서는 stop 신호·대기·재시작을 다루는 식으로 나눌 수 있다. 파일 이동은 섞지 않는다.

| 데이터/동작 | 권고 방식 | 주의할 점 |
| --- | --- | --- |
| 일반 event | 고정 큐와 짧은 ISR-safe 동기화 | 기존 순서·용량·drop 의미 보존 |
| queue overflow | 별도 atomic flag/counter 또는 동등한 전달 수단 | 가득 찬 큐에 overflow 보고를 의존하지 않음 |
| 진단 결과 + native error | 일관된 snapshot 또는 제어 문맥에서 함께 반영 | 서로 다른 사건의 값이 섞이지 않음 |
| stop 완료 | ISR-safe notification + 현재 세대/상태 확인 | 이전 신호가 다음 stop을 완료시키지 않음 |
| callback 전용 상태 | 소유권과 초기화·IRQ enable 경계 명시 | 일반 필드 자체를 무조건 금지하지 않음 |
| DMA buffer 공급 | driver가 요구하는 callback 시점 유지 | 지연 처리 도입으로 underrun을 만들지 않음 |

대기 전에 stopping과 generation을 확정하고, mutex를 풀어 대기한 뒤 다시 상태를 확인한다. 기다리는 동안 재초기화·다른 요청이 끼어들어도 소유권이 바뀌지 않게 한다. IRQ 안에서는 mutex나 blocking wait를 사용하지 않는다.

**필수 시험:** queue overflow와 진단 조회 교차, stale stop 신호, stop 직전/직후 callback, timeout 뒤 늦은 callback, 반복 start/stop, block 하나가 정지 대기 중일 때 다른 block의 진행, fault 이후 자원 보유와 명시적 복구.

**완료 기준:** 공유 데이터의 writer/reader와 동기화 규칙이 명확하다. 동작 시험·target 검증이 있고 관련 HIL에서 데이터와 stop/restart를 확인한다. 단순 atomic 치환 또는 semaphore 호출 존재만 확인하는 시험으로 끝내지 않는다.

### R04 — File 공유 slot의 retain/release를 일관되게 만든다

**범위:** LittleFS `FS.cpp`의 copy/assignment/close와 관련 설명. 기존 복사 가능한 File API를 유지한다.

slot 유효성·generation·참조 수 갱신·마지막 close를 같은 동기화 정책 아래 처리한다. source/destination이 서로 다른 File 객체이면서 같은 slot을 공유하는 경우를 포함한다. 동일 File 객체를 동시에 변경하는 지원 범위는 별도 명시한다. 내부 helper의 lock 소유 규칙을 정해 중첩 호출이 불명확해지지 않게 한다.

**필수 시험:** copy/copy assignment/self assignment/move/close 조합, 마지막 참조 close, stale slot, slot 재사용, 두 스레드의 서로 다른 handle에서 retain/release 교차. no-op mutex stub만으로 경쟁 검증을 대신하지 않는다.

**완료 기준:** 참조 수가 정확하고 마지막 close가 한 번 발생하며 slot이 정상 회수된다. 파일 내용과 기존 저장 형식은 유지된다. header의 ‘이동 전용’ 등 실제 API와 다른 설명도 수정한다.

### R05 — 제품 identity 표시와 생성 원본을 정리한다

`BoardSystem::coreVersion()`의 고정 문자열을 실제 제품 identity와 연결한다. 어떤 값이 source 개발 버전이고 어떤 값이 패키지 release 버전인지 정의한다. 정식 승격 전 개발 소스를 이미 공개된 stable처럼 표시하지 않는다.

이미 분리된 schema 상수는 유지한다. 제품 identity의 중복 정의부터 줄이고, 불필요하게 거대한 새 manifest를 도입하지 않는다. 생성 header를 사용한다면 그 입력·생성 규칙이 build 의존성과 package에 포함되도록 한다.

**완료 기준:** 런타임 BoardInfo·빌드 artifact·설치 package의 버전 의미가 일치하며, 제품 버전 변경이 관련 없는 schema 변경을 강제하지 않는다.

## 5. 동작 기준을 확보한 뒤 수행할 분할

### R06 — builder의 순수 모듈부터 추출한다

권장 순서는 **configuration/feature 해석 → source graph → artifact 검증 → cache/lock → SDK 환경·process/build → upload**다. configuration과 artifact 검증도 실제 CLI 출력 계약을 유지한다.

- 기존 `.cmd`와 Python 진입점을 유지하고 내부 package에 위임한다.
- `-I` 실행을 유지한다. launcher의 신뢰된 설치 디렉터리를 기준으로 명시적으로 내부 package를 로드한다. CWD나 외부 PYTHONPATH에 기대지 않는다.
- `BuildContext`, `ToolEnvironment`, `ArtifactManifest` 등 내부 모델의 필수 필드를 명확하게 한다. 외부 JSON schema 변경과 Python 타입 정리는 분리한다.
- 기존 bundled feature schema/allowlist를 확장한다. 외부 라이브러리가 임의의 설정·source를 주입할 수 있도록 범위를 넓히지 않는다.
- package 포함 목록·checksum·source identity에 새 파일을 반영한다.

**필수 검증:** 기존 CLI argument/exit/diagnostic, checkout 밖 CWD, 한국어·공백 경로, 실제 압축 해제 설치본의 `-I` 실행, frontend에서 artifact까지 대표 전체 build. 이후 cache/lock을 옮길 때 SDK·board·profile·overlay 변경, 중단 후 재시도, lock 충돌, 손상 artifact 거부를 추가한다.

**성능 개선은 별도:** cold/no-change/sketch-edit/profile-change와 readiness metadata-only 변경을 비교한다. 코드 생성 입력과 release evidence를 구분하되 필요한 cache invalidation을 제거하지 않는다. key 입력이나 저장 형식 변경은 해당 호환성 규칙에 따라 검증한다.

### R07 — EventFabric을 첫 Fabric 파일 분할로 사용한다

`EventFabric.cpp`에서 endpoint 검증·registry, TIMER/EGU/GPIOTE 처리, DPPI/PPIB 연결의 책임 경계를 정리한다. 첫 PR은 현재 상태·잠금·순서·메모리 배치를 가능한 한 유지한 추출로 제한한다.

public header와 호출법은 유지한다. 내부 context는 작은 accessor/API로 공유하며 여러 파일이 전역 상태를 직접 수정하도록 `extern`을 늘리지 않는다. 새 공통 HAL을 만들지 않는다.

**완료 기준:** 잘못된 endpoint·도메인·중복 channel 거부, route 연결·해제, 자원 회수의 기존 동작이 유지된다. 선택/비선택 profile에서 누락·중복 source가 없고 관련 target/HIL 결과가 연결된다. LOC 목표 달성만으로 완료 처리하지 않는다.

### R08 — 자원 관리와 RuntimePeripheralRoute의 책임을 분리한다

기존 IoResourceManager를 유지하면서 순수 identity/충돌 정책, 예약·commit·rollback 처리, Zephyr 동기화, board registry의 경계를 만든다. 공통 primitive는 두 개 이상의 실제 사용처에서 의미가 같다는 것이 확인된 것부터 추출한다.

RuntimePeripheralRoute는 lifecycle phase와 **획득한 자원의 기록**을 분리해 표현한다. pin별 부분 commit, PM reference, pinctrl 설치, block lease가 남은 상태를 잃지 않는다. 정지 확인 없이 소멸자가 모든 lease를 풀도록 바꾸지 않는다.

**필수 시험:** 별칭의 물리 자원 충돌, 오래된 generation 거부, 중간 pin handover 실패, PM 획득/반납 실패, pinctrl 복원 실패, rollback 재진입, 이중 release, 복구 가능한 경우의 capacity 회복과 불확실한 경우의 fault 유지.

**완료 기준:** 실패 위치마다 남은 자원이 설명 가능하고 다음 연산이 안전하게 거부되거나 복구된다. manager를 하나 더 만들지 않는다.

### R09 — Arduino SPI에서 facade/backend 경계를 검증한다

표준 Arduino SPI를 기본 파일럿으로 선택한다. 전송·라우트 개선과 연결하기 쉽기 때문이다. 실제 유지보수 요구가 Wire에 집중되어 있다면 Wire부터 시작해도 되지만 두 개를 동시에 전면 개편하지 않는다.

facade는 Arduino 설정·반환값·transaction 의미를 담당하고, backend는 Zephyr device·pinctrl·PM·driver 오류를 담당한다. route와 lease는 기존 공통 수명주기를 사용한다. SPI frequency 정책은 nRF54 backend 안에 두고 불필요한 가상 class 계층을 만들지 않는다.

**완료 기준:** `begin/end`, transaction, CS·mode·bit order·속도 처리와 재초기화가 유지된다. 이후 Wire는 repeated-start/NACK/timeout, HardwareSerial은 console/runtime 분리와 flush 의미를 같은 방식으로 검증한다. flush는 소프트웨어 queue 비움, driver 전송 완료, 마지막 stop bit 완료를 구분해 관찰한다.

### R10 — Serial Fabric orchestration과 동시 호출 정책을 정리한다

이미 분리된 UARTE/SPIM/SPIS/TWIM/TWIS adapter를 다시 통합하지 않는다. 공통 registry, instance lookup, IRQ 연결, handover/recovery, 요청 상태와 DMA 소유권을 필요한 경계로 분리한다.

먼저 같은 handle의 연산을 어떻게 직렬화하는지 확정한다. 전역 자원 lock과 block/operation 상태 보호의 순서를 문서화하고, 측정된 정지 지연에 따라 lock 범위를 줄인다. lock을 줄였다는 사실 자체를 성능 개선으로 보고하지 않는다.

**완료 기준:** submit/deactivate/cancel 교차와 다른 block의 동시 진행이 검증된다. 기존 Arduino device와 직접 nrfx backend의 소유권 관계가 설명 가능하다. **현재 Kconfig 상호 배제는 유지**하며, 같은 block을 동시에 소유하지 못하게 보장하는 별도 설계·시험 없이는 해제하지 않는다.

### R11 — Analog/Stream에 검증된 분리 방식을 적용한다

Analog는 SAADC와 PWM sequence, Stream은 PDM/I2S/QDEC backend를 분리한다. R03에서 수정한 동기화·stop 계약과 각 기능의 buffer/sample/frame 의미를 유지한다. lifecycle·큐·DMA 검증 중 같은 의미만 공통화한다.

**완료 기준:** 연속 데이터 패턴, double buffer 경계, underrun/overflow, 취소·정지·재시작, 복합 부하가 기능별로 검증된다. 각 기능의 실시간 제약을 공통 API에 맞추기 위해 약화하지 않는다.

### R12 — BLE와 Storage를 후속 작업 범위에 포함한다

BLE는 GAP의 connection/advertising/scanning, GATT의 database/server/client, Security의 pairing/bond/인증 요청과 profile 구현을 분리한다. 현재 connection 참조·generation·stale event 거부와 고정 큐 정책을 보존한다.

**필수 시험:** disconnect 후 늦은 callback, pairing 실패, bond 저장 실패, 재연결, queue overflow, callback에서 재진입하는 API. EEPROM/LittleFS는 저장 실패·손상 복구·재부팅 후 내용 유지까지 확인한다.

기능 metadata를 더 세분화할 때는 실제 flash/RAM 절감과 설치 예제 호환성을 측정한다. 이름만 분리하거나 기능을 끈 결과를 리팩토링에 의한 메모리 개선으로 계산하지 않는다.

## 6. 도구·설정·검증 운영 정리

### R13 — package·정책 데이터·문서 생성은 검증 가능한 범위부터 적용한다

- 패키저의 입력 해석·생성·검증을 나누되 공개 entrypoint와 과거 release 재현 경로를 보존한다. legacy 파일의 폴더 이동은 자체 목적이 아니다.
- DTS는 하드웨어 사실, board/product 정책은 허용 route·지원 수준·검증 상태를 담당한다. 실제로 중복된 값부터 원본을 지정한다.
- 기존 feature·inventory·readiness schema를 최대한 활용한다. schema를 하나의 거대한 문서로 합치지 않는다.
- 생성기는 deterministic하게 동작하고, 생성 후 diff가 남는지 CI에서 확인한다. 생성기와 동일 원본에서 만든 기대값만 비교하지 말고 독립적인 계약·부정 사례·실기 증거도 둔다.
- 기존 raw evidence는 보존한다. 이후 큰 원시 로그는 불변 보관 위치·hash·commit·fixture·판정 index와 함께 관리한다. 만료되는 CI artifact만 남기지 않는다.
- 현재 테스트 위치와 runner를 먼저 유지한다. domain tag/metadata를 추가한 뒤 필요할 때 점진적으로 정리한다.

### 변경 종류별로 필요한 검증

| 변경 | 최소한 확인할 것 | 완료로 오인하면 안 되는 것 |
| --- | --- | --- |
| 문서만 변경 | UTF-8·링크·용어·기준 commit·실제 상태 | 문서 검사 PASS가 기술 검증 PASS는 아님 |
| CMake/Kconfig/source 목록 | resolved config·target 소속·선택/비선택 profile build·package | configure 성공이나 문자열 일치만으로 완료 아님 |
| 전송/ISR/lifecycle | 동작·failure injection·target·영향 HIL | Host mock이나 no-op mutex로 물리 동시성 PASS 아님 |
| 파일 분할 | 기존 계약·동작 회귀·source 포함·flash/RAM 영향 | 줄 수 감소만으로 성공 아님 |
| builder/package | CLI/schema·고정 Python 격리 실행·실제 설치본·대표 전체 build | 개발 checkout에서 import 성공만으로 완료 아님 |
| BLE/저장장치 | 데이터·연결 수명주기·오류 복구·재시작 후 지속성 | 기본 예제 실행만으로 모든 오류 경로 PASS 아님 |

현재 진입점은 `tools/ci/run_m12_gate.py`의 `host`, `contract`, `inventory`, `docs`, `package`, `examples`다. 예제 발견 gate는 예제 compile이 아니다. 형식 검사는 기존 `tools/format/README.md`의 고정 formatter 절차를 따른다. CI 실행 환경과 일반 로컬 Python 환경은 구분해 기록한다.

문자열 기반 계약 검사는 공개 이름·설정·금지 패턴 보호에 남긴다. 동작을 주장하는 시험은 가능한 한 실제 구현과 관측 결과를 사용한다. 순수 host 로직에는 사용 가능한 환경에서 sanitizer·실제 thread 동기화·결정적인 interleaving 시험을 추가한다. sanitizer를 실행하지 않은 환경은 실행했다고 표시하지 않는다.

### CI와 HIL 운영

PR에는 변경 영역의 빠른 계약·동작 시험과 대표 target build를 연결한다. Kconfig/CMake/lock/shared resource 변경은 더 넓은 matrix를 요구한다. 통합·RC에서는 전체 재현 빌드와 설치 검증을 수행한다. scheduled HIL은 fixture 가용성과 실행 범위가 정해진 뒤 별도 설정한다.

HIL 결과는 최소한 commit·board/SDK·ELF hash·fixture·probe identity·실행 시간·원시 로그 hash·판정·실패 분류를 연결한다. 인프라 실패도 모든 시도를 보존하고, 장치 상태가 불명확한 실패를 자동 반복하여 PASS로 덮지 않는다. 재시도 횟수·전제 상태·복구 절차를 명시한다.

## 7. 개선 여부를 판단할 지표

| 지표 | 측정 방법 | 판단 기준 |
| --- | --- | --- |
| 정확성 | stale/overflow/timeout/partial rollback 회귀 | 알려진 실패가 차단되고 새 경계 실패가 없음 |
| flash/RAM | 같은 SDK·profile·기능의 ELF/map 비교 | 변화 이유를 설명. 의도 없는 증가는 원인 조사 |
| build 시간 | cold/no-change/sketch-edit/profile-change를 분리 | 반복 측정으로 노이즈 구분, configure/build 시간 따로 기록 |
| stop 및 block 간 지연 | 같은 fixture에서 최대값·분포·timeout 수 | 사용자 요구와 기존 기준에 비춰 판단 |
| 자원 안정성 | 반복 start/stop·오류 주입 후 lease/slot/queue 상태 | 정상 회복 또는 명시적인 fault 보존 |
| 설치 호환성 | package 설치본의 IDE/CLI·예제·업로드 경로 | checkout 의존 없이 기존 계약 유지 |
| 유지보수성 | 기능 변경 시 수정되는 책임 영역·시험 경계 | 무관한 backend 수정과 숨은 전역 의존 감소 |

지금 임의로 ‘2배 빠르게’, ‘RAM 20% 감소’, ‘모든 파일 400줄 이하’를 성공 기준으로 정하지 않는다. 기준 측정과 실제 제품 요구를 보고 수치 목표를 정한다.

## 8. PR 완료 기준과 되돌리기

모든 구현 PR에는 문제와 결과 동작, 공개 계약 영향, 실행한 검사와 NOT RUN, 메모리·시간 영향이 필요한지, 관련 T 항목과 증거 링크를 기록한다. 수정과 무관한 포맷·이름·폴더 변경을 섞지 않는다.

1. 동작 결함은 의미 있는 회귀 시험으로 보호한다. 구현의 문자열 모양만 복제한 시험으로 끝내지 않는다.
2. 구조 분할은 동작 변경을 분리하고 새 translation unit의 init 순서·IRQ symbol·link 의존성을 확인한다.
3. 영향을 받는 source·manifest·package 목록이 일치한다. 공개 entrypoint와 설치 경로가 유지된다.
4. 종료/rollback 실패는 오류와 남은 자원 상태를 숨기지 않는다.
5. 관련 검사가 통과하면 새로운 근거 없이 같은 검사를 무한 반복하지 않는다. 남은 target/HIL/RC 항목은 별도로 진행한다.
6. 회귀가 발견되면 해당 작은 변경을 되돌리거나 수정한다. 전체 재작성을 위한 장기 분기에서 여러 문제를 함께 고치지 않는다.

### R14 — RC를 다시 고정하고 기존 release gate로 검증한다

R00~R13을 확정한 commit과 package identity로 current-source T11·T12~T15와 T16~T18 사용자용 통합을 연결한다. 그 입력으로 RC를 고정해 target·재현성·설치 수명주기를 검증한다. 현재 readiness의 미해결 항목을 실제 증거로 해소하고, 필요한 사용자 최종 확인과 공개 절차는 기존 TODO의 T19~T24에 따라 진행한다. 리팩토링 PR 병합만으로 release 준비가 끝났다고 판단하지 않는다.

## 9. 바로 다음 작업의 구체적인 산출물

다음 구현 차례에는 **R00과 R01을 먼저 구체화**하는 것이 좋다. 결과물은 아래 네 가지면 충분하다.

1. 실제 착수 commit과 기존 검사·실기 상태를 연결한 짧은 기준선 기록.
2. SPIM/SPIS/TWIM/TWIS가 현재 어느 target에 등록되는지 보여주는 재현 시험.
3. 네 source를 명시적인 Core target으로 모으는 최소 변경.
4. 유효한 personality profile의 실제 빌드·소속 target·최종 참조 심볼 확인 결과.

그다음 R02~R13을 번호 순서와 의존성에 따라 작은 변경으로 이어간다. 매 작업의 software gate를 닫되 최종 외부 결선 PASS는 R13 뒤 current-source T11부터 시작한다. 이 과정에서 기존 공개 자산·파일 경로·활성 TODO를 보존하면 큰 구조 개편도 검증 가능한 상태로 진행할 수 있다.

## 10. 참고 문서에서 누락되거나 구체화가 부족했던 항목의 보완

2026-09-06 추가. 다음은 초기 문서에서 충분히 연결하지 못한 원문 제안이다. 제외한 작업으로 취급하지 않는다. 기존 R 작업에 연결하며, 아직 실행하거나 도입 완료한 상태는 아니다.

### 10.1 Kconfig와 CMake의 구조 분할 — 원문 §16, R13 연결

R01의 source 등록 결함 수정과 별도로 구조 분할을 수행한다. Kconfig는 core/serial/analog/event/stream/BLE/storage/system의 실제 정의와 의존성을 확인한 뒤 기능별 파일로 나누고 최상위에서 포함한다. CMake는 source 선택, 생성물, build identity, provenance의 책임을 분리한다. 원문의 예시 파일명은 후보이며 실제 중복·호출 scope를 보고 확정한다.

기존 CONFIG 이름, default, depends/select 관계, menu 의미를 유지한다. CMake 함수·macro·include의 변수 scope가 바뀌지 않도록 검증한다. 유효한 profile의 resolved .config와 target source 목록을 전후 비교하고 target build를 수행한다. symbol rename과 기능 정책 변경은 같은 PR에 넣지 않는다.

### 10.2 공개 API·ABI·폐기 정책 — 원문 §12, R00/R09/R10 연결

표준 Arduino API와 후보 Fabric API의 지원 상태를 구분해 기록한다. 소스 호환성, 공개 struct/enum layout, binary ABI를 각각 어디까지 약속하는지 명시한다. 공개 enum 값은 의미 없이 재배치하지 않는다.

실제로 API를 폐기할 때는 migration과 forwarding/alias를 제공하고, 안정 API에는 최소 한 minor release 동안의 호환 기간을 기본 제안으로 둔다. 아직 안정화되지 않은 Fabric의 experimental namespace는 조건부 검토한다. 현재 namespace를 변경하지 않은 상태에서 이 정책을 이미 적용했다고 표시하지 않는다.

public header의 Zephyr/nrfx 결합을 줄이는 목표를 유지한다. 기존 노출이 있으면 소비자를 확인해 단계적으로 감춘다. public header 단독 compile과 실제 지원 include 조합을 확인한다.

### 10.3 정적 분석 도구와 적용 범위 — 원문 §19, R06/R07 이후 연결

| 도구 후보 | 최초 적용 범위 | 도입 완료 기준 |
| --- | --- | --- |
| 기존 clang-format | 현재 first-party 대상 | 기존 style gate 유지 |
| clang-tidy | 추출한 순수 domain 및 작은 adapter 경계 | 고정 toolchain 설정에서 유효한 규칙 선정, 실제 결함과 억제 사유 기록 |
| Ruff | 분리한 first-party Python 모듈 | 규칙·버전 고정, 기존 출력/동작 변경과 포맷 변경 분리 |
| mypy 또는 pyright | builder 내부 모델·순수 모듈 | 둘 중 하나를 평가 후 선택, 필수 필드·오류 경계 타입 검사 |
| 제한적인 CMake lint | 분리한 first-party CMake | Zephyr 전용 관례를 오탐 처리하지 않는 규칙 |

SDK·Zephyr·third-party 전체에 일괄 -Werror를 적용하지 않는다. 도구 도입으로 모든 기존 파일을 한 번에 재작성하지 않는다. 실제 실행 환경에서 지원하는 버전과 설정을 확인해 고정한다.

### 10.4 PR Fast/Full·Main·Nightly·Release와 pairwise — 원문 §19/§24

| 계층 | 구체적인 작업 |
| --- | --- |
| PR Fast | 영향받는 Host/Python, style, generated drift, 대표 target build |
| PR Full | 영향받는 Arduino 예제·Zephyr integration·personality 단독 build |
| Main/통합 | 전체 예제·package lifecycle와 유효한 pairwise feature matrix |
| Nightly 후보 | 넓은 조합·장시간 시험·지원 환경의 sanitizer·조건이 갖춰진 HIL |
| Release | clean install·실기 upload·hash·license/SBOM/provenance·최종 readiness |

pairwise는 모든 기능의 무조건적인 동시 활성화가 아니다. Kconfig와 물리 자원 제약을 만족하는 쌍을 생성하고, 금지된 조합은 명시적 거부 시험으로 따로 확인한다. matrix와 필요한 hardware fixture를 기록한다. scheduled HIL은 별도 실행 범위가 정해지기 전 자동 생성하지 않는다.

### 10.5 ADR과 문서 역할 — 원문 §21, R00/R03/R08/R13 연결

다음 결정을 ADR 또는 기존 동등한 결정 기록으로 연결한다. 이미 관련 계약이 있으면 그대로 연결하고 중복 원본을 만들지 않는다.

- Loader 없이 전체 Zephyr firmware를 빌드하는 이유.
- 고정 메모리 자원 관리자·lease·generation을 유지하는 이유.
- ISR와 일반 스레드의 상태 소유권 및 stop 신호 처리.
- DTS의 물리 사실과 제품 정책의 원본 구분.
- builder protocol·제품 버전·각 schema의 독립 수명주기.
- Fabric 파일 경계와 공개 API 유지 방식.

설계·계약·runbook·생성 문서·release 기록의 역할을 구분한다. 디렉터리 이동 시 incoming link와 현재 TODO를 함께 확인한다. Issues/Projects 이전을 위해 활성 TODO를 지금 제거하지 않는다.

### 10.6 빌더의 세부 외부 계약과 기반 모듈 — 원문 §13

R06의 범위에 errors/models, path 처리, strict JSON, size report 책임을 명시적으로 포함한다. 이미 있는 helper는 재사용하고 새로운 범용 parser나 error 체계를 중복 도입하지 않는다.

회귀 목록에 CLI argument, exit code, 오류 marker, 메시지 prefix, IDE가 읽는 stdout/stderr, artifact filename, manifest JSON schema, cache directory layout, source recording 순서, lock timeout, stale lock 처리, atomic write, transactional publish를 각각 등록한다.

순수 출력은 golden 비교를 적용하되 시간·절대 경로 같은 환경 의존 필드를 어떤 규칙으로 비교하는지 명시한다. strict JSON은 현재 입력 거부 계약을 고정한다. publish 중간 실패는 이전 정상 산출물을 보존하는지 확인하고, 성공한 부분 파일만 남은 상태를 정상 완료로 처리하지 않는다.

### 10.7 패키저의 license·SBOM·provenance 책임 — 원문 §14

R13의 입력/생성/검증 분리에 package model, manifest, archive, Boards Manager index, hash, license 수집·검증, SBOM, provenance의 책임을 각각 포함한다. 별도 Python 파일 개수는 실제 결합도를 보고 정한다.

생성 성공과 검증 성공을 구분한다. archive에 들어간 실제 파일·license·hash와 SBOM/provenance가 일치하는지 확인한다. 기존 공개 자산은 다시 생성하여 덮어쓰지 않는다. 현재 스크립트 진입점과 경로 의존을 보존하며 legacy 이동은 필요성과 호환 wrapper가 확인된 경우에만 한다.

### 10.8 기존 파일에서 신규 파일로의 대응표 — 원문 §6/§9/§10/§13/§14/§16/§17

각 분할 PR 전에 다음 대응표를 작성한다. 원문의 전체 디렉터리 트리를 그대로 도입하는 대신, 변경을 실제로 리뷰할 수 있는 단위까지 구체화한다.

| 기록할 항목 | 필요한 내용 |
| --- | --- |
| 기존 구현 | source·함수·class·context의 현재 위치 |
| 신규 책임 | 옮길 모듈과 맡길 일, 유지할 기존 wrapper |
| 상태 소유권 | mutex/spinlock·generation·정적 context의 소유 위치 |
| 연결 방식 | public/internal include, factory/accessor, IRQ symbol |
| 빌드·배포 | CMake source, feature 선택, package 포함 목록 |
| 동작 검증 | 그대로 유지할 시험, 추가할 경계·실기 시험 |

factory/registry/backend/common 파일명은 이 표에서 확정한다. 분할 전후 public entrypoint와 private 초기화 순서를 확인한다. 단순히 ‘나중에 파일명을 정한다’는 이유로 대응표 작성을 생략하지 않는다.

### 10.9 공통 primitive의 개별 검토 — 원문 §11.3

FixedRingBuffer, IsrMailbox, DmaBufferTracker, MutexGuard, SpinLockGuard, Timeout, LeaseTransaction, FaultLatch, DiagnosticSnapshot을 후보 목록으로 유지한다. 기존 중복 구현과 사용처를 찾아 현재 overflow 정책·callback 문맥·buffer ownership이 같은 항목부터 추출한다. 서로 다른 peripheral lifecycle을 거대한 template로 통합하지 않는다는 원문 원칙에 동의한다.

R02/R03에서 필요한 작은 primitive는 먼저 추출할 수 있다. 모든 공통 도구를 미리 완성해야 Event 분할을 시작할 수 있다는 의존성은 만들지 않는다.

### 10.10 기준선·호환성 시험의 누락 보강 — 원문 §18.1/§18.2

R00의 기준선에 모든 기존 예제의 compile 상태, 공개 header compile, 전역 symbol, ELF/flash/RAM, artifact filename, package index 구조, HIL UART marker를 명시적으로 연결한다. 환경이나 실기 전제가 없어 실행하지 못한 항목은 이유와 NOT RUN을 기록한다.

외부 라이브러리 호환성은 실제 지원 대상에서 대표군을 선택하고 사용 버전을 고정한다. 전체 외부 Arduino 생태계 호환을 검증했다는 표현은 하지 않는다. 기존 milestone·fixture·capability를 metadata로 남기며 테스트 디렉터리 이동은 runner·CI 참조를 유지할 수 있을 때 진행한다.

### 10.11 HIL 실패 분류와 측정값 — 원문 §20

현재 결과 schema와 비교해 DUT_FAILURE, FLASH_FAILURE, PROBE_DISCONNECTED, UART_TIMEOUT, FIXTURE_FAILURE, RUNNER_INFRA_FAILURE, CONTRACT_MISMATCH 같은 분류의 대응 관계를 명시한다. enum 이름 자체를 현재 schema에 즉시 강제하지 않는다.

기능별로 요청/실제 clock, 전송 byte 수, CRC 등 판정에 필요한 측정값을 추가한다. UART marker와 JSON 판정이 일치하는지 확인한다. 재시도는 인프라 분류 외에도 장치 변경 여부·복구 상태를 확인하고 모든 시도를 보존한다.

### 10.12 PR·브랜치·완료 체크리스트 — 원문 §22~§27

원문의 19개 PR 순서를 그대로 복사하지 않고 R00~R14에 추가 발견 결함을 포함해 재배치했다. 브랜치 이름은 작업의 실제 범위가 정해질 때 정한다. 브랜치 예시를 채택하지 않은 것은 작업 내용의 제외가 아니다.

각 PR의 체크리스트에는 구조 경계, ISR/lock, 자원·DMA, public API, 내부 오류의 조기 변환 여부, CLI/publish, Host/target/HIL, generated drift를 넣는다. 단순 source 변경 때문에 cache key가 달라지는 경우에 schema bump를 강제하는 원문 체크 항목은 적용하지 않는다.
