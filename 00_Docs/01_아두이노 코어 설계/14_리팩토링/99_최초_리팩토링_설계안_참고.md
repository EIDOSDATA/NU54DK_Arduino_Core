# NU54DK Arduino Core 전체 리팩토링 및 파일 분할 계획

> 대상 저장소: [EIDOSDATA/NU54DK_Arduino_Core](https://github.com/EIDOSDATA/NU54DK_Arduino_Core)  
> 분석 기준: 2026-09-05 당시 저장소 구조 및 `main` 브랜치 정적 분석  
> 문서 목적: 기존 동작과 호환성을 보존하면서 코드 구조, 동시성, 빌드 도구, 패키징, 검증 체계를 단계적으로 개선하기 위한 실행 계획

---

## 1. 문서 요약

이 저장소는 단순한 Arduino Core가 아니다. 다음 세 가지 제품이 하나의 저장소 안에 결합되어 있다.

1. **Arduino 사용자 API 계층**
   - `Arduino.h`
   - `Serial`, `Serial1`
   - `Wire`
   - `SPI`
   - GPIO, ADC, PWM, tone 등

2. **NU54DK/nRF54L15 런타임 계층**
   - Zephyr 및 NCS
   - nrfx 드라이버
   - Devicetree와 pinctrl
   - PM, IRQ, DMA
   - 리소스 소유권과 peripheral routing
   - Analog/Event/Serial/Stream Fabric

3. **빌드·배포·검증 도구 계층**
   - `nu54-builder`
   - Arduino IDE와 Zephyr 빌드 연결
   - NCS/toolchain lock 및 무결성 검사
   - Boards Manager 패키징
   - 계약 JSON 및 검증 스크립트
   - CI와 실제 보드 HIL

현재 저장소의 가장 큰 문제는 기능 부족이 아니라, **서로 다른 책임과 수명주기를 가진 코드가 큰 파일과 큰 모듈 안에 함께 들어 있다는 점**이다.

따라서 권장 방향은 전체 재작성보다 다음 순서의 **점진적 리팩토링**이다.

1. 현재 외부 동작을 characterization test로 고정한다.
2. CMake 및 동시성 위험 요소를 먼저 수정한다.
3. 공통 리소스, 상태 머신, IRQ 전달 primitive를 추출한다.
4. 대형 Fabric 파일을 주변장치 단위로 분할한다.
5. `Wire`, `SPI`, `HardwareSerial`을 Arduino facade와 backend로 분리한다.
6. Python 빌더와 패키저를 패키지 구조로 분할한다.
7. DTS와 제품 정책에서 생성 코드를 만드는 단일 진실 공급원 체계를 구축한다.

핵심 원칙은 다음과 같다.

> **현재의 엄격한 빌드·검증·리소스 안전성은 유지하고, Arduino API, domain 상태 머신, Zephyr adapter, nRF54L15 정책, NU54DK 보드 데이터를 명확히 분리한다.**

## 2. 리팩토링 목표

### 2.1 주요 목표

- 기존 Arduino API 소스 호환성 유지
- 기존 전역 객체와 심볼 유지
  - `Serial`
  - `Serial1`
  - `Wire`
  - `SPI`
- ISR과 일반 스레드 간 데이터 레이스 제거
- 주변장치별 상태 머신과 수명주기 명확화
- rollback 가능한 peripheral route 구조 보존 및 단순화
- 동적 할당 없이 결정적 메모리 사용 유지
- 대형 `.cpp` 및 Python 단일 파일 분할
- 빌더의 CLI, exit code, manifest, cache 계약 유지
- DTS, 정책 파일, C++, 문서 사이의 중복 하드코딩 제거
- host unit test와 fault injection 확대
- CI/HIL 실패 원인 분류 및 증적 개선
- 패키징과 릴리스 재현성 보존

### 2.2 비목표

초기 리팩토링에서는 다음을 목표로 하지 않는다.

- 전체 코드 재작성
- Arduino 공개 API의 대규모 변경
- 동적 할당 기반 객체 모델 전환
- C++ exception의 MCU runtime 도입
- 아직 요구되지 않은 범용 멀티-MCU HAL 설계
- Zephyr/NCS 계층을 감추기 위한 과도한 추상화
- 파일 이동과 하드웨어 동작 변경을 한 PR에서 동시에 수행

## 3. 현재 구조에 대한 평가

### 3.1 강점

현재 저장소는 다음 부분이 이미 강하다.

- NCS, Zephyr, 도구 및 패키지 무결성을 엄격하게 검사한다.
- Arduino IDE와 Zephyr/NCS 빌드를 연결하는 독자적인 빌드 어댑터가 있다.
- 고정 크기 테이블 기반 리소스 소유권 관리가 있다.
- peripheral route에 reserve, commit, rollback 개념이 있다.
- 동적 할당을 피하고 결정적 메모리 모델을 유지한다.
- 계약 JSON, 검증 스크립트, CI, HIL 증적을 함께 관리한다.
- Boards Manager 패키지와 릴리스 증적 재현성을 중요하게 다룬다.

이 강점은 리팩토링 과정에서 제거하거나 약화시키면 안 된다.

### 3.2 핵심 문제

- 공개 Arduino API와 하드웨어 제어 코드가 같은 파일에 존재한다.
- 서로 다른 주변장치가 하나의 Fabric 구현 파일에 존재한다.
- IRQ 콜백과 control-plane 상태 갱신이 명확히 분리되지 않았다.
- 일부 대형 파일이 factory, registry, context, IRQ, PM, DMA, diagnostics를 모두 소유한다.
- Python 빌더와 패키저가 지나치게 큰 단일 파일이다.
- 하드웨어 사실과 제품 정책이 DTS, C++, Python, JSON, 문서에 반복된다.
- 버전 종류가 제품 버전, 빌더 버전, 스키마 버전 등으로 명확히 분리되어 있지 않다.

## 5. 즉시 먼저 처리할 P0 항목

대형 파일 분할 전에 다음 항목을 먼저 고정하거나 수정해야 한다.

### 5.1 Zephyr CMake source 등록 순서 점검

`zephyr_library_sources()`와 `zephyr_library_named()` 호출 순서가 기능 조합에 따라 현재 library context에 의존하지 않도록 정리해야 한다.

권장 형태:

```cmake
set(NUCODE_ARDUINO_CORE_SOURCES
    ${CMAKE_CURRENT_LIST_DIR}/../cores/arduino/Arduino.cpp
    ${CMAKE_CURRENT_LIST_DIR}/../cores/arduino/HardwareSerial.cpp
)

if(CONFIG_NUCODE_SERIAL_FABRIC_SPIM)
    list(APPEND NUCODE_ARDUINO_CORE_SOURCES
        ${CMAKE_CURRENT_LIST_DIR}/../cores/arduino/internal/SpimFabric.cpp
    )
endif()

if(CONFIG_NUCODE_SERIAL_FABRIC_TWIM)
    list(APPEND NUCODE_ARDUINO_CORE_SOURCES
        ${CMAKE_CURRENT_LIST_DIR}/../cores/arduino/internal/TwimFabric.cpp
    )
endif()

zephyr_library_named(nucode_arduino_core)
zephyr_library_sources(${NUCODE_ARDUINO_CORE_SOURCES})
```

필수 테스트:

- SPIM만 활성화
- SPIS만 활성화
- TWIM만 활성화
- TWIS만 활성화
- 여러 personality 조합
- 모든 Fabric personality 비활성화
- 최종 ELF 또는 map에서 예상 심볼 존재 확인

### 5.2 IRQ와 일반 스레드 간 데이터 레이스 제거

다음과 같은 일반 필드를 IRQ 또는 nrfx callback과 control thread가 동시에 수정하는 구조는 제거해야 한다.

- `last_result`
- `last_driver_error`
- `first_callback`
- `ignore_initial_request`
- stop 완료 플래그
- 일반 `volatile bool`

`volatile`은 스레드 동기화 수단이 아니다. mutex를 조회 측에서만 잡더라도 ISR이 같은 mutex를 잡지 않으면 상호 배제가 되지 않는다.

권장 구조:

```text
IRQ / nrfx callback
    ↓
고정 크기 ISR event ring 또는 k_msgq
    ↓
atomic overflow/error flag
    ↓
k_sem 또는 k_poll_signal
    ↓
control thread가 이벤트 소비
    ↓
mutex 아래 lifecycle/diagnostics 상태 갱신
```

예시:

```cpp
struct I2sRuntimeSync {
    struct k_sem stopped;
    atomic_t event_overflow;
    atomic_t irq_error;
};

static void i2sCallback(/* ... */)
{
    if (eventIsStopped()) {
        k_sem_give(&runtimeSync.stopped);
    }

    if (!pushIsrEvent(event)) {
        atomic_set(&runtimeSync.event_overflow, 1);
    }
}
```

제어 스레드는 전역 mutex를 잡은 상태로 busy-wait하지 않는다.

```cpp
lockState();
transitionToStopping();
unlockState();

const int rc = k_sem_take(&runtimeSync.stopped, timeout);

lockState();
completeOrFaultStop(rc);
unlockState();
```

프로젝트 차원의 규칙:

> ISR은 일반 control-plane 상태를 직접 수정하지 않는다. ISR에서 직접 수정 가능한 것은 atomic 값, 고정 크기 event queue, semaphore 또는 signal로 제한한다.

## 6. 목표 아키텍처

### 6.1 의존성 방향

```text
Arduino API facade
        ↓
순수 C++ domain/service
        ↓
Zephyr adapter
        ↓
nRF54L15 SoC policy
        ↓
NU54DK generated board data
```

반대 방향의 의존은 허용하지 않는 것이 좋다.

예:

- public Arduino header가 `nrfx_*` 타입을 노출하지 않는다.
- public Arduino header가 `struct device`를 노출하지 않는다.
- public Arduino header가 `k_mutex`를 알지 않는다.
- public Arduino header가 DTS macro를 직접 사용하지 않는다.

### 6.2 권장 디렉터리 구조

```text
cores/arduino/
├─ Arduino.h
├─ Wire.h
├─ SPI.h
├─ HardwareSerial.h
│
├─ api/
│  ├─ gpio/
│  ├─ serial/
│  ├─ wire/
│  ├─ spi/
│  └─ timing/
│
├─ domain/
│  ├─ lifecycle/
│  ├─ resources/
│  ├─ routing/
│  ├─ dma/
│  ├─ diagnostics/
│  └─ buffers/
│
├─ platform/
│  ├─ zephyr/
│  │  ├─ kernel/
│  │  ├─ device/
│  │  ├─ pm/
│  │  ├─ pinctrl/
│  │  └─ drivers/
│  └─ nrf54l15/
│     ├─ serial/
│     ├─ analog/
│     ├─ event/
│     ├─ stream/
│     └─ errata/
│
└─ internal/
   └─ concurrency/

variants/nu54dk/
├─ policy/
├─ generated/
└─ pins/
```

모든 디렉터리를 한 번에 이동하지 말고, 새 코드를 이 구조에 배치하면서 기존 경로에는 forwarding header 또는 wrapper를 유지한다.

## 7. 파일 분할 판단 기준

파일 크기만으로 분할 여부를 결정하지 않는다. 다음 조건을 함께 본다.

### 7.1 LOC 경고 기준

```text
0~400 LOC
    일반적으로 허용

400~700 LOC
    책임이 둘 이상인지 검토

700~1,000 LOC
    적극적인 분할 후보

1,000 LOC 이상
    generated code 또는 단일 lookup table이 아니라면 원칙적으로 분할

1,500 LOC 이상
    즉시 리팩토링 대상
```

### 7.2 책임 기준

다음 중 두세 개 이상에 해당하면 분할한다.

- 한 `.cpp`에 public class 구현이 둘 이상 존재
- 한 `.cpp`에 서로 다른 하드웨어 peripheral 종류가 둘 이상 존재
- 서로 독립적인 IRQ handler가 여러 개 존재
- 서로 독립적인 context 배열이 여러 개 존재
- 하나의 전역 mutex가 관련 없는 peripheral을 모두 잠금
- factory와 실제 driver 구현이 함께 존재
- Arduino 반환값 변환과 저수준 리소스 소유권이 함께 존재
- GPIO snapshot, PM, pinctrl, driver lifecycle이 한 함수에 함께 존재
- 테스트하려면 전체 Zephyr runtime을 띄워야 함

### 7.3 분할하지 않아도 되는 경우

- 단일 하드웨어 블록만 처리
- 상태 머신이 하나
- 변경 이유가 하나
- public class가 하나
- 대부분이 register table 또는 정적 mapping
- 테스트 경계가 이미 명확함

## 8. 파일별 분할 우선순위

> LOC는 분석 시점의 근사값이다. 실제 착수 전 `cloc` 또는 동일한 스크립트로 다시 측정한다.

| 파일 | 근사 크기 | 판정 | 핵심 이유 |
|---|---:|---|---|
| `StreamFabric.cpp` | 약 1,550 LOC | 반드시 분할 | PDM, I2S, QDEC, IRQ, DMA, factory가 한 파일에 존재 |

## 11. 공통 기반 리팩토링

## 11.1 `IoResourceManager`

현재의 fixed-size resource ownership, generation, reserve/commit/rollback 개념은 유지할 가치가 크다.

다음처럼 분리한다.

```text
ResourceTable
    순수 C++ 데이터 구조

OwnershipEngine
    reserve, commit, rollback, release 규칙

SynchronizedResourceManager
    Zephyr mutex wrapper

ResourceRegistry
    생성된 board resource 목록
```

host에서 검증할 속성:

- 동일 exclusive resource에 두 committed owner가 존재하지 않음
- stale generation token이 새 lease를 release하지 못함
- rollback 이후 상태가 reserve 이전과 동일함
- commit은 한 번만 성공함
- release 이후 capacity가 복구됨
- 겹치는 DMA range를 동시에 확보할 수 없음

RAII는 rollback 보조에 제한적으로 사용한다.

```cpp
auto lease = resourceManager.reserve(request);
if (!lease) {
    return Error::resource_busy;
}

RollbackGuard rollback{lease};

if (!configurePins()) {
    return Error::pin_config_failed;
}

if (!startDevice()) {
    return Error::driver_start_failed;
}

lease.commit();
rollback.dismiss();
```

정상 release는 실패를 관찰할 수 있도록 명시적으로 수행하는 편이 좋다.

## 17. 안전한 파일 분할 방법

### 17.1 첫 분할 PR에서 하지 않을 것

`StreamFabric.cpp`를 나누면서 다음을 동시에 하지 않는다.

- mutex 구조 변경
- busy-wait 제거
- event queue 교체
- DMA lease 변경
- 오류 코드 변경
- 공개 API 변경
- lifecycle 의미 변경

첫 PR에서는 다음만 수행한다.

- 함수 이동
- private context 이동
- include 변경
- CMake source 추가
- namespace 유지
- public symbol 유지
- 동일 테스트 결과 확인

### 17.2 전역 `extern` 남발 금지

나쁜 방식:

```cpp
extern Context g_contexts[4];
extern struct k_mutex g_mutex;
```

권장 방식:

```cpp
PdmRuntime &pdmRuntime(std::uint8_t instance) noexcept;
I2sRuntime &i2sRuntime() noexcept;
QdecRuntime &qdecRuntime(std::uint8_t instance) noexcept;
```

또는 하나의 private runtime accessor를 사용한다.

### 17.3 public header 유지

구현 `.cpp`를 여러 translation unit으로 나누더라도 사용자 include는 그대로 유지할 수 있다.

```cpp
#include <nucode/StreamFabric.h>

auto *pdm = streamFabric().pdm(20);
auto *i2s = streamFabric().i2s(20);
```

## 24. 리팩토링 완료 기준

다음 조건을 Definition of Done으로 사용한다.

### 동시성

- IRQ가 non-atomic control-plane 필드를 직접 수정하지 않음
- 비동기 완료를 `volatile` spin loop로 기다리는 코드가 없음
- 장시간 driver wait 동안 전역 Fabric mutex를 잡지 않음
- callback queue overflow 동작이 명시되고 테스트됨

### 리소스와 상태 머신

- 모든 lifecycle transition이 enum 또는 명시적 state로 표현됨
- rollback edge가 테스트됨
- stale generation token test 존재
- resource release 후 capacity 복구 검증
- DMA range 충돌 test 존재

### 파일 구조

- `EventFabric`, `AnalogFabric`, `StreamFabric`이 peripheral 단위로 분리됨
- `nu54_builder.py`가 package 구조로 분리됨
- `nu54_package.py`가 생성/검증 모듈로 분리됨
- Arduino facade가 Zephyr/nrfx 구현을 직접 소유하지 않음

### API 호환성

- `Wire`, `SPI`, `Serial`, `Serial1` 소스 호환성 유지
- 기존 include 경로 유지 또는 forwarding 제공
- 공개 header에서 Zephyr/nrfx 타입 미노출
- deprecated API migration 경로 제공

### 빌드 및 검증

- 모든 기존 예제 compile
- personality별 독립 build
- 대표 pairwise feature build
- generated drift check 통과
- 패키지 clean install 및 upload 통과
- flash/RAM 변화가 기준치를 넘으면 근거 기록
- HIL 결과에 board, revision, failure class 포함

### 도구 계약

- builder CLI 및 exit code golden test
- artifact schema version 명시
- cache schema version 명시
- transactional publish 유지
- 동일 입력에 재현 가능한 manifest와 package 생성

## 25. 하지 말아야 할 것

### 25.1 전체 재작성

현재 코드에는 실제 하드웨어에서 축적된 예외 처리와 복구 로직이 많다. 새 코드가 더 깔끔해 보여도 숨겨진 동작을 잃을 수 있다.

### 25.2 파일 이동과 기능 변경 혼합

한 PR에서 파일 이동, 상태 머신 수정, IRQ 모델 변경, 핀 정책 변경을 동시에 하면 HIL 회귀 원인을 추적하기 어렵다.

### 25.3 너무 이른 범용 HAL

두 번째 실제 보드 또는 MCU 요구사항이 나오기 전에 모든 MCU를 위한 추상 계층을 만들지 않는다.

### 25.4 동적 할당과 exception의 무분별한 도입

MCU runtime의 결정성 및 fixed-memory 방향과 충돌한다.

### 25.5 HIL만으로 검증

HIL은 최종 확인에 강하지만 모든 rollback과 race 경로를 빠르게 검증하기 어렵다. host unit test와 fault injection이 선행되어야 한다.

### 25.6 과도한 파일 세분화

하나의 상태 머신을 이해하려고 열 개의 파일을 오가야 하는 구조는 피한다. 파일 분할은 변경 이유와 테스트 경계를 기준으로 한다.

## 28. 최종 권고

이 프로젝트에서 가장 중요한 것은 파일을 단순히 작게 만드는 것이 아니다. 다음 경계를 코드 구조에 드러내는 것이 목적이다.

```text
Arduino 호환 API
≠ peripheral 상태 머신
≠ Zephyr driver 호출
≠ nRF54L15 SoC 정책
≠ NU54DK 보드 정책
≠ 빌드 어댑터
≠ 패키징 도구
```

대형 파일 중에서는 다음을 실제 분할 대상으로 확정하는 것이 좋다.

```text
반드시 분할
    EventFabric.cpp
    AnalogFabric.cpp
    StreamFabric.cpp
    nu54_builder.py
    nu54_package.py

강하게 권장
    SPI.cpp
    Wire.cpp

권장
    HardwareSerial.cpp
    SerialFabric.cpp

현재 유지
    SystemFabric.cpp
```

실제 실행 순서는 다음으로 정리한다.

1. characterization test로 현재 동작 고정
2. CMake source registration 정리
3. ISR과 control-plane 동기화 수정
4. 공통 fixed-memory primitive 추출
5. `EventFabric` 분할
6. `AnalogFabric` 분할
7. `StreamFabric` 분할
8. `SerialFabric` orchestration 분할
9. `Wire`, `SPI`, `HardwareSerial` facade/backend 분리
10. 빌더와 패키저 package화
11. DTS + product policy code generation 도입
12. CI/HIL 및 릴리스 증적 구조 고도화

이 순서를 따르면 기존 동작을 보호하면서도 대형 파일, 복잡한 상태 공유, 도구 단일 파일 문제를 단계적으로 제거할 수 있다.
