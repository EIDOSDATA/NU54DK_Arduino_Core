## 1. 사용 방법

03번 운영계획을 먼저 읽고, 아래 §2~§7을 작업 한 건당 복사해 작성한다. R02·R03처럼 범위가 큰 작업은 R02-a 등의 내부 하위 식별자를 사용할 수 있지만, 기존 F/R/T 연결을 유지한다.

계획 정비 단계에서는 리팩토링 source 변경을 실행하지 않는다. 이후 구현을 명시적으로 시작할 때도
해당 R 한 건의 범위와 기존 안전·승인 조건을 적용한다. 검증이 불가능한 항목은 완료 체크 대신
원인과 NOT RUN을 남긴다.

양식의 상태값은 설명용이다. 저장소의 기존 JSON schema에 새로운 enum을 강제로 추가하지 않는다. 실제 gate 결과를 기록할 때는 현재 runner가 사용하는 상태·실패 분류를 그대로 사용한다.

Fixture 301의 기능 기준은 `e2f045c1b4272d986d17456c5af051fe8af74f19`다. **위 표에는 각 R 작업을
실제로 시작한 checkout 값을 적는다.** 기능 기준 SHA를 이후 모든 작업의 기본값으로 복사하지 않는다.

기준 정보를 읽는 명령 예시는 아래와 같다. 실제 저장소 루트에서 실행하며, 오류가 발생하면 임의 경로로 대체하지 않고 원인을 기록한다. 이 명령은 checkout·branch·source를 바꾸지 않는다.

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short
git log -1 --format="%H%n%cI%n%s"
git submodule status --recursive
git ls-tree HEAD board_package/NU54DK_Zephyr_DTS
```

SDK·toolchain 값은 현재 프로젝트의 lock 및 실제 build 기록과 대조한다. 이 양식 작성을 위해 SDK를 update하거나 board submodule을 새 revision으로 이동하지 않는다.

source 변경이 없는 기록 작업에는 수정 전/후 비교가 적용되지 않을 수 있다. 해당 없음의 이유를 적는다. 이번 문서 생성으로 위 시험을 PASS 처리하지 않는다.

기존 software gate 진입점 예시는 다음과 같다. **현재 checkout에서 실제 지원 여부와 고정 실행 환경을 확인한 뒤, 영향 분석으로 필요한 것만 실행한다.** 이 목록이 target build/HIL/설치 검증을 대체하지 않는다. [P1]

```powershell
python tools/ci/run_m12_gate.py contract
python tools/ci/run_m12_gate.py inventory
python tools/ci/run_m12_gate.py docs
python tools/ci/run_m12_gate.py host
python tools/ci/run_m12_gate.py package
```

실행 전 필요한 도구·dependency가 없는 경우 임의 SDK로 바꾸지 않는다. `examples` gate의 discovery는 예제 compile이 아니다. 실제 target/HIL 명령은 해당 fixture와 profile의 기존 runbook에서 가져오고, 현재 session·UID·승인 조건을 확인해 별도 기록한다.
