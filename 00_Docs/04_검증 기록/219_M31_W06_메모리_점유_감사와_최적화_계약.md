# 219 — M31-W06 메모리 점유 감사와 최적화 계약

## 1. 판정

M31의 일부 Arduino BLE role image가 사용하는 RAM 84~97%는 Channel Sounding 또는
LE Audio 기능 자체의 정상 비용으로 판정하지 않는다. 현재 image에는 역할과 관계없는
Arduino peripheral runtime, 범용 GATT/L2CAP, advanced GAP와 고정 pool이 함께 링크된다.
이 상태에서 W06 자원 예산을 PASS로 닫지 않는다.

이 기록은 최적화 구현 완료 기록이 아니다. **2026-09-21 후속 사용자 결정**에 따라 문서를
`main`에 반영하고 **`M31-MEM-OPT`**를 생성한 뒤, 다음 구현 작업에서 P0~P2 최적화를 먼저
진행한다. 기존 W04·W05 성공·실패 원본은 보존하며 두 작업의 완료를 최적화 착수 조건으로
두지 않는다. 최적화된 image로 W04·W05 잔여와 영향 재검증을 수행하고 W06 자원 manifest·
M19~M30 회귀로 이어간다. 이번 요청은 문서·main 반영·브랜치 생성까지만이다.

## 2. 비교 기준

NU54DK application RAM region은 262,144 bytes다. 아래 값은 runtime high-water가 아니라
link 시 예약된 `.data + .bss`다. linker의 RAM region 사용량은 정렬·별도 section 등에 따라
이 합계와 다를 수 있으므로 최종 비교에서는 두 값과 분모를 함께 기록한다.

## 3. 공통 원인

### 3.1 feature fragment가 역할보다 넓다

`libraries/NUCODE_BLE/zephyr/feature.yml`은 `NUCODE_BLE.h` 선택 시
`ble-nus.conf`를 병합한다. 이 fragment는 NUS 외에 central/peripheral/observer,
extended·periodic advertising, PAwR, 범용 GATT/cache, LE CoC, SMP·bonding,
settings/ZMS와 privacy까지 함께 활성화한다.

빌더 병합 경로는 `tools/nu54-builder/src/nu54_builder_impl/configuration.py`의
feature conf 수집·병합과 `build.py`의 최종 구성 생성이다. CS/DF/ISO/Audio의 role
fragment가 필요한 기능을 추가하더라도 공통 fragment에서 켠 미사용 기능을 제거하지 않는다.

### 3.2 `ble` profile이 Arduino peripheral 전체를 포함한다

`variants/nu54dk/profiles/ble/prj.conf`와
`zephyr/cmake/source_selection.cmake`의 현재 조합은 BLE role image에도 Serial1, Wire,
SPI, ADC, PWM, GPIO/interrupt와 I/O ownership runtime을 포함한다. `prj.conf`를 role별로
만드는 구조 자체는 맞지만 Core 정적 상태의 source gate까지 충분히 연결되지 않았다.

### 3.3 고정 geometry가 실제 Kconfig capacity를 따르지 않는다

범용 GATT는 `GattInternal.h`의 service/characteristic/descriptor 고정 배열과
characteristic별 notification·indication 512-byte staging을 가진다.
`CONFIG_NUCODE_BLE_GATT_MAX_CHARACTERISTICS_PER_SERVICE`를 낮춰도 현재 배열 크기는
`BLEService::maximum_characteristics`를 사용하므로 RAM이 줄지 않고 등록 시 거부 상한만
바뀐다. GAP periodic/PAwR queue도 기능 사용 여부와 관계없이 정의된다.

## 4. CS map의 대표 정적 점유

| 대상 | bytes | 역할 고유 여부 | 조치 |
| --- | ---: | --- | --- |
| 범용 GATT service slots | 45,248 | 아니오 | GATT off gate 또는 role capacity 적용 |
| 32-pin runtime states | 26,112 | 아니오 | compact ownership state와 sidecar 분리 |
| Serial1/Wire/SPI/PWM route 6개 | 25,344 | 아니오 | source-level 조건부 제외 |
| SDC mempool | 17,909 | 일부 | controller role·count별 재산정 |
| main stack | 8,192 | 일부 | high-water 뒤 축소 |
| malloc arena | 4,096~8,192 | 일부 | public Arduino heap 계약을 유지하며 계측 |
| generic GATT event queue/state | 약 7,900 | 아니오 또는 과대 | server/client·depth 분리 |
| GAP/L2CAP context·queue·pool | 약 18,500 | 대부분 아니오 | advanced GAP·CoC opt-in |
| CS initiator local/peer steps | 약 7,172 | 예 | 최장 procedure 검증 전 유지 |
| CS reflector read pool | 약 2,836 | 예 | fragmented RAS 검증 전 유지 |

`PinRuntimeState`는 32개 pin 각각에 최대 16-entry `IoResourceLease`를 포함한다.
`RuntimePeripheralRoute`도 block lease와 pin handover별 lease를 중복 소유한다. 소유권의
generation·rollback 의미는 유지해야 하지만 단일 GPIO pad와 고정 peripheral route에
16-entry 범용 transaction 전체를 영구 할당할 필요는 없다.

DF responder의 `mem_iq_report` 약 13,252 bytes와 `mem_pdu_rx` 약 12,852 bytes는
controller DF 고유 비용으로 별도 관리한다. TX-only, response-only, RX role을 나누지 않고
이 pool을 일괄 제거해서는 안 된다.

## 5. 최적화 작업

### P0 — 기준선과 역할별 dead feature 제거

1. 대표 image의 final `.config`, text/data/bss, map 상위 RAM symbol, feature fragment와
   capacity를 machine-readable manifest로 만든다.
2. 기존 full `ble` profile은 호환 preset으로 유지하고, CS/DF/ISO/Audio 내부·고급 role에
   lean fragment를 추가한다.
3. 미사용 Serial1/Wire/SPI/ADC/PWM, GPIO interrupt, NUS, 범용 GATT, LE CoC,
   advanced GAP, 반대 link role을 final `.config`에서 제거한다.
4. `NUCODE_BLE` base를 최소 core, NUS, GATT server/client, CoC, persistent security,
   periodic/PAwR fragment로 분리한다.
5. Kconfig를 끄는 데 그치지 않고 `zephyr_library_sources_ifdef` 또는 생성 source list로
   translation unit 자체를 제외한다. 전역 객체를 함수 내부 `static`으로 옮기는 것만으로
   정적 예약이 줄었다고 판정하지 않고 ELF/map에서 실제 제거 여부를 확인한다.

단순히 `--whole-archive`를 제거하지 않는다. Zephyr device/init/callback과 iterable section이
조용히 탈락할 수 있으므로 source gate를 먼저 적용하고 link root를 검증한다.

### P1 — 공통 고정 상태를 right-size한다

1. GATT server/client를 분리하고 service·characteristic·descriptor·value·event depth를
   실제 Kconfig 값으로 배열 크기에 반영한다.
2. characteristic별 notify/indicate staging을 bounded shared TX pool로 바꾼다.
3. periodic/PAwR/scan queue와 LE CoC pool을 역할별로 완전히 제외하거나 필요한 수로 제한한다.
4. `PinRuntimeState`의 일반 mode/owner/generation과 interrupt handover state를 분리한다.
5. `RuntimePeripheralRoute`는 block 1개와 실제 pin 수에 맞는 compact transaction을 사용한다.
6. I/O resource slot 수는 profile별로 나누되 Peripheral Fabric의 128-slot 계약을 공통으로
   축소하지 않는다.

공개 `Serial1`, `Wire`, `SPI`, PWM, BLE class·method·constant는 유지한다. full preset의
기본 capacity도 즉시 줄이지 않고 lean role에서 먼저 검증한다.

### P2 — 계측 뒤 조정한다

1. `BT_MAX_CONN`, link role, ACL/ATT/L2CAP/ISO count·size, paired/resolving/CCC 수와
   SDC mempool을 실제 role별로 조정한다.
2. thread analyzer와 heap high-water로 main/workqueue/BT thread stack, malloc arena와
   Zephyr heap을 줄인다. 최악 HIL에서 20~30% 여유를 유지한다.
3. Audio는 source/sink 방향별 encoder/decoder, ASE/ISO, HAS preset, OTS/ATT/L2CAP
   concurrency를 분리한다.
4. DF는 TX/response/RX별 IQ/PDU pool을, CS는 최대 procedure와 fragmented RAS를
   만족하는 step/reassembly pool을 별도로 산정한다.
5. security core와 bonding/settings/privacy, BAS/DIS/HIDS를 분리한다. SMP에 필요한
   RNG/ECDH/AES/CMAC과 DFU 서명·rollback 구성은 근거 없이 제거하지 않는다.

## 6. 금지 사항

- RAM 사용률을 낮추기 위해 stack·heap을 계측 없이 먼저 축소하지 않는다.
- CS step/reassembly, DF IQ report, Audio ISO/ASE buffer를 공통 Core 낭비보다 먼저 줄이지 않는다.
- full profile의 공개 API를 삭제하거나 silent truncation을 도입하지 않는다.
- native sample과 profile·기능 분모가 다른 Arduino image의 차이 전체를 낭비로 계산하지 않는다.
- 네 기능 image의 RAM을 합산해 단일 MCU 동시 사용량으로 기록하지 않는다.

## 7. 완료 gate

| gate | 완료 조건 |
| --- | --- |
| source/config | 비활성 기능 object와 금지 symbol이 ELF/map에 없음 |
| build | 전체 공개 예제와 대표 full/lean fragment pristine build PASS |
| API | 기존 full preset의 공개 API/기본 capacity 호환, lean capability query·명시 오류 |
| ownership | AC-02A generation/rollback/handover와 자원 고갈 회귀 PASS |
| BLE | GAP/NUS/GATT/cache/CoC/periodic/PAwR의 소유 example 회귀 PASS |
| W04 | controller command/event/Host callback/raw IQ와 cleanup을 분리해 재검증 |
| W05 | secure RAS 100, stop/restart 20, disconnect/reconnect 20, wrong-key negative 재검증 |
| Audio/ISO | stream drop·corrupt·cross-link 0, sync loss/restart와 role별 buffer gate PASS |
| resource | image별 절대 byte와 headroom, stack/heap high-water, pool capacity 기록 |
| W06 regression | current source M19~M30 영향 회귀와 resource leak 0 |

RAM budget gate는 초기에는 75% 경고, 85% 이상 실패 또는 명시적 승인으로 둔다. 최종 상한은
최적화된 clean build의 역할별 기준선을 만든 뒤 고정한다. native 대비 Arduino 증가량도 함께
기록하되 API·queue·buffer 차이를 분리한다.

## 8. 실행 순서

1. 현재 W04·W05의 exact 실패·성공 원본을 보존하고 M31 릴리스 문서를 `main`에 반영한다.
2. 갱신된 `main`에서 정확한 이름 **`M31-MEM-OPT`**로 분기한다. 이번 작업은 여기까지다.
3. 다음 구현 요청에서 P0 → P1 → P2 순으로 최적화하며 작은 단위로 검증·커밋한다.
4. 각 단계에서 RAM delta와 해당 기능의 회귀를 기록한다. W04·W05 완료를 먼저 요구하지 않는다.
5. 최적화 image로 W04 connected IQ 안정성·cleanup, W05 wrong-key·복구 등 잔여를 닫는다.
6. 같은 최적화 기준으로 W06 자원·수명주기·M19~M30 회귀 → W07 설치 예제·3보드 역할 →
   W08 원장·문서·Windows 릴리스 준비를 진행한다. 실제 공개에는 별도 배포 gate와 승인이 필요하다.

최적화의 국소 회귀, W04·W05 기능 완료, W06 전체 영향 회귀는 서로 다른 판정이다. 과거
고점유 image를 먼저 최종 승인했다가 최적화 후 같은 완료 묶음을 반복하는 순서를 피하되,
변경된 image에 필요한 재검증을 생략하지 않는다.
