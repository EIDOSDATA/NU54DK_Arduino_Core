## 1. 목적과 판정 범위

M1은 Arduino API를 구현하기 전에 다음 기반이 실제 NU54DK에서 성립하는지 확인하는
단계다.

1. 고정한 NCS/Zephyr 환경에서 C++ 애플리케이션을 clean build할 수 있다.
2. 외부 보드 package를 `BOARD_ROOT`로 사용해 올바른 NU54DK Devicetree를 생성한다.
3. VS Code Actions의 **Flash**와 같은 기본 runner 경로로 온보드 CMSIS-DAP를 사용할 수
   있다.
4. 동일 이미지를 일반 flash로 3회 연속 기록하고 애플리케이션을 다시 실행할 수 있다.
5. mass erase나 recover 없이 동작하며, build 실패와 probe 실패를 구분할 수 있다.

M1은 Arduino `setup()`/`loop()`, `.ino`, Build Adapter, 외장 J-Link와 전체 Serial API를
검증하지 않는다.

## 3. 재현 명령

아래 명령은 NCS v3.4.0 Toolchain 환경이 활성화된 PowerShell에서 실행한다. 실제 설치
위치와 probe UID만 사용자 환경에 맞게 바꾼다.

```powershell
$NcsRoot = "C:/ncs/v3.4.0"
$CoreRoot = "C:/path/to/NU54DK_Arduino_Core"
$BoardRoot = "$CoreRoot/board_package/NU54DK_Zephyr_DTS"
$Board = "nrf54l15dk/nrf54l15/cpuapp/nu54dk"

west build --pristine always --no-sysbuild `
  -b $Board `
  -s "$NcsRoot/zephyr/samples/cpp/hello_world" `
  -d "$CoreRoot/build/m1-cpp-hello" `
  -- "-DBOARD_ROOT=$BoardRoot"

west build --pristine always --no-sysbuild `
  -b $Board `
  -s "$NcsRoot/zephyr/samples/basic/blinky" `
  -d "$CoreRoot/build/m1-blinky" `
  -- "-DBOARD_ROOT=$BoardRoot"

west flash -d "$CoreRoot/build/m1-blinky" --dev-id <PROBE_UID>
```

보드 DTS, Kconfig 또는 runner 인자를 변경한 첫 빌드에서는 pristine configure가
필요하다. 그 이후 일반 소스 수정과 반복 flash에서 매번 pristine build를 사용하지
않는다.

## 6. pyOCD 기본 runner 확정

### 6.1 최초 증상

초기 `--target=nrf54l` 설정만으로 연결하면 CMSIS-DAP probe는 열거되지만 SWD의 No ACK
또는 Unexpected ACK로 연결이 실패했다. `under-reset` 연결을 사용하면 기록은
가능했으나, pyOCD의 마지막 hardware reset 뒤 target AP에 다시 접근하는 과정이 간헐적으로
실패했다. 따라서 이 문제는 compile이나 HEX 생성 문제가 아니라 probe의 연결/reset
sequence 문제로 분리되었다.

500 kHz에서는 이미 같은 image가 들어 있는 비교/skip 세션이 성공했지만, 다른 image를
실제로 기록하려는 세션의 CoreSight discovery 중 AP 응답 오류가 재현되었다. 100 kHz에서
실제 programming을 먼저 통과한 뒤 250 kHz에서도 변경 image의 sector erase와 page
programming이 성공했다. 성능과 안정성 사이의 기준값으로 250 kHz를 선택했다.

### 6.2 보드 기본 인자

NU54DK `board.cmake`의 pyOCD runner를 다음 값으로 확정했다.

```yaml
pyocd:
  - --dt-flash=y
  - --target=nrf54l
  - --frequency=250000
  - --tool-opt=-M=under-reset
  - --tool-opt=-O=auto_unlock=false
  - --tool-opt=-O=cmsis_dap.prefer_v1=true
  - --tool-opt=-O=load.post_reset=emulated
```

| 인자 | 이유 |
| --- | --- |
| `--frequency=250000` | 변경 image의 실제 page programming까지 안정적으로 통과한 SWD 기준 속도 |
| `-M=under-reset` | target reset을 유지한 상태로 최초 debug access를 확보 |
| `auto_unlock=false` | 잠긴 target에서 일반 Flash가 자동 mass erase하는 동작을 차단 |
| `cmsis_dap.prefer_v1=true` | 이 보드에서 안정적으로 동작한 CMSIS-DAP v1 HID transport를 우선 사용 |
| `load.post_reset=emulated` | 기록 뒤 hardware reset과 AP 재접근 사이의 race를 피하고 pyOCD의 emulated core reset으로 새 image를 시작 |

pyOCD의 일반 session 기본값은 잠긴 target을 erase하여 자동으로 unlock할 수 있으므로
보드 runner에서 이를 명시적으로 비활성화했다. 일반 Flash는 잠긴 target에서 실패해야
하며, unlock/recover는 데이터 삭제를 인지한 사용자가 별도로 실행해야 한다.

`load.post_reset=emulated`는 mass erase나 recover가 아니다. 플래시 세션의 최초 연결은
`under-reset`으로 시작하며, 기록 뒤에는 별도의 hardware reset 대신 pyOCD가 core reset을
모사하여 새 image를 실행한다. 완전한 전원 인가 부팅과 hardware reset 동작은 물리 Reset
또는 power cycle로 별도 시험할 수 있다. 향후 변경된 image, 주변장치 사용량이 큰 image와
debug session에서도 이 정책을 회귀 검증한다.

이 설정은 `runners.yaml`에 생성된다. 검증한 기본 `west flash` 명령은 nRF Connect for
VS Code Actions의 **Flash**가 실행하는 형식과 같지만, 이 변경 뒤 UI 버튼 자체를 누른
시험은 아직 별도로 기록하지 않았다.

## 7. 반복 플래시와 실기 실행 결과

먼저 C++ 기준 image를 기록한 뒤 동일한 blinky HEX를 기본 runner 명령으로 3회 연속
플래시했다. 따라서 첫 회차는 실제 sector erase/page programming 경로를, 다음 두 회차는
변경 없는 image 비교와 재시작 경로를 검증했다. 명령에는 `-r pyocd`조차 지정하지 않아
생성된 기본 runner 선택까지 함께 검증했다.

```powershell
west flash -d <CORE_ROOT>/build/m1-blinky --dev-id <PROBE_UID>
```

| 회차 | 종료 코드 | 경과 시간 | 결과 |
| ---: | ---: | ---: | --- |
| 1 | 0 | 12.543초 | 8 sector, 32,768 B erase 및 8 page, 32,768 B program 뒤 재시작 성공 |
| 2 | 0 | 18.204초 | 변경 없음, 8 page, 32,768 B skip 뒤 재시작 성공 |
| 3 | 0 | 10.920초 | 변경 없음, 8 page, 32,768 B skip 뒤 재시작 성공 |

세 실행 모두 `--erase`와 recover를 사용하지 않았고 `auto_unlock=false`가 생성된
`runners.yaml`을 사용했다. 첫 회차의 8 sector erase는 변경 page를 쓰기 위한 일반 sector
programming이며 전체 RRAM을 지우는 chip/mass erase가 아니다. 다음 두 회차는 변경할
page가 없어 각각 32,768 B를 skip했고 지운 sector 수는 0이었다.

| 항목 | 결과 |
| --- | --- |
| blinky FLASH | 30,292 B / 1,524 KB, 1.94% |
| blinky RAM | 5,800 B / 256 KB, 2.21% |
| blinky HEX SHA-256 | `CE1EB849020F93BCAACBE0F9B15E06D91D1DAD3E0AC5015C946637D23BCB3316` |
| 실행 증거 | 사용자가 실제 NU54DK의 LED0 점멸을 육안 확인 |

LED0는 `DT_ALIAS(led0)`를 사용하며 1초 주기로 상태를 바꾼다. 따라서 이 확인은 올바른
Devicetree alias, GPIO 초기화, image 실행과 반복 delay가 모두 작동한다는 실기 증거다.

## 8. 알려진 경고와 남은 항목

| 항목 | 판정 및 후속 조치 |
| --- | --- |
| `Board ID 5415 is not recognized` | pyOCD가 probe의 접두 ID를 board database와 연결하지 못했다는 비치명 경고다. `--target=nrf54l`을 명시하므로 flash에는 영향이 없었다. |
| `NRF54L15 is not in a secure state` | AHB-AP가 접근 가능하고 APPROTECT가 적용되지 않은 상태라는 pyOCD 표현이다. 제품의 전체 보안 상태 판정이 아니며, M1은 secure provisioning 정책을 검증하지 않았다. |
| `NRF_PLATFORM_LUMOS` deprecated warning | NCS/Zephyr 기준 환경에서 발생한 알려진 경고로, NU54DK Core source 오류가 아니다. SDK 업데이트 때 재평가한다. |
| UART20/VCOM 로그 | 두 COM port를 열 수 있었지만 sample 출력 byte를 수신하지 못했다. LED 실행 증거로 M1은 통과하며, VCOM bridge와 solder bridge 상태는 Serial 단계에서 별도 해결한다. |
| 외장 J-Link | runner 등록은 확인했지만 실기 flash/debug는 M1 범위가 아니다. M8에서 별도 검증한다. |
| pyOCD debug | 기본 debug runner 생성은 확인했지만 source breakpoint와 reset 회귀는 M8에서 검증한다. |

**결정 게이트: CONDITIONAL GO.** 로컬 하드웨어 경로는 M2 착수를 허용할 만큼
검증되었다. 다만 공개 재현 기준선으로 M1을 완전히 닫으려면 보드 package의 runner
변경을 먼저 commit하고, 상위 Core의 submodule gitlink와 이 문서의 revision을 갱신해야
한다. UART/VCOM, 외장 J-Link와 source-level debug는 각각 Serial 및 M8 업로드·디버그
단계의 추적 항목으로 유지한다.
