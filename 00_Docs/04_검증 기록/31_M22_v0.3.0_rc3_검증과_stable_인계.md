## 1. 판정 요약

RC3는 loaderless application 범위를 실제 DTS·linker·Arduino maximum과 일치시키고, 고정 host,
package example 및 실제 pyOCD Upload gate를 통과했다. 공개 Boards Manager clean-room은 신규 설치,
설치 identity, 29/29 예제 compile와 Blink compile까지 통과했다. 이어지는 Upload 도중 프로젝트
소유자가 보드의 reset 버튼을 눌러 CMSIS-DAP SWD 연결이 끊겼고 runner는 의도대로 실패로 닫혔다.

같은 설치본·HEX·명시 probe 선택으로 즉시 다시 실행한 비파괴 pyOCD Upload는 성공했다. 프로젝트
소유자는 실패 원인을 사용자 reset 개입으로 확인하고, 전체 29개 예제를 다시 수행하는 clean-room
재실행은 요구하지 않기로 결정했다. 따라서 이 기록은 자동 clean-room 전체 PASS라고 주장하지
않는다. 중단 뒤 남은 downgrade·upgrade·uninstall·reinstall 구간은 `v0.3.0` stable 공개 전 다른
Windows PC의 stable lifecycle에서 다시 판정한다.

## 3. 메모리 계약

| 영역 | 범위 | 크기 |
| --- | --- | ---: |
| Application | `0x000000..0x16c000` | 1,490,944 byte / 1,456 KiB |
| LittleFS | `0x16c000..0x174000` | 32 KiB |
| Settings/ZMS | `0x174000..0x17d000` | 36 KiB |

DTS code partition, Zephyr linker FLASH와 Arduino maximum Sketch size는 모두 `1,490,944` byte다.
RC1/RC2의 696 KiB dual-slot 표기는 역사 기록이며 RC3 기본 loaderless layout에는 적용하지 않는다.

## 5. 다른 PC 인계 상태

이 기록 다음 commit은 source와 패키징 허용목록을 `0.3.0` stable 사전 공개 상태로 바꾼다.
`v0.3.0` tag, GitHub stable Release와 root stable index는 아직 만들거나 수정하지 않는다.

다른 Windows PC에서는 다음 순서로 마무리한다.

1. 인계 commit을 새 경로에 clone하고 submodule을 exact revision으로 초기화한다.
2. host/software gate와 `0.3.0` stable package 재현 build를 실행한다.
3. stable package의 runtime payload가 RC3의 고정 payload와 일치하는지 확인한다.
4. 격리 Arduino 환경에서 `0.2.0 → 0.3.0 → 0.2.0 → 0.3.0 → uninstall`을 검증한다.
5. 설치본 29개 예제 compile과 실제 NU54DK pyOCD Upload를 확인한다.
6. 모든 결과가 PASS한 exact commit에 annotated `v0.3.0` tag를 만들고 7개 stable 자산을 공개한다.
7. root stable index에 `0.3.0`, `0.2.0`, `0.1.0` 순으로 추가하고 공개 URL을 재검증한다.
8. 공개 commit·archive identity와 Release ID를 후속 기록에 고정한다.

이 절차가 끝나기 전에는 `v0.3.0`을 공개 stable 또는 M22 완료로 표시하지 않는다.
