# 252 — M31 P2 CS 장절차·반복 계수 경계 진단

## 판정

고정 NCS `v3.4.0`과 현재 `M31-MEM-OPT`의 adaptive
`tests/arduino-cli/p2_cs_initiator`를 exact 두 NU54DK에서 사용했다.
두 실험 모두 공개 API와 reflector image는 그대로 두고 initiator backend의
진단 빌드 값만 일시적으로 바꿨다. 빌드 후 backend 소스를 기본값으로
되돌렸으며 제품 기본값이나 SDK를 변경하지 않았다. 따라서 두 결과는
**진단 image 범위의 국소 PASS**이지 기본 CS의 최대 step·fragmented RAS
완료가 아니다. 두 진단 image는 변경 중 빌드되어 `source_clean=false`이며,
최종 기본 복구 image는 변경 전의 고정 SHA-256과 일치한다.

| Image | 일시 변경한 설정 | 실기 | 원본 |
| --- | --- | --- | --- |
| 장절차 | `max_procedure_len=1000`, `min_subevent_len=10000`, `max_subevent_len=75000`; `main_mode_repetition=0` 유지 | raw 10/10, 실제 local/peer 94~98 step·counter gap 0·양측 STOP | [장절차 10건](evidence/m31-p2-native-comparison-2cf92933/cs-long-procedure-10.json) |
| 반복 3 | 위 장절차 값 + `main_mode_repetition=3` | raw 10/10, 실제 local/peer 93~96 step·counter gap 0·양측 STOP | [반복 3의 10건](evidence/m31-p2-native-comparison-2cf92933/cs-repeat3-10.json) |
| 기본 image 복구 | 제품 기본 `max_procedure_len=128`, subevent `16000/16000`, 반복 `0` | raw 100/100·counter gap 0·양측 STOP | [기본 복구 100건](evidence/m31-p2-native-comparison-2cf92933/cs-default-recovery-after-max-100.json) |

진단값은 `libraries/NUCODE_BLE_ChannelSounding/src/NUCODE_BLE_ChannelSounding_Initiator.cpp`의
`RasInitiator::start()`와 config 생성 경로에서 각각 위 숫자만 바꿔 빌드했다.
`arduino-cli`는 현재 저장소를 가리키는 격리 사용자 경로의 `0.4.1-dev`
adaptive platform을 사용했다. 두 진단 image의 정적 FLASH/RAM은 모두
`243,720/80,458 B`다. 장절차 initiator HEX SHA-256은
`48fb6c27504077959acf1419f6965bc1cc66e00511a51e8c781a9f6adc2050e6`,
반복 3은 `57622827b6c601227cc4f00f99cddc8561861e8731f4a0ca3cbecedc76ba84a8`,
reflector는 기존 `1efe4958284c05bc91a3695029d5f0e5d4eb1ad513eb0ac19148972f8d3a8ba5`다.
기본 복구 initiator는 기존
`989b19432357e0f678de8426827b7ddfe1d4424b90c2c557ace599a263a2e6e2`다.
원본에는 각 image와 익명화한 probe hash, UART·STOP이 있다.

첫 장절차 JSON의 `P2_READY` 이전에는 이전 UART 수명의 `CS_RAW counter=16`
한 줄이 남아 있다. 판정기는 READY **이후**의 새 raw 10건만 센다.
반복 3 JSON에는 이 선행 줄이 없다. 두 경우 모두 실제 RAS segment 수는
계측하지 않았으므로 498 B ATT MTU를 넘는 **분할이 발생했다는 직접 증거가
없다**. 고정 SDK의 `BT_RAS_MAX_STEPS_PER_PROCEDURE=256` 예약은
capacity 상한이지 이번 실행의 step 사용량이 아니다. 절차 길이와 반복
계수만 늘려도 결과가 약 96 step에 머문 이유는 아직 특정하지 못했다.

두 이미지의 정상 종료 stack high-water 중 initiator BT RX WQ는
`1,520/3,200 B`, BT TX는 `744/3,200 B`, BT LW WQ는 `936/2,104 B`,
main은 `1,048/8,192 B`였다. 관찰된 libc malloc peak는 0 B, 별도
Zephyr `k_heap` peak는 264 B였다. 이 값은 10개 단기 실행이며 최악
절차의 메모리 여유가 아니다. 따라서 RAS 버퍼·stack·heap·controller pool은
축소하지 않는다.

## 남은 검증

실제 절차 header의 step 수·subevent 수·RAS segment 수를 같은 counter에
연결해 계측하고, 256-step 용량에 가까운 입력 및 분할 재조립·오류/재전송
경로를 검증해야 한다. [245번 장기 누락](245_M31_P2_CS_장기_연속성_진단.md)의
정상 callback 뒤 누락과 불완전 raw도 미해결이며 이번 10건으로 닫지 않는다.
**P2 전체·W05는 미완료**다.

후속 [255번 채널맵 반복 진단](255_M31_P2_CS_256_step_분할_RAS_진단.md)은
다른 진단 image에서 실제 256-step·분할 RAS 정상 경로를 확인했다. 이 기록의
93~98 step 결과를 소급 변경하지 않는다. 당시 0-gap 기준의 장기 연속성
HOLD는 현행 P2 판정으로 승계하지 않는다. [260번 판정 정정](260_M31_P2_CS_누락_분류와_256_step_장시간.md)
