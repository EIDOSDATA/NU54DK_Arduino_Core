## 5. 필수 gate

M22 final evidence는 다음 네 종류가 정확히 한 번씩 PASS해야 한다.

| Gate | 확인 범위 |
| --- | --- |
| `host` | 전체 host/CI/release contract, exact source와 fail-closed 정책 |
| `package-examples` | RC archive를 설치한 뒤 29개 예제 전체 compile |
| `rc-upload` | 설치본 Blink를 지정 CMSIS-DAP UID로 upload, mass erase 없음 |
| `cleanroom` | 공개 RC URL에서 새 격리 root로 설치·compile·upload·정리 |

각 fixed gate evidence는 plan의 release version, target commit, board revision과 artifact hash에
묶인다. Probe UID는 evidence에 기록하지 않고, 명령 계약에는 redaction 상태만 남긴다.

## 6. Public prerelease와 clean-room 순서

RC index와 ZIP은 public URL에서 다운로드할 수 있어야 Boards Manager clean-room을 실행할 수 있다.
따라서 안전한 순서는 다음과 같다.

1. Final 문서·source commit을 push하고 Core와 board worktree clean 확인
2. Exact commit에서 package를 두 번 생성·비교하고 plan 검증
3. Host, package example와 local RC upload gate 실행
4. Annotated tag `v0.3.0-rc.1`을 exact commit에 생성·push
5. 7개 exact asset의 Public Prerelease를 만들고 `validation in progress`로 표시
6. Tag commit, 익명 asset 크기·SHA-256과 stable index 불변 확인
7. 공개 RC index로 installed-package 29개 compile
8. 동일 PC 격리 clean-room 설치·compile·지정 UID upload
9. 네 evidence를 final evidence로 결합
10. Release 설명만 `validated`로 갱신하고 asset과 tag는 교체하지 않음

## 7. 동일 PC 격리 clean-room

검증 root는 기본 `C:\NU54CI\M22` 아래의 새로운 단일 run leaf다. 현재 사용자 Arduino data,
downloads, sketchbook과 prerequisite root를 재사용하지 않는다. 공개 RC index/ZIP을 다시 다운로드하고
설치된 manifest의 exact Core·board revision을 plan과 비교한다.

성공하면 다음 조건을 만족할 때 exact run leaf 하나만 삭제한다.

- Cleanup marker의 run ID와 token 일치
- Evidence가 run leaf 밖에 존재
- Evidence SHA-256이 marker와 일치
- 삭제 대상이 승인된 parent의 직접 자식

Parent, sibling run, 외부 evidence와 public log는 보존한다. 실패한 run leaf는 원인 분석을 위해
자동 삭제하지 않는다.
