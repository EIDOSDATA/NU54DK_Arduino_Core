# M30-W08 실제 전원 HIL과 M30 완료

## 결론

2026-09-15에 exact core revision
`ae5186f7790a748641fb04128c16156519ee1017`로 `M30-POWER-01`의 네 전원 손실 주입 지점을
각각 세 번 검증했다. 수락 대상 **12/12**가 실제 DUT target USB 전원 차단과 복구를 통과했고,
recovery failure와 invalid image boot는 모두 0이다. 이 결과로 M30-W08과 M30의 8개 작업 묶음,
10개 test ID를 완료로 판정한다.

정규 계약은 기존과 같은 **4 injection point × 3회**다. Reset 명령, 단순 COM 재열거 또는 케이블
존재 확인을 실제 전원 차단으로 대체하지 않았다.

## 장비와 안전 경계

- Peripheral DUT: 실행 시점 `E:` DAPLink MSD와 해당 target UART
- Central relay: 실행 시점 `G:` DAPLink MSD와 해당 target UART
- 실제 차단 대상: Peripheral DUT의 target USB만 해당
- Central USB: 전체 시험 동안 연결 유지
- probe identity: 원시 UID를 저장하지 않고 SHA-256 identity만 manifest에 보존
- flash backend: DAPLink MSD exact-range 기록
- bond storage 초기화: preflight에서 두 보드의 36 KiB storage 범위만 초기화
- reset 대체: 없음
- mass erase 또는 recover: 없음

드라이브 문자는 실행 시점 mapping이며 장비의 영구 식별자가 아니다. 재실행할 때는 각
`DETAILS.TXT`의 probe identity와 target UART를 다시 대조해야 한다.

수락된 실제 절단은 12회다. 사용자의 순서 변경에 따라 실제 수행 순서는
`1,2,3,4,5,6,7,10,11,12,8,9`였고, 최종 journal은 계약의 논리 순서 `1~12`로 정규화했다.
각 선택 실행 결과 파일과 `execution_order`가 실제 수행 순서를 보존한다.

## Harness 경계 timeout 감사

첫 `mcuboot_test_swap` 복구 시도에서 실제 분리·복원은 관측됐지만 Peripheral `READY`가 60초
안에 도착하지 않아 host timeout이 발생했다. MCUboot의 `UPGRADING` 관찰 훅도 60초이므로 host
복구 한도와 의도된 target 대기가 정확히 겹친 것이 원인이었다. 시험 종료 후 양쪽 `READY`를 직접
확인했고 제품 image 손상이나 USB 경로 고장이 아님을 판별했다.

이 시도는 수락 12회에 포함하지 않았으며 실패 당시 journal을 별도 보존했다. 복구 한도를 120초로
늘린 뒤 같은 7번 지점부터 다시 실행해 7~12를 모두 통과했다. 따라서 관측한 물리 cycle은 총
13회, 정규 수락 attempt는 12회, DUT recovery failure는 0이다.
