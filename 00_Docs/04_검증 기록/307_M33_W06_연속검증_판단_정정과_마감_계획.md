# M33-W06 연속 검증 판단 정정과 마감 계획

기록일: **2026-11-02 KST**. 대상은 `Dev-0.6.0-M33`의 검증 운영과 설명 오류다.
이 문서는 원본 PASS/FAIL을 다시 판정하거나 W06 완료를 선언하지 않는다.
**11월3일 후속:** 아래 계획은 당시 판단 정정 기록이다. 이후 사용자가 같은 source의 온전한 증거로
1~7 전체 마감을 승인했다. 현행 순서는 [M33 인계](../M33_HANDOFF.md), S15 #1 실패와 교정은
[308번](308_M33_W06_READY_판정_불일치_교정과_독립_마감_재개.md)을 따른다. 무중단49 의무는 계속 없다.
현행 실행 상태는 [M33 인계](../M33_HANDOFF.md), 과거 개발 완료 요약은
[306번 기록](306_M33_W06_개발_49개_완료와_최종_빌드_중단_인계.md)이 소유한다.

## 1. 결론과 사용자 결정

정상 reset·새 펌웨어 업로드·초기화를 전제로 각 항목을 검증할 때, 전체 #1~#49를 중단 없이
연속 실행해야 한다는 기술적 필연성은 확인되지 않았다. 기존 독립 PASS의 원본 검증과 변경 영향
회귀를 사용한다. 전체49 재시작, #30~#49 일괄 재실행, 별도 선행 #29 focused20을 기본 일정에서 뺀다.
구체적인 실패·변경 영향·원본 증거 누락이 확인됐을 때만 필요한 실행 범위를 정한다.

이는 기능별 cycles·negative·security·STOP·cleanup·retry 조건을 줄이는 결정이 아니다.
연속 사용·상태 전환·누적 자원 요구가 실제 제품 요구에 있다면 그 시나리오의 시험은 의미가 있다.
이번 정정은 그러한 특정 요구 없이 **전체49 연속 재실행을 무조건 필수로 삼은 판단**에 관한 것이다.

최신 사용자 지시는 논의와 오류를 문서화하고 중복·폐기된 지시를 정리한 다음,
아래 1~7번을 기존 승인 범위에서 진행하는 것이다. 중간에 제안했던 “#1 후 #30~#49, 나중에 다시
연속49”도 폐기됐다. 정지 지시가 최신이라고 남긴 오래된 continuation은 현재 지시가 아니다.

## 3. J-Link의 정상 reset과 이번 시험 도구의 차이

SEGGER J-Link Commander의 `LoadFile`은 기본 reset 동작을 사용하고 `noreset`은 별도 선택이다.
Cortex-M reset은 장치별 전략에 따라 SYSRESETREQ 또는 reset pin 등을 사용한다. 정상 reset 후
사용자 앱이 먼저 실행되지 않도록 halt하는 전략도 제공한다. 모든 플래싱이 물리 nRESET pin을
반드시 토글한다고 단정하지 않지만, 정상 J-Link 업로드에 reset이 없다는 설명은 근거가 없었다.
근거: [J-Link Commander / LoadFile](https://kb.segger.com/J-Link_Commander#LoadFile),
[J-Link Reset Strategies](https://kb.segger.com/J-Link_Reset_Strategies) — 2026-11-02 확인.

이번 custom 경로는 J-Link SWD transport 위에서 pyOCD를 사용한다. `SAFE_SESSION_OPTIONS`의
`connect_mode="attach"`, `FileProgrammer(..., no_reset=True)`를 사용하면서 공통 HEX helper의
`reset_and_halt_before_program` 기본값도 False였다. program 뒤 reset이 있더라도, 그보다 먼저
RAM flash algorithm에 진입할 때 이전 앱의 실행 상태가 남을 수 있었다.

따라서 문제는 J-Link 장비의 reset 기능 부족이나 일반 사용자의 업로드 방식이 아니라 **시험 도구의
program 전 준비 누락**이었다. 수정은 기존 SYSRESETREQ reset-and-halt 옵션의 기본값을 True로
바꾸고 HALTED 확인을 그대로 사용하는 것이다. 이번 변경에서 reset pin을 새로 구동한 것은 아니다.
`defer_reset`은 program 후 시작을 지연하는 의미이며, program 전 reset-and-halt와 양립한다.

리셋과 flash/NVM 소거는 다른 동작이다. 정상 reset을 이유로 본딩/NVS 또는 PC 측 UART 버퍼까지
모두 비워졌다고 주장하지 않는다. 필요한 보존·정리 조건은 해당 기능의 원형 시험으로 확인한다.
이 사실도 전체49 연속 실행의 일반적 의무를 만들지는 않는다.

## 4. 실제 진단과 수정 범위

- 진단 A: 이전 앱의 MPU_CTRL=5·CONTROL=2 상태에서 RAM init PC `0x20000015`가 약30초 후 -1을
  반환했다. 뒤의 IPSR=3·HFSR.FORCED·이전 앱 `arch_system_halt` PC·r0=20은 instruction-access
  fault 경로와 부합한다. pyOCD의 내부 VERIFY→ERASE fallback 뒤 init은 HardFault 문맥에서 성공했다.
- 진단 B: 기존 pre-program reset 옵션을 켠 뒤 MPU_CTRL=0·CONTROL=0·IPSR=0에서 init3회가
  각각 약0.1초에 0으로 반환했다. 원형 시간 제한·bounded retry·sector 범위는 유지했다.
- A와 B의 선행 image는 다르고 계측 시간도 원래 deadline을 소비한다. 두 결과는 S13 진단이며,
  원래 #1의 마지막 약11.5초 FlashFailure subtype은 로그에 없어 동일 원인이라고 소급 확정하지 않는다.
- 대상 앱 HEX는 실제 program했다. 직접 MPU/보안 레지스터 변경과 DAP/J-Link **프로브 firmware 갱신**은
  하지 않았다. “firmware 변경 없음”이라고 앱 program까지 없었던 것처럼 표현하지 않는다.
- S14 수정은 HIL helper·안전한 오류 분류 기록·회귀시험·Host ID pin·문서다. 제품 C/C++·SDK·board
  submodule·프로브 firmware는 변경하지 않았다. 실제 diff는
  [93fc19f1](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/commit/93fc19f14ea54d8002b61fba81366d964a4071d7)이다.
- 회귀242는 94+36+15+17+16+19+45개다. 공식 Host651은 별도 계약이다. J-Link sidecar에는 기존
  helper가 허용한 FlashFailure 분류·정수만 추가하고 원래 FAIL·예외·close·receipt pin을 유지했다.

진단 수락 원본은 `D:/w06/control/s13-flash-observe1-acceptance.json`
(`f7ef3a09be56c691ebf061677b40002261dd7de0e92fe681a5a40916ce2b55d9`)과
`s13-flash-reset-compare1-acceptance.json`
(`7085a494ab58126ec1dc781946794e2e6e22b9145a5b136152b91fa53782e242`)이다.
B 종료의 debug/OS/COM/lock 확인을 최신 세 보드의 image·RAM·application STOP 검증으로 확대하지 않는다.
원본의 `application_STOP_claimed=false`, formal credit0을 유지한다.

## 6. 원형 마감 도구가 실제 요구하는 것

`tools/bluetooth/m33_regression.py`의 `assemble`은 `--campaign-matrix`와 여러
`--campaign-evidence FIELD:ID=PATH`를 모두 지원한다. `assemble_closure`·`validate_closure`는
33 family+8 resource+8 automatic peer의 원본 PASS·같은 clean source·hash 사슬을 검사한다.
같은 프로세스, 실행 시각의 연속성, 한 번의 #1→#49 실행 자체는 검사하지 않는다.

따라서 유효한 독립 actual evidence가 있으면 원형으로 조립하며, 새 validator나 합성 PASS 계층을
만들 필요가 없다. 저장 증거 재검증은 원본 무결성 확인이며 새 물리 실행이 아니다.
반면 서로 다른 source의 개발49와 유실 raw를 최신 S14의 exact closure로 바꾸는 것은 허용되지 않는다.
이 제약은 연속 실행 의무와 다르다. 이번 문서 정리로 source 검사나 개별 assertion을 완화하지 않는다.

기존 증거로 충족하지 못한 마감 입력은 실제 미충족으로 보고한다. 그 사실만으로 전체 실행을
자동 시작하거나 완료를 합성하지 않는다. 동일 source 조건과 재실행 제외 범위가 충돌하면,
구체적인 증거 목록과 가능한 마감 범위를 먼저 제시한 뒤 남은 범위를 결정한다.

## 7. 현재 1~7 작업 순서

1. **현재 상태 확인:** owner·실제 프로세스·COM·공통3lock·마지막 종료 기록을 확인한다.
   자동점검 w06은 PAUSED 유지. 오래된 상태 capture를 현재 보드 상태로 재사용하지 않는다.
2. **이미 시작한 CI·Actions 결과 확인:** S14 CI `41405732886`/attempt1의 9 job PASS를 확인했다.
   Actions `41405696091`/attempt1은 실제 API 완료 결과와 artifact identity를 확인한다. 중복 dispatch하지 않는다.
3. **기존 실적 정리:** 개발49의 당시 기록, B 진단, 회귀242와 CI의 범위를 구분한다.
   #1 재실기·전체49·#30~49·별도focused29를 기본 재실행 목록에 넣지 않는다.
4. **파이프라인 미충족 확인·처리:** Host651·Actions141·ecosystem2·runtime9·stage150의 실제
   source·완료·원본 존재를 확인한다. 필요한 완료 입력과 이미 있는 기록을 구분해 처리한다.
5. **남은 마감 항목:** 별도3보드1800초 soak·자원/지원·risk7·qualification3의 미완료 입력을 확인한다.
   자원/자동 peer는 원래49에 포함되므로 별도 중복 시험층을 만들지 않는다. 과거 qualification 근거는 보존한다.
6. **판정·내보내기:** 유효한 독립 증거를 원형 validator·strict closure/export에 연결한다.
   source·원본 누락은 그대로 보고하며 보안·STOP·retry·개별 합격 기준은 유지한다.
7. **최종 기록:** 문서·증거·validator 결과를 정리하고 승인된 branch에 commit/push,
   해당 commit CI를 확인한다. 문서 마감과 W06의 실제 완료 여부는 구분해서 기록한다.

실행 결과는 [현행 인계](../M33_HANDOFF.md)에 갱신한다. 이 목록은 **증거 충족 확인과 잔여 작업의 순서**이며
열거한 모든 항목을 새로 재실행하라는 지시가 아니다.
