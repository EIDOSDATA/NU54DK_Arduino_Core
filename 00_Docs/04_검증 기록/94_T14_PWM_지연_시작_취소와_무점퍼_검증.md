# T14 PWM 지연 시작 취소와 무점퍼 검증

2026-09-07. 사용자가 보드 간 결선을 해제하고 자동 진행을 승인한 범위에서 PWM 결함 수정,
두 보드 무점퍼 회귀, 전체 소프트웨어 검증과 증거 정리를 수행했다. **PWM 미시작 STOP 결함은
수정·회귀를 완료했다.** T12 전체와 T13 이후의 실기·공개 gate는 별도다.

## 수정과 재현

고정 SDK의 nrfx PWM은 START_VIA_TASK 준비만으로 POWERED_ON 상태가 된다. 실제 시작이
없으면 STOPPED를 받지 못해 기존 Fabric stop이 timeout했다. Host fake가 미시작 PWM에도
STOPPED를 주던 가정을 교정해 production 경로를 실행했다. 새 8개 회귀 중 수정 전 6개가
실패했고, 수정 후 8개와 기존 Analog/Stream 26개가 모두 통과했다.

새 실행 전에 nrfx IRQ가 소비하지 않는 DMA READY·SEQSTARTED 흔적을 지운다. 지연 시작이고
시작 흔적이 없을 때만 PWM을 disable하고 다시 확인해 준비를 취소한다. disable과 DMA 시작이
겹치면 일반 STOP 확인 경로를 사용하며 timeout에서는 lease를 유지한다. 취소 과정에서
사용자 sequence를 강제로 시작하지 않는다. 미시작 취소는 logical stopped event를 전달하며
하드웨어 STOPPED 발생으로 기록하지 않는다.

외부 START DPPI 구독은 연결 소유자가 먼저 해제해야 한다. 구독이 남으면 stop은
ownership_conflict로 거부한다. START 주소는 해당 active 실행 동안만 유효하며 CPU/ISR의
raw START와 stop을 동시에 호출하지 않는 계약을 header에 명시했다. SDK·board·공개 API
signature는 유지했다.

[Nordic PWM register 설명](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/pwm.html-topic)의
DMA READY는 pointer/count 수신, SEQSTARTED는 최초 PWM 주기 시작을 나타낸다. 두 종류를
함께 사용해 DMA 준비와 파형 시작 사이도 일반 STOP/lease 보호 경로에 남긴다.

## 실패 보존과 설치 검증

첫 설치 예제 병렬 실행은 26 PASS·3 FAIL이었다. LittleFSPersistence, CustomGattPeripheral,
SystemOffWake는 제품 source 변경 없이 개별 verbose 재실행에서 모두 통과했다.
첫 실패의 짧은 출력만으로 원인은 확정할 수 없다. Windows 실행 차단으로 단정하지 않는다.
LittleFS의 첫 성공 후 cache 정리로 live/configure 원본이 사라져, 다시 빌드하고 두 원본을
즉시 보존했다. 최종 29개는 ELF/HEX 등 실제 artifact, source 입력 hash, live/configure의
동일 40자리 core/board revision, 설치 경로와 금지 경로 누출 여부를 모두 대조했다.

이전 원격 [f17e603 Host 검사](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/34078612021/job/101609473270)는
Windows 임시 경로의 RUNNER~1과 runneradmin 표기가 섞인 M27 test fixture에서 실패했다.
실제 discovery가 반환하는 정규 경로와 맞도록 fixture root에 resolve()를 적용했다.
실제 Windows 8.3 TEMP alias에서도 이전 fixture의 subpath 실패를 재현했고, 수정 후 동일
조건의 5개 시험을 통과했다. [재현 기록](evidence/t14-pwm-deferred-080d771/m27-short-path-reproduction.json)을
보존한다. 로컬 최종 전체 Host가 통과했다. 원격 CI는 GitHub Actions의 해당 push source와 Software Gates·Reproducible Builds 두 workflow 로그를 원본으로 사용한다.

초기 Host 고정 suite 개수 실패, 초안 CMake/stdlib 설정 실패, package 설치 경로 불일치도
준비 과정의 실패로 보존했다. 첫 내부 HIL의 시간 판정 오류와 재검증은 95번에 분리했다.

## 푸시 후 원격 CI 교정

첫 push `1f050f4`의 [Software Gates](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/34089221888)는
5개 job PASS 뒤 Host와 M14 단독 job에서 각각 실패했다. Host는 R06 시험의 TEMP short alias와
정규 source path를 직접 비교했고, M14는 module 실행에서 형제 host_compiler를 찾지 못했다.
제품 build·PWM 동작의 실패로 재분류하지 않으며 두 원격 로그를 그대로 보존한다.

R06 fixture root를 resolve()하고, M14는 package 실행에서 상대 import, discovery에서는
기존 import를 사용한다. M14는 같은 단독 명령의 수정 전 import 실패를 재현하고 수정 후
module 5개·discovery 5개 PASS를 확인했다. R06은 실제 Windows 8.3 TEMP alias로 수정 전
1 FAIL을 재현하고 수정 후 4 PASS를 확인했다. 그 TEMP 조건의 canonical 전체 Host도
85그룹 680 PASS·1 조건부 SKIP다. 최종 실행은 clean exact 9c9db04이며 개별 source SHA도
기록했다. 앞선 dirty 실행의 679 PASS·2 조건부 SKIP는 별도 로그에 보존한다.
제품·SDK·HIL 입력은 변경하지 않았다.

[후속 원본과 SHA](evidence/ci-nojumper-followup-1f050f4/raw-files.json),
[전체 Host 독립 감사](evidence/ci-nojumper-followup-1f050f4/ci-short-temp-host-audit.json)를
보존한다. 이후 원격 결과는 수정본 push SHA에 대응하는 두 workflow 원본으로 확인한다.

## 원격 MinGW weak 링크 순서 교정

두 번째 push `815f0a5`에서는 앞선 R06과 M14 교정을 통과했다. Software Gates 6개 job은
PASS였고, Windows Host의 R12 GAP이 GNU MinGW 15.2.0 링크에서 실패했다. Stack에 실제
정의된 prepareGattDatabase/pollGatt 등 weak 기본 함수 8개가 undefined reference로 남았다.
[원격 실행](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/34090120916)의 로그를 보존한다.

호출자 object를 weak 정의보다 먼저 읽을 때 fallback을 잃는 증상은
[Binutils의 PE-COFF 수정 논의](https://sourceware.org/pipermail/binutils/2026-May/149479.html)와
일치한다. 세 BLE Host 시험의 링크 목록에서 Stack을 GAP 앞에 두었다. 제품 source나 weak
속성을 바꾸지 않으므로 GATT·Security의 실제 strong 정의가 기본 구현을 대체하는 계약도 유지한다.
로컬 GCC 16.1.0/Binutils 2.47은 수정 전 GAP도 통과했으며, 이를 원격 실패의 재현으로 표시하지 않는다.
수정 후 GAP·GATT·Security 세 시험은 GNU와 LLVM에서 모두 통과했다. Exact clean `65f5ae2`의
전체 Host도 GNU 도구·실제 Windows short TEMP로 85그룹 680 PASS·1 조건부 SKIP다.

[원본과 SHA](evidence/ci-ble-link-order-815f0a5/raw-files.json),
[전체 GNU Host 독립 감사](evidence/ci-ble-link-order-815f0a5/host-gcc-final-audit.json)를 보존한다.
최종 원격 Software Gates·Reproducible Builds는 후속 push SHA의 실행 결과로 확인한다.
