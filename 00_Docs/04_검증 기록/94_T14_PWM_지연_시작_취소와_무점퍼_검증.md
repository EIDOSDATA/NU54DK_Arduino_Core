2026-09-07. 사용자가 보드 간 결선을 해제하고 자동 진행을 승인한 범위에서 PWM 결함 수정,
두 보드 무점퍼 회귀, 전체 소프트웨어 검증과 증거 정리를 수행했다. **PWM 미시작 STOP 결함: 해결 완료.**
`080d771` 수정과 미시작 DMA 취소 1,968회 실기 회귀가 근거다. T12 전체와 T13 이후의 실기·공개 gate는 별도다.

## 수정과 재현

고정 SDK의 nrfx PWM은 START_VIA_TASK 준비만으로 POWERED_ON 상태가 된다. 실제 시작이
없으면 STOPPED를 받지 못해 기존 Fabric stop이 timeout했다. Host fake가 미시작 PWM에도
STOPPED를 주던 가정을 교정해 production 경로를 실행했다. 새 8 개 회귀 중 수정 전 6 개가
실패했고, 수정 후 8 개와 기존 Analog/Stream 26 개가 모두 통과했다.

새 실행 전에 nrfx IRQ가 소비하지 않는 DMA READY·SEQSTARTED 흔적을 지운다. 지연 시작이고
시작 흔적이 없을 때만 PWM을 disable하고 다시 확인해 준비를 취소한다. disable과 DMA 시작이
겹치면 일반 STOP 확인 경로를 사용하며 timeout에서는 lease를 유지한다. 취소 과정에서
사용자 sequence를 강제로 시작하지 않는다. 미시작 취소는 logical stopped event를 전달하며
하드웨어 STOPPED 발생으로 기록하지 않는다.

외부 START DPPI 구독은 연결 소유자가 먼저 해제해야 한다. 구독이 남으면 stop은
ownership_conflict로 거부한다. START 주소는 해당 active 실행 동안만 유효하며 CPU/ISR의
raw START와 stop을 동시에 호출하지 않는 계약을 header에 명시했다. SDK·board·공개 API
signature는 유지했다.

[Nordic PWM register 설명](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/pwm.html-topic)의
DMA READY는 pointer/count 수신, SEQSTARTED는 최초 PWM 주기 시작을 나타낸다. 두 종류를
함께 사용해 DMA 준비와 파형 시작 사이도 일반 STOP/lease 보호 경로에 남긴다.

## 원격 MinGW weak 링크 순서 검사 — 단독 해결 불충분

두 번째 push `815f0a5`에서는 앞선 R06과 M14 교정을 통과했다. Software Gates 6 개 job은
PASS였고, Windows Host의 R12 GAP이 GNU MinGW 15.2.0 링크에서 실패했다. Stack에 실제
정의된 prepareGattDatabase/pollGatt 등 weak 기본 함수 8 개가 undefined reference로 남았다.
[원격 실행](https://github.com/EIDOSDATA/NU54DK_Arduino_Core/actions/runs/34090120916)의 로그를 보존한다.

호출자 object를 weak 정의보다 먼저 읽을 때 fallback을 잃는 증상은
[Binutils의 PE-COFF 수정 논의](https://sourceware.org/pipermail/binutils/2026-May/149479.html)와
일치한다. 세 BLE Host 시험의 링크 목록에서 Stack을 GAP 앞에 두었다. 제품 source나 weak
속성을 바꾸지 않으므로 GATT·Security의 실제 strong 정의가 기본 구현을 대체하는 계약도 유지한다.
로컬 GCC 16.1.0/Binutils 2.47은 수정 전 GAP도 통과했으며, 이를 원격 실패의 재현으로 표시하지 않는다.
수정 후 GAP·GATT·Security 세 시험은 GNU와 LLVM에서 모두 통과했다. Exact clean `65f5ae2`의
전체 Host도 GNU 도구·실제 Windows short TEMP로 85 그룹 680 PASS·1 조건부 SKIP다.

[원본과 SHA](evidence/ci-ble-link-order-815f0a5/raw-files.json),
[전체 GNU Host 독립 감사](evidence/ci-ble-link-order-815f0a5/host-gcc-final-audit.json)를 보존한다.

## 같은 MinGW 배포본 재현과 CI 링커 선택

`8016737` 원격에서도 링크 순서 변경만으로는 GAP 실패가 해소되지 않았다. 앞선 65f5ae2의
로컬 GNU 16.1 PASS와 원격 GNU 15.2 결과를 혼동하지 않는다. 원격 runner의 실제
[설치 스크립트](https://raw.githubusercontent.com/actions/runner-images/win25-vs2026/20260824.214/images/windows/scripts/build/Install-Mingw64.ps1)는

검증해 C:/u4ci15n에 풀고 세 BLE 링크 실패를 모두 재현했다. GNU Binutils는 2.46.0.20260210이다.

동일 GCC에 `-fuse-ld=lld`만 지정하면 세 실행 파일의 compile/link가 모두 성공한다.
Security 12 scenario는 실행 PASS다. GAP 10·GATT 11 scenario는 로컬 Windows application
control의 WinError 4551로 실행이 차단돼 PASS로 기록하지 않는다. 이 관측은 Host의
PE-COFF 링크 도구 차이이며 제품 source·weak 속성·ARM target 설정을 바꾸지 않았다.
Windows CI Host job에만 기존 compiler flag 경로로 LLD를 선택하고 GCC/LLD version을 로그에
남기도록 했다. CI 계약 45 개는 통과했다. 전체 실행은 후속 push의 원격 Host에서 확인한다.

## 원격 BLE 실행 통과와 패키저 UTF-8 교정

`f67f568` 원격의 GCC 15.2/LLD 20.1.8은 GAP·GATT·Security 세 수명주기 시험을 모두 실행해
통과했다. 이후 R13 격리 CLI의 한글 도움말에서 CP1252 UnicodeEncodeError가 발생했다.
`python -I`는 PYTHONUTF8 환경도 무시하므로 package CLI 진입점에서 stdout/stderr를
UTF-8로 지정했다. Python import 소비자의 출력 설정에는 적용하지 않는다.

실제 격리 Python의 출력을 CP1252로 설정한 회귀가 수정 전 실패하고 수정 후 통과했다.

WinError 4551로 중단됐고 12 개 scenario 오류와 이후 미실행을 보존한다. 직전 전체 로컬
PASS는 65f5ae2의 680 PASS·1 조건부 SKIP이며 최신 실행에 복사하지 않는다. 새 전체 계획에는
인코딩 회귀 1 개가 추가됐고 최종 전체 판정은 원격 결과로 확인한다. Package CLI 출력만
변경했으므로 이전 firmware/설치 예제 결과의 source 범위는 유지한다. Package 생성·검증
함수와 archive 정책은 변경하지 않았다.
