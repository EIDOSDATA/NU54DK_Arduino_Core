# T13 S 자원 충돌 수용과 세 복구 묶음 재검증

> 과거 검증 이력입니다. 준비·다음 작업·실행 조건은 기록 당시 기준이며, 현재 상태는 [v0.4.0 TODO](../TODO_v0.4.0.md)를 따릅니다.

## 당시 결정: 연속 전환 시험 제외·실기 중지

이 기록 이후 S 검증은 재개·종료됐다. 현재 S 종료와 U 준비는
[113번](113_T13_S_범위_종료와_U_준비.md)을 따르며, 아래 당시 실행 순서를 재지시하지 않는다.

사용자가 같은 GPIO/공유 block에서 UART/SPI/TWI를 연속 전환하는 시험은 과도하며
필요 없으므로 중단하라고 명시했다. T13/T17 범위 변경으로 전체 handover 묶음
(serial00/20/21/22/30, 예행·100 회 반복·동일 전환 경로의 SPI timing 진단)을
v0.4.0 필수 검증과 자동 실행에서 제외한다. 다른 이름이나 진단 단계로 다시 실행하지 않는다.
기존 소스와 성공/실패 원본은 재현 이력으로 보존한다. 오류 원인이 Zephyr의 필연적 한계라고
확정된 것은 아니며, 제외 결정을 제품 결함 수정이나 물리 PASS로 기록하지 않는다.

과거 handover2/5를 현행 미완료 항목으로 요구하지 않는다. 기존 5 개 모두 진행률 분모·분자에서
빼며 새로 통과한 항목으로 더하지 않는다. T12/QDEC 완료, 정상 안정성 36/36, 고정 serial21/21,
PWM6/6, 자원 충돌 사용자 수용 완료를 유지한다. 최근 세 묶음은 TWIM 완료·SPI 전환 제외·
I2S B 복구 미완료로 정리한다. 다른 S 오류 복구·System OFF·U와 T13 전체·RC·공개는 미완료다.

현재 실기는 사용자 중지 상태이며 새 flash·진단·시험은 실행하지 않는다. 재개 지시가 오면
5c4c3e0의 I2S 중단 꼬리 판정 준비 상태부터 대조한다. 해당 소스의 새 I2S 실기는 아직 0 회다.
같은 I2S의 공급 중단·정상 재시작은 이번에 제외한 통신 종류/역할 연속 전환과 다른 항목이다.

## SPI 단일 변수 비교 도구

`spi-timing-diagnostic --handover-instance 20|21|22 --spi-timing-mode baseline|4mhz|rxdelay0`을
추가했다. 기존 10 개 역할 전환을 한 번 실행하며 세 비교는 각각 8 MHz/RXDELAY1,
4 MHz/RXDELAY1,8 MHz/RXDELAY0이다. UART/TWI 속도·GPIO·buffer·guard·STOP은 유지한다.
Opcode182는 fixture/wiring 미점유 상태에서만 모드를 선택하며 실제 SPI DMA 제출 전에만
선택을 적용한다. Opcode183으로 양쪽 ENABLE/CONFIG/PRESCALER/RXDELAY/CSNDUR·
DMA AMOUNT·P1.06/07 GPIO 설정을 보존한다. 제품 core 기본값은 변경하지 않았다.
진단에는 정식 handover/soak PASS를 부여하지 않고 다른 block·동시 부하는 거부한다.

새 Host 4 시험은 선택 범위·단일 변수·실제 레지스터 불일치·양쪽 raw 보존과
정식 100 회/soak 대체 거부를 검사한다. 초안 전체 T13 Host 93 시험 중 91 개는 통과했고,
기존 plan/runtime C++ 실행 시험 2 개는 Windows 앱 제어 WinError4551로 차단됐다.
전체 Host PASS로 표기하지 않으며 보안 정책을 바꾸지 않는다. 새 exact 소스의 전체 Host는
원격 Windows CI에서 별도로 확인한다. 초안 target은 두 역할 2/2 build-only PASS다.
최초 target 요청의 출력 경로 길이 거부는 별도 실패 로그로 보존하고 짧은 새 경로에서 빌드했다.
정렬·계약·문서 검사를 통과했다. 이 초안 빌드는 flash에 사용하지 않고 커밋 뒤 clean exact
checkout에서 새 이미지와 필요한 gate를 생성한다.
[초안 검사 원본](evidence/t13-spi-timing-draft-7c0fde3/manifest.json)의 source는 수정 전 base7c0fde3이며
해당 commit의 exact 실행 결과가 아니다. 이 문서와 함께 반영하는 진단 코드의 초안 검사로 구분한다.

Nordic의 [PRESCALER 정의](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/spim.html-register.prescaler)는
낮은 분주값에서 RXDELAY 조정이 필요할 수 있음을 명시한다. 이 사실은 비교 가설의 근거이며
현재 오류의 원인 확정은 아니다. [RXDELAY 정의](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/spim.html-register.iftiming.rxdelay)와
고정 SDK의 인스턴스별 범위를 대조했다. SPIS 수신 오류를 SPIM 수신 지연 하나로 설명하지 않는다.

## 22:35 이후 첫 실패와 대조

[I2S B 예행](evidence/t13-i2s-b-preflight-7c0fde3/manifest.json)은 A가 첫 RX256 word 중 3 word의
불일치를 감지해 자동 STOP했다. 최초 위치는 22, lease 만료는 0이다. A가 master 클록을 멈춰
B는 completed1/queued3에서 정체했고, 의도한 네 버퍼 뒤 공급 생략에는 도달하지 않았다.
양쪽 STOP·GPIO 반환을 확인했으며 정식 100 회를 시작하지 않았다. 이 실패는 과거 repeat97의
복구 후 1 word 오류와 구분한다. 해당 경로의 기존 기록은 최초 버퍼 전체를 읽지 못했으므로,
I2S error 6을 관측하면 STOP 전 opcode118의 최초 오류·RX 전체를 보존하도록 실행기를 보강한다.

같은 S에서 [정상 I2S3 초](evidence/t13-i2s-normal-preflight-2a68cd2/manifest.json)는 2a68cd2에서
PASS했다. 이는 B 공급 중단·복구 100 회나 이전 간헐 오류의 해결 근거가 아니다.

[SPI 진단 최초 실행](evidence/t13-spi-timing-enable-first-2a68cd2/manifest.json)은 SPI 전송 전
타이밍 판정에서 실패했다. 원인은 진단 도구가 PREPARE 후 SPIM ENABLE7을 요구한 잘못된
전제다. 실제 SPIM은 ENABLE0, CONFIG0, PRESCALER2, RXDELAY1, CSNDUR255였다.
고정 `nrfx_spim.c`는 구성 단계에서 비활성 상태를 유지하고 transfer에서 enable하므로,
준비 시점 판정과 RXDELAY0 적용의 전제를 ENABLE0으로 교정한다. 활성 7을 받아들이도록
범위를 넓히지 않는다. 기존 소스의 SPI 데이터 불일치 원인과 다른 시험 도구 오류다.

타이밍 진단을 끈 [SPI20 기본 예행](evidence/t13-spi20-handover-preflight-2a68cd2/manifest.json)은
UART/SPI/TWI 순·역방향 10단계와 새 payload·양쪽 STOP을 모두 통과했다. 정식 100 회는 별도다.
수정된 준비 시점 Host 4와 I2S 실패 보존 Host 7이 통과했으며 초안 target도 2/2를 통과했다.
Exact 재빌드와 원격 전체 Host 확인 후 교정된 진단을 다시 실행한다.
[교정 초안·현재 실행 종료 감사](evidence/t13-three-diagnostic-fix-draft-2a68cd2/manifest.json)는
base2a68cd2 이후 수정의 준비 근거이며 exact 실기 합격이 아니다.
