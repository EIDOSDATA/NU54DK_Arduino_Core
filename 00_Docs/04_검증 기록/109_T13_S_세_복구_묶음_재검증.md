# T13 S 자원 충돌 수용과 세 복구 묶음 재검증

2026-09-08 22:13 KST에 사용자가 자원 충돌 묶음을 PASS 처리하고 나머지 세 묶음을 시험하도록
지시했다. T13/T14 재개 범위는 TWIM20/21/22/30 취소, I2S B 공급 중단 후 복구,
serial20/21/22 역할 전환이다. 실패 재현과 원인별 진단, 필요한 수정·Host/target·실기 재시험을
진행하고 원본·문서·commit/push를 남긴다.

## 자원 충돌 완료 결정

**자원 충돌 묶음은 PASS(사용자 수용)로 완료 처리한다.** 실제 근거는 예행14/14와
UART21 role1 mode1/2/3·role2 mode1/2의 각100회, 합계500회다.
나머지9조건의100회 반복은 사용자 결정으로 생략한다. 미실행900회를 수행했다고 기록하거나
실제14조건 모두100회 PASS로 바꾸지 않는다. 원래 증거와 [108번](108_T13_S_자동_실행_종료와_재개_항목.md)의
21:26 시점 수치를 보존한다. 이 결정은 표에 있던14조건 serial 자원 충돌 묶음에 적용한다.

## 새 S 실행과 준비

- 현재17신호+GND S 결선·동일 전압·DAP UART 분리/SWD 연결·P2.07/08 미연결과 실행 중
  유지/변경 전 통보를 새로 확인했다. 회신은 “예, 현재 S 상태이며 실행 중 유지합니다”다.
- 새 확인 기준22:13:18 KST, 최대12시간 기한은 다음 날10:13:18 KST다. 이전21:26:14 만료
  확인서는 수정하지 않았다. 새 USB 열거에서 기존 두 exact UID와 일치하는 장치를 확인했다.
  현재 A COM12/13, B COM14/15이며 이 값은 새 열거 결과다.
- 실행 소스는 clean `7c0fde3233fc8bf90ce146080453a9602e2b20cb`, board gitlink는
  `fe65f2f0880bd05b32e562d9bf1ee59142b4f4d3`이다. 격리 checkout `C:/tsua04`,
  S image `C:/t4y04`를 사용한다. 실제 검증 중인 checkout은 변경하지 않는다.
- exact target2/2·T13 Host89·정렬/계약/문서 검사와 해당 소스 원격15/15 SUCCESS를 확인했다.
  원격 전체 Host는109묶음819시험이다. SWD10MHz·exact UID·controlled sector flash·
  auto_unlock=false를 유지하며 각 campaign에서 전체 결선과 양쪽 종료를 새로 확인한다.

## SPI 단일 변수 비교 도구

`spi-timing-diagnostic --handover-instance 20|21|22 --spi-timing-mode baseline|4mhz|rxdelay0`을
추가했다. 기존10개 역할 전환을 한 번 실행하며 세 비교는 각각8MHz/RXDELAY1,
4MHz/RXDELAY1,8MHz/RXDELAY0이다. UART/TWI 속도·GPIO·buffer·guard·STOP은 유지한다.
Opcode182는 fixture/wiring 미점유 상태에서만 모드를 선택하며 실제 SPI DMA 제출 전에만
선택을 적용한다. Opcode183으로 양쪽 ENABLE/CONFIG/PRESCALER/RXDELAY/CSNDUR·
DMA AMOUNT·P1.06/07 GPIO 설정을 보존한다. 제품 core 기본값은 변경하지 않았다.
진단에는 정식 handover/soak PASS를 부여하지 않고 다른 block·동시 부하는 거부한다.

새 Host4시험은 선택 범위·단일 변수·실제 레지스터 불일치·양쪽 raw 보존과
정식100회/soak 대체 거부를 검사한다. 초안 전체 T13 Host93시험 중91개는 통과했고,
기존 plan/runtime C++ 실행 시험2개는 Windows 앱 제어 WinError4551로 차단됐다.
전체 Host PASS로 표기하지 않으며 보안 정책을 바꾸지 않는다. 새 exact 소스의 전체 Host는
원격 Windows CI에서 별도로 확인한다. 초안 target은 두 역할2/2 build-only PASS다.
최초 target 요청의 출력 경로 길이 거부는 별도 실패 로그로 보존하고 짧은 새 경로에서 빌드했다.
정렬·계약·문서 검사를 통과했다. 이 초안 빌드는 flash에 사용하지 않고 커밋 뒤 clean exact
checkout에서 새 이미지와 필요한 gate를 생성한다.
[초안 검사 원본](evidence/t13-spi-timing-draft-7c0fde3/manifest.json)의 source는 수정 전 base7c0fde3이며
해당 commit의 exact 실행 결과가 아니다. 이 문서와 함께 반영하는 진단 코드의 초안 검사로 구분한다.

Nordic의 [PRESCALER 정의](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/spim.html-register.prescaler)는
낮은 분주값에서 RXDELAY 조정이 필요할 수 있음을 명시한다. 이 사실은 비교 가설의 근거이며
현재 오류의 원인 확정은 아니다. [RXDELAY 정의](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/spim.html-register.iftiming.rxdelay)와
고정 SDK의 인스턴스별 범위를 대조했다. SPIS 수신 오류를 SPIM 수신 지연 하나로 설명하지 않는다.

## 22:35 이후 첫 실패와 대조

[I2S B 예행](evidence/t13-i2s-b-preflight-7c0fde3/manifest.json)은 A가 첫 RX256word 중3word의
불일치를 감지해 자동 STOP했다. 최초 위치는22, lease 만료는0이다. A가 master 클록을 멈춰
B는 completed1/queued3에서 정체했고, 의도한 네 버퍼 뒤 공급 생략에는 도달하지 않았다.
양쪽 STOP·GPIO 반환을 확인했으며 정식100회를 시작하지 않았다. 이 실패는 과거 repeat97의
복구 후1word 오류와 구분한다. 해당 경로의 기존 기록은 최초 버퍼 전체를 읽지 못했으므로,
I2S error6을 관측하면 STOP 전 opcode118의 최초 오류·RX 전체를 보존하도록 실행기를 보강한다.

같은 S에서 [정상 I2S3초](evidence/t13-i2s-normal-preflight-2a68cd2/manifest.json)는2a68cd2에서
PASS했다. 이는 B 공급 중단·복구100회나 이전 간헐 오류의 해결 근거가 아니다.

[SPI 진단 최초 실행](evidence/t13-spi-timing-enable-first-2a68cd2/manifest.json)은 SPI 전송 전
타이밍 판정에서 실패했다. 원인은 진단 도구가 PREPARE 후 SPIM ENABLE7을 요구한 잘못된
전제다. 실제 SPIM은 ENABLE0, CONFIG0, PRESCALER2, RXDELAY1, CSNDUR255였다.
고정 `nrfx_spim.c`는 구성 단계에서 비활성 상태를 유지하고 transfer에서 enable하므로,
준비 시점 판정과 RXDELAY0 적용의 전제를 ENABLE0으로 교정한다. 활성7을 받아들이도록
범위를 넓히지 않는다. 기존 소스의 SPI 데이터 불일치 원인과 다른 시험 도구 오류다.

타이밍 진단을 끈 [SPI20 기본 예행](evidence/t13-spi20-handover-preflight-2a68cd2/manifest.json)은
UART/SPI/TWI 순·역방향10단계와 새 payload·양쪽 STOP을 모두 통과했다. 정식100회는 별도다.
수정된 준비 시점 Host4와 I2S 실패 보존 Host7이 통과했으며 초안 target도2/2를 통과했다.
Exact 재빌드와 원격 전체 Host 확인 후 교정된 진단을 다시 실행한다.
[교정 초안·현재 실행 종료 감사](evidence/t13-three-diagnostic-fix-draft-2a68cd2/manifest.json)는
base2a68cd2 이후 수정의 준비 근거이며 exact 실기 합격이 아니다.
[SPI 진단 최초 exact 준비](evidence/t13-spi-timing-exact-2a68cd2/manifest.json)는 target2/2와
원격 전체 Host110묶음823시험 PASS를 포함한다. 이후 발견된 ENABLE 판정 오류와 구분한다.
[SPI21 기본 예행](evidence/t13-spi21-handover-preflight-2a68cd2/manifest.json)도10단계 PASS다.

세 묶음을 끝내면 사용자가 지목한 네 묶음은 종료된다. **S 전체 완료는 아니다.** 기존의
UART CTS/parity/break/RX 공급 지연, SPI/TWI 미실행 오류 조건, System OFF와 요구별
구현·증거 대조는108번과 [T13 계획](../../tests/hil/nu54dk/T13_PLAN.md)에 남는다.
이 항목들을 U로 옮기지 않는다. T12/QDEC 보고 후 완료 상태는 유지한다.
