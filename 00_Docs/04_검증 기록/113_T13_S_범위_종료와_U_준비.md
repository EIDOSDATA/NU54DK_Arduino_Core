# T13 S 범위 종료와 U 준비

## 결론

요청한 S 58조건은 **정식 PASS 56 + 범위 제외 2**로 종료한다. 제외한 2조건은 T13 전용
peer 제어 System OFF timer/GPIO 결합 시험이다. 이를 58/58 PASS로 쓰지 않으며, 실제 T13
timer/GPIO wake 성공도 주장하지 않는다.

일반 사용자가 사용하는 `BoardSystem::enterSystemOffAfter()`와
`BoardSystem::enterSystemOffOnButton()`은 M15의 한 SWD 격리 세션에서 각각 실제 reset cause
`2048`과 `128`로 PASS했다. 완료 source `c47239d954c45fd173d8d1393e3ea5c9c86e111a` 이후 현재
source까지 두 함수에는 공백을 제외한 실질 diff가 없다. 따라서 UART21 DMA 정리와 A→B 제어를
추가한 T13 결합 시험은 공개 API의 필수 기능 증명이 아니라 추가 회귀·시험 자동화 범위다.

## 과거 마지막 T13 시도와 판정 — 현행 문제 목록 아님

아래 GPIO 전달·SWD 진단은 사용자 결정에 따라 현재 문제·재실행 목록에서 삭제했다.
과거 원본과 진단기 오류 정정만 보존하며 새로운 코어 결함으로 등록하지 않는다.

마지막 exact source는 `dee41fe62eea96f718bcb46e96c1312c7507d5be`, build는 `C:/tz19`다.
두 역할 image·ELF hash, Host·target·style·contract·inventory·docs gate와 실행 preflight를
확인했다. Mass erase·unlock·recover는 사용하지 않았다.

| 원본 | 관측 | 판정 |
| --- | --- | --- |
| `s123-42` | controller1 net5 A P1.06→B P1.07 LOW 실패 | 펌웨어 명령과 별도 DAP GPIO 구동으로 재현. T13 OFF 미도달 |
| `s123-43` | 전체 17선 105검사 통과 뒤 pre-traffic bridge 판정 실패 | **판정기 수정 완료**. 실행기 기준선 오류 교정이며 System OFF 실기 PASS는 아님 |
| `s123-44` | net5 LOW 실패, 직접 DAP에서 초기 A→B 17 sample 불일치 뒤 정상화 | 진단 중 관측 불일치. 이 결과만으로 전기 경로의 원인을 확정하지 않음 |
| UART switch 재접점 | net5 직접 DAP 60/60 PASS | 조작 이후 정상화 관측이며 접점/U7 고장이나 영구 수리를 입증하지 않음 |
| `s123-45` | net3 P1.04 LOW 실패 | System OFF 진입 전 전체 결선 gate에서 종료 |
| net3 직접 DAP | CPU halt·직접 GPIO 검사 시도 두 번에 SWD No ACK / Unexpected ACK 0 기록. 두 원본의 samples는 비어 있음 | 진단기 핀 설정 오류 확인. 정확한 오류 발생 명령과 원인은 원본만으로 확정할 수 없으며, S 결선 불량이나 코어 결함 근거로 사용하지 않음 |

2026-09-10 후속 원본·진단기 대조에서 `direct_net3_dap_diagnostic_04.py`와 `05.py`가
`PINS=(4, 4)`로 A P1.04↔B P1.04를 검사하도록 설정된 오류를 확인했다.
[S 결선표](../../tests/hil/nu54dk/T13_PLAN.md)의 실제 대응은 A P1.04↔B P1.05다.
이는 설명 문자열만의 문제가 아니라 직접 GPIO 레지스터 접근에 쓰는 핀 설정의 오류다.
두 JSON 원본도 잘못된 동명 핀 경로를 표시하며, 완료 sample 없이 cleanup의 SWD 오류만 남겼다.
따라서 이전의 “A LOW 직후 B 단절 두 번 재현”이라는 인과 단정과 U7 원인 추정을 철회한다.
진단기 설정 오류가 SWD 오류 자체의 원인이었는지도 이 기록만으로 확정하지 않는다.

P1.04~P1.07이 회로도 1·6쪽의 SB9~SB12·U7 `SN74AVC4T245`를 통해 온보드 UART와
공유한다는 사실과, 이번 오류 원인이 U7이라는 주장은 별개다. 사용자의 납땜·단선 오류나
일반 GPIO·System OFF 기능 결함으로 분류하지 않는다. 원본을 보존하고 문서 판정만 정정했으며,
보드 재접속·GPIO 재검사·완료한 S 재실행은 하지 않았다.

종료 시 두 보드 P1.04 `PIN_CNF=0`을 직접 읽고 CPU를 실행시켜 sleep 상태로 복구했다. 출력·강제
LOW·halt를 남기지 않았다.

## 기존 System OFF 근거와 사용자 영향

[M15 기준선](17_M15_NU54DK_Board_System_기준선.md)은 다음을 이미 실제 보드에서 확인했다.

- GRTC 약 2초 System OFF wake, `RESET_CLOCK`, raw cause `2048`
- 사용자 SW0/P1.13 active-low System OFF wake, `LOW_POWER_WAKE`, raw cause `128`
- 두 단계를 같은 SWD 격리 세션에서 순서대로 실행하고 최종 `timed=PASS`, `button=PASS`

따라서 T13 추가 결합 시험 제외로 일반 사용자의 System OFF API 지원 상태가 낮아지지 않는다.
달라지는 것은 UART21 DMA 정리·peer 자동 제어를 함께 묶은 T13 회귀 증거가 추가되지 않는다는
점뿐이다.

## S 종료 집계와 U 경계

| 구분 | 결과 |
| --- | ---: |
| 정식 PASS | 56 |
| T13 System OFF 추가 결합 제외 | 2 |
| 요청한 S 범위 | 58 |
| 남은 S 실행 | 0 |

QDEC과 시리얼 handover 제외도 유지한다. U 실행 준비에는 다음을 확인했다.

| U 준비 항목 | 결과 |
| --- | --- |
| exact source / board | `dee41fe62eea96f718bcb46e96c1312c7507d5be` / `fe65f2f0880bd05b32e562d9bf1ee59142b4f4d3` |
| build | `C:/tz20`, `nucode.v04.t13_u_dut`·`peer` 2/2 PASS |
| role1 HEX / ELF | `28e3a1358fe5e1f3e2813ffb3803317f58d3b32aca87cebee3dad2c1e2fdb9cf` / `9a103484f184ef7318e33b9b8be826ca80f849ce2cd3a0d82fc467abb762dbe5` |
| role2 HEX / ELF | `88323815e1b60b33c047a22f3075b45707c5a3b4de490c97210f380c0ff7ea63` / `b8d827586166254e3bd542a045382010f16dab33e570e5a43385db8bc14d1505` |
| U 관련 Host | 48/48 PASS |
| T13 Host 전체 | 149/151 PASS, 2건은 생성 실행 파일의 Windows application-control 차단이며 assertion 실패 없음 |
| 원격 | Software Gates run `34440392750` SUCCESS, Reproducible Builds run `34440392752` SUCCESS |

U에서 허용하는 것은 UARTE00 1 Mbit/s 8N1 full-duplex 180초, 양 역할 RTS/CTS 정지·재개,
TX/RX DMA 취소와 fresh restart뿐이다. SPI/TWI/I2S/PDM/PWM, parity/break, reverse serial,
handover와 System OFF는 probe 접근 전에 거부한다.

S 결선을 U 확인으로 재사용하지 않고, U 실기는 사용자가 S→U 네 선을 재배치한 뒤 별도
`v04-t13-u-session`과 전체 17선 open-drain 검사로 시작하도록 당시 준비했다. 이번 준비 단계에서는
U 실기를 실행하지 않았다. 이후 사용자는 UARTE00에 필요한 4신호+GND만 연결하기로 범위를
확정했고, `7f78a36c`에서 U 검사를 net 11·13·15·16으로 한정했다. 이는 S의 기존 17신호 검사
범위를 축소하지 않는다.
