# 공통 결선 검사와 승인 전 자동 진행 계획

2026-09-07. 사용자가 동시 안정성 축소안에 동의하고 관련 문서·수정·commit/push와 결선 검사 펌웨어를 요청했다. 공통 결선 완료를 보고했으며 P2.07/P2.08 추가 여부를 포함한 정확한 연결 목록을 대조한다. 이 문서는 준비 및 의사결정 기록이며 실제 실행 결과는 아래에 별도로 기록한다.

## 현행 안정성 기준

| 항목 | 시간·반복 | 판정 |
| --- | --- | --- |
| 단독 | 각 인스턴스 180초 | 32개 순차 측정 96분 |
| 동시 | 각 확정 조합 1800초 | 서로 다른 자원 조합을 누락하지 않음 |
| 대표 고부하 | 전체 조합 중 하나 3600초 | 해당 조합의 1800초를 대체; family마다 추가하지 않음 |
| 오류 복구·handover | 각 100회 | 기존 유지 |
| loss·예상치 못한 reset·guard 손상 | 0 | 기존 유지 |

동시 조합 수 N일 때 순차 측정은 `96 + 30*N + 30`분이다. N=2/4/6이면 3시간 6분/4시간 6분/5시간 6분이며 준비·복구·분석·재시험 시간은 제외한다. 대표 조합은 단독 기능 검증 후 실제 동시 buffer 교체·처리 부하와 자원 사용 근거로 실행 전에 고정한다. 최대 지원 속도 보증이나 기존 2시간과의 동등성은 주장하지 않는다.

[시험 JSON](../../tests/hil/nu54dk/v04_test_plan.json)을 원본으로 생성 문서를 갱신한다. 일반 기능 campaign 기본 기간 0과 최대 7200초는 보존한다. 단독/동시/대표 시간은 실행에 명시하고 실제 연속 시간을 기록한다. 여러 설정을 중간마다 종료하는 기능 sweep가 전체 instance의 연속 안정성 근거를 대신하지 않는다. 이전 98번과 역사 기록의 원본 값·검사 결과는 유지한다.

## 결선 검사 준비 — Fixture 501 revision 1

[공통 결선 catalog](../../tests/hil/nu54dk/v04_common_fixture.json)의 17신호+GND만 사용한다. P1.06/P1.07 두 data 선만 교차하며 다른 신호는 동일 GPIO끼리 1:1이다. GPIO P2.07/P2.08, 전원 레일, 외부 출력과 외부 풀업은 포함하지 않는다. 이전 408/420/430의 catalog·확인서 의미는 변경하지 않는다.

검사 펌웨어는 부팅 시 17개 신호를 입력으로 두고 명시적인 arm 뒤에만 약한 pull-up과 단일 open-drain LOW를 사용한다. HIGH를 push-pull로 출력하지 않는다. 한 선씩 LOW로 당겨 양쪽 모든 선을 관측하고, 해제 뒤 복귀를 확인한다. A→B/B→A를 각 3회 반복해 단선·교차 오류·선간 연결·stuck level을 판정한다. 한 LOW는 최대 500ms이고 Host 통신이 끊겨도 펌웨어가 해제한다. arm lease는 10초이며 만료되면 핀을 입력으로 반환한다.

임의 주소/핀 명령을 받지 않으며 핀 소유권과 다른 HIL 모드의 배타 관계를 검사한다. 계측용 HAL 경로이므로 checker 통과를 Arduino GPIO API·GPIOTE 기능 PASS로 확대하지 않는다. USB 등 다른 GND 경로가 존재할 수 있어 이 검사는 GND 점퍼 자체의 연속성이나 접촉 저항을 독립적으로 증명하지 않는다. 전원·스위치·GND 연결은 사용자 확인과 함께 사용한다.

실행은 새로 열거한 exact UID, SWD 10 MHz, 배타 lock, `auto_unlock=false`, sector flash, controlled reset/halt/identity/start를 사용한다. 새 source·HEX·catalog hash와 30분 이내 실제 사용자 확인을 대조한다. 이전 COM/확인 시각을 복사하지 않는다. 실패 원본과 cleanup을 보존하며 실패가 있으면 다음 출력 모드로 진행하지 않는다.

## 자동 진행과 현장 조작의 경계

T12 기능 → T13 복구/동시/안정성 → T15 지원 범위 → T16~T18 사용자 설치 경로/문서/공개 준비 → R14/T19 RC 고정 및 전체 회귀 → T20/T21 비공개 패키지 재현·설치·업로드까지 자동으로 가능한 작업을 진행한다. 결함이 발견되면 T14 수정과 영향 회귀를 수행한다. T22에서 exact commit·최종 자산·검사 결과를 제시하고 사용자 승인을 받는다. 승인 전 tag/Release/공개 index 쓰기는 하지 않는다.

현재 17신호 결선은 남은 PWM/GPIO/GPIOTE/QDEC/I2S를 묶기 위한 것이다. 통신의 넓은 동시 topology, PDM 회귀, System OFF 복구, 설치본 예제의 출력 배치는 별도로 대조해야 한다. 해당 배선·DAP 스위치·USB 재연결이 필요하면 현장 조작을 요청한다. 공통 결선 하나로 승인 직전까지 무인 완료가 보장되는 상태는 아니다. 자동화 프로그램·heartbeat/cancel도 필요한 만큼 구현/검증하며 timeout이나 확인서 만료를 제거해 무인 실행으로 보이게 하지 않는다.

## 잠정 일정

현재 미구현 시험·통합 작업을 포함한 계획 예산이며 측정된 완료 ETA가 아니다. 큰 결함 없이 진행될 때 결선 checker 준비/실기 1~2시간, 남은 T12 시험 보완/실기 6~12시간, T13 준비·복구·안정성 5~8시간, 지원 범위/사용자 통합 4~8시간, RC/패키지/설치 회귀 4~8시간으로 **약 20~40시간의 실제 작업 시간**을 잡는다. 현장 조작 대기·CI 대기와 결함 수정/재시험은 별도이며 각 단계 완료 후 실제 측정으로 다시 추정한다. 안정성 순수 측정 3~5시간만으로 릴리스 준비 전체가 끝나는 것은 아니다.

65b0c7b 기반 구현 작업 트리에서 전체 Host 87그룹·총 701개 중 **699 PASS·2 조건부 SKIP**, pair target **2/2**, 계약 45·package 20·정렬 379개 및 inventory를 통과했다. SKIP은 설치 Arduino CLI 조건과 의도한 dirty-source M27이며, clean commit 후 M27을 따로 재검사한다. 새 checker Host 6개, 시간/시험표 11개, 기존 fixture 12개도 통과했다. [준비 manifest와 원본 압축 로그](evidence/t12-common-wiring-preparation-65b0c7b/manifest.json)에 명령·시각·SHA를 보존했다.

10:45 읽기 보조 assertion은 이전 postflight의 A PIN_CNF=0을 기대했지만 재연결 후 실제 값은 2여서 실패했다. 기존 기대값을 현재 보드 상태로 재사용한 진단 오류이며 두 값 모두 입력 방향이다. 원본을 보존하고 고정 SDK의 DIR bit로 17개 전부를 다시 읽었다. 10:47:36 UTC 두 exact UID·0d7f382 identity·CPUID·SLEEPING, PWM/DPPI off와 양쪽 17개 입력을 확인했다. 이 두 읽기는 reset/halt/flash나 GPIO 변경을 하지 않았다.

사용자의 17신호+GND 그대로라는 응답 수신 뒤 관측 시각은 10:40:02 UTC다. 새 source/HEX 확인서는 이 현재 배선 확인에 묶고 실제 실행 전에 30분 유효시간과 보드/스위치 조건을 대조한다. 준비 build C:/wic04는 작업 트리 검사이며 flash에는 다음 clean commit의 새 build를 사용한다.

### 첫 결선 검사 — 8c1cfe2, P1.10 전달 실패

Exact 8c1cfe2의 clean pair build 2/2와 clean M27 9/9를 통과했다. 10:58:15~10:58:34 UTC controlled flash/start와 첫 검사를 실행했다. 두 flash는 SWD 10 MHz·단일 CMSIS-DAP 명령·sector erase로 성공했으며 mass erase/recover는 하지 않았다. [실행 원본](evidence/t12-common-wiring-8c1cfe2/result.json), [journal](evidence/t12-common-wiring-8c1cfe2/result.json.jsonl), [SHA manifest](evidence/t12-common-wiring-8c1cfe2/manifest.json)에 보존한다.

- 양쪽 17개 baseline 입력은 모두 HIGH였고, 방향은 입력·pull-up/소유권 mask는 0x1FFFF였다.
- A→B P1.14 첫 LOW/해제는 양쪽에서 일치해 1 net-round PASS다.
- 다음 A→B P1.10은 A raw level=0x1FFFD·output direction=0x2였으나 B raw level=0x1FFFF로 LOW가 전달되지 않았다. B 방향은 입력이며 다른 신호도 HIGH였다. 배선 위치/접촉 또는 다른 전기적 원인은 아직 확정하지 않는다.
- 즉시 양쪽 STOP을 수행했다. 두 snapshot에서 output direction/pull-up/owned mask=0, active LOW=none, armed=0을 확인했다.
- 합계 **1 PASS·1 FAIL·100 net-round 미실행**이다. B→A와 pulse/lease 자동 해제 실기는 아직 미실행이며 전체 결선 PASS가 아니다.

사용자에게 두 USB를 분리한 뒤 A GPIO P1.10(P4-8)↔B GPIO P1.10(P4-8)의 위치·접촉 확인과 재연결을 요청했다. 다른 16신호+GND는 유지하도록 안내했다. 결과를 실패 상태로 보존하고 다음 PWM/stream 출력 시험은 시작하지 않는다. 새 확인 뒤 별도 결과 파일로 재시험한다.

8c1cfe2는 main에 푸시했다. 이전 65b0c7b의 Software와 Reproducible 두 workflow는 SUCCESS를 확인했으며 8c1cfe2 이후 원격 검사는 별도 확인한다. 사용자용 진단 HEX/ELF·build record·catalog·안내를 8c1cfe2 이름의 ZIP으로 내보내고 각 파일 SHA-256과 ZIP 무결성을 검사했다. 정식 공개 패키지나 RC가 아니다.
