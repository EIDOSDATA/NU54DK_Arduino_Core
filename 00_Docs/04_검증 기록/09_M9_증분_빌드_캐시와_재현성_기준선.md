# M9 증분 빌드, 캐시와 재현성 기준선

## 1. 목적과 결론

M9는 Arduino IDE/CLI가 매번 다른 임시 빌드 경로를 사용하더라도 동일한 Sketch와 동일한
Zephyr 구성은 같은 영구 Ninja 트리를 재사용하게 만드는 단계다. 구현과 자동 회귀 결과는
다음과 같다.

- Sketch 및 일반 Arduino library의 소스 본문 변경은 같은 cache key를 유지한다.
- `prj.conf`, `app.overlay`, Core/module, DTS, 보드 package, NCS 및 toolchain 변경은 새
  cache key를 선택한다.
- 새 key는 최초 한 번만 `--pristine=always`로 구성한다.
- 무변경 build와 Arduino 임시 build 경로 변경은 같은 persistent tree를 재사용한다.
- 손상된 `build.ninja`는 `build-graph-recovery`로 진단하고 같은 key에서 명시적으로 pristine
  복구한다.
- cache별 운영체제 lock, 진단용 JSON metadata, 상태 전이, 입력 manifest, 접근 시각, quota와
  LRU 정리를 구현했다.
- 전용 ccache namespace와 통계를 build manifest에 기록한다.

M9 완료 조건을 모두 충족했으며 결과는 **완료**다.

## 3. 영구 캐시 구조

기본 root는 다음과 같다.

~~~text
%LOCALAPPDATA%/NUCODE/NU54DK_Arduino_Core/build-cache/
├─ v1/<2자리>/<32자리 directory key>/
│  ├─ input-manifest.json
│  ├─ state.json
│  ├─ access.json
│  ├─ app/
│  └─ build/
└─ compiler-cache/
~~~

Windows의 object 경로 제한을 피하기 위해 directory에는 SHA-256 앞 128 bit를 사용한다. 전체
64자리 SHA-256은 `input-manifest.json`의 canonical 내용으로 재계산할 수 있으며
`state.json`, Arduino session context와 artifact manifest에 저장한다. 기존 directory의
전체 digest가 현재 입력과 다르면
`E_CACHE_KEY_COLLISION`으로 중단하므로 축약 key 충돌이 다른 build tree를 재사용하게 하지
않는다.

Arduino `{build.path}/nu54-zephyr/context.json`은 작은 session pointer다. 실제
`app/`과 `build/`는 위 persistent entry에 있으며 Arduino의 임시 경로가 바뀌어도 Sketch
root와 구성 입력이 같으면 같은 entry를 가리킨다.

`NUCODE_BUILD_CACHE_ROOT`로 root를 변경할 수 있다. 자동 회귀는 전역 사용자 cache를
오염시키지 않도록 시험별 임시 root를 사용한다.

## 4. Cache key 계약

정렬된 canonical JSON을 SHA-256으로 계산하며 다음을 포함한다.

- cache schema와 Build Adapter version
- platform root, Core/module/variant/DTS/template 내용 지문
- FQBN, Zephyr board와 sysbuild 여부
- canonical Sketch root
- Sketch `prj.conf`와 `app.overlay` 내용 hash
- 보드 package root, 정확한 Git revision과 board content hash
- NCS root, sdk-nrf/Zephyr revision과 manifest/version file hash
- toolchain root, bundle ID, `environment.json`, manifest와 compiler version

`.ino`, Sketch `.cpp/.c` 및 일반 Arduino library source 본문은 key에 넣지 않는다. Arduino가
생성한 Sketch source는 cache 내부 `generated-sources/`에 category와 상대 경로를 보존한
logical source ID로 mirror된다. 외부 library source는 private `"Config.h"` 같은 include 의미를
보존하기 위해 원래 위치에서 컴파일한다. 두 경우 모두 Ninja dependency와 내용 변경으로 증분
컴파일하며 Arduino `{build.path}`의 임시 prefix는 source identity에 들어가지 않는다.

Core/module, 보드, config처럼 ABI 또는 generated header를 바꾸는 입력은 새 tree를
선택한다. 개발 checkout의 dirty Core도 content hash로 즉시 분리된다.

## 5. 상태, 잠금과 실패 복구

Cache 상태는 다음 순서로 원자적으로 기록한다.

~~~text
configuring → ready → building → ready
                       └──────→ failed
~~~

동시성의 권위는 Windows의 `Global\\NUCODE_NU54_*` named mutex와 POSIX의 `flock`이다. 운영체제가
process 종료와 crash 때 lock을 자동 회수한다. `.adapter.lock`에는 PID, host, 작업명, 생성 시각과
무작위 token을 진단용으로만 기록하며 직렬화 여부를 이 JSON만으로 판단하지 않는다. Probe lock은
사용자별 임시 경로가 달라도 동일 probe UID에서 같은 논리 mutex를 사용한다. M9 cache는 local
filesystem 전용이며 UNC/network root는 명시적으로 거부한다.

새 key와 손상 복구에서만 pristine configure를 사용한다. CMake cache와 `build.ninja`가 모두
정상이고 입력 manifest/state가 일치하면 prepare configure를 생략한다. 손상 복구 횟수와
이유는 context와 `state.json`에 남는다.

새 build는 session context를 `built` 상태로 만들기 전까지 upload할 수 없다. build가 성공한 뒤
ELF/HEX/BIN/map, 공개 artifact manifest와 session context를 하나의 publication transaction으로
교체한다. 예외와 `Ctrl+C`가 발생하면 이전 generation 전체를 복원하며, rollback 자체가 실패하면
수동 복구 backup 경로를 보존한다. 따라서 실패 뒤 오래된 firmware를 현재 결과처럼 upload할 수
없다.

## 6. ccache와 quota

NCS bundle의 ccache를 다음 전용 namespace로 실행한다.

~~~text
<build-cache-root>/compiler-cache
~~~

기본 compiler cache 상한은 2 GiB다. `CCACHE_COMPILERCHECK=content`를 사용하고 build 전후
`--print-stats` 차이를 context와 artifact manifest에 기록한다.

Build tree 자동 정리 기본값은 다음과 같다.

| 설정 | 기본값 | 환경 변수 |
| --- | ---: | --- |
| 전체 build tree 용량 | 12 GiB | `NUCODE_BUILD_CACHE_MAX_BYTES` |
| build tree entry 수 | 8 | `NUCODE_BUILD_CACHE_MAX_ENTRIES` |
| compiler cache 용량 | 2 GiB | `NUCODE_CCACHE_MAX_SIZE` |

LRU 정리는 현재 build, 활성 lock과 `.pin` entry를 건너뛴다. 삭제 대상은 schema namespace
내부의 정확한 key directory인지 canonical path로 확인한다.

## 7. 관리 명령

~~~powershell
tools\nu54-builder\nu54-builder.cmd cache list
tools\nu54-builder\nu54-builder.cmd cache inspect <64자리-cache-key>
tools\nu54-builder\nu54-builder.cmd cache prune
tools\nu54-builder\nu54-builder.cmd cache remove <64자리-cache-key>
tools\nu54-builder\nu54-builder.cmd cache clear
tools\nu54-builder\nu54-builder.cmd cache clear --include-compiler
~~~

`clean-build`는 현재 Arduino session이 참조하는 build tree 한 개만 제거하고 compiler cache는
보존한다. `cache clear`는 비활성 build tree 전체를 지우며 `--include-compiler`를 명시한
경우에만 compiler cache도 지운다.

## 8. 자동 검증

### 8.1 Host 계약

~~~powershell
python -m unittest discover -s tests/host -p "test_*.py" -v
~~~

결과: 전체 **43/43 PASS**.

M9 host 시험은 canonical key, 128-bit directory/full digest 보존, target/NCS/Zephyr/
toolchain/board invalidation, content fingerprint, Arduino build path 독립 source ID, 외부 library의
private-header 의미, OS lock 직렬화와 crash 회수, probe logical mutex, entry/byte quota의
current/pinned/active LRU 보호, 잘못된 key/활성 lock/축약 key 충돌 삭제 차단, publish transaction
rollback, stale upload 차단, clean 후 재생성과 상태 전이를 검증한다.

### 8.2 실제 Arduino CLI 증분 회귀

~~~powershell
python tests/arduino-cli/run_smoke.py `
  --tests library parallel m9 `
  --evidence build/m9/m9-smoke.json
~~~

결과: `library`, `parallel`, `m9` **3/3 named group PASS**. `library` group은 Sketch-local header,
일반 사용자 library와 전이 dependency를 발견하고, 동일 이름 library root를 A에서 B로 바꿨을 때
stale source record 없이 같은 key/tree의 실제 compile provenance가 B로 전환되는지 확인한다.
`parallel` group은 서로 다른 Sketch 격리를 확인한다. `m9` group은 다음 11개 시나리오를 한
세션에서 자동 판정한다.

| 시나리오 | 기대 | 결과 |

## 9. 실측 기준선

실측값은 현재 개발 PC의 단일 실행이며 다른 PC에 대한 성능 보장은 아니다. 정확성 gate와
성능 회귀의 비교 기준으로만 사용한다.

| 시나리오 | prepare configure | link/build | ccache 핵심 변화 | cache 크기 |
| --- | ---: | ---: | --- | ---: |
| cold | 15.13 s | 93.43 s | miss 255, direct hit 1 | 27.20 MB |
| no-change | 0 s | 1.23 s | compiler 활동 0 | 27.20 MB |
| Sketch 한 줄 수정 | 0 s | 3.57 s | miss 1, direct hit 1 | 27.20 MB |
| 다른 Arduino build path | 0 s | 1.12 s | compiler 활동 0 | 27.21 MB |
| 같은 key 병렬 worker 1 | 0 s | 1.46 s | compiler 활동 0 | 27.21 MB |
| 같은 key 병렬 worker 2 | 0 s | 1.33 s | compiler 활동 0 | 27.21 MB |
| `prj.conf` 새 key | 18.95 s | 74.78 s | miss 255, direct hit 1 | 27.21 MB |
| `app.overlay` 새 key | 14.18 s | 88.75 s | miss 255, direct hit 1 | 27.22 MB |
| `module.yml` 새 key | 18.38 s | 80.03 s | miss 255, direct hit 1 | 27.22 MB |
| DTS binding 새 key | 14.08 s | 74.43 s | miss 255, direct hit 1 | 27.22 MB |
| `build.ninja` 복구 | 18.00 s | 13.49 s | direct hit 256, miss 0 | 27.15 MB |

`link/build` 시간은 Adapter의 final link 단계 전체 wall time이며 source graph 변경 시 발생한
non-pristine link configure를 포함한다. cold build의 link configure는 evidence에 별도로
기록됐으며
no-change 및 Sketch 수정에서는 0 s였다. Cache 크기는 십진 MB로 표시했다.

새 configuration key는 별도 Ninja tree를 만들기 때문에 최초 build 비용이 든다. 반면
무변경 build와 Sketch/library source edit는 동일 tree를 유지한다. 시간 목표를 임의로
정하지 않고 이후 같은 도구 identity에서 이 기준선과 비교한다.

## 11. 범위와 후속 작업

- 원격 binary cache 서비스는 지원하지 않는다.
- 서로 다른 NCS/toolchain identity 사이에서 tree를 공유하지 않는다.
- bit-for-bit ELF 동일성은 timestamp와 tool 출력까지 고정하는 release package 단계에서 별도
  관리한다. M9는 cache key, `.config`, DTS, source graph와 artifact provenance의 일치를
  보장한다.
- clean Windows의 최초 SDK 설치와 Boards Manager lifecycle은 M10에서 검증한다.
