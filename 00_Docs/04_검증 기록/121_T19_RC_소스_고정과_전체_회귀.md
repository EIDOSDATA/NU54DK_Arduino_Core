# T19 RC 소스 고정과 전체 회귀

## 결론

**R14와 T19를 완료했습니다.** `051567ba449e3ecf26ff80bab741ac636b123eba`의 runtime
source를 고정해 Host·계약·inventory·문서·전체 v0.4.0 target build와 RC package 이중
재현성을 확인했습니다. 기능 결함은 발견되지 않았고, 최초 target build 실패는 Windows archive
도구의 260자 경로 경계로 원인을 특정해 짧은 출력 경로를 강제한 뒤 해결했습니다.

이 기록은 T20 Boards Manager 설치 수명주기와 T21 stable 후보 검증을 대신하지 않습니다.
tag·GitHub Release·stable index 공개도 수행하지 않았습니다.

## Windows 경로 실패와 해결

첫 실행 `C:\r14`와 단일 worker 재현 `C:\t19`에서
`nucode.t16.peripheral_profile`의 CRACEN archive 단계가 다음 object를 읽지 못했습니다.

```text
cracen_spake2p_key_management.c.obj: No such file or directory
```

컴파일 오류가 아니라 object의 최종 절대 경로가 `C:\t19`에서도 **261자**가 되어 legacy
`arm-zephyr-eabi-ar.exe`의 Windows 경로 경계를 넘은 문제였습니다. 단일 worker에서도 동일하게
재현됐으므로 병렬 build 경쟁은 원인이 아닙니다. `run_zephyr_build.py`가 허용하는 Windows 출력
경로 길이를 4자로 제한하고, 가장 긴 T16 crypto object가 259자 이하인지 계약 검사에 추가했습니다.

수정 commit `051567ba`에서 `C:\t`로 전체 그룹을 새로 만들었고 35개 모두 성공했습니다.
실패 원본은 로컬에 보존했으며 핵심 hash는 다음과 같습니다.

## RC package 이중 재현성

프로젝트 소유자 승인만 남습니다.
