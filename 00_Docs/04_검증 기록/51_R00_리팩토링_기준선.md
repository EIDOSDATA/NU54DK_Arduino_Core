이 표는 actual source 확인이며 새 실패 재현 결과가 아니다. 각 수정에서 production 함수를 사용하는
Host/fault-injection 시험으로 수정 전 실패와 수정 후 통과를 같은 입력에서 기록한다.

Fixture 201~203/301은 `v04_fixture.py`의 style 0/1/2를 통해 sync와 async를 모두 실행한다.
`fixture_hil.cpp`에서 style 1은 SPIM/TWIM `transfer()`, 다른 style은 `transferAsync()` 및
다음 buffer 제출이다. 동기 성공 뒤 controller count는 요청값으로 기록하므로 이것만으로 DMA 완료를
증명하지 않는다. Host는 양쪽 terminal·실제 RX snapshot·byte 수를 독립 Python pattern과 대조하고
random seed·방향별 salt·STOP/guard를 확인한다. 기존 PASS는 해당 실행의 유효한 역사 증거로 유지한다.

새로 확인한 runner metadata 제한: DATA scope가 모든 style에 `asynchronous-single-or-double-buffer`로
기록된다. R10의 runner 회귀에서 실제 sync/async에 맞춰 새 결과만 교정하고 과거 evidence는 수정하지 않는다.

이 표는 책임 계획이다. 각 분할 직전에 실제 신규 파일명·함수·context owner·include/IRQ/CMake 연결의
상세 대응표를 작업 기록에 확정한다. 여러 파일에 mutable extern을 늘리거나 새 resource manager를
추가하지 않는다. API·enum·schema·pin/SDK/board 변경과 전역 format은 구조 분할에 섞지 않는다.

R02는 제출 시 operation generation을 확정한다. 요청 ID 없는 driver는 abort/STOP과 pending IRQ
정리로 이전 callback이 다음 operation에 도달하지 않는 경계를 먼저 증명한다. 늦은 callback에 단순히
현재 generation을 붙이는 방식은 사용하지 않는다. 성공·cancel/error에서 DMA 종료가 확인되면 buffer를
반환하고, 미정지 timeout은 fault·lease·buffer 소유를 유지하며 재사용을 거부한다.

R03는 IRQ writer와 thread reader가 같은 짧은 ISR-safe 보호를 사용한다. 진단 pair를 함께 읽고
overflow는 가득 찬 event queue와 별도로 관측한다. stop 상태·세대를 예약한 뒤 장시간 대기에서
공유 mutex를 풀고, 다시 획득한 뒤 동일 세대·상태를 확인한다. ISR buffer 공급 시점은 유지한다.

Host SKIP은 M13 설치 discovery opt-in과 작업 문서가 dirty인 동안 clean-checkout 전용 M27 검사다.
예제 발견은 별도 `examples` gate로 PASS했고, clean 상태 검사는 commit 후 실행한다. Compiler 부재
또는 native 동작 시험 SKIP은 없었다.

대표 build는 `run_zephyr_build.py --group all --jobs 4`에 아래 10개 `--suite`를 명시해 실행했다.
전체 49개 target gate를 대신하지 않는다. Output root는 `C:/r00`이며 기존 폴더를 재사용·삭제하지 않았다.
숫자는 bundled Arm `size`의 text+data 및 data+bss byte 합계다. 각 ELF의 public/global defined symbol을
`nm --extern-only --defined-only --demangle`로 저장했으며 R07 이후 같은 profile 비교에 사용한다.

기존 Fixture 301의 record 1,986개·cleanup 2개·campaign 2개, 10 MHz SWD·실패 0과 image/result
