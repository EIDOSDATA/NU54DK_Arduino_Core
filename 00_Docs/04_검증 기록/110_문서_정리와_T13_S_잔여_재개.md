## 당시 결과

S 순서 1~3의 확정 완료는 **37/58 조건(63.8%)**, 잔여는 **21 조건**이다.
이는 정상 안정성 36/36과 별도 집계다. 가장 최근 실제 실행은 source `3f4a18906f6d72df45f5a07f901b6a7aef716a2a`,
build `C:/t5t04`의 RX 공급 지연이며, 2026-09-09 15:44 KST까지 두 역할 각 400/400을 완료했다.
현재 hardware process는 종료 상태이고, 이번 문서 정리 중 보드·GPIO·펌웨어는 조작하지 않았다.

U는 **소프트웨어 준비 완료·재결선/실기 NOT RUN**이다. S 마감 뒤 U 준비까지가 목표이며,
QDEC 재진단과 Serial handover는 사용자 지시로 제외한다. 이미 완료한 정상 36 조건이나
자원 충돌의 면제된 900 회를 새로 예약하지 않는다. RC·정식 공개도 수행하지 않았다.

## 당시 다음 실행 경계

사용자는 시간제 재확인 요구를 폐기하고, 손대지 않은 현재 결선의 GPIO 연결성을 먼저 확인한 뒤
정상일 경우 끝까지 계속하도록 지시했다. **문서에 남은 30 분/12 시간 사용자 확인 만료를 재개 장애로 사용하지 않는다.**
구형 runner의 시간 검사 코드 자체는 이번 문서 정리에서 바꾸지 않았으므로 실기 재개 전 정합화가 필요하다.
이는 firmware pulse/watchdog/lease, exact UID·image 검증, 배타 probe lock,
controlled sector flash·`auto_unlock=false`, 양쪽 STOP·clock·핀 반환 검사를 폐기한 것이 아니다.

문서 정리 후 첫 하드웨어 작업은 S 전체 17 신호 연결성 확인이다. 현재 재검사는 아직 NOT RUN이다.
문제가 발생하면 GPIO 연결성을 다시 확인하고, nRF54L15의 CMSIS-DAP 디버거로 최초 오류 시점의
GPIO·PSEL·DMA·UARTE/I2S/TWI·clock·SCB/NVIC·RAM을 보존해 원인을 분리한다.
새 관측 없이 같은 수정과 시험을 무한 반복하지 않는다. 원본 보존 → 원인에 맞는 한정 수정 →
영향 회귀 → 해당 정식 조건의 새 실행 순서다. U에는 실제 결선 변경과 별도 설정 확인이 필요하다.

## 해결한 원인과 수정

### UART line 오류: 제품의 RX 정지·pending abort와 fixture 시작 순서

- source 8f6596d의 callback trace 진단에서 role1 event queue overflow와 error mask 2/4/6을
  관측했다. 약 509 µs에 callback 32 건이 들어왔고, 오류가 난 RX를 계속 유지한 것이 첫 제품 원인이다.
  source 16f298b는 첫 hardware error 뒤 async RX abort를 요청했다. 그러나 abort가 진행 중일 때
  lifecycle STOP이 `-EINPROGRESS`를 받은 뒤 소프트웨어 flag를 먼저 지워 UARTE ENABLE이 남았고
  정상 재시작이 wrong-state7로 실패했다. source 46b7dc2는 pending abort를 기다린 뒤 상태를
  정리한다. 관련 UART/T13 Host·문서·계약·정렬 gate와 원격 Windows Host가 통과했다.
  trace ON CMSIS-DAP에서는 정리 뒤 active/RX/cancel0, UARTE ENABLE/INTEN/RXTO/SHORTS0,
  XO/PLL off와 핀 반환을 확인했다. [진단·gate·레지스터 원본](evidence/t13-uart-error-stop-diagnosis-46b7dc2/manifest.json).
- trace OFF source 46b7dc2에서 UART20 A parity 예행·100 회를 먼저 통과했다. 이어 이전에 실패했던
  UART20 A·UART22 A break와 UART20/21/22/30 B break, UART20 B·UART21 A/B·UART22 A/B·
  UART30 A parity를 각각 예행 뒤 100/100 완료했다. source b6ac3bef의 기존 UART21/30 A break와
  합쳐 break8/8이며, 아래 UART30 B까지 합쳐 parity8/8이다. 각 100 회 감사값은 양쪽 cleanup 303 그룹,
  idle 600기록, expected-fault200 건과 최종 17 핀 반환이다. SDK Python/pyOCD 경로 문제로 보드 실행
  전 끝난 UART20 A break 예행 2 건도 삭제하지 않았다.
  [신규 break6·parity7 원본](evidence/t13-uart-break-parity-results-46b7dc2/manifest.json).
- source 46b7dc2 UART30 B parity는 89 회 완료 뒤 90 회차 최초 오류가 mask 14
  (parity+framing+break)여서 즉시 중단했다. 허용 mask 2/6을 14로 넓히지 않았다. CMSIS-DAP로
  cleanup 뒤 양쪽 UARTE30 ERRORSRC/ENABLE/INTEN/EVENTS_ERROR/RXTO0, XO/PLL off, PSEL disconnect와
  context active/TX/RX/cancel0을 확인했다. [nRF54L15 UARTE 정의](https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/uarte.html-topic?contentId=IH1i5evkVp96RAHz1B~e5g)는
  RXD가 한 data frame보다 오래 active LOW일 때 BREAK를 세우고 reception 자체는 계속한다고 명시한다.
  8N1 peer의 정상 frame에는 stop HIGH가 있으므로 무작위 payload를 BREAK 허용 근거로 삼지 않았다.
- parity 러너가 DUT RX를 먼저 시작하고 그 뒤 peer TX를 시작해, PREPARE 뒤 아직 구동되지 않은 선을
  DUT가 잠시 관측할 수 있었다. source 2e4ec73은 parity에서 peer TX를 먼저 시작하도록 바꾸고 Host
  회귀로 명령 순서를 고정했다. exact 로컬 UART/T13/docs/contract/style와 T13 두 역할 target,
  원격 Software gate를 통과했다. 일반 pair suite를 잘못 고른 첫 build는 image 검사에서 보드 기록 전
  거부해 보존했고 T13 전용 새 build만 사용했다. UART30 B는 예행 1 회와 본시험 100/100을 통과했다.
  본시험은 cleanup 303 그룹·idle 600·expected-fault200·최종 핀 반환을 독립 재감사했다.
  [90 회차 실패·디버거·수정 gate·최종 PASS](evidence/t13-uart30-b-parity-start-order-2e4ec73/manifest.json).

### 연속 통신: UARTE 완료 버퍼 재공급과 TWIS 승격 버퍼 등록

cdf33d67의 C01 role1 정식 시도는 99 회차와 13 회차에 실패했다. TWI22 DWT 100 회는 적중 0,
네 lane 감시에서는 89 회차 role2 UART30이 먼저 기록됐다. 비대칭 TX 고구동 비교도 role2 UART30
43 회차 framing·role1 UART21 14 회차 framing/break로 실패해 **TX drive만의 원인 가설은 기각**했다.

c21e57a2의 제품 수정은 다음 두 경로다.

- UARTE: 최초 두 RX DMA 뒤 `rx_buffer_needed`가 발생해도 완료 버퍼를 다시 공급하지 않았다.
  `provideReceiveBuffer()`에 active/cancel/lease/completed 상태·nrfx 호출 경합 검사를 추가하고
  HIL이 완료 slot을 즉시 재공급하도록 했다. 독립 20 ms phase에서 열리던 수신 공백을 닫는 수정이다.
- TWIS: 두 번째 queued TX/RX를 current로 승격하면서 실제 hardware pointer를 prepare하지 않았다.
  completion event를 노출하기 전에 `nrfx_twis_tx_prepare()`/`nrfx_twis_rx_prepare()`를 호출하고
  실패를 명시적 event로 남겼다.

Exact c21e57a2의 T13 Host 134/134·style 418/418·docs 225·contract 45·DUT/peer target와
Software Gates run34305312825를 통과했다. DUT HEX SHA는 `6da48b51...bb46`, peer는
`80de8867...79e5`이며 전체 hash와 Windows 임시 실행파일 차단·PDM 4/4 재실행도
[C01 수정 원본](evidence/t13-c01-buffer-fix-c21e57a2/manifest.json)에 보존한다.

후속 C01 정상 900 초는 네 lane 진행·오류 0으로 통과했다. CTS A는 secure register 진단 주소 보완 뒤
새 100/100, B는 첫 정식 repeat28에서 TWIM DATA_NACK·TWIS 205/256으로 실패했다.
SDA 연결성 200/200·불일치 0을 확인하고, 한정 DWT 진단 100 회와 **별도 정식 재실행 100/100**을 통과했다.
최종 RX/TX 256/256, ERRORSRC·DMA BUSERROR 0, SDA=P1.10·SCL=P1.14와 양쪽 STOP/idle을 확인했다.
최초 DATA_NACK를 삭제하거나 DWT 진단 횟수를 정식 PASS에 합산하지 않았다.

### RX 공급 지연: fixture의 재시작 DMA slot 순서

`81231574-rxdelay-r1-dwt-01`은 `complete()`의 lane_error=3을 포착했다.
UARTE20 TX/RX AMOUNT는 각각 1024, PSEL은 정상, DMA bus-error 주소는 0이었다.
두 버퍼가 모두 반환된 뒤 누적 완료 수가 홀수이면 다음 expected slot은 1인데,
fixture는 재시작마다 slot 0부터 제출했다. source `3f4a1890`은
`lane.received.completed % 2`로 첫 수신 버퍼를 선택하도록 수정했다.

관련 Host 12·style 418·docs·contract·exact DUT/peer target를 통과했고
Software Gates run34316184454의 Windows Host도 PASS다.
예행은 역할 A 4/4·B 4/4, 정식은 각 역할 UART20/21/22/30 × 100 회 = 400/400이었다.
두 정식 campaign마다 전체 S 결선 105 건, cleanup 803 그룹과 최종 STOP/idle을 확인했다.
이 결과는 제한된 2 ms 공급 지연 복구이며 무제한 RX 지연이나 새 180 초 안정성 결과가 아니다.

## 당시 I2S 실패 경계와 미완료 부분 — 후속 완료는 111번

- source 6ba43ce0 원래 경로 `B P1.06 SDOUT -> A P1.07 SDIN`은 B 공급 중단 뒤 7 회차 재시작에서
  A 수신 27 word가 불일치했다. A 패드 observer는 3,821전이를 보았고 수신 데이터 3,819와는 2차이지만
  기대 4,085보다 264 부족했다. B TX RAM·DMA·I2S 설정과 양쪽 guard는 정상이었다. 따라서 A DMA/RAM
  내부보다 실제 A SDIN 패드 또는 그 앞의 B 출력·보드 간 경로가 먼저 소실된 경계다.
- source ad62e1f1은 현재 두 data 선을 물리 변경하지 않고 반대로 사용하는 진단을 추가했다. 최초 실행은
  firmware dispatcher가 mode2를 거부해 I2S에 도달하지 못했고, source da070998이 이를 수정했다.
  다음 실행은 role1 sample729에서 1 word 불일치로 중단됐다. 실패 레지스터의 `PSEL.SDOUT=P1.06`,
  `PSEL.SDIN=P1.07`은 공급 중단 전 단계가 여전히 원래 경로였음을 증명했다. 이 결과를 교환 경로
  실패로 쓰지 않았다.
- source 4d01c262은 mode2일 때 공급 중단 전과 재시작 뒤 모두 같은 교환 경로를 선택하도록 Host runner를
  수정하고 명령 순서 단위시험을 추가했다. exact T13 Host 134·style 418·docs 225·contract 45, 두 역할
  target과 원격 Software 7/7을 통과했다.
- 교환 경로 `B P1.07 SDOUT -> A P1.06 SDIN`은 B underrun 실제 관측 100 건과 STOP 뒤 새 seed 재시작
  **100/100**을 통과했다. A의 100 회 물리 전이 합계는 관측 1,635,317, 기대 1,635,145, 수신 1,635,145이며
  회차별 관측-수신 최대 차이는 4다. 실패·미확정 0, cleanup 203, 양쪽 idle 400기록을 확인했다.

따라서 nRF54L15 I2S 주변장치·DMA·클록·공통 소프트웨어 경로는 교환 endpoint에서 정상이고, 남은
결함 경계는 원래 `B P1.06 출력/A P1.07 입력` endpoint 쌍과 그 사이 물리 경로다. 현재 고정 S 결선은
한 endpoint만 다른 핀에 연결할 수 없어 B P1.06과 A P1.07을 개별 분리하지 못한다. 이를 숨기고
교환 경로 결과를 formal 정상 soak로 소급하지 않는다. 실패·dispatcher 거부·선행 경로 오류·교환
100 회와 exact gate 원본 51 개는 [I2S endpoint 진단 manifest](evidence/t13-i2s-endpoint-diagnosis-4d01c262/manifest.json)에
원문 SHA-256과 deterministic gzip으로 보존했다. 종료 시 두 보드 STOP, clock reference0, 핀 idle이며
hardware process는 없다.

해당 net6의 무flash 200-pulse 재검사 도구와 생성 검사는 준비됐지만
이번 정리 시점 재검사는 NOT RUN이다. 교환 경로의 진단 100 회를 원래 경로의 formal 1 조건으로 올리지 않는다.
