# M22 v0.3.0-rc.2 통합 릴리스 기준선

| 항목 | 내용 |
| --- | --- |
| 기록 ID | VALIDATION-M22-RC2-001 |
| 대상 | `v0.3.0-rc.2` |
| 판정 | **준비 중 — package, tag, 공개 자산과 gate evidence 미확정** |
| Core commit | 실행 전 미확정 |
| Board package | 실행 전 exact gitlink 기록 |
| 기준 SDK | NCS v3.4.0 / Zephyr 4.4.0 / Toolchain `dcbdc366a1` |

| 문서 작성일 | 2026-09-02 |

## 1. 목적과 판정 경계

M22 RC2는 AC-01~AC-03과 M19~M21의 개발 결과를 8개 library·29개 예제 package로 통합하고,
공개 Boards Manager URL의 전체 설치 수명주기를 다시 검증하는 release gate입니다.

RC1 public clean-room은 tagged harness가 Nordic 설치 leaf를 먼저 만들어 중단됐습니다. RC2는
그 교정을 새 source identity에 포함하고 모든 필수 gate를 새로 실행합니다. RC1의 fixed gate
PASS를 RC2 PASS로 복사하거나 상속하지 않습니다.

현재 상태는 다음과 같습니다.

- RC2 source commit과 annotated tag: **미확정**
- 두 번의 독립 package byte 재현성: **NOT RUN**
- RC2 Public Prerelease와 7개 자산: **미공개**
- Host, package examples와 RC upload fixed gate: **NOT RUN**
- Public URL 기반 동일 PC 격리 clean-room: **NOT RUN**
- M22 RC2 final evidence: **미생성**
- Stable `v0.3.0`: **범위 밖, 아직 공개 아님**

## 2. RC1 erratum 선행 조건

RC2 실행 전에 다음 교정이 source와 host test에 함께 포함돼야 합니다.

1. Clean-room 준비 단계는 격리 run root와 일반 작업 directory만 만듭니다.
2. `ncs/v3.4.0`과 `ncs/toolchains/dcbdc366a1` exact install leaf는 미리 만들지 않습니다.
3. Nordic installer가 두 leaf를 직접 생성합니다.
4. Layout host test는 상위 `ncs`와 state directory가 존재하면서 두 install leaf가 없음을
   검증합니다.
5. 교정 runner의 exact path, size와 SHA-256을 RC2 plan에 기록합니다.

RC1 실패의 원본 identity와 증거는
[RC1 clean-room 검증 중단 기록](<../05_릴리스/13_v0.3.0_rc1_cleanroom_검증_중단_기록.md>)에
보존합니다.

## 3. Stable 불변 guard

RC2는 stable package index를 생성하거나 덮어쓰지 않습니다. 실행 전후 다음 identity가 모두
같아야 합니다.

| 항목 | 고정 값 |
| --- | --- |
| Stable index | `package_nucode_nu54dk_index.json` |
| 크기 | 1,877 byte |
| SHA-256 | `5ae7fbe13f71c52950879064685694cf4b062557572f187e81476639724e5344` |
| Git blob | `b2a3ac2d4c3babf366541406764e5f900f2f4e6d` |
| Stable version 순서 | `0.2.0`, `0.1.0` |

RC2는 별도 per-tag `package_nucode_nu54dk_rc_index.json`을 사용합니다. RC1, 과거 RC,
`v0.1.0`, `v0.2.0`의 tag와 자산도 변경하지 않습니다.

## 4. RC2 공개 자산 allowlist

Public Prerelease에는 다음 7개만 공개합니다.

1. `nucode-nu54dk-zephyr-0.3.0-rc.2.zip`
2. `nucode-nu54dk-zephyr-0.3.0-rc.2.CHECKSUMS.sha256`
3. `nucode-nu54dk-zephyr-0.3.0-rc.2.license-inventory.json`
4. `nucode-nu54dk-zephyr-0.3.0-rc.2.release-manifest.json`
5. `nucode-nu54dk-zephyr-0.3.0-rc.2.THIRD_PARTY_NOTICES.md`
6. `nucode-nu54dk-zephyr-0.3.0-rc.2.spdx.json`
7. `package_nucode_nu54dk_rc_index.json`

Plan, private evidence, HIL log, final evidence와 stable index는 Release 자산이 아닙니다. 두 독립
package build의 filename, size, SHA-256과 전체 byte가 같을 때만 plan을 확정합니다.

## 5. Package와 예제 계약

| Profile | 수 | Library |
| --- | ---: | --- |
| Standard | 22 | NUCODE NU54DK 17, Wire 1, SPI 1, Servo 1, EEPROM 1, LittleFS 1 |
| BLE | 7 | NUCODE BLE 6, NUCODE BLE Security 1 |
| 합계 | 29 | 8개 bundled library |

Package lock은 library directory, 예제 이름과 profile을 exact 목록으로 고정해야 합니다. Source
tree compile과 설치 archive compile을 구분하며 설치본 evidence는 RC2 plan의 exact Core와
board revision을 보고해야 합니다.

## 6. 필수 gate

| Gate | 현재 상태 | 완료 조건 |
| --- | --- | --- |
| `host` | NOT RUN | 전체 host/CI/release contract와 install-leaf 회귀 PASS |
| `package-examples` | NOT RUN | RC2 archive 설치 뒤 예제 29/29 compile PASS |
| `rc-upload` | NOT RUN | 설치본 Blink의 지정 CMSIS-DAP UID Upload, mass erase 없음 |
| `cleanroom` | NOT RUN | 공개 RC2 URL에서 설치·29개 compile·Upload·수명주기·cleanup PASS |

각 fixed gate evidence는 RC2 plan SHA-256과 target commit에 묶여야 합니다. Probe UID는 evidence와
public log에 기록하지 않습니다. 네 gate가 정확히 한 번씩 PASS하기 전에는 final evidence를
생성하지 않습니다.

## 7. 실행 순서

1. Final source와 문서를 clean commit으로 push하고 Core/board worktree를 확인합니다.
2. Exact commit에서 package를 두 번 생성해 byte-for-byte 비교하고 plan을 검증합니다.
3. Host, package-examples와 rc-upload fixed gate를 실행합니다.
4. Exact commit에 annotated tag `v0.3.0-rc.2`를 만들고 push합니다.
5. 정확히 7개 자산의 Public Prerelease를 `validation in progress` 상태로 공개합니다.
6. Tag target, 익명 asset 크기·SHA-256과 stable index 불변을 확인합니다.
7. 공개 RC2 index에서 새 exact run leaf로 동일 PC 격리 clean-room을 실행합니다.
8. Clean-room 설치본 29개 compile, 지정 UID Upload, downgrade/upgrade, uninstall/reinstall을
   확인합니다.
9. Marker, evidence hash와 reparse 검사를 통과한 exact run leaf만 자동 정리합니다.
10. 네 evidence를 RC2 final evidence로 결합합니다.
11. Release 설명만 validation 완료 상태로 갱신하고 tag와 자산은 교체하지 않습니다.

## 8. Clean-room cleanup 계약

- 모든 mutable Arduino, NCS, Toolchain, cache와 profile 경로는 새 exact run leaf 아래에 둡니다.
- 실행 전 install leaf 미생성 회귀를 통과해야 합니다.
- 성공 시 marker의 run ID/token, 외부 evidence path/hash와 reparse point 부재를 확인합니다.
- 승인된 parent의 직접 자식인 exact run leaf 하나만 삭제합니다.
- Parent, sibling run과 외부 evidence/log는 보존합니다.
- 실패하면 조사할 수 있도록 run leaf를 자동 삭제하지 않습니다.

## 10. 완료 조건

M22 RC2 완료는 다음 조건을 모두 충족해야 합니다.

- Exact clean source, board gitlink와 runner byte가 RC2 plan에 고정됨
- 두 독립 package build가 byte-identical
- Public Prerelease에 allowlist 7개만 존재하고 익명 다운로드 hash가 plan과 일치
- 설치본 29개 예제 compile과 지정 UID Upload PASS
- Public URL 동일 PC 격리 clean-room 전체 수명주기와 cleanup PASS
- Stable index의 크기, SHA-256, blob과 version 순서 불변
- Final evidence가 네 필수 gate를 정확히 한 번씩 결합
- 알려진 제약, migration, testing과 troubleshooting 공개

하나라도 미완료면 상태는 준비 또는 검증 진행으로 유지하며 `v0.3.0` stable 지원을 선언하지
않습니다.
