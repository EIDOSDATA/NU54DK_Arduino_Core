# 245 — M31 P2 CS 장기 연속성·중단 상태 진단

## 판정 경계

두 exact NU54DK의 보안 연결과 Arduino `RasInitiator`/`RasReflector` 경로에서
CS raw 결과를 300~1,000개 수집했다. 모든 실행은 probe/COM 역할을 먼저
검증하고 자동 unlock 없이 sector flash 또는 reset-halt-drain-resume으로 시작했다.
원본에는 image SHA-256, 익명화한 probe hash, UART 및 STOP 결과가 있다.
이 진단 중 저장소에 미커밋 변경이 있었으므로 `source_clean=false`이며,
각 결과는 해당 image·부하의 실기 판정이지 clean-source 릴리스 근거가 아니다.

기존 라이브러리는 subevent가 abort되어도 procedure 전체가 `COMPLETE`면
`local_busy`를 유지했다. 해당 abort에는 상대 RAS callback이 오지 않을 수
있으므로 다음 정상 procedure가 `busy`로 연쇄 폐기될 수 있다. 또 늦게 도착한
이전 counter의 RAS callback이 현재 counter의 로컬 step과 잠금을 지웠다.
첫 수정은 abort 시 현재 로컬 step/잠금을 정리하고, counter가 다른 RAS callback은
현재 step을 건드리지 않게 했다. 그러나 확장 진단에서 325·427번은 **같은
procedure의 abort된 subevent 뒤 정상 subevent**가 들어온 것을 확인했다.
첫 수정의 counter 전체 폐기 정책이 두 번째 정상 callback까지 버렸다.
이에 procedure abort와 subevent abort를 분리하고 후자는 다음 subevent가
다시 로컬 step을 수집하도록 바꿨다. 두 번째 수정도 1,000건 두 image에서
연속성을 닫지 못했다. 컨트롤러의 **실제 CS 동기화 실패**를 가짜 raw 성공으로
바꾸지는 않는다.
위 500건 두 번의 PASS는 첫 수정 효과의 관찰이지
모든 RF 조건·fragmented RAS·최대 procedure의 완료 판정이 아니다.

623번은 controller callback 두 건 모두 abort가 없고 마지막 96 step을 보고했지만
Arduino raw로 전달되지 않았다. 624번의 6 step·RTT 0은 외부에서 유효한 거리
결과로 사용할 수 없다. 623번의 RAS 도착 순서/결합과 624번의 부분 결과 발생
조건은 미확정이다. 확장 진단의 `P2_CS_MISSING`은 STOP 시점에 controller가
앞서간 counter까지 출력해 수백 줄이 되었으므로 그 뒤쪽은 실제 누락으로
계산하지 않는다. 시험 sketch는 전달된 마지막 counter까지만 출력하도록 고쳤다.

진단 callback은 `NUCODE_P2_CS_DIAGNOSTICS`를 켠 시험 sketch에만 넣었다.
controller callback의 `step_data_buf`는 callback 순서에 따라 다른 소비자가
길이를 변경할 수 있으므로 그 길이 flag만으로 controller 원본 buffer가
비었다고 단정하지 않는다. 위의 abort status/reason·reported step은 별도
header 값이다. 512-counter 진단 image의 정적 RAM 95,310 B와
1,024-counter 확장 진단의 110,158 B는 관찰 배열을 포함하며,
관찰 배열이 없는 수정 image는 80,458 B였다. 이 차이를 제품 최적화 절감량이나
동일 조건의 stack high-water로 비교하지 않는다.

첫 관찰 배열 없는 1,000건 실행의 CS initiator stack 최고치는 `BT RX WQ`
1,520/3,200 B, `BT LW WQ` 936/2,104 B, `BT GATT DM WQ` 352/1,304 B,
`MPSL Work` 504/1,024 B, main 1,048/8,192 B, ISR0 600/2,048 B다.
이는 해당 정상·단발 누락 부하의 관찰값일 뿐, 내부 SDC pool high-water나
모든 연결/오류 경로의 안전 여유가 아니다. 따라서 stack·heap·controller
pool을 이번 결과만으로 축소하지 않는다.

## 남은 gate

2차 수정 진단에서 정상 callback 뒤 누락된 89·149·262·408번을 RAS 도착 순서·
로컬 단일 버퍼의 busy/drop·queue 상태로 분류해야 한다. 90·106·446·971번은
RF sync abort reason 2이며 유효 raw로 세지 않는다. 623번 정상 callback 뒤
누락과 624번 불완전 raw도 별도 원인을 추적한다.
진단 전용 image의 27번 `busy`는 하나의 로컬 절차 버퍼가 상대 RAS
도착 전 다음 controller callback을 거부하는 경로를 직접 보여준다.
다만 한 건의 추적만으로 모든 정상 callback 누락의 원인을 동일하게 확정하지 않는다.
고정 NCS의 `nrf/subsys/bluetooth/services/ras/rreq/ras_rreq.c`도 실시간
구독마다 `counter_in_progress`와 peer 출력 버퍼를 각각 하나씩 사용한다.
완료 callback 뒤 그 버퍼를 재설정하므로, 로컬 버퍼만 두 개로 늘리는 변경을
RAS 전달 연속성의 충분조건으로 간주하지 않는다. 로컬 busy와 RAS segment
도착·완료 순서를 같은 counter 기준으로 함께 계측해야 한다. 이는 소스 구조에서
도출한 다음 진단 조건이지, 현재 누락의 단일 원인 확정은 아니다.
절차 간격을 네 배로 늘리는 완화안만으로도 누락이 사라지지 않아, 원래
5-event 설정을 유지한다. 간격만 바꾼 image를 native 동등 비교나 수정 완료
근거로 사용하지 않는다.
최대 procedure·fragmented RAS·재연결/오류 복구의 메모리 및 연속성,
반사기 역할의 동적 사용량과 native 동등 조건 비교도 남는다. P2 전체와
M31-W05/W06은 이 기록만으로 완료하지 않는다.
