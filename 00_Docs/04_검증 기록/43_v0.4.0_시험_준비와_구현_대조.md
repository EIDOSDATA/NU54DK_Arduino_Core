## 1. 준비와 실기 상태의 분리

[시험 목록](<../01_아두이노 코어 설계/12_v0.4.0_기능_시험_목록.md>)은 75개 identity와 19개
시험 family를 연결한다. JSON의 숫자는 초기 engineering 기준이며 기존 실측값이나 최고 속도
보증이 아니다. API/clock/배선 성립 조건을 대조하고 executable vector로 고정하기 전까지 T01은
부분 준비다. `verify_v04_test_plan.py` 성공은 대상 누락·문서 drift 검사이며 물리 PASS가 아니다.

현재 source/build/semantic 표시는 inventory의 이전 근거를 인용한다. 최신 실제 온보드 근거는
[41번](41_M24_M26_온보드_protocol_교정과_실기_재검증.md)의 `51c1986`에 한정된다.
새 계획의 1MHz UART, flow/error, 100회 반복, 600초/7,200초 soak는 아직 수행하지 않았다.

## 4. 보드와 회로도 대조

읽기 전용 조회에서 기존 DUT UID 끝 `fd7d106d`는 COM5/COM6, peer 끝 `c887aaf1`은 COM7/COM8로
동시에 열거됐다. COM 번호 자체를 역할의 영구 ID로 사용하지 않는다. 이 조회는 SWD 응답·flash·시험 PASS가 아니다.

회로도 9페이지 전체를 PNG로 렌더해 읽었다. Page 1/2의 모듈 pin과 공유선, 3의 전원/PMIC,
6의 UART/SWD enable, 7의 I2C pull-up, 8의 button/LED, 9의 header를 대조했다.
원본 PDF에 이미 일부 `Cannot open file` 그림 placeholder가 있고 Poppler가 Symbol/ArialUnicode
대체 font 경고를 냈다. 중요한 연결선·pin 표·스위치 회로는 판독되며 PDF 자체는 수정하지 않았다.

- 두 보드는 각자 USB 전원 사용. 공통 GND와 승인 signal만 연결하고 VBUS/VEXT/VBAT/3.3V/VDD_MOD끼리 연결하지 않는다.

### 첫 통합 검사 실패와 수정

`866852f`의 첫 target 검사(`C:/nb/06`)는 기존 18개 build-only 성공, 새 pair 2개는
SPIS compatible node 부재로 Kconfig 단계에서 실패했다(408.70초). 기존 M24 SPI overlay와
같이 disabled SPIS node를 명시했다. Driver를 켜거나 warning 전체를 무시하지 않는다.
Host 전체 검사에서는 v0.4.0 suite 수의 옛 기대값 18과 새 실제값 20이 달라 실패했다.
기대값을 20으로 갱신하고 재검사한다. 실패한 image의 flash는 수행하지 않았다.

추가로 controlled reset 직후 SRAM의 identity/request/response marker를 HALTED 상태에서
지워 이전 boot의 ready 값이 새 시작 확인으로 오인되지 않도록 했다.

### 두 보드 진단 — 단독 PASS와 통합 실패를 분리

`34475a0`은 Host 전체, 문서 142개, inventory와 target 20/20 build-only를 통과했다
(451.47초, `C:/nb/07`). Pair preflight에서 두 exact UID·role·HEX/ELF/source를 확인했다.
첫 통합 HIL은 DUT ping 뒤 PMIC 100kHz 첫 전송에서 `stop_timeout`으로 중단됐다.
SWD와 CPU는 응답했고 CFSR/HFSR는 0이었다. 동일 source의 기존 단독 TWIM20/21/22
400kHz 시험은 다시 3/3 PASS다. 따라서 USB 인식 실패나 보드 고장으로 확정하지 않는다.

별도 진단에서 두 보드 모두 TIMER00은 10,000us에 약 80,024 ticks, TIMER10은 약
20,005 ticks, TIMER20은 약 10,003 ticks를 반환했다. 분주 계산이 모든 instance에
16MHz base를 가정한 결함을 확인해 실제 HAL base clock으로 계산하도록 수정했다.
128/32/16MHz와 범위·2의 거듭제곱 분주 경계는 production helper를 Host C++로 검사한다.

내부 VDD 단발은 두 보드 모두 4092 raw와 정상 STOP을 반환했다. 뒤이어 VSS 시작은
실패했다. nrfx의 공통 enum 전체가 nRF54L15 입력은 아니며, pinned SDK의 이 칩 mapping은
VDD·AVDD 및 제공되는 DVDD다. 불가능한 입력은 configure 단계에서 거부하고 무배선
ADC 시험은 VDD/AVDD로 교정했다. 이는 VSS를 구현했다고 보고하는 변경이 아니다.

통합 I2C 실패 원인은 계속 분리 시험한다. 새 통합 image의 400/100kHz와 반환 코드를

두 role만 선택할 수 있으나 evidence gate를 `m12-zephyr-build-subset`으로 구분하며
최종 전체 group 회귀를 대체하지 않는다.

### NFC pad 설정 누락 분리와 온보드 UART 통합 준비

`01fc2d7`의 pair 2/2 build-only와 Host 전체는 통과했으나 PMIC는 100/400kHz,
SWD 유지/명령 중 분리 네 조합 모두 같은 timeout이었다. 속도·SWD polling만의 문제는 아니다.
기존 단독 image와 overlay를 직접 대조하니 새 pair에 `&uicr { nfct-pins-as-gpios; };`가
빠져 있었다. PMIC의 P1.2/P1.3은 NFC pad라 해당 선언을 추가하고 누락 회귀 검사를 넣었다.
실기 재시험 전에는 원인 해결 PASS로 승격하지 않는다.

같은 pair image에 온보드 UARTE20/21/22/30 arm/status/stop 명령을 준비했다.
독립 TX/RX pattern, 1~1024 byte 단일/이중 buffer, 16-byte guard와 사용하지 않은
padding, parity/flow control을 판정할 기반이다. UART payload 전송·실기 판정은 다음 검사다.

첫 UART 통합 build(`0143ddc`, `C:/nb/09`)는 Zephyr minimal C++ 환경에 `<cstring>`이 없어
2개 role 모두 compile 실패했다. 기존 C library의 `<string.h>`/`memset`으로 교정했다.
실패 image는 flash하지 않았다.

`6a45403` pair 2/2 build PASS(60.18초) 뒤 DUT의 PMIC 3 instance × 100/400kHz와
44개 TIMER capture는 통과했다. 이로써 NFC pad 설정 누락이 통합 PMIC 실패의 원인이었음을
재현/교정했다. ADC AVDD 판정은 4092 raw 포화로 실패했고 peer에는 아직 진행하지 않았다.
Pinned nrfx default는 gain=1/internal 0.9 V로 VDD와 AVDD 둘 다 포화될 수 있다.
후보 channel 설정에 nRF54L15의 8개 gain을 추가하되 기존 기본값 1은 유지하며,
내부 rail 시험은 gain=1/4(3.6 V full scale)로 바꾼다. 외부 reference pin 지원은 추가하지 않는다.
기존 포화 PASS는 변환/STOP의 증거이지 rail 전압 정확도 또는 full-range ADC 검증이 아니다.

### 격리 checkout과 반복 UART 진단

사용자가 원본 checkout에서 코드 정렬만 수행 중임을 확인했다. 정렬 변경은 보존하고
`C:/nb/s04` / `codex/v04-prep-20260905`에서 exact source 검사와 구현을 이어간다.
`e4b70ab`의 `C:/nb/11` build는 끝났지만 원본 dirty 검사로 flash 전에 거부됐다.
격리 checkout의 같은 source를 `C:/nb/12`에서 새로 2/2 build-only(67.96초)했다.

DUT의 내부 rail은 gain=1/4에서 VDD 3740~3756, AVDD 1008~1064 raw로 구분됐다.
MDK는 AVDD를 내부 **0.9 V rail**로 정의한다. AVDD 판정은 이상적 1024 code의 ±25%
(768~1280)로 명시하고, VDD 2500~4000과 겹치지 않게 한다. 이는 정밀 교정 검사가 아니다.

같은 실행에서 PMIC 사용 후 UARTE20 activate가 실패했다. Fresh boot UART sweep는 진행돼
약 50개 조합 뒤 1Mbps/flow/1024에서 수신 timeout이 났지만 그 조합의 별도 fresh 실행은
DUT에서 통과했다. Peer는 첫 port discovery 때 다른 VCOM의 잔류 109 byte 때문에 중단됐다.
두 보드 전체 UART PASS로 세지 않는다.

이를 분리하기 위해 UART discovery를 **firmware TX challenge → 유일 VCOM 선택**으로 바꿨다.
두 COM에 무작정 payload를 보내지 않고, port를 유지하며 설정 변경 뒤 pre-arm 100ms quiet를
확인한다. 그 이전 폐기 bytes는 기록하고, arm 이후 noisy/truncated/다른 port 응답은 계속 거부한다.
64 vectors × 4 onboard instances, DMA buffer state, 무수신 cancel과 TWIM↔UART handover를
공통 runner에 연결했다. 흐름 제어를 켠 데이터 통과와 강제 CTS backpressure 검증은 구분한다.

UARTE adapter는 disabled block의 공유 DMA READY(RXSTARTED)와 SHORTS를 초기화한 뒤
nrfx를 시작한다. 실제 ENABLE이 남아 있으면 소유권을 우회하지 않고 거부한다. nrfx가
부분 초기화 후 실패하면 uninit하며 새 activation에서 이전 이벤트 큐를 분리한다.
이 수정의 target/물리 회귀는 다음 실행에서 확인한다.

`e61594a` Host 전체와 pair 2/2 build(69.77초)는 통과했다. DUT UARTE20은 64개 vector와
cancel·TWIM↔UART handover까지 통과했고 UARTE21의 1Mbps/no-flow/1024×2에서 중단됐다.
중단 후 SWD 조회는 첫 buffer complete, 두 번째 DMA-owned, 오류 0으로 반환했다.
Pinned nrfx 문서에 따르면 `RX_ENABLE_CONT` 없이 다음 buffer를 시작하면 ISR에서 START하므로
무흐름제어 고속 전송에서 gap 동안 FIFO가 넘칠 수 있다. API에 기본 false의 명시적
`continuous_receive`를 추가하고, 32 byte 이상 이중 buffer에서만 허용한다. ISR 지연은
한 buffer 소비 시간보다 짧아야 하며 무한 queue/무제한 지연 보증이 아니다. HIL은 해당
경로를 선택하고 단일/1-byte buffer는 기존 interrupt-linked 방식으로 구분한다.
모든 timeout은 실패로 남기며 재시도 성공으로 앞선 실패를 덮어쓰지 않는다.

### 두 보드 primitives 완료와 UART 64-byte 손실 위치

`5e6ef07` pair 2/2 build-only는 65.33초에 통과했다(`C:/nb/14`). 별도
`--onboard-suite primitives --rounds 100` 실행은 두 보드에서 **902개 판정 PASS**였다.
각 보드는 ping 1, TWIM20/21/22 × 100/400kHz 각각 100회 묶음 6, TIMER 44 CC,
VDD/AVDD × 1/32 samples 각각 100회 400항목이다. I2C는 합쳐 1,200번 읽었으며
902는 각 묶음과 개별 ADC/capture 판정 개수이지 서로 다른 instance 수가 아니다.

- [두 보드 primitives PASS](evidence/5e6ef07/pair-primitives-5e6ef07.json)
- [UART burst FAIL](evidence/5e6ef07/pair-5e6ef07-smoke.json)
- [중단 후 RX SRAM 진단 — PASS 아님](evidence/5e6ef07/uart-stall-5e6ef07.json)

UART run은 DUT UARTE20, 1Mbps, parity off, flow on, 1024×2에서 실패했다.
`continuous_receive` 적용 후에도 같은 종류의 손실이 남았으므로 그것만으로 해결됐다고
하지 않는다. SWD 응답 정상/CPU sleeping, 오류 0, 첫 buffer completed/둘째 DMA-owned였다.
seed `1059724907`의 독립 expected 2048 bytes와 SRAM을 대조하면 첫 1216 bytes는 일치하고,
expected `[1216:1280]` **64 bytes가 누락**, 이후 768 bytes는 expected `[1280:2048]`와 일치한다.
마지막 64 bytes는 초기 `0xCC` 그대로다. 손실 위치는 첫/둘째 buffer 전환 직후가 아니었다.
이 관측만으로 USB bridge·Windows·AMD 또는 코어 중 어느 곳이 원인인지 확정하지 않는다.

다음 분리 진단은 `--uart-producer paced-64`를 명시한다. Host가 64 byte를 쓰고 해당
chunk의 wire 시간+2ms를 기다린다. 기본 `burst`는 그대로이며 자동 재시도/자동 속도 저하를
하지 않는다. 두 방식은 evidence에 따로 기록한다. Paced 성공도 무간격 고속 burst·최대 처리량
PASS가 아니며, 손실 원인 분리와 외부 peer 연속 전송 검증은 계속 남는다.

### DMA MAXCNT의 단위 교정 준비

Pinned NCS `v3.4.0`의 `nrf54l15_types.h`와 실제 HAL 대입식을 대조했다. PWM은
15-bit **byte count**라 uint16 값 최대 16383개(개별/파형 load는 4의 배수 16380),
SAADC는 15-bit **sample count** 최대 32767, I2S는 14-bit **word count** 최대 16383이다.
이들을 일괄 UINT16_MAX로 허용하던 후보 검사를 실제 단위로 교정한다. 나눗셈으로 먼저
상한을 계산해 크기 곱셈 overflow도 막으며 경계/경계+1/0/SIZE_MAX를 native Host로 검사한다.
이는 MAXCNT 조기 거부 보완이다. 전체 RAM 적합성·alignment·동적 queue 소유권·실물 overflow
시험까지 끝났다는 뜻이 아니다. T07에 계속 추적한다.
