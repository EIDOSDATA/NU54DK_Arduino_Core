## 1. 완료 범위

M28-W07은 2보드에서 확장 광고·PAwR·privacy와 기존 M19~M21 회귀를 수행하고, 3보드에서
mixed-role 2-link·periodic/PAST·link별 제어·1,800초 soak를 수행했다. W08은 실제 결과를
readiness 원장·현행 설계·TODO·인계 문서에 연결하고 M29 착수 경계를 고정했다.

정적 NCS source의 여섯 capability는 계속 `candidate`로 남긴다. 실제 HCI 6/6, Core 구현,
Host 시험, target build와 RF HIL은 각각 다른 증거이며 어느 하나로 나머지를 대신하지 않는다.

## 4. LINK 재연결 실패 진단과 수정

초기 3보드 LINK 실행은 callback 횟수만으로 재연결 성공을 계산해 peer 한쪽에서 곧 취소된
half-connection도 성공으로 셌다. 최종 조건으로 다시 실행하자 peripheral peer는 20회를 끝냈지만
mixed DUT가 `unexpected-link-disconnect`로 닫혔다. 실패 transcript는 다음 디렉터리에 그대로
보존했다.

- `m28-w07-10231641-b3-link-final`
- `m28-w07-48c38627-b3-link-final`
- `m28-w07-8fb2390a-b3-link-final`
- `m28-w07-ab15d11f-b3-link-final`
- `m28-w07-1500785d-b3-link-final`
- `m28-w07-1500785d-b3-link-swap-diagnostic`

BLE RF 경로라 확인할 보드 간 GPIO 결선은 없었다. 대신 세 보드의 DAP identity, SWD IDCODE와
3.3 V target 전압을 먼저 재확인했다. CMSIS-DAP으로 mixed DUT의 SRAM 상태와 fault/error 상태를
읽은 결과는 다음과 같았다.

| 진단 | 관측 |
| --- | --- |
| Mixed incoming callback | 최초 1 + 재연결 20 = 21회 |
| Central의 실제 public connection | 최초 1 + 재연결 19 = 20회 |
| GAP 마지막 오류 | `BLEError::driver_error` = 17 |
| Zephyr/HCI 원인 | driver `-2`, HCI `UNKNOWN_CONN_ID` |
| Fault/queue 상태 | fault register 0, event drop 0 |
| 보드 교환 진단 | F/G peer 역할을 바꿔도 동일 실패 — 특정 보드 RF 결함 제외 |

원인을 한 번에 섞지 않고 다음 순서로 수정·동일 조건 재검증했다.

1. `48c38627` — 실제 `bt_conn_info.role`과 고정 role slot을 대조하고, 이미 소유한 pointer의 중복
   callback과 성공처럼 도착한 unowned connection을 거부했다.
2. `8fb2390a` — 이전 generation object가 실제 recycle된 뒤에만 재연결할 수 있도록
   `BLEEvent::connection_recycled`를 추가하고 `bt_conn_cb.recycled`를 main-thread event로 전달했다.
3. `ab15d11f` — peer advertising 재시작과 central 재연결 순서를 object recycle 이후로 옮겼다.
4. `1500785d`의 10초 connection timeout 가설은 더 이른 실패를 만들어 기각했고 최종 source에서
   되돌렸다.
5. `289e3d10` — discovery·subscription 뒤 `LINK_UP` GATT write를 상대가 수신해야만 양쪽의 같은
   generation 재연결을 성공으로 계산하도록 protocol을 강화했다. HCI `UNKNOWN_CONN_ID`는 recycle
   뒤 최대 3회의 유한 재시도만 허용하고 `attempt_failures`를 evidence에 남겼다.

같은 세 보드·같은 역할·같은 수치 조건으로 다시 실행한 `289e3d10…`에서 LINK가 PASS했다.
최종 PASS의 `attempt_failures=0`이며 timeout 확대나 이유 없는 무한 재시도로 통과시키지 않았다.

## 6. 지원 경계와 M29 인계

M28에서 검증한 첫 공개 자원 경계는 총 2-link, local central 1 + peripheral 1, extended advertising
set 1개, periodic sync 1개와 compile-time 고정 queue/payload storage다. 기존 `BLEDevice`,
`BLEAdvertising`, `BLEScan`, `BLEConnection` symbol과 handle 없는 central 우선 호환 view를 유지한다.

M28은 link별 GAP 수명·상태·event와 link-control 격리를 검증했다. 기존 GATT client는 local central
link를, GATT server는 실제 subscribe한 incoming link를 사용하지만, 두 link의 임의 동시 GATT 작업과
동시 security/bond 정책 확대는 M28 지원 주장에 넣지 않는다. GATT/CoC 확장은 M29, security/profile
확장은 M30에서 별도 자원·상호운용 계약과 함께 검증한다.

다음 작업은 M29 ATT/GATT·L2CAP이다. 시작 전에 deprecated signed write와 experimental EATT의
공개 정책, long/reliable operation·descriptor/cache·LE CoC의 고정 자원과 malformed/credit/
starvation 시험을 확정한다. Mobile/desktop cross-vendor 상호운용, Bluetooth qualification과
v0.5.0 공개는 아직 완료로 주장하지 않는다.
