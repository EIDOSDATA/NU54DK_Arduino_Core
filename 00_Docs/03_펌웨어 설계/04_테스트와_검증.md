## 1. 문서 목적

이 문서는 Loader 없는 Native Full Zephyr 방식의 NU54DK Arduino Core를 어떤 계층에서 검증하고, 단계 완료를 어떤 증거로 판단할지 정의한다. 실행하지 않았거나 증거를 회수하지 못한 항목을 성공으로 표시하지 않는다. 예제의 존재, compile 성공, hardware 동작 및 Arduino 호환성은 서로 다른 증거다.

관련 문서는 다음과 같다.

- [M3 GPIO·시간·Scheduler 기준선](<../04_검증 기록/03_M3_GPIO_시간과_Scheduler_기준선.md>)
- [M6 기본 Arduino API, Serial과 인터럽트 기준선](<../04_검증 기록/06_M6_기본_Arduino_API_Serial과_인터럽트_기준선.md>)
- [M7 Wire·SPI·ADC·PWM 기준선](<../04_검증 기록/07_M7_Wire_SPI_ADC_PWM_기준선.md>)

시험의 목표는 다음과 같다.

- Arduino API의 signature와 실제 의미를 검증한다.
- Arduino CLI에서 만들어진 Sketch가 완전한 Zephyr firmware로 빌드되는지 검증한다.
- NCS/Zephyr thread, Kconfig 및 Devicetree와 Arduino runtime의 공존을 확인한다.
- 실제 NU54DK의 GPIO와 주변장치 route를 검증한다.
- pyOCD/CMSIS-DAP 및 외장 J-Link의 build/upload/debug 경로를 독립적으로 확인한다.
- 증분 build와 cache가 빠르기 전에 먼저 정확한지 검증한다.
- 고정 release artifact가 clean Windows 환경에서 재현되는지 확인한다.

## 2. 시험 원칙

1. **계층을 혼동하지 않는다.** Host test 통과는 실제 GPIO 동작 증거가 아니며, Blink 통과는 전체 API 호환 증거가 아니다.
2. **지원 선언에는 증거가 필요하다.** `지원` 상태는 signature, semantic, Zephyr coexistence 및 HIL 시험이 모두 연결되어야 한다.
3. **negative test를 포함한다.** 잘못된 pin, 비활성 peripheral, 충돌 overlay와 timeout이 조용히 성공해서는 안 된다.
4. **일반 Flash와 Recovery를 분리한다.** 정규 test에서 mass erase나 recover를 사용하지 않는다.
5. **실측 전 성능 목표를 만들지 않는다.** cold/warm build 및 flash 기준값을 먼저 수집한 뒤 허용 회귀 폭을 정한다.
6. **고정 revision을 시험한다.** Core, board submodule, ArduinoCore-API, NCS, Toolchain과 test fixture revision을 결과에 기록한다.
7. **재현 가능한 명령을 남긴다.** GUI 버튼만 누른 결과는 명령·설정과 artifact가 없으면 release 증거로 충분하지 않다.
8. **하드웨어 안전을 우선한다.** 출력끼리 직결하거나 GRTC/PWM과 button 단락 가능성이 있는 pin을 무검토로 시험하지 않는다.
9. **Skip을 Pass로 계산하지 않는다.** 장비나 기능이 없으면 `SKIP` 또는 `BLOCKED`로 기록한다.
10. **실패 원인을 보존한다.** 실패 log와 artifact도 재현과 회귀 분석에 필요하므로 성공 결과와 같은 방식으로 보관한다.

## 3. 결과 상태

| 상태 | 의미 |
| --- | --- |
| PASS | 사전에 정의한 조건과 oracle을 모두 만족 |
| FAIL | 명령은 실행되었으나 결과가 조건을 만족하지 않음 |
| BLOCKED | 환경, 장비, license 또는 선행 결함으로 시험을 실행할 수 없음 |
| SKIP | 해당 build/profile에서 의도적으로 적용되지 않으며 이유가 승인됨 |
| NOT RUN | 아직 실행하지 않음 |
| EVIDENCE MISSING | 시험 일부를 실행했지만 필수 trace 또는 log를 회수하지 못해 PASS로 판정할 수 없음 |
| FLAKY | 반복 결과가 일관되지 않아 지원 증거로 사용할 수 없음 |

`FLAKY`는 PASS와 같지 않다. 반복 성공률과 실패 log를 분석하고 원인을 제거한 뒤 다시 PASS 판정을 받아야 한다.

### 3.1 2026-08-27 M3 판정

M3는 sample·negative·실기·자동 회귀를 완료했다.

| 시험 또는 증거 | 현재 결과 | 판정 경계 |
| --- | --- | --- |
| `samples/zephyr/blink` | PASS | clean build와 LED0 점멸 육안 확인 |
| `samples/zephyr/gpio_input_smoke` build·버튼 육안 | PASS | clean build와 버튼에 따른 LED 동작 확인 |
| GPIO 입력 RAM trace | SKIP | 사용자 결정으로 M3 필수 증거에서 제외 |
| `samples/zephyr/runtime_timing` | PASS | 내부 timing·scheduler trace PASS |
| Core 비활성 negative | PASS | 일반 Zephyr 앱에 Core가 주입되지 않음 |
| `led0` 누락 negative | PASS | 자동 pristine build의 한국어 진단 일치 |
| 외부 GPIO/time 계측 | SKIP | 사용자 결정으로 M3 필수 증거에서 제외 |
| ztest/Twister | PASS | NU54DK device test 1/1, test case 9/9 |
| 32-bit rollover·긴 delay | PASS | production helper 경계값 주입 시험 3/3 |
| 실제 PM·전력 계측 | SKIP | 사용자 결정으로 M3 필수 증거에서 제외 |
| 외장 J-Link HIL | SKIP | M8 선택 경로에서 별도 검증 |

일반 build의 loop 반환 기본값은
`CONFIG_NUCODE_ARDUINO_LOOP_SLEEP_ONE_TICK=y`다. `runtime_timing` sample은 네 정책을
직접 비교하기 위해 `CONFIG_NUCODE_ARDUINO_LOOP_NONE=y`로 Core 자동 정책만 끈다. 이
override를 일반 기본값 변경으로 해석하지 않는다.

M3 build의 `runners.yaml`에는 `nrfutil`, `jlink`, `pyocd`가 available로 생성되고
flash/debug 기본 runner는 `pyocd`다. J-Link의 `nRF54L15_M33`, 4000 kHz metadata가
존재해도 실제 J-Link HIL PASS로 판정하지 않는다.

### 3.2 2026-08-27 M6 판정

M6는 공통 API, Serial과 interrupt 구현·자동 검증에 더해 실제 P1.13 버튼의 세 edge를
확인했으므로 **완료**로 판정한다.

| 시험 또는 증거 | 현재 결과 | 판정 경계 |
| --- | --- | --- |
| M4 API 계약 target 회귀 | PASS | 34,908 B FLASH / 15,032 B RAM |
| `serial_echo` pristine target build | PASS | 38,408 B FLASH / 17,528 B RAM |
| 실제 DAP UART Serial HIL | PASS | DAPLink sequence 7, COM10 READY와 고유 payload echo |
| `interrupt_button` pristine target build | PASS | 36,712 B FLASH / 17,200 B RAM |
| Arduino CLI staged package | PASS | SerialEcho와 InterruptButton 모두 Full Zephyr compile |
| Serial callback conflict | PASS | 의도한 configure/build 실패와 진단 일치 |
| `m6_core_api` pristine build | PASS | 295/295, 88,688 B FLASH / 29,448 B RAM |
| `m6_core_api` target ztest | PASS | Common 3/3, interrupt 2/2, Serial 5/5; 합계 10/10 |
| `serialEventRun()` runtime HIL | PASS | ELF strong `T`, DAPLink sequence 10/109,056 B, COM10 `serial_event=3 PASS` |
| 실제 P1.13 버튼 ISR edge | PASS | DAPLink sequence 25/COM10; FALLING 1, RISING 1, CHANGE 누름 1·해제 누적 2 |

target ztest는 GPIO emulator로 `FALLING`, `RISING`, `CHANGE`, parameter callback, detach와
`pinMode()` auto-detach를 결정적으로 검증했다. 실제 P1.13 active-low 배선에서도
누름=`FALLING`, 해제=`RISING`, 양 edge=`CHANGE` token을 회수했다. HIL 판정 계층만
35 ms 안정화를 사용했으며 Core의 raw edge 의미는 바꾸지 않았다. 로직 애널라이저,
오실로스코프 또는 신호발생기는 사용하지 않았다.

### 3.3 2026-08-27 M7 조건부 완료 판정

M7 target 의미 시험, Arduino CLI compile과 승인된 peripheral driver HIL을 완료했다. 실제
IMU 응답과 물리 SPI data 경로는 확인하지 못했으므로 다음 표에 제한을 분리해 기록한다.

| 시험 또는 증거 | 현재 결과 | 판정 경계 |
| --- | --- | --- |
| M7 Core target build | **PASS** | gain 1/4·SPI frequency·zero-byte probe 기준 pristine 310/310, FLASH 100,544 B/RAM 28,376 B |
| Wire emulator | **PASS** | seq20 COM10 target ztest 4/4 |
| SPI emulator | **PASS** | seq20 COM10 target ztest 3/3 |
| ADC/PWM emulator | **PASS** | seq20 COM10 target ztest ADC 2/2 + PWM 2/2 |
| Arduino CLI M7 smoke | **PASS** | exit 0; WireWhoAmI·SPITransaction·AnalogReadA0·PWMFade 4/4 compile/artifact, 전체 Kconfig y/n matrix·chosen·Sketch overlay 원문 병합 검증 |
| live build record provenance | **PASS** | configure와 동일한 Core input scope; public header·library metadata·DTS binding mutation마다 hash·dirty 변경과 복원 확인 |
| Builder incremental invalidation | **PASS** | `module.yml`과 DTS binding을 독립 변경할 때 같은 workspace에서 각각 재configure, pristine configure 누계 1 유지 |
| 전체 staged Builder 회귀 | **PASS** | session 87999, exit 0; blink·library·config·error·parallel·incremental·m6·m7 named group 8/8 |
| HIL host protocol unittest | **PASS** | 고정 0x6B IMU 5/5 + peripheral parser 5/5, 합계 10/10 |
| M7 config negative | **PASS** | Wire chosen 누락·non-SPI00 chosen·SPI00/uart00 충돌 3/3 expected-fail, stable diagnostic marker 일치 |
| 고정 I2C HIL | **미확정** | seq18/123,904 B와 COM10 고정 request까지 성공했으나 target RX 오류; 0x6A 접근·scan·fallback 없음 |
| A0 실기 | **PASS** | seq14 gain 1/6 `-EINVAL` 후 수정; seq17 gain 1/4 raw=3176, 범위만 검증 |
| PWM 실기 | **PASS** | seq17 duty 0/128/255 driver 실행; 실제 파형 주장 없음 |
| SPI controller 실기 | **PASS** | seq14 1 MHz/div128 `-EINVAL` 후 수정; seq17 4 MHz/div32, rx=0x00, data 경로 미검증 |
| 물리 SPI data 경로 | **미검증** | fixture가 없어 loopback/target data 일치를 주장하지 않음 |

seq20은 283,136-byte target ztest image를 DAPLink로 기록했고 COM10에서 1/1 configuration,
합계 11/11과
`PROJECT EXECUTION SUCCESSFUL`을 확인했다. 외부 logic analyzer, oscilloscope와 정밀
전압원은 M7 완료 조건이 아니다. 실제 SPI fixture가 없고 고정 0x6B IMU가 RX 오류로
식별되지 않았지만 0x6A 접근 금지를 지켰고 나머지 승인된 자동·실기 시험이 통과했다. 물리
SPI data 경로도 fixture가 없어 검증하지 못했으므로 M7을 **조건부 완료**로 판정한다.

첫 peripheral 실기 sequence 14에서는 ADC gain 1/6과 SPI 1 MHz가 각각 `-EINVAL`로
실패했다. Core overlay의 ADC gain을 1/4로, shipped SPI sample을 4 MHz로 수정한 뒤 sequence
17에서 166,400-byte image를 기록해 A0 raw=3176, PWM duty 0/128/255와 SPI driver
`rx=0x00`을 확인했다. seq17 runner의 장치 발견·flash/UART marker·peripheral oracle 검사는
9/9 PASS이며, 별도 peripheral parser unittest는 5/5다. 뒤이은 discover-only 실행에서
sequence 17이 유지되어 재flash가 없었음을 확인했다. 이 결과는 ADC 전압 정확도, PWM 파형,
SPI loopback/target data를 증명하지 않는다.

### 4.2 v0.1 OS 범위

Windows가 유일한 v0.1 필수 host다. Linux/macOS에서 우연히 동작해도 clean-machine CI와 실기 회귀가 없으면 공식 지원으로 표시하지 않는다. 이후 OS를 추가할 때 같은 path, package, build 및 upload 시험을 독립적으로 통과해야 한다.

### 4.3 공통 PowerShell 변수

~~~powershell
$CoreRoot = (Resolve-Path ".").Path
$BoardRoot = Join-Path $CoreRoot "board_package/NU54DK_Zephyr_DTS"
$Board = "nrf54l15dk/nrf54l15/cpuapp/nu54dk"
~~~

`<PROBE_UID>`, `<JLINK_SERIAL>`, `<NU54DK_FQBN>` 및 URL 표기는 해당 단계에서 실제 값으로 대체하고 결과 manifest에 기록한다.

## 5. 시험 계층

| 계층 | 실행 위치 | 검증 대상 | 검증하지 못하는 것 |
| --- | --- | --- | --- |
| Host unit | Windows host | 순수 C/C++ logic, parser, pin table 변환, cache key | 실제 Zephyr scheduler와 GPIO |
| ArduinoCore-API upstream | Host 및 target compile | 공통 `String`, `Print`, `Stream` 계약 | NU54DK peripheral backend |
| ztest/Twister | Zephyr native/board build | Kconfig, Devicetree, context, backend unit/integration | 모든 실제 회로 전기 동작 |
| west-native sample | NU54DK target | Core module, runtime와 Zephyr 직접 build | Arduino CLI 전처리와 library discovery |
| Arduino CLI | Windows host + target | `.ino`, library discovery, Build Adapter, upload recipe | 계측 장비가 필요한 analog/timing 정확도 |
| HIL | 실제 NU54DK | GPIO/UART/I2C/SPI/ADC/PWM/IRQ/flash | 다른 OS와 다른 board revision |
| Clean-machine | 새 Windows VM/PC | package 설치, 경로, dependency, end-to-end | 장기 hardware 신뢰성 |

한 계층의 실패를 다른 계층의 mock으로 덮지 않는다. 예를 들어 UART mock test가 PASS여도 DAP UART Serial Echo HIL이 실패하면 `Serial 지원`으로 선언할 수 없다.

## 6. Host unit test

### 6.1 대상

- Arduino 논리 pin 번호의 range 검사와 descriptor lookup
- Devicetree/generated interface와 분리된 순수 mapping logic
- circular buffer와 overflow 정책
- Serial timeout 계산
- `Print`, `Stream`, `String`의 upstream 또는 추가 edge case
- Build Adapter option parser와 path quoting
- canonical path와 cache key 생성
- artifact resolver의 `zephyr.hex`/`merged.hex` 선택
- library manifest 정렬과 중복 제거
- diagnostic source map 처리

### 6.2 필수 case

- zero-length, maximum-length 및 invalid input
- 32-bit time counter wrap-around
- UTF-8 경로와 공백 경로
- Windows drive letter 대소문자와 separator 정규화
- 두 동시 build의 서로 다른 project ID
- dependency revision, conf 및 overlay 변경에 따른 cache key 변화
- Sketch source 내용 변경이 무조건 새 build-tree key를 만들지 않는지 확인

### 6.3 실행 예시

~~~powershell
cmake -S tests/host -B build/host
cmake --build build/host --config Debug
ctest --test-dir build/host -C Debug --output-on-failure
~~~

### 6.4 Exit criteria

- 모든 P0 host test PASS
- sanitizer를 지원하는 host compiler 조합에서는 address/undefined behavior test PASS
- seed를 사용하는 test는 실패를 재현할 seed를 log에 남김
- line coverage 수치는 baseline을 수집한 뒤 목표를 정하며, 임의 수치를 사전에 완료 조건으로 사용하지 않음

## 7. ArduinoCore-API 검증

### 7.1 검토 원칙

- tag 또는 commit을 고정한다.
- upstream test를 수정 없이 먼저 실행하고 결과를 baseline으로 남긴다.
- NU54DK용 patch가 필요하면 upstream 원본 변경과 Core adapter 변경을 구분한다.
- header compile 성공과 hardware method 구현 완료를 구분한다.
- GNU LGPL 2.1 계열 license 원문, source revision 및 변경 내역을 evidence manifest와 release package에 포함한다.

### 7.2 시험 대상

- `String` allocation, copy/move, concatenation, numeric conversion
- `Print`의 integer base, floating point, partial write와 error
- `Stream` timeout, parse, find와 partial input
- `Printable` dispatch
- `HardwareSerial`, `Client`, `Server`, `UDP` 등 abstract interface의 compile contract
- legacy global alias와 namespace 사용
- NCS compiler의 C++ standard, exception 및 RTTI 설정

### 7.3 Exit criteria

- 고정 revision과 upstream test 결과가 연결됨
- 제외한 upstream test마다 hardware 미지원, 미구현 또는 upstream environment 문제 사유가 있음
- Core source와 third-party source의 license 구분이 검토됨
- NCS target compile에서 warning/error 정책을 통과함

## 8. Zephyr ztest와 Twister

### 8.1 test 분류

| 분류 | 주요 대상 |
| --- | --- |
| `runtime` | setup/loop 순서, main thread stack, yield/idle과 fairness 정책 |
| `time` | millis/micros 변환, wrap-around, delay와 다른 thread 공존 |
| `gpio` | pin validation, mode mapping, 오류 반환/diagnostic |
| `interrupt` | callback registration, detach 경쟁, context 제한 |
| `serial` | ring buffer, timeout, partial write, console ownership 구성 |
| `wire` | errno mapping, 32-byte buffer와 deferred repeated-start, no-STOP read 거부 |
| `spi` | mode/frequency/bit-order config, 8/16/buffer transfer와 Core owner/state |
| `analog` | A0 고정 12-bit raw·오류 -1, PWM 고정 8-bit duty와 범위 거부 |
| `config` | Kconfig/overlay positive·negative 조합 |

### 8.2 platform

- 순수 logic과 fake device가 가능한 test는 `native_sim` 후보로 둔다.
- nRF54L15 Devicetree, driver 또는 SoC compile 검증은 실제 board target으로 build한다.
- 실제 전기 신호가 필요한 항목은 ztest PASS만으로 끝내지 않고 HIL로 연결한다.

### 8.3 실행 예시

~~~powershell
west twister `
  -T tests/zephyr `
  -p $Board `
  --board-root $BoardRoot `
  --extra-args "EXTRA_ZEPHYR_MODULES=$CoreRoot" `
  --outdir build/twister-nu54dk
~~~

지원되는 test에 한해 별도 native 실행을 추가한다.

~~~powershell
west twister `
  -T tests/zephyr `
  -p native_sim `
  --outdir build/twister-native
~~~

### 8.4 필수 negative configuration

- 존재하지 않는 Arduino pin
- Devicetree에서 비활성인 SPI controller를 기본 객체가 요구하는 구성
- SPI00과 uart00을 동시에 활성화하는 구성
- Wire의 `requestFrom(..., false)`와 deferred transaction 주소 불일치
- M7 HIL protocol에 0x6A 주소·임의 register·scan 입력을 추가하려는 변경
- `LED_BUILTIN`이나 임의 pin을 PWM 역할로 사용하는 요청
- `setup()/loop()`를 실행하는 Zephyr main thread stack이 너무 작은 구성
- Serial non-owning wrapper가 Zephyr console의 baud, pinctrl 또는 device lifetime을 변경하려는 구성
- A0 이외 ADC pin, 0..255 밖 PWM 값, 지원하지 않는 SPI mode 또는 nrfx runtime prescaler predicate가 거부하는 frequency

### 8.5 Exit criteria

- P0 suite PASS
- negative 구성은 예상한 configure/build error와 메시지로 FAIL
- warning을 무시하여 성공 처리하지 않음
- Twister report, generated `.config`와 `zephyr.dts`를 CI artifact로 보존

| 경로 class | 예시 의미 | 확인 내용 |
| --- | --- | --- |
| ASCII 짧은 경로 | 기본 baseline | 모든 명령의 기준 |

## 12. 빌드와 cache 회귀

### 12.1 시나리오

| 시나리오 | 예상 동작 |
| --- | --- |
| 완전 cold build | configure와 전체 필요한 object compile |
| 변경 없는 rebuild | configure/compile 최소화, artifact 동일성 확인 |
| Sketch 한 줄 변경 | 같은 build tree에서 Sketch와 의존 link만 갱신 |
| Core source 변경 | 영향받는 Core object와 link 갱신 |
| Arduino library source 변경 | 해당 library object와 link 갱신 |
| `prj.conf` 변경 | CMake/Kconfig reconfigure 후 필요한 object 갱신 |
| `app.overlay` 변경 | Devicetree regenerate 후 영향 object 갱신 |
| board submodule commit 변경 | 다른 key 또는 명시적 reconfigure |
| NCS/Toolchain revision 변경 | cache 공유 금지, 다른 key |
| Build Adapter schema 변경 | 생성물 호환성에 따라 key invalidation |
| 실패 후 재실행 | 손상된 generated state를 감지하고 이유를 log |
| 두 Sketch 병렬 build | 서로 다른 tree/lock으로 독립 실행 |

### 12.2 측정값

- wall-clock build time
- CMake configure 여부와 시간
- compile한 translation unit 수
- link 수행 여부
- compiler cache hit/miss
- build tree와 compiler cache 사용량
- clean이 발생한 이유
- image size와 section 변화

### 12.3 판정 원칙

- 정상 Sketch 수정에서 `pristine always`를 사용하면 FAIL이다.
- no-change build가 전체 compile되면 correctness는 PASS일 수 있어도 performance gate는 FAIL이다.
- stale `.config` 또는 `zephyr.dts`를 재사용하면 즉시 correctness FAIL이다.
- 성능 허용치는 동일 PC, power profile, antivirus 조건과 반복 횟수를 기록한 baseline 이후 결정한다.
- 한 번의 가장 빠른 결과가 아니라 median과 outlier를 함께 기록한다.

### Exit criteria

- 각 시나리오의 예상 invalidation과 실제 build graph가 일치
- cache key unit/negative test PASS
- stale configuration injection test PASS
- quota/LRU 정리가 현재 사용 중인 tree를 제거하지 않음
- clean build와 cache clear가 서로 다른 사용자 명령으로 동작

## 13. NU54DK HIL 시험

### 13.1 최소 장비

- NU54DK 보드와 안정적인 전원/데이터 USB 케이블
- DAP UART를 열 수 있는 serial terminal 또는 test harness
- 해당 단계에서 이미 연결하기로 한 known device 또는 안전한 board-local fixture

logic analyzer, oscilloscope, 가변 전압원과 신호발생기는 선택적인 결함 분석 도구다.
사용자가 외부 계측을 필수 범위에서 제외했으므로 단계 완료 조건으로 요구하지 않는다.
외장 J-Link도 M8 선택 경로를 실제로 검증할 때만 필요하다.

### 13.2 Fixture manifest

HIL 실행마다 다음을 기록한다.

- 보드 revision과 식별자
- CMSIS-DAP firmware/version과 UID
- solder bridge 또는 jumper 상태
- UART port
- I2C/SPI 장치 part number와 address
- 사용한 경우에만 ADC 입력 fixture와 측정 장비
- 사용한 경우에만 PWM/interrupt 외부 계측 channel
- 외장 J-Link serial과 software version
- 배선 사진 또는 diagram revision

### 13.3 안전 점검

- P1.10의 LED/PWM 공유를 인식한다.
- P1.8과 P0.4를 GRTC output으로 설정한 상태에서 연결된 button으로 GND 단락하지 않는다.
- P2.7의 LED와 SWO/SB13 경로를 동시에 사용하지 않는다.
- I2C22와 대체 SERIAL22 mode를 동시에 활성화하지 않는다.
- SPI00과 uart00을 동시에 활성화하지 않는다.
- M7 IMU HIL은 0x6A address의 probe·register pointer write·read·write·fallback을 모두 금지한다.
- M7 IMU HIL은 오직 0x6B의 WHO_AM_I register 0x0F만 repeated-start로 읽으며 기대 반환 값은 0x6A다.
- ADC pin에 허용 전압을 넘기지 않는다.
- output-output loopback은 series resistor와 전압 수준을 검토한다.
- destructive erase/recover test는 별도 승인과 backup 이후에만 실행한다.

### 13.4 API별 HIL

| 영역 | 방법 | PASS 기준 |
| --- | --- | --- |
| GPIO output | 온보드 LED 또는 board-local 상태 | 요청 level/polarity와 관찰 결과 일치 |
| GPIO input | button 또는 신호발생기 | pull과 active level, bounce 정책 기록 |
| Time | target 내부 counter와 자동 경계값 주입 | monotonic, rollover, delay와 scheduler 공존 통과 |
| Interrupt | 온보드 버튼 또는 자동 GPIO emulator | mode별 callback count, raw edge와 detach 후 무호출 |
| Serial | DAP UART loopback/echo | `DT_CHOSEN(zephyr_console)` 장치를 재초기화하지 않고 실제 config, RX/TX, overflow 정책과 반복 전송 통과 |
| I2C | 고정 0x6B/0x0F WHO_AM_I read | repeated-start와 반환 값 0x6A; 0x6A 주소 접근·scan 없음 |
| SPI | 4 MHz driver 경로, emulator와 fixture가 있을 때만 물리 loopback/device | nrfx runtime clock predicate·mode·bit order와 transfer 의미 일치; Core의 별도 근사값 탐색 없음, CS는 Sketch 소유 |
| ADC | A0/P1.12 실제 driver와 자동 변환 경계 | 12-bit raw 0..4095 또는 명시적 오류 -1; 외부 정확도 계측 불필요 |
| PWM | P1.10 driver 상태 | 0·중간값·255 적용; LED_BUILTIN P2.9 거부; 외부 duty/frequency 계측 불필요 |
| Zephyr 공존 | Arduino loop + Zephyr thread | starvation, deadlock 및 resource ownership 위반 없음 |

### 13.5 반복성

- 기본 flash/upload는 최소 10회 반복한다.
- Serial과 bus test는 cold reset을 포함한다.
- timing/analog 측정은 여러 sample을 기록하고 평균만으로 outlier를 숨기지 않는다.
- flaky hardware test는 원인을 해결하기 전 지원 증거로 사용하지 않는다.

## 15. 외장 J-Link 시험

### 15.1 전제

J-Link는 NU54DK 온보드 probe가 아니라 외장 debug probe 경로다. M3 build의
`runners.yaml`에는 `jlink`, `nRF54L15_M33`와 4000 kHz 인자가 실제로 생성됐다. 이는
runner metadata 검증 PASS이며, 외장 probe flash/debug HIL 증거는 아니다.

### 15.2 flash/debug

~~~powershell
west flash -d <BUILD_DIR> -r jlink --dev-id <JLINK_SERIAL>
west debug -d <BUILD_DIR> -r jlink --dev-id <JLINK_SERIAL>
~~~

### 15.3 필수 case

- J-Link software/version과 target device 인식
- 동일 pyOCD 기준 image의 flash 및 reset
- source breakpoint
- 여러 J-Link 연결 시 serial 선택
- SWD speed 기본값과 override
- 일반 Flash에서 불필요한 mass erase 미실행
- pyOCD와 J-Link가 같은 source tree/build artifact를 번갈아 사용

### 15.4 라이선스와 배포

- J-Link software를 Core package에 임의 재배포하지 않는다.

- 지원 OS와 J-Link software version을 명시한다.
- tool이 없을 때 pyOCD 경로까지 실패하지 않고 J-Link만 명확히 unavailable로 표시한다.

### 15.5 Exit criteria

- flash와 source debug HIL PASS
- 생성된 `runners.yaml`에 실제 J-Link runner와 필요한 argument가 존재
- 외부 prerequisite와 version 확인 방법 문서화
- 검증되지 않으면 API/Core 전체 실패로 과장하지 않고 v0.1 선택 runner를 `미구현`으로 표시

## 16. API conformance HIL 기준

API 지원 상태를 바꾸기 위한 최소 증거는 다음과 같다.

| 목표 상태 | 필수 증거 |

| 부분 지원 | 지원 조합 positive HIL + 비지원 조합 negative test + 제한 문서/diagnostic |
| 의미 차이 | 차이 비교 문서 + 실제 측정 + 영향 예제 + 회귀 test |
| 하드웨어 미지원 | MCU/회로 근거 + 대체 경로가 정식 지원이 아님을 명시 |
| 미구현 | 구현 증거 없음; test는 NOT RUN 또는 예상 compile failure |

API가 여러 overload 또는 mode를 가지면 한 경로의 PASS로 전체 API를 지원 처리하지 않는다. 예를 들어 SPI mode 0만 시험했다면 mode 0 범위의 `부분 지원`이며 mode 1~3까지 자동 확대하지 않는다.

## 17. 단계별 Exit criteria

구현 로드맵의 단계 종료와 시험 증거를 다음과 같이 연결한다.

| 단계 | 필수 시험 | Exit evidence |
| --- | --- | --- |
| M0 | submodule 경로와 commit 검사 | `.gitmodules`, gitlink, `git submodule status` |
| M1 | C++ clean build, pyOCD 3회 flash, UART/GPIO 실행 | environment manifest, build/flash log, probe 정보 |
| M2 | module 인식, setup/loop, static constructor | Twister 또는 target runtime log와 ELF/map |
| M3 | GPIO/time/scheduler/idle | **완료**: sample·negative와 NU54DK Twister 9/9 증거는 [M3 기준선](<../04_검증 기록/03_M3_GPIO_시간과_Scheduler_기준선.md>)에 보관 |
| M4 | ArduinoCore-API upstream/host compile, license audit | pinned SHA, host report, license manifest |
| M5 | Arduino CLI 수직 build, library, source map, 병렬 build | CLI logs, generated source manifest, negative compile report |
| M6 | Serial/interrupt/GPIO/time HIL | **완료**: COM10 Serial HIL, target ztest 10/10, runtime hook HIL과 API matrix, 실제 P1.13 세 edge HIL 통과 |
| M7 | I2C/SPI/ADC/PWM HIL과 conflict negative test | **조건부 완료**: NU54DK Twister target 11/11·전체 Builder 8/8(M7 예제 4/4)·driver HIL 통과; IMU WHO_AM_I 미확정과 물리 SPI data 경로 미검증은 [M7 기준선](<../04_검증 기록/07_M7_Wire_SPI_ADC_PWM_기준선.md>)에 기록 |
| M8 | pyOCD upload/debug, 선택 J-Link upload/debug | 10회 flash log, debug record, runners.yaml |
| M9 | build invalidation/cache/stale test | timing CSV/JSON, key manifest, rebuild logs |
| M10 | clean Windows package install/compile/upload | VM image metadata, package checksum, end-to-end log |
| M11 | 전체 release regression과 독립 재현 | signed/hashed report, SBOM, API matrix, known issues |

단계 상태를 `완료`로 변경할 때 이 표의 증거 위치를 구현 로드맵에 연결한다.

## 18. 증거 보관

### 18.1 Run ID

각 실행에 다음 형태의 식별자를 부여한다.

~~~text
<UTC 또는 KST timestamp>-<core-short-sha>-<suite>-<board-id>
~~~

### 18.2 필수 metadata

- run ID와 시작/종료 시각
- test suite와 command line
- 결과 상태와 exit code
- Windows version과 machine class
- Core commit과 dirty state
- board submodule commit과 dirty state
- ArduinoCore-API commit
- NCS/Zephyr/Toolchain/west/CMake/Ninja/Python version
- board target, `BOARD_ROOT`, conf와 overlay hash
- probe type, UID/serial, firmware와 tool version
- HIL fixture revision
- 생성 artifact의 SHA-256
- 실패 요약과 관련 issue

### 18.3 보관 대상

- console log
- JUnit/Twister/CTest report
- `zephyr.elf`, `.map`, `.config`, `zephyr.dts`
- flash에 실제 사용한 `.hex` 또는 `merged.hex`
- `runners.yaml`, build manifest와 cache diagnostic
- 선택적으로 사용한 logic analyzer/oscilloscope 원본 또는 export
- UART capture
- package archive, checksum, SBOM와 license manifest

대용량 binary와 계측 원본을 Git source history에 무조건 추가하지 않는다. CI artifact 또는 release storage에 보관하고, 저장소에는 요약 report, checksum 및 위치를 남긴다. 보존 기간은 release/CI 정책에서 확정한다.

### 18.4 환경 manifest 예시 명령

~~~powershell
git rev-parse HEAD
git status --short
git submodule status
git -C board_package/NU54DK_Zephyr_DTS rev-parse HEAD
west --version
west list
cmake --version
ninja --version
python --version
pyocd --version
arduino-cli version
~~~

J-Link가 설치된 시험 환경은 해당 공식 executable의 version 출력도 함께 기록한다.

## 19. CI와 HIL 실행 시점

| 시점 | 필수 suite |
| --- | --- |
| Pull request | Markdown/link 검사, host unit, ArduinoCore-API test, Twister compile/native, Arduino CLI compile smoke |
| main merge | PR suite + board target build matrix + cache negative test |
| nightly | 대표 library corpus, 경로 행렬, clean/warm build measurement |
| HIL scheduled | pyOCD flash, runtime, GPIO, UART, interrupt, I2C/SPI/ADC/PWM |
| release candidate | 모든 필수 suite + clean Windows + pyOCD 10회 + 선택 J-Link + package/SBOM 검증 |

HIL 장비가 한 대라면 lock과 queue를 사용하고, test 종료 시 보드를 알려진 baseline image로 되돌린다. test 중단으로 probe나 serial port lock이 남지 않도록 timeout과 cleanup을 둔다.

## 20. 결함 등급과 릴리스 판정

| 등급 | 예시 | v0.1 판정 |
| --- | --- | --- |
| Blocker | build 불가, 잘못된 target flash, data 손상, 일반 upload에서 destructive erase | release 불가 |
| High | P0 API 오동작, 반복 flash 불안정, stale cache firmware | release 불가 |
| Medium | P1 제한 누락, 특정 경로 실패, diagnostic 불명확 | 수정 또는 명시적 범위 축소 필요 |
| Low | 문서 오타, 비핵심 예제 개선 | known issue로 허용 가능 |

`FLAKY`인 P0/HIL test는 High 이상으로 취급한다. 재실행으로 우연히 PASS한 결과만 선택해서 release하지 않는다.

## 21. 미확정 및 후속 검증 항목

다음 항목은 실제 baseline을 얻기 전 수치나 방식이 확정되지 않았다.

- 지원 pyOCD 정확한 version과 CMSIS-DAP firmware 조합
- J-Link 지원 software version과 외장 probe flash/debug HIL
- Arduino CLI FQBN
- C++ exception/RTTI 기본값
- main thread loop의 한 tick sleep 기본 정책에 대한 외부 idle/PM 계측과 장기 fairness 재검토
- `DT_CHOSEN(zephyr_console)` non-owning Serial wrapper의 세부 buffer 크기와 TX interleaving 동작
- Arduino 논리 pin 전체 목록
- 물리 SPI fixture 또는 known peripheral의 가용 여부
- A0 외부 정확도와 PWM 주파수·duty 정밀도; M7 완료 조건은 아니며 필요 시 후속 계측
- cold/warm build 시간 목표
- compiler cache 종류와 quota
- Boards Manager의 NCS/Toolchain 배포 방식

이 항목은 `지원`으로 가정하지 않는다. 각각 M1~M10의 결정 gate에서 실측과 검토 후 확정한다.

Serial의 장치 소유권 자체는 미확정 항목이 아니다. v1 설계는 `DT_CHOSEN(zephyr_console)`의 non-owning wrapper이며, Zephyr가 device initialization, pinctrl, baud와 lifetime을 소유한다. `begin()`/`end()`는 Arduino buffer/lifecycle만 처리하고, 동일 UART의 Zephyr shell RX 병행은 v1 시험·지원 범위에서 제외한다. 남은 항목은 이 결정이 실기에서 올바르게 동작하는지에 대한 검증이다.
