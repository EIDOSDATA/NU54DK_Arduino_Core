# v0.5.0 다중 Host 지원 착수 계약

| 항목 | 내용 |
| --- | --- |
| 문서 ID | BUILD-HOST-001 |
| 문서 개정 | 1.1 |
| 문서 상태 | 승인된 v0.5.0 구현·검증 계획 |
| 적용 시작 | M30 착수와 동시에 기반 정비 시작, M33 공개 전 완료 |
| 최종 갱신일 | 2026-09-15 |

## 1. 목적과 적용 경계

`v0.5.0`부터 Arduino IDE·Arduino CLI 사용 Host를 Windows 하나에서 세 운영체제 계열로
확장한다. 이 문서는 언제 시작하고, 무엇을 구현하고, 어떤 증거가 있어야 정식 지원으로 공개할지를
고정한다. M30~M32의 Bluetooth 기능 개발과 병행하되 M33 release gate에서 하나의 제품 계약으로
마감한다.

이 결정은 `v0.4.1`과 이전 공개 자산에 소급 적용하지 않는다. 현재 설치·지원 버전 `v0.4.1`은
Windows 10/11 x64 전용이며, 과거 문서·검증 기록의 당시 Host 판정은 그대로 보존한다. Linux
container의 Zephyr target build, Linux BLE peer 상호운용 또는 macOS에서 source가 해석되는 사실도
Arduino 사용자 Host 지원 PASS가 아니다.

## 2. v0.5.0 지원 목표

| Host 계열 | 정식 목표 범위 | 최소 기준 | Architecture | 현재 상태 |
| --- | --- | --- | --- | --- |
| Windows | Windows 10·11 | 각 지원 major의 최신 적용 가능한 누적 update | x86-64 | `v0.4.1`에서 지원 중, v0.5 회귀 필요 |
| Ubuntu | Ubuntu 24.04부터 당시 최신 stable까지 | `24.04` | AMD64 | 공통 기반 HOST-W01~W03 완료; 실제 Host 설치·build·HIL 미검증 |
| macOS | macOS 26부터 당시 최신 stable까지 | `26` | Apple Silicon ARM64 native | 공통 기반 HOST-W01~W03 완료; 실제 Host 설치·build·HIL 미검증 |

Ubuntu의 “24.04부터 최신”은 출시·지원 중인 각 Ubuntu release와 point release를 뜻한다. macOS의
“26부터 최신”도 출시·지원 중인 각 major와 point update를 뜻한다. 새 OS가 공개되었다는 이유만으로
자동 지원하지 않으며 다음 상태 전이를 따른다.

| 상태 | 의미 | 전이 조건 |
| --- | --- | --- |
| `candidate` | 범위에는 들어왔지만 아직 제품 PASS가 없음 | OS 출시·필수 upstream tool 제공 확인 |
| `supported` | 해당 Core release에서 사용자 지원 | clean install, build, upload, 대표 runtime와 lifecycle PASS |
| `archived` | 당시 증거는 보존하지만 현재 수정·지원 대상은 아님 | Ubuntu가 공식 지원 종료된 뒤 차기 Core 지원표에서 전환 |

Ubuntu의 지원 종료 release는 `archived`로 전환하되 당시 결과를 삭제하지 않는다. 새 Ubuntu release나
macOS major는 먼저 `candidate`로 등록하고 실제 Host 검증을 통과한 Core 유지보수 release에서
`supported`로 승격한다. 따라서 “최신까지”는 시험되지 않은 미래 버전을 미리 PASS로 선언하는 문구가
아니다.

현재 목표에서 제외하는 조합은 Linux ARM64·다른 Linux 배포판, Intel Mac, Rosetta 실행,
Windows on ARM, WSL·container를 통한 USB upload다. 별도 실증과 범위 승인이 있기 전에는 호환될 수
있다는 이유로 지원표에 올리지 않는다.

## 3. 시작 시점과 마일스톤 배치

다중 Host 작업은 M33 직전에 한꺼번에 이식하지 않는다. M30의 새 DFU·설치 경로가 Windows 전용
가정을 추가하지 않도록 **M30-W01과 동시에 HOST-W01을 시작**한다.

| 시점 | Host 작업 | Bluetooth 작업과의 연결 | 종료 조건 |
| --- | --- | --- | --- |
| M30 | HOST-W01~W03: 계약·Windows 가정 inventory, launcher·실행 파일·경로 추상화 | 보안·profile·최소 DFU 도구를 처음부터 공통 Python backend로 설계 | 세 Host에서 같은 명령 계획을 만들고 Windows 회귀 PASS |
| M31 | HOST-W04~W06: prerequisite, build/cache/package, CI matrix | ISO/Audio·DF·CS의 큰 build matrix를 실제 POSIX Host에서도 수행 | Ubuntu·macOS clean target build와 artifact 비교 PASS |
| M32 | HOST-W07: upload/debug/serial·설치 lifecycle·실물 Host HIL | Mesh·공존 검증에 사용할 runner와 evidence protocol을 Host 중립화 | 세 Host에서 대표 NU54DK upload/runtime와 재설치 PASS |
| M33 | HOST-W08: 전체 예제·회귀·지원표·release 문서 마감 | v0.5.0 통합·공개 gate | 지원 matrix 전 행 PASS, exact evidence와 package 공개 승인 |

M31 또는 M32의 전용 RF/audio 장비가 늦어져도 독립적인 Host 구현·시험은 계속한다. 반대로 Host
build만 통과했다고 해당 Bluetooth 기능의 RF/HIL을 PASS로 올리지 않는다.

## 4. 작업 묶음

| 작업 묶음 | 구현·검증 내용 | 주요 산출물 |
| --- | --- | --- |
| HOST-W01 | Windows 전용 가정과 외부 명령 전수 inventory, 지원/제외 범위 고정 | 기계 판정 inventory와 Host unit test |
| HOST-W02 | OS·architecture 판별, executable resolver, 환경 변수와 오류 계약 | 공통 Python Host descriptor, fail-closed parser |
| HOST-W03 | `.cmd`와 POSIX `.sh`의 얇은 launcher, shell 문자열 재해석 제거 | 동일 backend를 부르는 platform별 진입점 |
| HOST-W04 | nRF Util·sdk-manager·NCS·Zephyr·toolchain의 OS별 URL·hash·revision 고정 | platform별 prerequisite manifest와 설치/검증기 |
| HOST-W05 | cache·lock·경로·권한·case·symlink·공백·한글 경로 이식 | portable build/cache backend와 회귀 시험 |
| HOST-W06 | package metadata와 Linux/macOS/Windows CI build matrix | 세 Host package install·전체 예제 compile 증거 |
| HOST-W07 | CMSIS-DAP/pyOCD upload, 다중 probe UID, serial, 수동 debug와 lifecycle | 실제 NU54DK Host별 HIL·설치/갱신/제거 증거 |
| HOST-W08 | 결과 검토, 비효율 제거, 사용자 문서·문제 해결·지원표와 release gate | v0.5.0 공개 문서, 제한, exact 증거 색인 |

각 묶음은 source 후보, Host unit, target build, 실제 Host/HIL을 구분한다. 필수 단계가 실행되지
않으면 `NOT RUN`이며 문서나 mock 결과로 PASS를 대신하지 않는다.

현재 HOST-W01 inventory, HOST-W02 descriptor/resolver와 HOST-W03 launcher는 완료했다.
HOST-W04~W08은 남은 작업이며 Ubuntu/macOS 지원 행의 실증 완료를 뜻하지 않는다. 현재 개발 상태와
병행 순서는 [v0.5.0 TODO](../TODO_v0.5.0.md) 및
[문서 전면검토·개선 마일스톤](<../01_아두이노 코어 설계/18_문서_전면검토와_개선_마일스톤.md>)을 따른다.

## 5. 구현 원칙

1. Build Adapter·prerequisite·upload의 실제 동작은 공통 Python backend가 소유하고 `.cmd`와
   `.sh`는 인자를 그대로 전달하는 얇은 진입점으로 유지한다.
2. `python.exe`, `west.exe`, `git.exe`, `arm-zephyr-eabi-g++.exe`, `JLink.exe`,
   `%LOCALAPPDATA%` 같은 Windows 이름·경로를 기능 코드에 흩뿌리지 않는다. OS descriptor와
   명시적 resolver가 실제 파일·architecture·version을 확인한다.
3. Windows cache는 Local AppData, Linux는 XDG cache 또는 사용자 cache, macOS는 사용자
   Library cache를 기본값으로 사용한다. 환경 변수 override는 절대 경로·소유권·쓰기 가능 여부를
   검사하고 서로 다른 Host·SDK·Core의 cache identity를 섞지 않는다.
4. file lock은 Windows와 POSIX native lock을 사용하며 timeout, stale metadata와 child process
   exit code 의미를 동일하게 보존한다.
5. prerequisite manifest는 OS·architecture별 공식 배포 URL, SHA-256, version과 NCS/Zephyr/
   board revision을 고정한다. 지원되지 않는 platform, 잘못된 archive 또는 revision은 build 전에
   실패한다.
6. upload는 CMSIS-DAP + pyOCD를 공통 기본 경로로 유지한다. J-Link는 설치·선택된 경우의 별도
   조건부 경로이며, 임의 probe 선택·자동 recover·mass erase fallback을 허용하지 않는다.
7. M30의 MCUboot/DFU 도구도 같은 Host 추상화를 사용한다. 새 `.bat` 전용 절차를 추가한 뒤 M33에서
   이식하지 않는다.

고정 upstream 기준은 NCS v3.4.0의
[지원 Host 요구사항](https://github.com/nrfconnect/sdk-nrf/blob/v3.4.0/doc/nrf/installation/recommended_versions.rst)과
[설치 절차](https://github.com/nrfconnect/sdk-nrf/blob/v3.4.0/doc/nrf/installation/install_ncs.rst)를 따른다.
Ubuntu release의 지원 상태는 [Ubuntu 공식 release 목록](https://ubuntu.com/project/docs/release-team/list-of-releases/)을
기준으로 판정한다. Upstream이 제공한다는 사실은 이 Core의 설치·upload PASS를 대신하지 않는다.

## 6. 필수 검증 matrix

아래 항목을 Windows 10/11 x64, 지원 대상 Ubuntu AMD64 각 release, 지원 대상 Apple Silicon
macOS 각 major에서 실행한다. 공개 시점의 최소·최신 행만 표본으로 줄이지 않고 지원표에 올린 모든
OS 행을 판정한다.

| 계층 | 필수 시험 | PASS 기준 |
| --- | --- | --- |
| 정적·Host unit | OS/arch 판별, 경로·실행 파일 resolver, lock, parser, 잘못된 archive/revision/noise/timeout | fail-closed이고 세 Host에서 같은 오류 의미 유지 |
| Clean prerequisite | 권한 없는 새 사용자 영역에서 nRF Util/NCS/toolchain 설치와 재검증 | exact version·hash·revision 일치, 시스템 Python/Git 의존 없음 |
| Arduino 설치 | IDE 2.x와 CLI에서 index·post-install·board/example discovery | 승인 없는 임의 실행 없음, 설치 실패가 명확하고 재시도 가능 |
| Target build | v0.5.0 공개 예제 전체, cold/warm cache, profile별 build | 모든 예제 PASS, 산출물 manifest와 cache identity 정합 |
| Cross-Host 비교 | 같은 source/profile/options의 semantic artifact와 section/size 비교 | 허용한 metadata 차이 외 firmware 의미 동일 |
| Upload·runtime | 명시적 UID의 CMSIS-DAP/pyOCD upload, Blink·Serial·BLE 대표 예제 | 올바른 보드만 flash, READY/runtime 관측, 잘못된 UID 거부 |
| Debug·serial | ELF 기반 수동 debug, VCOM 열기/닫기·재접속, 다중 probe | 문서 절차 재현, port/UID 혼동과 무한 대기 없음 |
| Lifecycle | upgrade, 같은 버전 reinstall, downgrade 정책, uninstall 뒤 재설치 | 사용자 데이터·공유 SDK 정책 준수, stale package/cache 혼입 없음 |
| 경로 negative | 공백·한글, 긴 경로, case-sensitive path, symlink, 읽기 전용·권한 오류 | 지원 경로 PASS, 금지 조건은 원인을 보존해 즉시 실패 |
| OS 보안 | Linux udev/그룹, macOS quarantine/Gatekeeper·실행 권한 | 우회성 전역 권한 완화 없이 설치·upload 가능 |

Linux container target build는 Ubuntu 사용자 Host 행의 일부 build 증거로도 자동 합산하지 않는다.
macOS cross-compile도 실제 Apple Silicon 설치·USB upload를 대신하지 않는다. NU54DK의 M28/M29
3보드 RF 동작은 Host 중립 firmware 회귀로 재사용할 수 있으나, 세 Host 각각에서 대표 GPIO·Serial·
BLE compile/upload/runtime와 package lifecycle은 별도로 실행한다.

## 7. 증거와 실패 처리

각 실행은 다음을 구조화 evidence에 기록한다.

- OS 이름·version·build, architecture와 native/emulation 여부
- Core exact commit/package version, board·NCS·Zephyr·toolchain revision
- Arduino IDE/CLI, Python, nRF Util, pyOCD와 선택 runner version
- 선택 board UID의 비식별 hash, profile/options, command·exit code·timeout
- artifact manifest·SHA-256, 원본 log 위치와 성공/실패 분모

중복·누락·알 수 없는 OS/architecture·revision 불일치·noise·timeout은 fail-closed한다. 실패 시
무한 재시도하지 않고 `설치/권한`, `경로/실행 파일`, `build/cache`, `USB/probe`, `target/runtime`,
`upstream 비지원`으로 원인을 분류한다. 수정한 뒤 같은 OS·source·보드·입력으로 재검증하고 최초 실패와
최종 결과를 함께 보존한다.

## 8. 완료 조건과 공개 절차

`v0.5.0` 다중 Host 지원은 다음 조건을 모두 만족해야 완료다.

- HOST-W01~W08 구현·시험·문서가 완료되고 미실행 필수 행이 없다.
- Windows 10/11 x64, 지원 대상 Ubuntu 24.04+ AMD64, 지원 대상 macOS 26+ Apple Silicon의
  clean install·전체 공개 예제 build·대표 실제 upload/runtime·lifecycle이 PASS다.
- OS별 prerequisite 자산의 provenance·license·hash와 package 재현성이 확인됐다.
- 세 Host에서 생성한 firmware의 차이를 설명하거나 동일성을 증명했고 허용되지 않은 차이가 없다.
- Known issues·Troubleshooting·설치 예시가 Host별로 분리돼 사용자가 임의 경로를 추측할 필요가 없다.
- exact source와 evidence를 검증 기록에 연결하고 M33 release review에서 사람이 공개를 승인했다.

CI PASS만으로 tag·Release·stable index를 자동 공개하지 않는다. 새 OS 승격 또는 지원 종료도 지원표,
evidence와 유지보수 release를 함께 갱신한다.
