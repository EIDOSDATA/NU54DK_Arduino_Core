## 1. 목적과 적용 경계

`v0.5.0-rc.1`은 M31 완료 뒤 Windows 10/11 x64 공개 후보로 제공했다. 후속
`v0.5.0-rc.2`의 교정·자동 검증·GUI 연속 Blink 업로드 성공은 [RC2 TODO](../TODO_v0.5.0-RC2.md)에 보존한다.
정식 `v0.5.0` stable 승격·공개는 완료했으며 [274번 기록](<../04_검증 기록/274_v0.5.0_정식_릴리스_승인과_공개.md>)을 따른다.
2026-09-28 버전 배정에 따라 M32·M33과 연계한 후속 계획은 [v0.6.0 TODO](../TODO_v0.6.0.md)에서
관리한다. 이 문서는 기존 세 Host 계획과 M33-W07~W08의 OS별 최종 지원 gate를 유지하며,
무엇을 구현하고 어떤 증거가 있어야 해당 OS를 정식 지원할지 고정한다. 버전 배정은 Ubuntu/macOS의
지원 확정이나 Host 작업 재개가 아니다. 기존 파일명은 링크와 이력 추적을 위해 유지한다.
v0.5.0의 완료한 Windows package·설치·RC gate는 [v0.5.0 TODO](../TODO_v0.5.0.md)가 소유한다.

**현재 실행 상태:** 2026-11-10 W06을 실제 PASS46 + 명시 수락 #29·40·44로 마감한 뒤,
사용자가 HOST-W04부터 순차 구현과 문서 전면 갱신을 지시했다. C5 Windows 11 RC1 검증을 마감했고 C8·C9 부분 실적과 FAIL을 보존하고 C10 Ubuntu24.04/WSL2의 기준선·변경 영향 검증을 마감했다.
기존 W06 실적·FAIL과 고정 SDK를 보존하고 #29 원인 분석은 유예한다.
HOST-W01부터 HOST-W07까지 완료했다. OS별 빌드와 실기 범위는 [v0.6.0 지원표](<../05_릴리스/v0.6.0/SUPPORT_MATRIX.md>)에서 확인한다.
첫 native 설치 CI와 로컬 Host gate의 실패는 [312번](<../04_검증 기록/312_HOST_W04_최초_CI_실패와_교정_검증.md>)에 보존한다.
SDK 원본 변경 없이 설치기와 시험 환경을 교정하고 fresh source CI에서 검증한다.

이 결정은 `v0.4.1`과 이전 공개 자산에 소급 적용하지 않는다. 현재 설치·지원 버전 `v0.5.0`은
Windows 10/11 x64 전용이며, 과거 문서·검증 기록의 당시 Host 판정은 그대로 보존한다. Linux
container의 Zephyr target build, Linux BLE peer 상호운용 또는 macOS에서 source가 해석되는 사실도
Arduino 사용자 Host 지원 PASS가 아니다.

2026-11-15 프로젝트 소유자가 v0.6.0 목표를 위 다섯 행으로 확정했다. Windows 10과 Ubuntu 26.10은
이번 버전의 대상에서 제외한다. v0.5.0의 Windows 10/11 지원 기록과 앞선 7행 검증 기록은 보존한다.
공개 시점의 실제 OS 버전과 업데이트를 기록하고, 새 버전은 이후 제품 릴리스의 별도 검토를 거친다.

| 상태 | 의미 | 전이 조건 |
| --- | --- | --- |
| `candidate` | 범위에는 들어왔지만 아직 제품 PASS가 없음 | OS 출시·필수 upstream tool 제공 확인 |
| `supported` | 해당 Core release에서 사용자 지원 | clean install, build, upload, 대표 runtime와 lifecycle PASS |
| `archived` | 당시 증거는 보존하지만 현재 수정·지원 대상은 아님 | Ubuntu가 공식 지원 종료된 뒤 차기 Core 지원표에서 전환 |

Ubuntu의 지원 종료 release는 `archived`로 전환하되 당시 결과를 삭제하지 않는다. 새 Ubuntu release나
macOS major는 먼저 `candidate`로 등록하고 실제 Host 검증을 통과한 Core 유지보수 release에서
`supported`로 승격한다. 따라서 “최신까지”는 시험되지 않은 미래 버전을 미리 PASS로 선언하는 문구가
아니다.

현재 목표에서 제외하는 조합은 Linux ARM64·다른 Linux 배포판, Intel Mac, Rosetta 실행,
Windows on ARM, WSL1·판별 불명 WSL·container를 통한 USB upload다.
2026-11-15 사용자 승인으로 Ubuntu 24.04 LTS AMD64/WSL2 지원과 실제 USB 검증을 C6에서 추가한다.
WSL2의 실행 환경을 명시하고 native Ubuntu CI·실기 결과와 별도로 기록한다. C8의 부분 실기 PASS는
해당 OS 전체 완료가 아니다. 별도 source의 C5·C6·C7·C8 실적을 C9의 동일-source 결과로 합산하지 않는다.

## 3. 시작 시점과 마일스톤 배치

M30에서 공통 기반 HOST-W01-HOST-W03을 완료했다. HOST-W04-HOST-W08은 M33-W06 완료 후
아래 순서로 진행하며 M31 v0.5.0 Windows 릴리스의 선행조건으로 두지 않는다.
M32·M33의 v0.6.0 배정으로 아래 Host 작업이나 최종 gate를 생략·완료 처리하지 않는다.

| 시점 | Host 작업 | Bluetooth 작업과의 연결 | 종료 조건 |
| --- | --- | --- | --- |
| M30 | HOST-W01~HOST-W03: 계약·Windows 가정 inventory, launcher·실행 파일·경로 추상화 | 보안·profile·최소 DFU 도구를 처음부터 공통 Python backend로 설계 | 세 Host에서 같은 명령 계획을 만들고 Windows 회귀 PASS |
| M31 v0.5.0 | Windows package·설치·RC 회귀와 정식 공개 완료 | M31-W08 뒤 RC2 교정·GUI 사용자 확인·stable 승격 | Windows package 검증과 공개 smoke PASS; stable 별도 승인·공개 완료 |
| M33-W06 완료 직후 | HOST-W04~HOST-W06: prerequisite, build/cache/package, CI matrix | 기능 개발 후 각 native Host에서 build; 병렬 착수하지 않음 | Ubuntu·macOS clean target build와 artifact 비교 PASS |
| HOST-W04~W06 이후 | HOST-W07: upload/debug/serial·lifecycle 실행기·절차와 Windows 회귀 | runner·evidence protocol을 Host 중립화하고 M33-W07 RC1 준비로 연결 | 도구·자동 검사·실행 절차 완료; 실물 미실행은 별도 유지 |
| M33-W07 시험용 RC1 준비 후 | HOST-W08 문서 준비 및 HOST-W07 배정 실기 완료 | 최종 후보 식별자, 자산 및 변경 영향 검토 | HOST-W08과 M33-W07 마감 후 M33-W08 공개 승인 |

M32/M33과 Host는 독립 트랙이며 각자의 완료 분모를 사용한다. 실제 Ubuntu/macOS 장비가 없어도
보드 기반 firmware 기능 작업은 진행한다. Host의 정식 지원 판정은 해당 OS를 추가하는 후속
릴리스에서 수행한다. M33 완료나 다중 Host 완료를 M31 v0.5.0 Windows 릴리스 조건으로 삼지 않는다.
v0.6.0의 기존 M33-W07~W08 세 Host 계획·필수 OS별 증거는 유지하며, 착수 순서가 확정됐어도 실물 gate를
충족하기 전에는 추가 OS를 지원한다고 안내하지 않는다. 이 버전 배정만으로 v0.6.0을 Windows-only로
확정하거나 기존 완료 조건을 완화하지 않는다.
2026-09-16 무선 기능 계획은 [전체 Bluetooth 계약](<../01_아두이노 코어 설계/19_NCS_Bluetooth_전체_기능과_예제_실행_계약.md>)을
따르며 Host build 결과와 무선 기능 HIL은 개별 증거다.

최종 사용자 결정: **Ubuntu/macOS의 실제 설치·USB upload·serial·debug·lifecycle 검증 책임자는
사용자이며 실행 시점은 해당 OS를 추가할 후속 릴리스의 최종 단계**다. 개발자는 도구·예제·명령·기대 결과·실패 수집 절차를
먼저 완성하고 중간에 해당 PC 연결을 요구하며 구현을 멈추지 않는다. Windows 자동 회귀는 개발에서
계속 수행한다. 사용자 후속으로 넘긴 Apple/Google BLE peer 및 외장 장치의 실기와 달리,
Ubuntu/macOS의 최종 Host 지원 검증 gate는 유지한다. HOST-W07의 준비 완료와 실제 검증 완료를
분리하며 사용자 실기 전 HOST 전체를 8/8로 올리지 않는다.

## 5. 구현 원칙

1. Build Adapter·prerequisite·upload의 실제 동작은 공통 Python backend가 소유하고 `.cmd`와
   `.sh`는 인자를 그대로 전달하는 얇은 진입점으로 유지한다.
2. `python.exe`, `west.exe`, `git.exe`, `arm-zephyr-eabi-g++.exe`, `JLink.exe`,
   `%LOCALAPPDATA%` 같은 Windows 이름·경로를 기능 코드에 흩뿌리지 않는다. OS descriptor와
   명시적 resolver가 실제 파일·architecture·version을 확인한다.
3. Windows cache는 Local AppData, Linux는 XDG cache 또는 사용자 cache, macOS는 사용자
   Library cache를 기본값으로 사용한다. 환경 변수 override는 절대 경로·소유권·쓰기 가능 여부를
   검사하고 서로 다른 Host·SDK·Core의 cache identity를 섞지 않는다.
4. file lock은 Windows와 POSIX native lock을 사용하며 timeout, stale metadata와 child process
   exit code 의미를 동일하게 보존한다.
5. prerequisite manifest는 OS·architecture별 공식 배포 URL, SHA-256, version과 NCS/Zephyr/
   board revision을 고정한다. 지원되지 않는 platform, 잘못된 archive 또는 revision은 build 전에
   실패한다.
6. upload는 CMSIS-DAP + pyOCD를 공통 기본 경로로 유지한다. J-Link는 설치·선택된 경우의 별도
   조건부 경로이며, 임의 probe 선택·자동 recover·mass erase fallback을 허용하지 않는다.
7. M30의 MCUboot/DFU 도구도 같은 Host 추상화를 유지한다. 후속 Host 확장 때 불필요한 재이식이
   생기지 않도록 새 기능의 backend와 platform launcher를 분리한다.

고정 upstream 기준은 NCS v3.4.0의
[지원 Host 요구사항](https://github.com/nrfconnect/sdk-nrf/blob/v3.4.0/doc/nrf/installation/recommended_versions.rst)과
[설치 절차](https://github.com/nrfconnect/sdk-nrf/blob/v3.4.0/doc/nrf/installation/install_ncs.rst)를 따른다.
Ubuntu release의 지원 상태는 [Ubuntu 공식 release 목록](https://ubuntu.com/project/docs/release-team/list-of-releases/)을
기준으로 판정한다. Upstream이 제공한다는 사실은 이 Core의 설치·upload PASS를 대신하지 않는다.

## 6. 필수 검증 matrix

검증 단위는 **고정 도구 묶음과 실제 변경 영향**이다. 같은 OS 계열·CPU에서 OS 버전이 달라도
NCS3.4.0의 같은 toolchain archive를 선택한다. [고정 도구 선택 근거](12_Host별_고정_Nordic_환경_설치.md)를 따른다.
C5는 H12 이후 NUS 교정을 포함한 최신 전체 native 기준선이다. C5 이후 C10까지 firmware·SDK pin·
board·compile recipe는 바뀌지 않았다. 따라서 WSL2 허용·실행 환경·검증기 옵션 수정만으로 새 전체204를
필수로 만들지 않는다. C5 기준선의 exact source와 C10의 변경 영향·대표 실기 증거를 각각 연결한다.
SDK/compiler·firmware·compile 설정의 실제 변경이나 실패 분석에서 영향이 확인되면 해당 범위를 확대하고,
전체 영향이면 전체 시험을 명시 실행한다. 문서 변경·OS 버전 증가·source SHA 변경만으로 재실행하지 않는다.
동일-source/run/attempt 조건은 한 실행의 PASS를 집계할 때 유지하며, 매 변경의 전체 재시험 의무가 아니다.
원본 결과를 합쳐 C10 전체204 PASS로 만들지 않는다. 미검증 OS의 설치·권한·USB 호환성은 별도로 남긴다.

2026-11-16 사용자 지시에 따라 Ubuntu24.04/WSL2의 C10 기준선·변경 영향 검증을 마감했다. Ubuntu 26.04 LTS는 호환성 중심으로 확인한다. C5 Windows 11 완료를 유지하고 공통 도구 변경 영향만 제한 회귀한다. OS 버전 차이만으로 전체204를 반복하지 않으며 macOS 26·27도 보존된 기준선과 버전별 호환성을 구분한다. 각 증거의 실제 source·환경·PASS·FAIL을 보존하고 기준선과 변경 영향의 연결을 서로 다른 source의 단일 시험 실적으로 합산하지 않는다.

Windows 11 x64, Ubuntu 24.04 LTS·26.04 LTS AMD64, macOS 26·27 Apple Silicon의
다섯 지원 행은 아래에서 배정한 기준 검증·호환성 검증·변경 영향 검증으로 판정한다. 실제 OS와 실행 환경을 기록한다.

| 지원 행 | 이번 검증 범위 |
| --- | --- |
| Windows 11 | C5 실기 완료 기준선 + C10 Windows Server2025 제한 영향 검사 완료; 새 Windows11 실기로 표시하지 않음 |
| Ubuntu 24.04 LTS/WSL2 | C5 native 전체 빌드 기준선 + C10 WSL2 새 설치·대표4cold/4warm·대표 실기·IDE·재연결·수명주기·변경 영향 검증 |
| Ubuntu 26.04 LTS | 24.04 기준선과 연결한 설치·대표 cold/warm build·USB/serial/debug·lifecycle 호환성. 실제 실행 환경 명시 |
| macOS 26·27 Apple Silicon | 기존 native 전체 빌드 기준선 보존; 각 버전 설치·대표 build·장치/IDE/lifecycle 호환성과 변경 영향 검증 |

새 실패나 실제 변경 영향이 확인된 범위만 확대한다. 미실행 호환성 행은 NOT_RUN이며 기준선의 PASS로 대신하지 않는다.

| 계층 | 필수 시험 | PASS 기준 |
| --- | --- | --- |
| 정적·Host unit | OS/arch 판별, 경로·실행 파일 resolver, lock, parser, 잘못된 archive/revision/noise/timeout | fail-closed이고 세 Host에서 같은 오류 의미 유지 |
| Clean prerequisite | 권한 없는 새 사용자 영역에서 nRF Util/NCS/toolchain 설치와 재검증 | exact version·hash·revision 일치, 시스템 Python/Git 의존 없음 |
| Arduino 설치 | IDE 2.x와 CLI에서 index·post-install·board/example discovery | 승인 없는 임의 실행 없음, 설치 실패가 명확하고 재시도 가능 |
| Target build | C5 native 전체204·profile 기준선 보존. 새 Host 경로와 OS 버전은 대표 cold/warm·변경 영향 검증; 실제 영향이 있는 경우만 범위 확대 | 배정한 범위 PASS와 manifest/cache identity 정합. 대표 결과를204 PASS로 표시하지 않음 |
| Cross-Host 비교 | 같은 source/profile/options의 semantic artifact와 section/size 비교 | 허용한 metadata 차이 외 firmware 의미 동일. OS 버전별 전체 재시험 의무로 확대하지 않음 |
| Upload·runtime | 명시적 UID의 CMSIS-DAP/pyOCD upload, Blink·Serial·BLE 대표 예제 | 올바른 보드만 flash, READY/runtime 관측, 잘못된 UID 거부 |
| Debug·serial | ELF 기반 수동 debug, VCOM 열기/닫기·재접속, 다중 probe | 문서 절차 재현, port/UID 혼동과 무한 대기 없음 |
| Lifecycle | upgrade, 같은 버전 reinstall, downgrade 정책, uninstall 뒤 재설치 | 사용자 데이터·공유 SDK 정책 준수, stale package/cache 혼입 없음 |
| 경로 negative | 공백·한글, 긴 경로, case-sensitive path, symlink, 읽기 전용·권한 오류 | 지원 경로 PASS, 금지 조건은 원인을 보존해 즉시 실패 |
| OS 보안 | Linux udev/그룹, macOS quarantine/Gatekeeper·실행 권한 | 우회성 전역 권한 완화 없이 설치·upload 가능 |

Linux container target build는 Ubuntu 사용자 Host 행의 일부 build 증거로도 자동 합산하지 않는다.
macOS cross-compile도 실제 Apple Silicon 설치·USB upload를 대신하지 않는다. NU54DK의 M28/M29
3보드 RF 동작은 Host 중립 firmware 회귀로 재사용할 수 있다. 기존 Host 실기 기준선을 보존하고,
미검증 환경과 실제 변경 경로에 배정한 대표 GPIO·Serial·BLE·package lifecycle 호환성을 확인한다.
완료한 C5 Windows 실기 전체를 매 source 변경마다 다시 실행하지 않는다.

## 7. 증거와 실패 처리

각 실행은 다음을 구조화 evidence에 기록한다.

- OS 이름·version·build, architecture와 native/emulation 여부
- Core exact commit/package version, board·NCS·Zephyr·toolchain revision
- Arduino IDE/CLI, Python, nRF Util, pyOCD와 선택 runner version
- 선택 board UID의 비식별 hash, profile/options, command·exit code·timeout
- artifact manifest·SHA-256, 원본 log 위치와 성공/실패 분모

중복·누락·알 수 없는 OS/architecture·revision 불일치·noise·timeout은 fail-closed한다. 실패 시
무한 재시도하지 않고 `설치/권한`, `경로/실행 파일`, `build/cache`, `USB/probe`, `target/runtime`,
`upstream 비지원`으로 원인을 분류한다. 수정한 뒤 같은 OS·source·보드·입력으로 재검증하고 최초 실패와
최종 결과를 함께 보존한다.

## 8. 완료 조건과 공개 절차

후속 제품선의 다중 Host 지원은 다음 조건을 모두 만족해야 완료다. 이 gate는 폐기하지 않고
해당 OS 지원 릴리스로 이관한다. M31 v0.5.0 Windows 공개와 분리해 추적한다.

- HOST-W01~HOST-W08 구현·시험·문서가 완료되고 미실행 필수 행이 없다.
- Windows 11 x64, Ubuntu 24.04 LTS·26.04 LTS AMD64, macOS 26·27 Apple Silicon의
  각 행에 배정한 기준 검증 또는 호환성 검증과 변경 영향 검증이 PASS다. 전체 예제 반복을 모든 OS 버전에 요구하지 않는다.
- OS별 prerequisite 자산의 provenance·license·hash와 package 재현성이 확인됐다.
- 세 Host에서 생성한 firmware의 차이를 설명하거나 동일성을 증명했고 허용되지 않은 차이가 없다.
- Known issues·Troubleshooting·설치 예시가 Host별로 분리돼 사용자가 임의 경로를 추측할 필요가 없다.
- exact source와 evidence를 검증 기록에 연결하고 해당 OS를 추가할 release review에서 사람이 공개를 승인했다.

CI PASS만으로 tag·Release·stable index를 자동 공개하지 않는다. 새 OS 승격 또는 지원 종료도 지원표,
evidence와 유지보수 release를 함께 갱신한다.

HOST-W07 도구·RC1·Windows 회귀의 세부 실행은 [Host RC1 절차](15_Host_RC1_실기_도구와_증거_절차.md)를 따른다. 현행 다섯 행에서 CI 결과와 사용자 실기 결과를 각각 판정한다.
