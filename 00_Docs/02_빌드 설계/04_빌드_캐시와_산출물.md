# 빌드 캐시와 산출물 — v0.3.0 계약

| 항목 | 내용 |
| --- | --- |
| 대상 | `nucode:zephyr:nu54dk` `0.3.0` |
| 빌드 방식 | source record → `sources.cmake` → Zephyr CMake/Ninja |
| 기본 영구 캐시 | `%LOCALAPPDATA%\NU54\c` |
| 세션 상태 | `{build.path}/nu54-zephyr` |
| sysbuild | 사용하지 않음 |

이 문서는 현재 Build Adapter가 캐시를 식별하고 Arduino source를 Zephyr 빌드 그래프에
연결하며 산출물을 공개하는 계약만 설명한다. 실행 횟수, 시간, 파일 hash와 장애 주입 결과는
[M9 검증 기록](<../04_검증 기록/09_M9_증분_빌드_캐시와_재현성_기준선.md>)과
[M13 검증 기록](<../04_검증 기록/15_M13_구성_프로필_검증.md>)에 보존한다.

현재 단일 원본은
[`nu54_builder.py`](../../tools/nu54-builder/src/nu54_builder.py),
[`platform.txt`](../../platform.txt)와
[`zephyr-app` template](../../tools/nu54-builder/templates/zephyr-app)이다.

---

## 1. 설계 원칙

1. Arduino recipe는 sketch와 library source를 직접 최종 컴파일하지 않는다.
2. `record`가 Arduino가 선택한 source와 include directory를 기록한다.
3. `link`가 전달받은 object 목록에 대응하는 record만 모아 결정적인 `sources.cmake`를 만든다.
4. 실제 컴파일·링크와 증분 판단은 Zephyr CMake/Ninja가 수행한다.
5. 캐시 identity와 source 변경 감지는 분리한다. source 본문만 바뀌면 같은 Ninja tree를
   재사용하고 dependency graph가 필요한 target만 다시 빌드한다.
6. 공개 산출물과 manifest는 한 generation으로 원자적으로 교체한다.

과거 설계의 전용 Arduino compiler object cache, imported object, payload archive는 현재 계약이
아니다. Arduino가 요구하는 `.o`와 `.a`는 source 선택을 전달하기 위한 placeholder이며 Zephyr
link input으로 재사용하지 않는다.

## 2. 저장 위치

### 2.1 Arduino build 세션

~~~text
{build.path}/
├── <project>.elf
├── <project>.hex
├── <project>.bin
├── <project>.map
├── <project>.nu54-build.json
└── nu54-zephyr/
    ├── context.json
    ├── records/
    ├── artifact-staging/
    └── logs/
        └── flash.log
~~~

`nu54-zephyr`는 현재 Arduino build 요청을 영구 캐시 entry에 연결하는 세션 영역이다. 이를
독립 build cache로 취급하거나 다른 `build.path`에 복사해 재사용하지 않는다.

### 2.2 영구 Build Adapter 캐시

기본 위치는 다음과 같다.

~~~text
%LOCALAPPDATA%\NU54\c\
├── v1\<key[0:2]>\<key[0:32]>\
│   ├── input-manifest.json
│   ├── state.json
│   ├── access.json
│   ├── app\
│   └── build\
└── compiler-cache\
~~~

환경 변수 `NUCODE_BUILD_CACHE_ROOT`로 로컬 경로를 바꿀 수 있다. Windows UNC/network
경로는 lock과 원자적 교체를 보장할 수 없어 거부한다. 디렉터리 이름은 SHA-256의 앞 32자만
사용하지만 `input-manifest.json`과 `state.json`에 전체 key를 기록해 축약 충돌을 검출한다.

기본 제한은 build entry 8개 또는 12 GiB이며 오래 사용하지 않은 entry부터 정리한다.
`compiler-cache`는 ccache가 관리하고 기본 최대 크기는 2 GiB다. 현재 build와 사용 중이거나
pinned인 entry는 자동 정리하지 않는다.

## 3. 캐시 identity

### 3.1 key에 포함하는 것

| 입력 | 이유 |
| --- | --- |
| platform 내용과 Adapter version | recipe·template·runtime 계약 분리 |
| FQBN, Zephyr board, profile, non-sysbuild | build graph와 Kconfig/DTS 분리 |
| NCS·Zephyr revision과 toolchain bundle | ABI·도구 identity 분리 |
| NU54DK board package revision과 내용 | DTS·runner 설정 분리 |
| profile 파일과 선택된 feature manifest/config/overlay 내용 | 최종 Kconfig·DTS 구성 분리 |
| sketch root identity와 sketch sidecar 내용 | sketch별 전문가 override 분리 |
| 허용한 build 환경 override | 숨은 CMake/compiler 입력 분리 |

Sketch와 library **source 본문 hash는 cache key에 넣지 않는다.** 본문과 header 변경은 source
manifest, mirror 갱신 및 Ninja dependency로 처리한다. 따라서 작은 코드 수정마다 CMake tree를
새로 만들지 않는다.

### 3.2 provisional key와 final key

`prepare` 시점에는 Arduino가 어떤 library를 실제 선택할지 아직 확정되지 않았다. Adapter는
먼저 profile 기반 provisional cache를 준비한다. `link`에서 object→record 집합을 확인하고
사용된 bundled library의 feature를 해석한 뒤, 선택 feature가 포함된 final key로 context와
record를 원자적으로 이관한다.

이 2단계는 다음을 동시에 보장한다.

- Arduino prototype discovery가 build context 없이 시작되지 않음
- 사용하지 않은 library feature가 cache identity를 오염시키지 않음
- `standard`와 `ble`, 그리고 서로 다른 feature 조합이 같은 Ninja tree를 공유하지 않음

## 4. Source manifest 계약

### 4.1 `record`

각 Arduino compile recipe는 다음 정보를 JSON record로 남기고 빈 placeholder object와 depfile을
만든다.

- language: `c`, `cxx`, `asm`
- canonical source와 placeholder object 경로
- Arduino가 전달한 include directory
- platform root와 현재 cache key

`link`는 Arduino가 실제 전달한 object에 대응하는 record만 허용한다. record가 없거나 현재
context와 다르거나 precompiled library archive이면 실패한다.

### 4.2 `sources.cmake`

검증된 record는 stable order의 다음 두 CMake 목록으로 변환된다.

- `NUCODE_ARDUINO_SKETCH_SOURCES`
- `NUCODE_ARDUINO_INCLUDE_DIRS`

Core와 variant는 Zephyr module이 이미 소유하므로 record 목록에서 제외한다. Arduino가
`build.path` 안에 생성한 sketch source는 영구 cache의 `app/generated-sources`에 byte가 바뀔
때만 원자적으로 mirror한다. 설치 Core 밖의 library source는 원래 canonical 경로를 사용한다.
Sketch local include 우선권과 같은 파일 이름의 서로 다른 source identity는 유지한다.

`sources.cmake` 내용이 같으면 timestamp를 보존한다. 내용이 달라졌을 때만 non-pristine CMake
재구성이 필요하다.

## 5. CMake/Ninja 재사용 규칙

| 상황 | 처리 |
| --- | --- |
| 새 final cache identity | `west build --cmake-only --pristine=always`로 최초 구성 |
| cache state/input/build graph 손상 | 같은 identity를 pristine 복구하거나 새 identity 사용 |
| source 목록·include 목록 변경 | manifest를 갱신하고 non-pristine CMake 재구성 |
| `.ino`, `.cpp`, `.c`, header 본문 변경 | 같은 tree에서 Ninja dependency로 필요한 target만 재빌드 |
| profile·feature·board·toolchain 변경 | 다른 final cache identity 사용 |
| 변경 없음 | 구성과 컴파일을 건너뛰고 기존 graph/artifact를 재사용 가능 |

일반 build마다 pristine, Ninja clean 또는 cache directory 전체 삭제를 실행하지 않는다.
`state.json`은 `configuring`, `ready`, `building`, `failed` 같은 전이를 원자적으로 기록한다.
완료되지 않은 state, 다른 전체 key 또는 다른 input manifest는 cache hit로 인정하지 않는다.

## 6. 산출물과 manifest

Zephyr build tree의 canonical 산출물은 `zephyr.elf`, `zephyr.hex`, `zephyr.bin`,
`zephyr.map`이다. 성공한 `link`는 이를 다음 Arduino 이름으로 공개한다.

~~~text
{build.path}/<project>.elf
{build.path}/<project>.hex
{build.path}/<project>.bin
{build.path}/<project>.map
{build.path}/<project>.nu54-build.json
~~~

ELF는 symbol을 유지한 Full Zephyr image다. HEX는 일반 upload 입력이고 BIN은 외부 도구용
산출물이다. map은 진단용이며 `.config`와 `zephyr.dts`는 Zephyr build tree에 남는다.

`<project>.nu54-build.json`은 최소한 다음 관계를 증명한다.

- FQBN, Zephyr board, profile과 선택 feature
- cache key, input manifest와 session context
- source manifest provenance
- 공개 artifact의 canonical 경로, 크기와 SHA-256
- native Zephyr artifact와 공개 artifact의 동일성

`verify-artifact`는 Arduino objcopy 단계에서 HEX/BIN이 현재 manifest에 속하며 크기와 SHA-256이
맞는지 다시 검사한다. `flash`는 이보다 더 엄격하게 live context, cache generation,
toolchain identity와 native build tree까지 검증한다.

산출물 전체를 staging한 뒤 한 generation으로 교체한다. 일부 파일이나 manifest publish가
실패하면 직전 generation을 복원하며, 새 manifest와 오래된 ELF가 섞인 상태를 성공으로
남기지 않는다.

## 7. Lock과 실패 복구

- cache entry lock: configure, feature migration, build와 artifact publish 직렬화
- session lock: 같은 `build.path`의 context/record/flash 변경 직렬화
- maintenance lock: prune/remove/clear 상호 충돌 방지
- probe lock: 같은 probe의 동시 flash 직렬화

lock metadata에는 owner와 operation이 기록된다. timeout이 나면 사용자가 대상을 확인할 수
있도록 owner 정보를 오류에 포함한다. 활성 lock을 강제로 지우거나 cache root를 무차별
삭제하는 동작은 자동 복구에 포함하지 않는다.

실패한 configure/build는 `failed` state를 남기고 기존 성공 artifact generation을 현재
성공으로 덮지 않는다. 다음 요청은 state와 graph를 검사해 안전한 복구 경로를 선택한다.

## 8. 유지보수 명령

~~~powershell
& .\tools\nu54-builder\nu54-builder.cmd cache list
& .\tools\nu54-builder\nu54-builder.cmd cache inspect <full-cache-key>
& .\tools\nu54-builder\nu54-builder.cmd cache prune
& .\tools\nu54-builder\nu54-builder.cmd cache remove <full-cache-key>
& .\tools\nu54-builder\nu54-builder.cmd cache clear
~~~

`cache clear --include-compiler`만 build entry와 ccache를 함께 비운다. 특정 sketch session의
cache entry만 새로 시작하려면 Builder CLI의 `clean-build` 하위 명령을 직접 사용한다. 이 명령은
Arduino의 일반 compile/upload recipe에서 자동 호출되지 않으며, Nordic prerequisite 설치나 다른
cache entry까지 지우지 않는다.

## 9. 지원 경계

현재 계약에 포함하지 않는 항목은 다음과 같다.

- sysbuild/multi-image artifact
- 원격 또는 공유 network cache
- precompiled Arduino library archive
- cache tree 없이 artifact만으로 수행하는 `west flash`
- 임의 사용자 CMake/module 주입

구성 profile과 feature 선택은
[구성 프로필과 예제 배포](07_구성_프로필과_Arduino_예제_배포.md), upload 검증 경계는
[업로드와 디버그](05_업로드와_디버그.md)를 참고한다.
