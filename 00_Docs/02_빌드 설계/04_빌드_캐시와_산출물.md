# 빌드 캐시와 산출물 설계

| 항목 | 내용 |
| --- | --- |
| 문서 상태 | M9 구현 기준 — 2026-08-28 |
| 작성자 | Quantum / NUCODE |
| 기준 | NCS v3.4.0 / Zephyr 4.4.0 |
| 대상 | Windows 우선 Native Full Zephyr build |
| 핵심 정책 | 최초만 pristine, 이후 증분 build |

---

## 1. 목적

Loader 없는 Full Zephyr 방식은 sketch마다 Zephyr kernel, Core, subsystem 및 sketch를 하나의 firmware로 링크한다. 첫 빌드는 Loader 방식보다 무겁지만, 올바른 cache 구조를 사용하면 일반 sketch 수정에서는 kernel과 변경되지 않은 Core를 다시 컴파일할 필요가 없다.

이 문서는 다음을 보장하기 위한 cache와 artifact 계약을 정의한다.

- Arduino IDE가 임시 `{build.path}`를 바꿔도 Zephyr build cache를 재사용
- sketch, FQBN, NCS, board package 및 config가 다른 build 사이의 오염 방지
- 최초 configure 이후 일반 build에서 pristine 금지
- Kconfig 및 Devicetree 변경의 정확한 무효화
- 동시 build의 archive 및 Ninja tree 손상 방지
- Arduino가 기대하는 이름으로 Full Zephyr 산출물 export
- artifact의 출처와 hash 추적
- 안전한 LRU 정리

---

## 2. 범위

### 2.1 포함 범위

- Arduino 임시 build directory
- Adapter session context
- 영구 Zephyr build cache
- 전용 compiler object cache
- Arduino source record와 persistent source mirror
- cache key와 input fingerprint
- configure/build invalidation 규칙
- lock과 원자적 파일 교체
- ELF, HEX, BIN, map 및 metadata export
- artifact integrity와 provenance
- cache 청소 정책
- Windows path와 동시 실행

### 2.2 고정 조건

- Board target은 `nrf54l15dk/nrf54l15/cpuapp/nu54dk`다.
- `BOARD_ROOT`는 `<repo>/board_package/NU54DK_Zephyr_DTS`다.
- `EXTRA_ZEPHYR_MODULES`는 `<repo>`다.
- v0.1 build는 `--no-sysbuild`다.
- Loader/LLEXT 산출물은 없다.
- 일반 build와 upload는 build tree를 삭제하지 않는다.
- 일반 upload는 mass erase를 실행하지 않는다.

### 2.3 입력과 출력

캐시 계층의 입력은 sketch 및 library source, Arduino FQBN과 build property,
Core source revision, board package revision, NCS/Zephyr/toolchain version,
Kconfig fragment, Devicetree overlay 및 Adapter version이다. 경로는 비교 전에
canonicalize하고, 내용 변화가 중요한 입력은 hash 또는 명시적인 fingerprint로
기록한다.

출력은 다음 세 종류로 구분한다.

| 출력 종류 | 대표 파일 | 역할 |
| --- | --- | --- |
| 내부 build 상태 | `state.json`, session context, CMake cache, Ninja database | 증분 여부와 입력 일치 여부 판단 |
| 링크 입력 | source record, mirror와 `sources.cmake` | 현재 Arduino source graph를 Zephyr target에 전달 |
| 사용자 산출물 | ELF, HEX, BIN, map, artifact manifest | 업로드, 디버그, export 및 추적성 제공 |

각 출력의 정확한 경로, 갱신 시점과 원자성 계약은 아래 절에서 정의한다.

## 3. 처리 흐름

~~~text
Arduino build session 시작
        │
        ▼
입력 canonicalization 및 cache key 계산
        │
        ├─ 새 key ─► entry 생성 ─► 최초 1회 pristine configure
        │
        └─ 기존 key ► context/도구/version 검증
        │
        ▼
`nu54-zephyr/context.json`으로 Arduino build path와 persistent cache 연결
        │
        ▼
Arduino source graph 수집과 안정적인 source mirror 갱신
        │
        ▼
현재 source record로 `sources.cmake` 원자적 갱신
        │
        ▼
동일 key build lock 안에서 west 증분 build
        │
        ▼
ELF/HEX/BIN/map hash 검증 및 Arduino output으로 원자적 export
        │
        ▼
manifest와 last-access metadata 갱신
~~~

새 cache key에 대한 최초 구성과 기존 key의 일반 증분 build를 명확히 분리한다. 실패한 새 build가 이전 성공 artifact나 다른 key의 build tree를 변경하지 않게 한다.

## 4. 캐시 계층

### 4.1 계층 1: Arduino build directory

Arduino CLI와 IDE가 관리하는 작업 directory다.

~~~text
{build.path}/
├─ sketch/
├─ libraries/
├─ core/
├─ nu54-zephyr/
│  ├─ context.json
│  └─ records/
├─ <project>.elf
├─ <project>.hex
├─ <project>.bin
├─ <project>.map
└─ <project>.nu54-build.json
~~~

책임:

- 생성된 `.ino.cpp`
- Arduino가 요청한 sketch/library object
- Arduino lifecycle용 Core archive
- persistent cache를 가리키는 session context
- IDE/CLI가 직접 읽는 최종 export artifact

이 directory는 임시일 수 있으므로 Zephyr kernel cache의 유일한 저장소로 사용하지 않는다.

### 4.2 계층 2: Persistent Adapter cache

Windows 기본 위치는 nRF Security의 긴 object와 dependency file이 `MAX_PATH`를 넘지 않도록
의도적으로 짧게 유지한다.

~~~text
%LOCALAPPDATA%/NU54/c/v1/<2자리>/<32자리-directory-key>/
~~~

개발 checkout과 자동 시험에서는 `NUCODE_BUILD_CACHE_ROOT`로 다음과 같은 별도 경로를
지정할 수 있다.

~~~text
<repo>/build/adapter-cache/v1/<cache-key>/
~~~

Windows에서 override 경로를 길게 지정하면 Cracen/nRF Security의 `.obj.d` 경로가 compiler
한계를 넘을 수 있다. 이 경우 `%LOCALAPPDATA%/NU54/c`보다 비슷하거나 더 짧은 local 경로를
사용한다. network/UNC cache는 계속 허용하지 않는다.

다음 위치에는 쓰지 않는다.

- Boards Manager platform 설치 directory
- NCS 설치 directory
- board package submodule
- 사용자 sketch source directory의 숨겨진 임의 폴더

Persistent cache 책임:

- Zephyr CMake/Ninja build tree
- generated Kconfig 및 Devicetree
- 전용 ccache namespace
- 안정적인 logical ID의 source mirror
- input manifest와 context
- build logs
- lock metadata

### 4.3 계층 3: Exported artifact

사용자가 보관하거나 별도 upload에 사용할 결과다.

~~~text
<project>.elf
<project>.hex
<project>.bin
<project>.map
<project>.nu54-build.json
~~~

export artifact는 cache가 삭제돼도 독립적으로 검증할 수 있어야 한다. 다만 `west flash -d`가 필요한 runner workflow는 build tree가 있어야 하므로 direct HEX upload 지원 여부를 별도로 구분한다.

## 5. 캐시 디렉터리 계약

~~~text
<cache-root>/v1/<2자리>/<32자리-directory-key>/
├─ state.json
├─ input-manifest.json
├─ access.json
├─ .adapter.lock                 # OS lock 소유자의 진단용 metadata
├─ app/
│  ├─ CMakeLists.txt
│  ├─ prj.conf
│  ├─ app.overlay
│  ├─ sources.cmake
│  ├─ generated-sources/
│  └─ src/bootstrap.cpp
└─ build/
│  ├─ CMakeCache.txt
│  ├─ build.ninja
│  └─ zephyr/
│     ├─ .config
│     ├─ runners.yaml
│     ├─ zephyr.dts
│     ├─ zephyr.elf
│     ├─ zephyr.hex
│     ├─ zephyr.bin
│     └─ zephyr.map
~~~

전체 SHA-256은 metadata와 session context에 보존한다. directory에는 Windows object 경로
제한을 피하기 위해 앞 128 bit를 사용하며, 기존 entry의 전체 digest가 다르면 충돌 오류로
중단한다.

## 6. Cache key 계약

### 6.1 목표

Cache key는 ABI 또는 build graph가 호환되지 않는 두 build가 같은 Ninja tree를 공유하지 않게 한다. 반대로 `.ino` 본문만 변경됐을 때는 같은 key를 유지해야 한다.

### 6.2 key 입력

최소 다음 값을 canonical JSON으로 직렬화한 뒤 SHA-256을 계산한다.

| 입력 | 이유 |
| --- | --- |
| cache schema version | layout/계약 변경 분리 |
| Adapter version | compiler/link 동작 변경 분리 |
| Arduino platform/Core version | Core API/구현 변경 분리 |
| FQBN 전체 문자열 | board menu option 포함 |
| Zephyr board target | 다른 target 혼용 방지 |
| NCS version | SDK ABI/build graph 분리 |
| Zephyr version | kernel/build system 분리 |
| toolchain identity | compiler ABI 분리 |
| board package commit 또는 content hash | DTS/Kconfig/runner 변경 분리 |
| module commit 또는 content hash | Core CMake/Kconfig 변경 분리 |
| canonical sketch root | 서로 다른 sketch build tree 분리 |
| `prj.conf` content hash | Kconfig 변경 분리 |
| `app.overlay` content hash | Devicetree 변경 분리 |
| sysbuild boolean | build layout 분리 |

sketch `.ino/.cpp/.c`와 일반 Arduino library 본문의 hash는 cache key에 넣지 않는다. Arduino가
생성한 Sketch source는 cache 내부 mirror의 내용과 timestamp로, 외부 library source는 원래
경로의 Ninja dependency로 증분 처리한다.

### 6.3 key 표현

예시:

~~~text
7d/7d9e6a9f3f130c4a6af4a572e1a1f3ef
~~~

전체 SHA-256을 metadata에 저장하고 directory 이름은 충돌 가능성이 충분히 낮은 길이로 줄일 수 있다. 줄인 key가 충돌하면 전체 digest 비교 후 오류를 내거나 더 긴 key를 사용한다.

### 6.4 개발 checkout의 dirty source

Git commit만 key에 사용하면 commit되지 않은 Core/CMake 수정이 cache에 반영되지 않는다. 개발 mode에서는 최소 다음 파일 집합의 content fingerprint를 사용한다.

- `zephyr/module.yml`
- `zephyr/CMakeLists.txt`
- `zephyr/Kconfig`
- `cores/arduino/**`
- `variants/nu54dk/**`
- Adapter template와 schema

모든 source를 매번 hash하여 prebuild가 느려지지 않도록 file metadata cache를 사용할 수 있다. 정확성보다 속도를 우선해 변경을 누락해서는 안 된다.

## 7. 입력 fingerprint와 상태

### 7.1 `state.json`

~~~json
{
  "schema_version": 1,
  "cache_key": "sha256:...",
  "state": "ready",
  "first_configure_complete": true,
  "last_build_result": "success",
  "last_artifact_manifest": "C:/.../Blink.nu54-build.json",
  "created_at_utc": "2026-08-26T00:00:00Z",
  "last_accessed_at_utc": "2026-08-26T00:10:00Z"
}
~~~

가능한 state:

| 상태 | 의미 |
| --- | --- |
| `creating` | 최초 directory와 placeholder 생성 중 |
| `configuring` | CMake/Kconfig/DTS 구성 중 |
| `ready` | compile/link에 사용 가능 |
| `building` | final west build 진행 중 |
| `failed` | 마지막 작업 실패, 기존 성공 artifact 보존 가능 |
| `incompatible` | schema/version 불일치로 재사용 금지 |

### 7.2 session context

Arduino `{build.path}/nu54-zephyr/context.json`은 persistent cache를 가리키는 작은 파일이다.

~~~json
{
  "schema_version": 2,
  "cache_key": "...64자리 SHA-256...",
  "cache_dir": "C:/.../build-cache/v1/7d/...",
  "build_path": "C:/.../arduino-build",
  "app_dir": "C:/.../cache/app",
  "zephyr_build_dir": "C:/.../cache/build"
}
~~~

Arduino recipe는 가능한 한 session file만 직접 참조하고 나머지 path는 Adapter가 해석한다.

## 8. Pristine 및 증분 정책

### 8.1 최초 build

새 cache key directory에서만 다음 정책을 사용한다.

~~~text
west build --pristine always --cmake-only --no-sysbuild ...
~~~

directory가 비어 있더라도 명시적인 clean baseline을 위해 최초 1회만 허용한다.

### 8.2 일반 build

같은 key의 다음 build는 다음과 같다.

~~~text
west build -d <cache>/build
~~~

사용하지 않는 동작:

~~~text
west build -p always ...
west build --pristine always ...
build directory 매번 삭제
Ninja clean 매번 실행
~~~

### 8.3 CMake 재구성

같은 key 안에서 generated template 또는 CMake input timestamp가 달라졌으나 key 정책상 호환되는 경우:

~~~text
west build --cmake-only -d <cache>/build
~~~

그러나 `prj.conf`, `app.overlay`, board package, NCS 또는 Core build graph가 key 입력이면 변경 시 새 key가 생성되는 것이 기본이다.

### 8.4 변경 영향 표

| 변경 | 같은 cache key | Arduino object | Zephyr 처리 |
| --- | --- | --- | --- |
| `.ino` 본문 | 유지 | 변경된 sketch 재컴파일 | mirror 교체 후 relink |
| sketch `.cpp/.c` | 유지 | dependency에 따라 재컴파일 | mirror 교체 후 relink |
| 일반 library source | 유지 | 해당 library 재컴파일 | mirror 교체 후 relink |
| Arduino include header | 유지 | `.d`에 따라 관련 object 재컴파일 | 영향 source 재컴파일 |
| `prj.conf` | 새 key | 새 flags로 재컴파일 | 최초 configure/build |
| `app.overlay` | 새 key | 새 generated header로 재컴파일 | 최초 configure/build |
| FQBN menu option | 새 key | 새 build | 최초 configure/build |
| board target | 새 key | 새 build | 최초 configure/build |
| board package commit | 새 key | 새 build | 최초 configure/build |
| Core/module commit | 새 key | 새 build | 최초 configure/build |
| Adapter schema | 새 namespace 또는 key | 새 build | 최초 configure/build |
| NCS/toolchain version | 새 key | 새 build | 최초 configure/build |

### 8.5 generated header dependency

Arduino compiler wrapper가 생성한 `.d`에는 실제로 참조한 generated header가 포함돼야 한다.

- `autoconf.h`
- Devicetree generated header
- Core/variant headers
- Arduino library headers

Arduino CLI가 object를 skip하는 판단과 Adapter cache key가 서로 모순되지 않게 한다.

## 9. Source mirror 정책

### 9.1 고정 경로

Arduino CLI recipe는 compile 단계에서 source와 include directory를 session record로 남긴다.
prepare는 이전 Arduino placeholder record와 object만 무효화하여 매 compile의 실제 library
discovery 결과를 다시 수집한다. 최종 link 단계는 해당 run의 record만 읽어 cache 안의 다음
경로를 갱신한다.

~~~text
<cache>/app/generated-sources/<logical-id>_<source-name>
<cache>/app/sources.cmake
~~~

생성된 `.ino.cpp` 경로에서 Arduino `{build.path}` prefix를 제거하고 source category와 Sketch
상대 이름을 logical ID로 사용한다. 따라서 다른 임시 build path가 같은 `sources.cmake`와
Ninja 입력을 사용하고, Sketch와 library에 같은 파일명이 있어도 충돌하지 않는다. 외부 library
source는 `"Config.h"` 같은 private include의 원래 의미를 보존하기 위해 mirror하지 않고 원래
경로에서 컴파일한다.

### 9.2 갱신

1. 현재 link recipe가 전달한 object에 대응하는 source record만 읽는다.
2. source 존재와 include directory를 검증한다.
3. logical ID 순서로 결정적인 `sources.cmake`를 만든다.
4. Arduino가 생성한 source 본문이 달라졌을 때만 mirror를 원자적으로 교체한다.
5. source 집합이 같으면 `sources.cmake` timestamp를 보존한다.
6. source 집합이 바뀐 경우에만 non-pristine CMake configure를 실행한다.
7. Ninja가 변경된 mirror source만 다시 컴파일하고 최종 image를 relink한다.

### 9.3 금지 사항

- 이전 build directory의 object를 무조건 재귀 scan하지 않는다.
- source record가 없는 placeholder object를 임의로 추측하지 않는다.
- stale library source를 현재 source graph에 포함하지 않는다.
- Arduino 임시 build path를 mirror identity에 포함하지 않는다.
- link 실패 후 이전 artifact manifest를 정상 상태로 표시하지 않는다.

## 10. 산출물 계약

### 10.1 Canonical Zephyr 산출물

첫 `--no-sysbuild` 버전의 canonical source는 다음이다.

| 종류 | canonical 경로 |
| --- | --- |
| ELF | `<cache>/build/zephyr/zephyr.elf` |
| HEX | `<cache>/build/zephyr/zephyr.hex` |
| BIN | `<cache>/build/zephyr/zephyr.bin` |
| map | `<cache>/build/zephyr/zephyr.map` |
| Kconfig | `<cache>/build/zephyr/.config` |
| Devicetree | `<cache>/build/zephyr/zephyr.dts` |
| runner metadata | `<cache>/build/zephyr/runners.yaml` |

sysbuild를 나중에 추가할 때는 이 경로를 그대로 가정하지 않는다. `domains.yaml` 또는 build metadata를 통해 domain artifact를 결정하는 별도 schema version을 사용한다.

### 10.2 Arduino export 이름

| canonical | Arduino build output |
| --- | --- |
| `zephyr.elf` | `{build.project_name}.elf` |
| `zephyr.hex` | `{build.project_name}.hex` |
| `zephyr.bin` | `{build.project_name}.bin` |
| `zephyr.map` | `{build.project_name}.map` |
| provenance | `{build.project_name}.nu54-build.json` |

Loader용 `.zsk`, `.llext`, EDK 또는 loader image 이름을 사용하지 않는다.

### 10.3 ELF 정책

- Arduino build output의 ELF는 debug symbol을 포함한 Full Zephyr ELF다.
- 별도의 stripped ELF가 필요하면 다른 이름으로 생성한다.
- `debug.executable`은 symbol이 포함된 ELF를 가리킨다.
- ELF hash는 manifest에 저장한다.

### 10.4 HEX 정책

- 일반 SWD upload의 기본 artifact다.
- `--no-sysbuild` 첫 버전에서는 `zephyr.hex`가 canonical이다.
- `merged.hex` 존재를 가정하지 않는다.
- HEX에 Loader나 bootloader를 자동 merge하지 않는다.

### 10.5 BIN 정책

- tool 또는 사용자 export를 위해 제공한다.
- BIN의 load address가 필요한 upload 경로에서는 manifest에 address 정보가 없으면 사용하지 않는다.
- 일반 pyOCD/J-Link PoC는 Zephyr build metadata 또는 HEX를 우선한다.

### 10.6 Map과 configuration

map, `.config`, `zephyr.dts`는 일반 Arduino export 필수 파일은 아니지만 진단에 필수다. IDE output directory에는 map을 export하고 `.config`와 DTS는 persistent cache에 보존한다.

## 11. Artifact manifest

예시:

~~~json
{
  "schema_version": 2,
  "adapter_version": "0.1.0-dev.m9",
  "fqbn": "nucode:zephyr:nu54dk:upload_runner=pyocd",
~~~

## 12. Lock과 원자성

### 12.1 Lock 범위

| 작업 | Lock |
| --- | --- |
| context 읽기 | 불필요 |
| individual source compile | cache context는 read-only, Arduino object별 독립 |
| 최초 configure | cache key 전용 configure lock |
| source mirror와 manifest 교체 | cache key 전용 build lock |
| west final build | cache key 전용 build lock |
| export/manifest/context publish | session lock 안의 단일 rollback transaction |
| flash | session → cache → probe logical ID 순서의 lock |

### 12.2 Lock metadata

~~~json
{
  "schema_version": 1,
  "pid": 1234,
  "host": "WORKSTATION",
  "operation": "link-session",
  "token": "임의의 단일 소유자 token",
  "created_at_utc": "2026-08-26T00:00:00Z"
}
~~~

이 JSON은 진단 metadata이며 lock 권위가 아니다. Windows에서는 canonical cache 또는 logical
probe ID로 만든 `Global\\NUCODE_NU54_*` named mutex를, POSIX에서는 `flock`을 사용한다. 운영체제가
process 종료와 crash 때 소유권을 회수하므로 PID/host/timestamp를 이용한 임의 삭제를 하지
않는다. Local filesystem만 지원하며 UNC/network cache root는 거부한다.

### 12.3 실패 복구

- configure 실패 directory는 `failed`로 표시한다.
- 동일 입력 재시도 시 로그를 보존하고 필요한 단계부터 다시 수행한다.
- 이전 성공 ELF/HEX/manifest/context는 새 generation이 완전히 publish될 때까지 유지한다.
- publish 도중 예외 또는 `Ctrl+C`가 발생하면 이전 generation 전체를 rollback한다.
- rollback 자체가 실패하면 backup을 보존하고 수동 복구 경로를 오류에 출력한다.
- temp archive와 temp export는 정리 가능 목록에 기록한다.
- 손상된 `CMakeCache.txt` 또는 Ninja tree는 자동 mass delete하지 않고 새 cache key 또는 명시적 rebuild를 사용한다.

## 13. Cache 정리 정책

### 13.1 자동 정리 기준

다음 조합으로 LRU 정리를 수행할 수 있다.

- 최대 총 용량
- 최대 entry 수
- 마지막 접근 후 보존 기간
- incompatible schema entry
- 실패 상태의 보존 기간

M9 실측 후 기본값은 build tree 12 GiB 또는 8 entry, 전용 ccache 2 GiB로 고정했다.
각 값은 `NUCODE_BUILD_CACHE_MAX_BYTES`, `NUCODE_BUILD_CACHE_MAX_ENTRIES`,
`NUCODE_CCACHE_MAX_SIZE`로 조정한다.

### 13.2 보호 항목

다음 entry는 실행 중 자동 삭제하지 않는다.

- lock이 활성화된 entry
- 현재 Arduino session이 참조하는 entry
- 마지막 성공 build가 진행 중 export되는 entry
- 사용자가 pin한 entry를 지원할 경우 pin entry

### 13.3 사용자 명령

~~~text
nu54-builder cache list
nu54-builder cache inspect <key>
nu54-builder cache prune
nu54-builder cache remove <key>
nu54-builder cache clear
nu54-builder cache clear --include-compiler
~~~

`cache remove`는 정확한 key 하나만 대상으로 하고 삭제 전 canonical cache root 안에 있는지 검증한다.

## 14. 오류 처리

| 오류 | 감지 | 처리 |
| --- | --- | --- |
| cache schema 불일치 | `state.json` version | 새 namespace/key 생성, 기존 tree 재사용 금지 |
| NCS/toolchain mismatch | context와 doctor 비교 | 새 key 생성 또는 명시적 오류 |
| config hash mismatch | session/context 비교 | 잘못된 object/link 차단 |
| stale 진단 metadata | OS mutex/`flock` 획득 결과 | OS lock이 회수되면 metadata를 새 소유자로 원자 교체 |
| source record 또는 mirror 불일치 | source 존재와 결정적 manifest 검사 | link 중단 및 failed 상태 기록 |
| canonical artifact 없음 | west 성공 후 존재 검사 | `E_EXPORT_MISSING_ARTIFACT` |
| artifact hash 변경 | upload 전 manifest 비교 | upload 중단 |
| cache disk full | write/replace 오류 | 기존 성공 artifact 보존, 정리 안내 |
| 경로가 cache root 밖 | canonical path 검사 | 삭제/교체 금지 |
| 매번 pristine | command log 정책 검사 | 성능 회귀로 test 실패 |

일부 artifact가 존재한다는 이유만으로 실패 build를 성공으로 간주하지 않는다. child process exit code와 state transition이 모두 성공해야 한다.

## 15. 완료 기준

Cache 및 artifact 설계 v0는 다음을 만족해야 한다.

1. 같은 sketch와 동일 config가 같은 cache key를 얻는다.
2. 다른 sketch, FQBN, NCS, board package 또는 config가 같은 key를 공유하지 않는다.
3. 최초 configure에만 pristine이 실행된다.
4. 무변경 build가 Zephyr kernel 전체를 다시 컴파일하지 않는다.
5. `.ino`만 변경하면 sketch object와 final link 위주로 실행된다.
6. `prj.conf` 또는 overlay 변경이 새 configuration을 사용한다.
7. 동시 build가 context, source mirror 또는 Ninja tree를 손상시키지 않는다.
8. Full Zephyr ELF/HEX/BIN/map이 Arduino 이름으로 export된다.
9. manifest hash가 실제 artifact와 일치한다.
10. cache 삭제 후에도 export artifact 자체를 식별하고 검증할 수 있다.
11. 안전한 LRU prune과 단일 key 삭제가 가능하다.

## 16. 검증 체크리스트

### 16.1 Key와 invalidation

- [x] FQBN menu option이 key에 포함된다.
- [x] NCS, Zephyr 및 toolchain identity가 key에 포함된다.
- [x] board package revision이 key에 포함된다.
- [x] `prj.conf`와 overlay content가 key에 포함된다.
- [x] `.ino` 본문은 key에 포함되지 않는다.
- [x] dirty Core source 변경을 감지한다.

### 16.2 증분 성능

- [x] 최초 build command에만 pristine이 있다.
- [x] 두 번째 무변경 build의 compiler 작업 수를 기록했다.
- [x] `.ino` 한 줄 변경의 build 범위를 기록했다.
- [x] Sketch-local 및 library header 변경의 dependency rebuild를 확인했다.
- [x] config 변경이 새 key와 generated header를 사용한다.

### 16.3 원자성과 동시성

- [x] 두 compile process가 context를 동시에 읽을 수 있다.
- [x] 두 link process는 같은 key에서 직렬화된다.
- [x] 강제 종료 후 stale lock 복구를 시험했다.
- [x] source mirror replace가 원자적으로 수행된다.
- [x] export replace 중 종료돼도 이전 manifest를 현재 build로 인정하지 않는다.

### 16.4 산출물

- [x] ELF/HEX/BIN/map이 모두 생성된다.
- [x] manifest에 모든 artifact hash가 있다.
- [x] `.config`, DTS 및 `runners.yaml`을 cache에서 찾을 수 있다.
- [x] `merged.hex`를 잘못 요구하지 않는다.
- [x] Loader/LLEXT artifact가 없다.

### 16.5 정리

- [x] cache list가 key와 last access를 표시한다.
- [x] active lock entry가 prune되지 않는다.
- [x] cache root 외부 경로 삭제가 차단된다.
- [x] 정리 후 필요한 entry가 정상 재생성된다.

## 17. 범위 제외

M9 cache 구현에서는 다음을 제외한다.

- sysbuild domain cache
- remote/distributed cache
- shared network filesystem cache
- 원격 compiler object cache server
- cloud artifact storage
- signed artifact와 SBOM 생성
- reproducible build bit-for-bit 보장
- MCUboot/DFU용 merged image
- LLEXT loader와 sketch cache
- automatic NCS download cache(M10 범위)
